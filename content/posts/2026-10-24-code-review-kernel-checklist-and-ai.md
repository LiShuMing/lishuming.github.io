## 面试主线：沿状态变化证明安全

本篇面向数据库内核 Senior / Staff / Tech Lead 面试，把清单展开成可追问的推演。先识别 SQL 语义和状态所有者，再检查工具与测试覆盖的证据，AI 初筛可按需使用。人工需要核对语义、不变量（Invariant），也要复核工具发现和测试断言。默认的阻塞项是正确性、并发、资源、分布式语义；严重的设计/复杂度问题和有数据证明的性能退化同样可以阻塞（Google [What to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 把设计和复杂度列为重点）。其余性能和可观测性问题按影响判断；无法诊断关键失败可能使上线条件不成立。纯风格偏好用 Nit 标出，影响所有权理解或错误处理的可读性问题不能直接降为 Nit。

## 1. 分层：谁负责什么

| 层 | 负责者 | 内容 |
|---|---|---|
| 机械检查 | clang-format / clang-tidy / CI | 格式、常见 bug 模式、编译 |
| 运行时检测 | ASan / TSan / UBSan | 内存越界、use-after-free、数据竞争、UB |
| AI 初筛 | Copilot / Codex / CodeRabbit 等 | PR 摘要、可疑模式、遗漏测试 |
| 人工 | reviewer | 语义、不变量、兼容性、设计契合度 |

【事实】[GitHub Copilot code review](https://docs.github.com/en/copilot/using-github-copilot/code-review/using-copilot-code-review) 可以作为 reviewer 被请求，给出评论和修改建议；它的评论不算正式 approval，不能满足分支保护要求的审批。[Codex code review](https://developers.openai.com/codex/cloud/code-review) 支持在 GitHub PR 里 @codex 触发评审，并按仓库的 `AGENTS.md` 指引调整关注点。[CodeRabbit](https://docs.coderabbit.ai/) 支持自动摘要和逐行评论，并能用路径级规则配置。
【事实】[DORA 2025](https://dora.dev/research/2025/dora-report/) 的核心论点是：AI 是放大器，会放大组织已有的强项和弱项。工程基础（小批量交付、测试、平台）薄弱的团队，用了 AI 后吞吐量上去了，稳定性未必跟上。
【推断】AI reviewer 的误报和漏报都不可忽略。把它当成第一个读者，不要当最后一个审批人；仓库规则（AGENTS.md / 路径规则）里写明内核的不变量，比如“所有 Status 必须检查”“禁止在 pipeline driver 线程阻塞 IO”，可以据此提出更具体的检查要求，实际误报、漏报仍需验证。

## 2. P0：阻塞

**正确性**：边界（空输入、NULL 语义、溢出、极值）、错误路径、UB。SQL 引擎还要特别查 NULL 三值逻辑、decimal 精度、时区，以及 nullable 列和 const 列的特化分支。

**并发**：锁序、持锁期间做 IO 或 RPC、`memory_order` 是否真的建立了所需的 happens-before 关系（relaxed 计数器可以合法存在；release/acquire 写成对也不等于同步成立，acquire 必须读到对应的 release 序列）、回调跨越的对象生命周期。原稿的 false sharing（伪共享）示例应归到 P1 性能，不属于 P0 正确性。

**资源**：异常路径和提前 return 时是否泄漏，内存统计是否对称（consume 之后有没有 release），用 RAII guard 代替手写 try/catch 释放。

**分布式语义**：重试需要幂等操作、持久去重或等效的重复执行保护；部分成功须按协议完成恢复、回滚或补偿，不能假定都可撤销。超时与取消要核对下游 fragment 的接收与收敛行为；FE/BE 两端还要考虑版本兼容（升级期间新旧节点混跑）。

## 3. P1：强建议

- **性能**：热路径上的分配和拷贝、虚函数和分支、能否保持列式批处理不退化成逐行处理、SIMD 是否交给编译器自动向量化即可。原稿“SIMD 快 4–8 倍”只在特定向量宽度、元素位宽且计算密集时成立，不能当通用估计；实际收益要拿 benchmark 说话，审查时要求作者附上数据。
- **可观测性**：错误信息至少带 query_id、fragment/instance id、状态码；新增的执行路径要有 profile counter。
- **测试**：除了正常路径，还要测边界、并发压力和故障注入；改了执行算子，就应该补 SQL 级的回归测试。

## 4. P2：Nit

命名、函数拆分、注释写“为什么”而不是“做了什么”、TODO 关联 issue。全部加 `Nit:` 前缀，不阻塞。

## 5. 怎么审 AI 生成的代码

原稿的特征清单（幻觉 API、缺边界、过度设计、泛化命名）仍然成立。【推断】更有效的做法是从流程上约束：要求作者能逐段解释关键逻辑，答不上来就不合入；幻觉 API 交给编译和 CI 拦，人不必肉眼核对；AI 补的测试要检查断言是否真有约束力，常见问题是断言等价于“不崩溃”；大段生成的代码按普通 PR 的大小标准拆分。

## 6. 写评论的格式

`[P0/P1/Nit] 问题 → 原因（触发条件）→ 建议`，结尾留一句开放式提问。原稿给的 Mentor 式范例保留了这个结构。指出问题时针对代码本身，表述用“这里在 X 情况下会 Y”，不用“你写错了”。

## 7. 技术追问：从局部代码走到系统结果

以下均为【推断】性质的通用审查题，不绑定某个数据库版本或真实 PR。答题时应先声明假设；项目实际实现需要另外核对调用链。

### 优化器（Optimizer）：谓词能否越过外连接

**可能的问题**：“选择率很低的过滤条件，为什么不能直接推到扫描端？”

**精简强答**：谓词下推（Predicate Pushdown）先证明等价，再谈成本。以左外连接（Left Outer Join）为例，右侧不匹配时产生补 NULL 行；在连接后过滤右侧字段，和在右侧扫描时过滤，可能对这些行给出不同结果。要区分 ON 与 WHERE、保留侧与补 NULL 侧、谓词是否拒绝 NULL，以及普通谓词与运行时过滤器的语义。不能从“越早过滤越快”推出规则正确。

**追问**：“给反例，重复行和规则终止性又怎么看？”例如 `SELECT l.k FROM l LEFT JOIN r ON l.k=r.k WHERE r.v=1`，若只把 `r.v=1` 移入右侧扫描并删除上层过滤，无匹配的左侧行会被保留，结果改变。保留上层过滤、连接类型转换以及条件推导是不同改写，须分别论证。重复行按多重集语义（Bag Semantics）验证；规则是否反复互相触发，则检查匹配条件、状态标记或搜索框架的去重机制，不能只凭计划看起来合理。

**差答**：“NULL 加测试就行”“计划更短所以更快”。测试应覆盖决定等价性的条件；计划差异只说明路径变化，执行结果与运行成本仍需验证。

### C++ 执行器（Executor）：取消后谁还持有对象

**可能的问题**：“异步回调捕获 `this`，查询取消时会发生什么？”

**精简强答**：先画任务注册、运行、取消、回调完成和析构的先后关系。取消请求不等于回调已经退出；若析构后回调仍解引用 `this`，就存在释放后使用（Use-After-Free）。修复需要明确持有者、完成确认和清理责任，可以是延长任务状态生命周期或等待回调退出，具体方案取决于线程模型。

**追问**：“改成 `shared_ptr` 就够了吗？用原子变量标记完成呢？”共享所有权能延长寿命，但可能形成引用环或使查询资源延迟释放；等待退出若发生在执行回调所需的线程上，可能无法推进。原子标记本身不能证明其他字段可见，需写清发布与读取之间的同步关系，且可见性和对象存活是两个证明义务。

**差答**：“全部换智能指针”“TSan 没报就是安全”。检测器只观察执行到的路径，不能替代所有权推导。验证应主动控制取消与回调的交错，断言只完成一次且资源最终释放。

### 存储：发布新文件后崩溃，恢复读什么

**可能的问题**：“审查一次合并压缩（Compaction）或格式升级，你最先看什么？”

**精简强答**：先找恢复后决定可见文件集合的元数据，再沿新文件生成、持久化、元数据发布、旧文件回收检查状态变化。若系统以 manifest 指定文件集合，发布时引用的内容应满足恢复所需的持久性；旧文件回收还应受读者引用和快照约束。具体持久化与原子性保证取决于文件系统或对象存储接口，不能假定一次 rename 解决全部问题。

**追问**：“manifest 更新前后分别崩溃呢？新旧版本混跑呢？”列出每个切点恢复时选择哪一代文件、如何识别与清理孤儿文件，以及何时允许回收。格式升级分读兼容与写兼容，说明旧节点能否读新数据；切换配置通常不能撤销已经落盘的新格式。

**差答**：“写成功就删旧文件”“有校验和就不会丢数据”。校验和（Checksum）帮助检测损坏，不能证明发布顺序、可恢复性或旧读者安全。需要故障注入（Fault Injection）与恢复后数据断言，正常重启测试不足以覆盖所有切点。

### 分布式执行：超时是否意味着没有提交

**可能的问题**：“RPC 超时后重试，怎样避免重复提交？”

**精简强答**：超时只表示调用方未及时收到确认，服务端可能已提交。需要稳定操作标识、重复请求的识别范围，以及结果和去重状态在失败恢复后的对应关系；只在内存中记住请求，不能自动覆盖节点重启。先明确协议保证的是执行次数还是外部可见效果，不能直接许诺恰好一次（Exactly-Once）。

**追问**：“提交成功但响应丢失怎么办？换 leader 呢？去重记录何时清理？”回答要指向事务状态或等效的持久结果查询，以及旧请求在清理后是否还能到达。取消同样不能自动撤销已提交效果，应定义取消与提交竞态下调用方如何得知最终状态。

**差答**：“失败就重试”“用 query_id 去重”。标识只是入口，还缺原子性、保留周期和恢复边界。测试须包含响应丢失、重复到达、重启及部分节点成功，而不只是连接失败。

### OLAP 性能与 AI：如何验证一个看起来合理的优化

**可能的问题**：“AI 改写了向量化循环，微基准更快，能否合入？”

**精简强答**：向量化执行（Vectorized Execution）仍须保持 nullable、const、空批次、溢出与尾部处理的语义。微基准验证局部路径，查询级验证说明它是否影响总成本；保留编译选项、数据规模与分布、并发、缓存状态、硬件及重复运行条件，结合 profile 判断瓶颈是否转移。没有测到的负载只能列为限制。

**追问**：“只在均匀数据上受益呢？AI 测试也通过了呢？”增加倾斜、NULL 比例及资源压力等与改动相关的维度，检查断言是否会拒绝错误实现。AI 给出摘要不能建立语义或性能保证；作者与 reviewer 仍需解释关键分支和测量边界。

**差答**：“用了 SIMD 必然更快”“让 AI 证明代码没问题”。在内存带宽或其他算子占主导的查询上，局部计算优化未必转成查询收益；可编译也不证明错误路径和结果语义正确。

## 8. 面试现场如何证明审过代码

从上述一个领域挑真实案例，展示“调用入口 → 关键分支 → 状态所有者 → 失败出口”，再解释原测试为什么漏掉、补测的断言为什么能区分修复前后。只给文件名和函数清单不能证明理解调用关系。若引用某个项目，需要说明提交版本与代码位置；本文未核对具体实现，不能作为项目源码结论引用。

【推断】Senior 可把一个交错或 SQL 反例讲透；Staff 应继续解释跨模块保证由谁提供；Tech Lead 则补充评审分工、兼容部署和停止发布的条件。证据缺失时明确待验证项，不能用没有线上事故代替正确性证明，也不能把演练场景说成亲历事故。
