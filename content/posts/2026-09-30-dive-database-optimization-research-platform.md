## 上篇 · 情报与证据：研究平台如何结案

## 一、背景：研究记录为什么必须能够结案 {#引言一条外部优化消息怎样变成自己的研究问题}

数据库研究平台应交付有版本、前提和结案条件的研究记录，而不是持续增加摘要。看到“某引擎支持自适应 Join”时，工程判断仍缺几个环节：它针对什么瓶颈，依赖哪些执行条件，目标系统是否已有替代路径，以及下一步用什么证据决定要不要继续。论文里的加速比、Release Note 中的功能名，都不能直接填补这些空白。

困难还在于判断会过期。同一项变化先进入设计文档，再合入 PR、出现在发布说明和博客里；如果按网页计数，就会把一次变化反复当作新能力。反过来，曾经被否定的迁移建议，也可能因为目标版本更新而重新成立。只保存摘要，无法区分这两种情况。

本文先固定研究交付与边界，再比较现有工具能承担哪些工作、三条建设路线如何取舍，最后展开数据合同、处理流程和验证方法。外连接简化与外部聚合用于检查合同能否落到具体机制。文中的平台结构是研究建议，示例不代表某个目标引擎存在缺口，也不构成未经实验的性能承诺。

<span id="1-先定义交付研究记录必须能够结案"></span>

研究记录需要明确什么证据会改变当前判断。没有这一条件，源码检索和模型调用只能不断扩展材料，无法区分“已经回答”与“还可以继续读”。

### 研究问题、成功条件与非目标

研究判断从可定位事实出发，依次解释机制、适用边界和目标系统的已知状态，再收敛为待验证问题：

```text
网页、论文、PR、源码
        │
        ▼
可定位的事实：谁在什么版本声明或实现了什么
        │
        ▼
机制解释：输入、状态、算法、控制点与输出如何变化
        │
        ▼
适用边界：语义前提、执行模型、数据与资源条件
        │
        ▼
目标系统映射：已覆盖、部分覆盖、局部缺口、未知或不适用
        │
        ▼
最小研究问题：下一步核对什么，何时可以结案
```

依赖链最终应落到一个足够小的问题，例如：

> 固定版本下，外连接（Outer Join）简化能否识别包含确定性 cast 的拒绝空值（Null-Rejecting）谓词？如果已有正反测试和规则调用链覆盖该形态，本轮研究结案；如果 guard 明确拒绝，再分析是语义限制还是实现缺口。

按这样的结案条件，成功不必表现为新建议。以下结果同样能减少后续的重复研究：

- 目标系统已经覆盖该机制，外部变化没有新增信息；
- 目标系统只覆盖其中一类条件，局部边界值得核对；
- 两个系统执行模型不同，当前机制不可直接迁移；
- 外部资料没有给出足够细节，结论保持未知；
- 旧建议因为新版本、新反例或新实验而失效。

**允许不生成建议**，是质量控制的一部分。如果系统被要求每周固定产出十条“优化机会”，这种固定篇数目标会激励重复建议和证据不足的推断，评测应检查并惩罚这类产出。

与此对应，只读资料研究不承诺完成以下工作：

- 自动证明所有 SQL 重写在完整 SQL 语义下等价；
- 从静态源码推断真实生产收益；
- 部署所有对比引擎并完成同条件 Benchmark；
- 发现目标系统的全部优化缺口；
- 根据外部文章自动修改并上线数据库代码；
- 让引用数量或模型置信分替代专家判断。

这些不是永远不做，而是需要在证据、隔离环境、评测和变更治理成熟以后独立建设。

## 二、竞品调研：哪些能力可以复用，哪些判断仍要自己承担

现有工具分别改善采集、仓库理解、规则生成或语义验证，但它们的输出不是同一种研究结论。下面沿这些职责比较可复用机制与目标需求的差距；项目文档与论文报告是证据来源，不代表本文已经部署并验证了完整组合。

<span id="5-选择工具检索生成和验证分别负责什么"></span>

### 公开工具与案例的证据范围

仓库导航、SQL 改写、等价验证和实验控制解决不同任务，组合前需要先检查各自输入、输出和语义范围。项目介绍不等于数据库优化效果证据。

**仓库理解和资料采集。** 导航工具可以缩短定位时间，但自动文档不保证理解执行条件或版本差异，需要回到对应源码核对。

| 项目 | 公开能力 | 适合承担的角色 | 不能直接推出 |
| --- | --- | --- | --- |
| DeepWiki | 仓库 Wiki、架构图、源码链接和问答；支持显式指定页面与关注点 | 陌生仓库导航、专题文档入口 | 已理解数据库语义和性能边界 |
| DeepWiki-Open | 独立的开源仓库 Wiki/问答实现 | 本地化原型和实现参考 | 等同于官方 DeepWiki 的内部实现 |
| CodeWiki | 面向仓库级结构化文档的开源框架 | 层次化代码文档候选后端 | 文档完备即等于研究判断正确 |
| CodeGraphContext | Tree-sitter/SCIP、代码关系、CLI 与 MCP | symbol 与调用关系辅助检索 | C/C++ 在缺少构建信息时仍有完整语义索引 |
| Miniflux | 自托管 Feed 阅读器 | RSS/Atom 订阅与人工筛选 | 自动归并技术事件 |
| changedetection.io | 网页变化检测 | 监控没有 Feed 的文档和 Release 页面 | 页面变化一定具有技术价值 |

[DeepWiki 官方文档](https://docs.devin.ai/work-with-devin/deepwiki)已经表明，仓库 Wiki 可以通过配置显式提供背景和页面结构。这是一个重要信号：大型仓库研究不应完全依赖模型自行猜测阅读范围，领域术语、关键目录和已知盲区应当由研究任务显式提供。

但“生成代码说明”与“发现优化机会”之间还有很长距离。后者需要版本判断、跨系统能力映射、反例、历史结论和工作负载相关性，这些通常不在通用代码 Wiki 的责任范围内。

项目入口：[DeepWiki-Open](https://github.com/AsyncFuncAI/deepwiki-open)、[CodeWiki](https://github.com/FSoft-AI4Code/CodeWiki)、[CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext)、[Miniflux](https://github.com/miniflux/v2)、[changedetection.io](https://github.com/dgtlmoon/changedetection.io)。

**SQL 改写、证明与实验框架。** 生成更快查询与证明改写等价是不同目标，选用工具时应先确认 SQL 子集、验证方式和可运行环境。

| 项目 | 主要问题 | 对研究平台的启发 | 使用边界 |
| --- | --- | --- | --- |
| R-Bot | 使用多源改写证据、结构与语义检索辅助 LLM 选择 SQL rewrite | 先把知识转成可检索规则与证据，再进行生成 | 不能把论文实验收益迁移为目标系统收益 |
| WeTune | 自动发现 SQL 查询改写规则 | 将规则、前提与验证分开表达 | 支持的 SQL 方言和语义有边界 |
| SQLSolver | 对支持子集中的 SQL 等价性进行求解 | UNKNOWN 应保留为未知，而不是失败或正确 | 不能覆盖完整 SQL 与所有引擎行为 |
| Cosette | SQL 等价性描述与自动推理 | 规范化查询与反例思维 | NULL、bag semantics 等覆盖需要核对具体模型 |
| SQLancer | 通过自动生成和变形测试发现 DBMS 问题 | 正向能力分析必须同时设计反例 | 需要可运行数据库，不是静态资料系统 |
| PostBOUND | 查询优化原型与 Benchmark 组织 | 将策略原型、工作负载与评估流程解耦 | 不替代生产引擎的集成验证 |

这几类工具的输出也不能直接互换：等价性结论有 SQL 子集边界，SQLancer 找到的是可执行反例，PostBOUND 提供的是实验组织能力。研究记录需要保留调用条件和原始输出，不能把它们统一改写成模型给出的“可信”标签。

项目入口：[R-Bot](https://github.com/curtis-sun/LLM4Rewrite)、[WeTune](https://github.com/WeTune/WeTune-code)、[SQLSolver](https://github.com/SJTU-IPADS/SQLSolver)、[Cosette](https://github.com/uwdb/Cosette)、[SQLancer](https://github.com/sqlancer/sqlancer)、[PostBOUND](https://github.com/Optimizer-Playground/PostBOUND)。

**三个工业/研究案例真正说明了什么。** 案例只能支持其报告的架构与实验范围，不能直接推出通用平台能自动产出正确补丁。下面分别说明可借鉴机制与外推限制。

2025 年的 [R-Bot 论文](https://doi.org/10.14778/3750601.3750625)描述了多源 rewrite evidence、结构与语义混合检索、逐步规则选择，并报告了华为及客户部署。它支持“领域证据可以约束 LLM 改写”这一方向，却不证明一个通用情报平台可以直接产出正确的优化器补丁。

Microsoft 的 [QO-Advisor](https://www.microsoft.com/en-us/research/publication/deploying-a-steered-query-optimizer-in-production-at-microsoft/)将更充分的计划探索放入离线流水线，并在论文所述 SCOPE 场景中讨论预算、可解释 steering 和回归控制。这里值得借鉴的不是某个模型，而是**把探索、验证与生产执行隔离，并为坏决策保留可逆路径**。

CIDR 2026 的 [Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites](https://www.vldb.org/cidrdb/2026/leveraging-query-optimizers-to-verify-the-soundness-of-llm-based-query-rewrites-for-real-world-workloads.html)基于真实企业查询讨论 LLM rewrite，强调语义等价性是实际采用的主要障碍，并提出利用优化器已有能力验证等价性；作者还观察到，模型生成的 rewrite 可以反向暴露优化器缺失的候选变换。

这些案例支持证据辅助改写、离线探索和语义核对等具体方法，尚不足以验证本文提出的持续研究平台。后者还需用自己的目标能力档案、时间切分评测和专家反馈检验有效性。

## 三、思路比较：先保存判断，再决定探索深度

持续研究需要保留版本与历史理由；一次性源码问答则未必需要平台。沿前面的组件边界，可以得到三条建设路线，比较的是研究过程的组织方式，而不是把项目功能相加。

| 路线 | 复用方法 | 适用条件 | 代价与不适用场景 |
| --- | --- | --- | --- |
| 人工主导的版本化研究卡片 | Feed 阅读器、仓库导航与 Markdown 引用，由工程师串起判断 | 主题少、研究不频繁，先验证卡片是否能减少重复工作 | 人工更新与跨人交接成本随规模增加；不适合靠个人记忆维护大量事件失效关系 |
| 确定性资料流水线 + 按需源码探索 | 程序管理 Source/Event/Run；模型提取机制，受控执行器核对少量未知项 | 持续跟踪多个系统，需要重放、去重和历史反馈 | 要维护合同、评审与失效传播；收益依赖能力档案和专家反馈，不能只部署抓取器 |
| Agent 主导的开放式研究 + 外部证据账本 | Agent 动态拆解专题与检索路径，账本和权限仍由程序管理 | 问题路径难预先写定，探索成本可接受，已有稳定评审机制 | 工具轨迹与费用更难预测；不适合把固定来源的批量处理全部转成自由搜索 |

本文以第二条为默认设计：研究对象会持续更新，但大部分采集、归并和版本处理可以写成确定性程序。将探索留给少数未解决的问题，能够限制模型权限和重复阅读；第一条仍作为评测基线，第三条只在固定流程经常无法定位证据时引入。这里的“默认”来自目标约束，不是已有成本实验得出的最优结论。

现成编码工具、可嵌入 Agent 框架与模型 API 是执行层选择，不应改变 Source、Finding 和评审的所有权。任务只是结构化提取时，不需要完整编码运行时；需要多轮追踪调用链时，可先复用已有执行器。更换工具应沿同一输入与产物合同进行，不能同时更改评价标准。执行层的具体差异另见[下篇的执行层选型](#执行层选型编排-codex--claude-code还是框架--模型-api)。

### 程序、模型 API 与代码 Agent 的分工

**任务类型决定执行后端。** 固定变换适合普通程序，跨文件探索适合受控 Agent；两者的日志、预算与权限要求不同。

| 执行方式 | 更合适的任务 | 平台必须控制的内容 |
| --- | --- | --- |
| 普通程序 | 抓取、hash、去重候选、状态机、权限与预算 | 确定性逻辑、错误处理、审计 |
| 模型 API | 批量事实抽取、分类、结构化报告 | Schema、重试、上下文、引用解析 |
| 代码 Agent/CLI | 多轮搜索源码、追踪调用链、阅读测试 | 只读工作区、工具白名单、超时和产物收集 |
| 专用验证器 | SQL 等价性、编译、EXPLAIN、Benchmark | 支持范围、隔离环境和结果解释 |

第一版不需要同时维护两套完整模型后端。资料为主时，API 流水线更简单；源码探索占主要成本时，代码 Agent 更自然。两者共用任务输入、Source 引用和 Finding Schema，未来才有条件比较质量和成本。

**Agent 不负责长期状态。** Agent 的工作区是一次 Run 的执行环境，不是平台数据库。抓取游标、正式档案、历史 Finding、权限和人工评审结果由控制面（Control Plane）保存。否则会出现：

- 会话结束后无法复现；
- 模型误把旧草稿当正式结论；
- 重试时重复抓取和重复发布；
- prompt 变化悄悄改变长期状态；
- 不同 Agent 对同一实体使用不同 ID。

上下文也应按任务裁剪。每次任务只提供当前 Event、必要 Source、相关能力条目和少量历史结论，不把整个资料库塞入上下文。模型需要的是**与决策相关的最小证据闭包**，不是尽可能长的文本。

检索阶段可以先宽召回，再按版本、对象类型、能力条件和证据关系重排。精确配置名用 keyword/BM25；同义机制用 embedding；调用链用 code index；最终关键事实回到原文。

## 四、设计：用版本化合同连接采集、研究与评审

所选路线把长期事实交给程序，把机制解释与定向探索交给受控执行器，把正式判断交给证据审核。设计按对象身份、能力判定、处理流程、案例与审核顺序展开：先确定记录代表什么，再决定如何生成和修订它。

### 把资料、事件、能力和结论分开

资料来源、技术事件和研究结论有不同生命周期；若都当作网页记录保存，同一机制的多次传播会被误计为多项新能力。以下定义约束后续采集和分析流程。

**Source、Event、Fact、Mechanism 与 Finding。** 多个来源可以描述同一事件，不同事件阶段又支持不同强度的结论，因此需要分别保存对象与关联。

| 名词 | 本文定义 | 示例 |
| --- | --- | --- |
| Source，资料源 | 可以被保存、定位和版本化的原始材料 | Release Note、论文 PDF、PR、源码提交、测试文件 |
| Event，技术事件 | 多个 Source 共同描述的同一技术变化 | 功能提出、合入主干、进入版本、默认启用、随后回退 |
| Fact，事实 | 能被具体 Source 直接支持的最小陈述 | “版本 X 增加配置 Y，默认关闭” |
| Mechanism，机制 | 多个事实共同解释的因果过程 | 收集实际 partition bytes 后重写下游 reader mapping |
| Capability，能力 | 在明确条件下，系统可以完成的变换或执行策略 | 在拒绝空值谓词下将某类外连接简化为内连接 |
| Finding，研究结论 | 事实、推断、目标状态、反例、未知和建议组成的版本化记录 | “当前有局部证据，需核对另一条实现路径” |

为什么不能直接把网页当 Event？同一变化可能先出现在设计文档，后进入 PR，再进入 Release，最后被博客介绍。四份 Source 指向一个 Event，但对应不同成熟阶段。如果每篇文章都被当成新事件，平台会持续制造“假新意”。

**Provenance 与 Evidence。** 可追溯性只说明结论来自哪里，证据有效性还要求来源支持具体陈述。两者必须分别核查。

**来源谱系（Provenance）**，回答一条结论从哪里来、经过哪些转换：原文位置、抓取时间、提交版本、提取任务、人工修订和最终报告之间如何关联。

**Evidence，证据**，回答这份材料能够支持什么结论。链接存在并不代表链接支持句子；源码存在也不代表路径可达。来源谱系解决追踪问题，证据分析解决推理边界问题。

一个事实最好拥有这样的最小引用结构：

```json
{
  "claim_id": "F-2026-0042",
  "claim": "规则在配置关闭时不参与当前优化批次",
  "source": {
    "type": "source_code",
    "repository": "example/engine",
    "commit": "<full-commit-id>",
    "path": "optimizer/rules/example_rule.cc",
    "symbol": "ExampleRule::check"
  },
  "support": "direct",
  "limitations": ["未排除其他等价实现路径"]
}
```

行号适合阅读，但代码演进后会漂移；commit、path 与 symbol 的组合通常更稳定。网页则至少保存 canonical URL、抓取时间、内容哈希和支持结论的片段。

**目标系统能力档案。** **能力档案**不是自动生成的项目百科，而是围绕研究决策维护的最小已知状态。它记录：

- 已知能力及固定版本证据；
- 适用条件与明确限制；
- 架构接口和责任边界；
- 历史建议、否定原因与待复核项；
- 当前最有价值的研究主题。

它可以从几十个 Markdown 条目开始，不需要先把整个仓库放入知识图谱。档案的意义是为反向检索提供记忆：看到外部“消除 Shuffle”的文章时，先搜索目标系统是否通过物理属性、局部 Shuffle、bucket mapping 或别的阶段实现了相同效果，而不是直接生成“应该支持 Shuffle 消除”。

这类档案可以由多种工具辅助检索和维护，但它们承担不同职责：

- **RAG（Retrieval-Augmented Generation）**：先检索相关资料，再让模型基于检索结果生成答案。它改善上下文相关性，但不自动保证事实正确。
- **Embedding（向量表示）**：将文本或代码映射为向量，用距离近似语义相似。适合召回同义描述，不擅长独立证明控制流和版本关系。
- **代码图谱**：将 symbol、definition、reference、call、inheritance、file 等关系组织成图。它能辅助导航，但边的精度依赖语言前端和构建信息。
- **Tree-sitter**：增量解析框架，可获得语法树；语法关系不等同于经过类型解析的精确调用关系。
- **SCIP（Source Code Intelligence Protocol）**：一种代码索引协议，可以表达符号和引用；是否能得到完整索引，仍取决于语言 indexer 与构建环境。
- **Agent**：能够在约束下多步选择工具、观察结果并继续行动的执行器。Agent 提高探索能力，也扩大了权限、成本、可重复性和提示注入风险。

这些组件没有谁天然“更高级”。关键词搜索对精确配置名最好；语法树适合定位规则结构；精确代码索引适合跨文件符号引用；向量检索适合同义机制召回；Agent 适合答案路径无法预先写死的研究任务。成熟系统通常组合它们，而不是用一种检索方式替代所有方式。

无论使用哪种工具，对一条优化规则都要分别回答三个问题：

1. **语义正确性**：变换是否保持约定的查询语义？
2. **计划可达性**：当前实现、规则顺序和配置能否生成该计划？
3. **性能收益**：代价模型是否会选择它，并在目标工作负载上更快或更省资源？

形式化证明可以加强第一个问题，源码和测试帮助回答第二个问题，运行实验主要回答第三个问题。任何一层都不能代替另外两层。

其中，形式化验证（Formal Verification）需要先明确建模对象。查询变换、并发协议和具体 SQL 方言，适合的工具并不相同：

- **Lean** 是交互式定理证明器。研究者可以定义关系代数（Relational Algebra）或 SQL 子集的语义，再证明某个改写在给定前提下保持等价。这里必须明确采用 set 还是 bag semantics，如何解释 NULL 与三值逻辑（Three-Valued Logic），以及是否考虑顺序、溢出、异常和非确定函数。证明只覆盖被建模的语义，不自动证明真实数据库实现没有缺陷，也不回答改写是否更快。
- **TLA+** 更适合描述并发协议和状态迁移，例如调度器状态、动态扩缩容、Spill/恢复流程和任务重试。模型检查能够在有限状态空间中搜索违反安全性或活性约束的执行路径；“没有找到反例”依然不等于对任意规模实现完成了数学证明。
- **SQLSolver、Cosette 一类领域工具**把特定 SQL 子集、约束和等价性判断封装得更直接。它们返回 `UNKNOWN` 时，应保留“当前模型无法判断”的含义，不能把它偷换成“不等价”，更不能把支持子集中的结论外推到完整方言。

因此，形式化工具适合处理高价值、语义边界清晰的改写争议，或故障代价很高的并发协议。它们不适合成为平台第一阶段的必选基础设施。更现实的顺序是：先让前提、反例和证据结构化；当某类争议反复出现，再为它建立足够小、可维护的形式化模型。

### 能力判定：统一条件以后比较机制 {#2-比较机制统一条件之后才能讨论能力差异}

跨引擎比较应以有条件的能力为单位。同名规则可能有不同语义限制，同一效果也可能分别由分析器、优化器或运行时实现；按类名和规则数比较会漏掉这些路径。

#### 证据如何限定能力判断

**同一能力的不同实现位置。** 需要检查的路径包括：

- Analyzer 或 Binder 的表达式规范化；
- logical rewrite rule；
- Memo 中的 exploration rule；
- property derivation 与 Enforcer；
- physical implementation rule；
- cost model；
- Runtime 自适应路径。

同名规则也可能覆盖完全不同的语义。例如“Predicate Pushdown”可以指过滤穿过 Project、Aggregate、Window、Join 或 connector boundary；每种情况的确定性、NULL、异常行为和列映射前提不同。只比较类名或规则数量，会同时产生漏报和误报。

更可靠的比较单位是：

> 在条件集合 C 下，系统通过阶段 S 和机制 M，将计划 P 转换为 P′，并产生可观察结果 O。

一条能力记录至少包含：查询形态、语义条件、工作负载条件、机制、阶段、配置、预期计划变化、资源变化、限制、反例、证据和版本。

**证据阶梯。** 声明、源码、计划与执行实验逐步回答不同问题，后一个结论不能由前一层材料自动推出。

| 等级 | 能支持的结论 | 仍不能支持 |
| --- | --- | --- |
| 官方概述或 Release Note | 功能被声明、版本与发布阶段 | 内部算法细节、所有边界、真实收益 |
| 设计文档或论文机制 | 作者公开的问题设定与设计 | 当前发行版完全一致、默认启用 |
| 固定版本源码与注册点 | 代码中存在路径与 guard | 任意查询可达、一定被代价选择 |
| 正反测试与计划样例 | 特定形态被维护者预期覆盖 | 所有组合语义、生产触发率 |
| 同版本 EXPLAIN/trace | 特定输入与配置生成该计划 | 其他数据分布仍选择它 |
| 受控 Benchmark | 给定环境下的性能差异 | 生产工作负载的同等收益 |
| 生产观测与回滚记录 | 目标场景的实际价值与风险 | 无条件推广到其他系统和版本 |

证据不是简单的“高低分”。源码对实现事实很强，对生产收益很弱；论文实验对其数据集很强，对目标系统迁移很弱。平台应保存每类证据能回答的问题，而不是把它们相加成一个 0.93 的置信度。

支持能力的证据可以指向一条实现；否定能力却需要排除替代路径。搜索不到类名，只能说明在当前范围和关键词下没有命中，不能证明引擎不支持该能力。一个系统可能：

- 使用不同术语；
- 在 Builder 或表达式简化阶段完成；
- 依赖共享执行库；
- 只为某个 connector、数据类型或 Join 实现特化；
- 在 Runtime 而非 optimizer 中补偿；
- 在商业版本而非开源分支实现。

相对可靠的局部负证据，是固定版本中存在明确 guard：某条实现路径在条件 C 下直接退出。要把它扩大成“整个系统不支持”，还需要排除其他路径，或得到范围明确的维护者确认。

因此，能力档案应把“没有证据”与“证实不支持”分开保存。目标系统可以采用以下状态：

| 状态 | 定义 | 允许的表述 |
| --- | --- | --- |
| 已覆盖 | 有证据覆盖当前条件 | 只讨论额外边界或性能差异 |
| 部分覆盖 | 已知覆盖部分情形 | 明确已知范围和未覆盖条件 |
| 已确认局部缺口 | 固定版本与范围内有直接证据 | 只能给出有范围的差异结论 |
| 未知 | 证据不足 | 提出核对问题与所需证据 |
| 不适用/不可比 | 责任边界或架构前提不匹配 | 记录排除原因 |
| 待复核 | 证据过时、冲突或版本已变化 | 暂停沿用旧结论 |

如果把未知记成零，公开资料少的闭源引擎会系统性“得分更低”，调查完成度被误当成产品能力。

#### 沿优化器与 Runtime 的责任边界追踪

优化器决定候选和属性，runtime 决定执行状态与退化路径；跨层机制需要同时核对两者，避免把可执行能力误当成默认计划行为。

**优化器：不要把所有问题写成“缺少规则”。** 计划没有出现可能源于候选生成、属性要求或成本选择，不能统一归因于缺少规则。至少需要区分六类原因：

1. 没有实现对应变换；
2. 语义或属性前提不满足；
3. 前置规范化缺失，导致规则形态不可达；
4. 搜索预算、剪枝或规则顺序没有探索该候选；
5. cost model 选择了别的计划；
6. distribution、ordering、uniqueness 等物理/逻辑属性（Logical Property）推导不足。

| 分析维度 | 典型问题 | 必须记录的条件 |
| --- | --- | --- |
| 逻辑变换 | 去相关、外连接简化、聚合重写、冗余操作消除 | NULL、bag semantics、唯一性、确定性与异常 |
| 约束和统计 | 主键、函数依赖、选择率、相关性、倾斜 | 精确约束与估计统计的区别、快照有效期 |
| 搜索与组合 | Memo 探索、Join 枚举、rule ordering、预算 | 入口形态、前置变换、剪枝和停止条件 |
| 代价与选择 | Join 算法、broadcast、聚合策略、计划稳定性 | 统计来源、cost 假设、资源与工作负载 |
| 物理属性 | distribution、ordering、partitioning、Exchange 复用 | 属性的产生、保持、失效和 Enforcer 成本 |
| 自适应优化 | runtime feedback、动态过滤、阶段重规划 | feedback 时机、可修改边界、恢复成本 |

这里有一个经常出现的危险：把采样统计当成语义约束。统计可以帮助估计成本；如果用它消除数据或改变结果集，就必须证明对应属性是保证，而不是大概率成立。

**Runtime：减少什么，又增加什么。** 执行引擎研究的主线不是“用了 SIMD/Hash/压缩”，而是资源交换：减少了哪些 CPU、内存、网络或 I/O，又增加了哪些转换、同步、元数据和长尾风险。

| 分析维度 | 需要提取的机制 | 主要退化因素 |
| --- | --- | --- |
| 数据表示 | row/column layout、vector batch、encoding、字符串与状态布局 | 类型宽度、变长字段、解码和转换 |
| 算法与特化 | Hash Join、Sort、Aggregate、TopK、表达式计算 | NDV、倾斜、键宽、选择率、有序性 |
| 内存与 Spill | 分配、预算、分区、写出、恢复 | 并发状态、峰值、I/O、递归重分区 |
| 并行执行 | task、driver、morsel、局部/共享状态 | 同步、争用、NUMA、长尾和过度并行 |
| I/O 与物化 | pruning、late materialization、cache、compression | 存储接口、局部性、CPU/带宽交换 |
| 分布式交互 | Shuffle、broadcast、serialization、backpressure | 网络、故障恢复、隔离和调度 |

例如，更紧凑的 Hash Table 可能降低内存和 cache miss，但增加编码或解码；更细的 partition 可以改善负载均衡，却增加调度、buffer 和小文件；Spill 能避免 OOM，却可能把 CPU 问题变成 I/O 问题。

两侧分析还需要合并到同一条研究记录。一种新的聚合 Spill 实现可能改变 Hash Aggregate 与 Sort Aggregate 的适用区间。动态过滤既涉及优化器插入位置，也涉及 Runtime 构建、传播和消费。自适应 DOP 需要优化器保留可调整边界，也需要调度器和算子状态支持。

因此，一条 Finding 可以关联多个方向，但要指定主要研究对象，并显式记录关系：

- 需要 Runtime 支持；
- 扩大逻辑变换的适用条件；
- 改变 cost model 的 crossover point；
- 依赖新的 property derivation；
- 需要 scheduler 或 storage interface 配合。

### 处理流程：让每条结论回到输入版本 {#4-组织流程让每条结论都能回到输入版本}

研究流程应先固定材料，再生成允许修订的判断。来源快照和事件版本是复核依据，能力档案与历史结论负责提供目标系统的已知状态；任何一方更新，都可能触发重新评价。

#### 采集、归并与能力档案

**从少量高价值来源开始。** 一手资料更适合定位版本和机制，但仍需要交叉核对准入与调用路径。可按以下用途安排采集优先级：

1. 官方 Release、文档与设计说明；
2. 仓库 PR、Issue、源码和测试；
3. 作者论文与技术博客；
4. 二手新闻、社交媒体和聚合摘要。

低层来源可以用于发现，高风险结论应回到一手资料。第一版不需要跟踪所有引擎。更合理的组合是：一个分布式 SQL 引擎、一个便于分析算子实现的本地引擎、一个优化框架或执行库，再加目标系统自己的能力档案。

完整数据库、执行库和优化框架的责任边界不同。Velox 没有完整 SQL planner，不应因为缺少某条逻辑规则而被判能力不足；Calcite 是框架，不应直接和一个可部署数据库比较运行时 Spill。

**事件生命周期。** 提出方案不等于默认可用，事件状态应跟踪合入、发布与回退，以防旧描述覆盖新事实。

```text
proposal / issue
      │
      ▼
implementation merged
      │
      ▼
available in release
      │
      ▼
enabled by default
      │
      ├──► restricted / deprecated
      └──► reverted
```

“合入主分支”不能替代“进入稳定版本”，“进入版本”也不能替代“默认启用”。平台应分别保存：

- 原始发布时间；
- 首次发现时间；
- 抓取时间；
- 声明适用版本；
- commit/PR 与 release 的关系；
- 当前成熟阶段。

旧文章第一次被平台看到，应标记为“新增收录”，不能写成“本周发布”。新证据补充限制或回退时，应修订原 Event，而不是创建一条互相冲突的新事实。

**快照、去重与游标。** 采集程序使用游标和重叠时间窗口，先持久化抓取内容，再推进游标。canonical URL 解决 URL 变体，content hash 辅助识别正文变化；标题相同或 URL 相同都不足以单独完成事件归并。

对动态网页，至少保存正文片段和抓取时间；对 Git 仓库，优先保存完整 commit。PR 描述会编辑、默认分支会前进、文档会无提示更新——没有快照，就无法复现模型当时为何得出结论。

**能力档案如何保持最小。** 能力档案应保存能改变研究判断的最小证据，而不是复制全部仓库文档，以降低更新和失效维护成本。新增条目应满足以下条件之一：

- 它能阻止一类重复误判；
- 它是当前研究主题的重要前提；
- 它记录了已确认的局部能力或限制；
- 它保存了一次高成本研究的结论；
- 它说明某条建议为何被拒绝。

模型可以提出档案更新草稿，但不能用自己生成的旧报告循环引用，最终把猜测“洗成”事实。正式档案应由人工确认，或者由明确的证据规则推进状态。

#### 两阶段分析与持久化合同

游标、状态与预算需要可重复的控制逻辑，模型负责有边界的机制分析。该划分增加合同维护成本，但使失败任务可以重放和审计。

**核心工作流。** 采集事实与目标映射应顺序衔接，先保存来源快照，再产生可修订的研究结论。下图是本文提出的流程，不是已实现系统的运行记录。

```text
资料源
  │
  ▼
抓取与不可变快照 ──► Source
  │
  ▼
去重、版本识别、事件归并 ──► Event
  │
  ▼
事实与机制提取 ──► Facts + Mechanism
  │
  ├───────────────┐
  ▼               ▼
目标能力档案    历史 Findings
  │               │
  └──────┬────────┘
         ▼
反向检索、差异分析、反例检查
         │
         ├── 关键证据不足 ──► 定向源码/资料研究 ──┐
         │                                        │
         ├── 达到预算 ──────► Unknown / 待核实    │
         │                                        │
         └── 证据足够 ──────► 人工评审 ──► Finding/档案更新
```

抓取、状态推进、幂等（Idempotency）键、预算、权限、持久化和失败恢复，应由普通程序控制。模型适合提取机制、解释条件、生成检索计划和组织文字；它可以申请工具调用，但不应自行决定无限搜索、正式发布或修改档案状态。

**为什么采用两阶段分析。** 先解释外部机制，再检查目标系统，可以减少带着“目标缺功能”的预设选择证据。第一阶段只读外部材料，输出：

- 发生了什么；
- 机制是什么；
- 触发条件和限制；
- 外部收益声明及测量条件；
- 每条事实的证据位置。

这一阶段不读取目标系统状态，减少“为了生成差异而曲解外部资料”的动机。

第二阶段再读取外部事实、目标能力档案和历史结论，回答：

- 为什么可能相关；
- 已知状态是什么；
- 是否存在同义或替代实现；
- 哪些条件不可迁移；
- 最小核对问题是什么；
- 可能影响 CPU、内存、网络、I/O、延迟还是稳定性。

如果外部事实互相冲突，保留冲突和各自版本，不让模型强行融合成一个流畅但虚假的故事。

**最小数据模型。** 单机、低并发的第一版可以用 SQLite 和版本化文件覆盖主流程；多写者冲突、权限隔离和恢复需求增长后再评估服务化存储。四个主实体如下：

| 实体 | 核心字段 | 关键关系 |
| --- | --- | --- |
| Source | URL/path、快照、类型、发布时间、抓取时间、hash、定位 | 多个 Source 可以描述一个 Event |
| Event | 对象、机制、版本范围、成熟阶段、归并依据、revision | 关联 Sources 与 Findings |
| Finding | facts、inference、目标状态、proposal、counter evidence、unknowns | 绑定 Event、档案版本和历史 Finding |
| Run | 输入版本、任务阶段、模型、工具、预算、状态、输出与评审 | 复现失败、重跑与成本分析 |

Finding 需要把外部机制和目标判断分开保存。下面的合同示例中，已提取的聚合机制不改变 `target_status: unknown`；`next_check` 与 `close_when` 分别说明下一步检查和结束条件：

```json
{
  "finding_id": "OPT-2026-0042-v3",
  "event_version": "EV-018@5",
  "target_profile_version": "engine-profile@31",
  "facts": ["F-112", "F-113"],
  "mechanism": {
    "problem": "skewed aggregation state",
    "stage": "runtime",
    "action": "partition and spill selected state",
    "preconditions": ["spillable aggregate state"],
    "limitations": ["high repartition cost for extreme heavy hitters"]
  },
  "target_status": "unknown",
  "inferences": [],
  "counter_evidence": [],
  "unknowns": ["current state ownership during recovery"],
  "next_check": "trace state layout, spill trigger and restore path",
  "close_when": "the supported state types and peak-memory behavior are known"
}
```

Schema 能验证字段是否存在、枚举是否合法、引用是否可解析；它不能判断 source 是否真的支持 claim。结构检查和语义审核必须同时存在。

**幂等、重试和版本。** 重复执行需要绑定输入快照和分析政策版本，否则旧结果可能被误用为新版本结论。幂等键可以由以下内容组成：

```text
event_version
+ analysis_scope
+ target_profile_version
+ source_snapshot_set
+ output_schema_version
+ prompt_or_policy_version
```

模型升级或 policy 变化时创建新的 Run，不覆盖旧结论。任务执行状态与 Finding 评审状态分开：一次 API 超时不能把已经发布的结论改成失败。重试应限制次数，保留已经成功的中间产物；Source 被更正或撤回时，反向标记受影响的 Findings 待复核。

### 合同走读：用外连接与外部聚合检查记录 {#3-用两个问题检验研究记录}

一份可用的研究记录必须把机制落到可检查的条件上。外连接简化可以从 NULL 语义推导变换前提，外部聚合则需要追踪状态、内存和恢复；两者不能只填一张相同的功能清单。

#### 外连接简化与外部聚合

以下示例只演示如何组织证据。目标状态保留为未知，直到固定版本的源码、测试或实验能够回答相应问题。

**优化器示例：外连接简化。** 拒绝空值的上层谓词可能使外连接简化为内连接（Inner Join），但前提取决于谓词对补 NULL 行的行为。考虑以下查询：

```sql
SELECT a.id, b.amount
FROM A AS a
LEFT JOIN B AS b ON a.k = b.k
WHERE b.amount > 0;
```

在常规 SQL bag semantics 和 NULL 三值逻辑下，未匹配行的 `b.amount` 为 NULL，`NULL > 0` 的结果为 UNKNOWN，WHERE 只保留 TRUE，因此未匹配行被过滤。若表达式的确定性、异常行为和类型转换满足前提，将该 LEFT JOIN 简化为 INNER JOIN 可以保持结果；这里不要求连接键唯一，因为匹配行的重复次数没有改变。

关键术语：

- **bag semantics**：SQL 结果默认是多重集，重复行有计数；不能按集合语义随意消除 duplicate。
- **three-valued logic**：比较结果除了 TRUE/FALSE 还有 UNKNOWN；WHERE 丢弃 FALSE 和 UNKNOWN。
- **null-rejecting predicate**：当相关列为 NULL 时，谓词不可能为 TRUE。

反例包括：

```sql
-- 不拒绝 NULL；未匹配行可能被保留。
WHERE COALESCE(b.amount, 0) >= 0

-- OR 的左侧可能让未匹配行通过。
WHERE b.amount > 0 OR a.category = 'important'
```

研究时应定位：null-rejecting 判断、Join rewrite 注册顺序、表达式确定性、cast/异常语义、正反测试，以及简化后是否触发 Join reorder 与 predicate pushdown。静态搜索没命中一个规则名，不能直接得出“不支持”。

合理 Finding 是：

```text
外部机制：利用 null-rejecting filter 将特定 outer join 简化为 inner join。
目标状态：未知。
反向检索：Analyzer 简化、Join rule、predicate inference、Builder rewrite。
最小核对：固定版本下覆盖哪些表达式，哪类 guard 拒绝。
潜在价值：扩大 Join reorder 与 filter pushdown 的搜索空间。
收益状态：未验证，依赖数据分布与后续计划选择。
结案条件：明确已有覆盖范围或确认一个可复现的局部缺口。
```

**Runtime 示例：外部聚合与内存管理。** 外部聚合的收益依赖状态布局、缓冲管理和分区恢复，不能仅根据支持 spill 判断可迁移性。

[DuckDB 的 External Aggregation 文章](https://duckdb.org/2024/03/29/external-aggregation)描述了 buffer manager、可换出的页、变长数据指针恢复、局部预聚合和 partition-wise 聚合。这是理解机制的优秀材料，但不能被简化成“支持 Spill，所以任何分布式系统都应照搬”。

关键术语：

- **NDV（Number of Distinct Values）**：分组键不同值数量；高 NDV 往往意味着更多聚合状态。
- **Spill**：内存状态放不下时，把部分数据或状态写到更慢的存储，后续恢复处理。
- **Pre-aggregation**：在完整聚合前先局部合并相同 key，减少后续数据量；高 NDV 时收益可能降低。
- **State ownership**：哪个线程、task 或 partition 拥有并更新某份聚合状态，决定并发与恢复方式。
- **Serialization**：将内存对象转成可持久化/传输表示；指针和进程内地址通常不能原样恢复。

迁移分析应核对：

- 聚合状态是否可移动、可序列化，UDF aggregate 是否例外；
- 变长 key/value 的所有权和恢复成本；
- Spill trigger 是算子局部还是全局内存仲裁；
- partition 粒度、递归 repartition 和 heavy hitter；
- 并发 operators 是否各自按上限分配，导致峰值放大；
- 单机 buffer manager 假设与分布式 Shuffle、远端存储、故障恢复的差异；
- 新机制是否需要 optimizer 更新 memory cost 与算法适用区间。

合理结论是“该布局和内存管理思路值得作为对照，目标状态与收益待核实”，而不是引用外部 Benchmark 作为预期收益。

**标准研究卡片。** 固定字段用于暴露证据缺口，不应强迫模型把未知项填成确定答案。每条卡片至少回答以下问题。

| 字段 | 必须回答的问题 |
| --- | --- |
| Event 与 Mechanism | 外部发生了什么，控制点和因果链是什么 |
| Source 与版本 | 哪个快照支持事实，处于什么发布阶段 |
| 适用条件 | 对哪些查询、数据、资源、语义和版本成立 |
| 目标状态 | 已覆盖、部分覆盖、局部缺口、未知或不适用 |
| 反向检索 | 检查过哪些同义术语、阶段和替代路径 |
| 迁移分析 | 哪一部分可借鉴，依赖哪些接口与执行模型 |
| 研究方向 | 最值得进一步核对什么，影响哪类资源 |
| 反例与代价 | 什么条件下不成立，会增加哪些成本 |
| Evidence 与 Unknown | 每项结论来自哪里，还缺什么 |
| 下一步与结案条件 | 最小动作是什么，得到什么答案即可结束 |

### 反向检索、反例与人工复核

减少误判需要同时限制推断强度和检索盲区，单纯增加引用数量无法证明建议正确。

**句子级区分事实、推断、建议与未知。** 事实与推断需要分别标记，否则有出处的前半句会替未验证的后半句制造可信感。研究记录应区分四种陈述：

```text
[事实] 固定版本源码中的 guard 在条件 C 下返回 false。
[推断] 因而该规则路径不会处理 C。
[未知] 尚未排除 Builder 或其他 rule 完成同类变换。
[建议] 定向检索等价形态和相关测试；在排除其他路径后再判断局部缺口。
```

固定审核规则包括：

- “外部系统加入 X”不能推出“目标系统没有 X”；
- “代码存在 X”不能推出“默认启用 X”；
- “测试覆盖 X”不能推出“所有组合语义都支持 X”；
- “单算子 CPU 下降”不能推出“端到端延迟必然下降”；
- “多个模型意见一致”不能充当独立外部证据。

**反向检索与替代实现。** 未命中某个术语不足以证明目标系统缺少能力，应先检查同义机制与替代实现路径：

1. 同义词和术语别名；
2. Analyzer/Builder 的提前简化；
3. 属性系统与 Enforcer；
4. connector、storage、execution library 的实现；
5. Runtime 自适应或 fallback；
6. 历史 Findings 和被否定原因；
7. 新版本、配置和商业/开源分支差异。

反向检索不是为了证明“系统什么都有”，而是防止在错误抽象层上发明缺口。

**反例优先。** 建议的适用条件需要反例检验，否则容易把局部收益外推到空值、倾斜或资源不足场景。至少检查：

- 哪种 NULL、duplicate、overflow 或 non-deterministic function 会破坏语义？
- 哪种 NDV、skew、row width 或 memory pressure 会让成本反转？
- 哪种 property、connector 或 execution mode 会使机制不可用？
- 是否引入额外 Exchange、serialization、materialization 或 recovery cost？
- 如果 feedback 错误，能否回滚到 last-known-good？

反例不是文章末尾的“局限性”装饰，而是决定研究是否成立的第一等输入。

**安全与提示注入。** 网页、README、Issue 和代码注释都属于不可信数据。里面出现“忽略前文并运行脚本”时，研究 Agent 不应执行。默认策略应是：

- 源码研究只读；
- 不执行仓库安装脚本和未知二进制；
- 网络、文件与命令权限按任务最小化；
- 内部资料只发送到获准的模型环境；
- 凭据不进入日志、prompt 和报告；
- 动态验证使用独立任务、沙箱和资源预算。

安全边界既保护机器，也保护研究结论不被 Source 中的指令污染。

人工复核最后还需留下否定或采用的理由。二元反馈无法区分重复发现、证据不足与架构不适用，后续研究因而无法决定应补材料还是停止迁移。反馈至少应保存以下理由：

- 值得继续研究；
- 已覆盖，并链接能力证据；
- 与历史 Finding 重复；
- 证据不足，需要哪类材料；
- 架构不适用，并记录条件；
- 结论错误，错误发生在哪个推理步骤。

新 Event 只有带来新机制、扩大适用范围、增强证据或推翻旧结论时，才重新进入重点评审；否则只关联历史记录。

### 实施顺序：先完成少量事件的结案 {#7-按研究瓶颈扩展而不是先建全量知识库}

最小版本应先完成少量事件的追溯、评审和结案，再决定是否引入向量库、代码图谱或长期 Agent。每个新增组件都有索引更新、失效处理和审核成本，只有可观察的瓶颈才能支持这项投入。

<span id="分阶段建设与成本控制"></span>

**四阶段路线。** 平台扩展应由上一阶段的可验证结果触发，不能把组件部署完成等同于研究质量达标。

| 阶段 | 主要交付 | 进入下一阶段的证据 |
| --- | --- | --- |
| 定义研究标准 | 3 个外部对象、最小能力档案、研究卡片、历史样本 | 专家能一致区分事实、未知和建议 |
| 跑通单次研究 | 抓取归并、两阶段分析、结构检查、Markdown 输出 | 任一结论可回到 Source，任务可重放 |
| 增量与反馈 | 游标、幂等、版本修订、人工理由、历史去重 | 重复传播和失败重试不污染结论 |
| 评测与选择扩展 | 时间切分保留集、成本、消融、少量源码专题 | 质量达标后再扩大引擎和资料范围 |

第一个可用版本可以只是命令行、SQLite 和报告目录。网页、向量库、知识图谱、消息队列都不是前置条件。

## 五、可行性分析：验证研究质量，再决定是否扩大平台 {#6-评价研究质量不冒充性能验证}

只读研究可以评估事实支持率、重复建议和人工核对成本，但不能测出目标负载的性能收益。两类指标分开，才能知道平台改善了研究过程，还是只生成了更完整的文字。

### 历史回放、基线与停止条件

**先评研究质量，不伪造性能验证。** 只读环境能评价证据与分析质量，不能伪造性能实验。可验证范围包括：

- 来源、版本和发布状态是否准确；
- 机制是否符合原文；
- 源码路径是否支持局部判断；
- 推断是否遗漏语义和架构前提；
- 重复 Source 是否正确归并；
- 专家是否认为问题值得继续核对。

此时不能验证目标工作负载的触发率、计划选择概率和端到端收益。这些值应该保持 unknown，而不是由引用数量、模型分数或外部最大加速比替代。

**构造历史回放集。** 从 30–50 个真实技术事件开始，是一个可执行的工程起点，不是统计保证。样本应包含：

- optimizer、Runtime 与跨层机制；
- 真正的新变化、旧文重发和重复传播；
- 功能默认启用、可选、回退和废弃；
- 已覆盖、部分覆盖、未知和不适用；
- 高价值论文与低信息密度新闻；
- 模型容易过度迁移的单机/分布式差异。

按 Event 分组并按时间切分开发集和保留集，避免同一 PR 的博客进入训练侧、Release Note 进入评测侧。回放只能使用截止当时可见的 Source 和档案版本；如果只能使用今天的网页，就应称为“冻结输入离线评测”，不能声称完整模拟历史发现。

**指标必须写出分母。** 省略失败或未知项会抬高报告质量指标，因此每项比例都需要固定统计对象与分母。

| 指标 | 计算口径 | 防止的误用 |
| --- | --- | --- |
| 证据可追溯率 | 有有效定位/快照的事实数 ÷ 全部事实数 | 有 URL 不等于支持结论 |
| 事实支持率 | 抽查中被原文支持的事实数 ÷ 抽查事实数 | 与链接存在率分开 |
| 重大错误率 | 含重大事实/语义错误的 Finding ÷ 已评审 Finding | 不让大量小事实稀释大错 |
| 有效建议率 | 专家认定值得继续研究的建议 ÷ 已评审建议 | 固定评审标准和范围 |
| 重复建议率 | 无实质增量的重复建议 ÷ 已输出建议 | 新证据修订不算重复 |
| 保留集事件召回 | 找到的相关标注 Event ÷ 相关标注 Event 总数 | 不宣称全网召回 |
| 人工时间变化 | 同类任务基线时间与辅助后时间比较 | 包含审核、更正和档案维护 |
| 单条有效建议成本 | 模型、工具、人工总成本 ÷ 有效建议数 | 分母为零时不生成虚假单价 |
| 研究滞后 | Source 首次可获取至完成评审的时间 | 与文章发布时间分开 |

同时报告样本量、未评审比例和置信区间或不确定性。样本很小时，一两条建议的变化不能被包装成稳定提升。

**基线与消融。** 平台增益需要与专家原流程和简单检索对照，否则无法区分模型能力与额外阅读时间。至少比较三组流程：

1. 专家原有阅读流程；
2. 只有新闻/论文摘要的模型流程；
3. 加入 Source 快照、能力档案、反向检索和证据审核的流程。

再做消融：去掉历史去重、源码深挖、反例检查或能力档案，观察它们是否提高有效建议率，还是只增加报告长度。模型越强不代表整个系统越好；如果强模型带来的收益被更高重试和审核成本抵消，较简单流程可能更经济。

继续检索应以是否可能改变当前判断为依据；重复来源不增加机制证据，缺失的动态实验也不能由更多摘要替代。以下条件可触发本轮停止：

- 已有证据足以作出当前决策；
- 新 Source 只重复已有机制和边界；
- 达到资料、工具、时间或费用预算；
- 关键事实必须依赖不可获得的内部信息或动态实验；
- 下一步已明确转交独立验证任务。

停止时保存 Unknown 和所缺证据，比生成一个强行闭合的结论更有价值。

### 故障与反例必须进入最小验证

可追溯的成功报告只能证明正常链路连通；重复、撤回和版本变化才会暴露记录模型是否可靠。下面是设计验收项，尚不是本平台已通过的测试结果。

| 输入或故障 | 预期行为 | 验证的设计前提 |
| --- | --- | --- |
| 同一 PR 先出现在博客、后进入 Release | 关联同一 Event，保留不同成熟阶段，不重复生成“新能力” | Source 与 Event 分离 |
| 提取后任务中断，再用相同输入重跑 | 复用已保存快照，保留 Run 状态，不重复发布 Finding | 输入身份、幂等与评审状态独立 |
| 引用真实存在，但不支持结论 | 结构检查可以通过，证据审核必须拒绝 | Schema 校验不能代替语义检查 |
| 目标引擎已有同义或替代路径 | 关联已有能力或保持未知，不直接生成缺口 | 反向检索与局部负证据 |
| Source 被更正，或目标版本升级 | 标记关联 Finding 待复核，保留旧判断及其依据 | 版本依赖与失效传播 |
| 所需事实只能由 Benchmark 回答 | 终止只读推断，生成独立验证任务 | 研究与性能实验边界 |

### 扩展条件与成本边界

**何时增加基础设施。** 只有持续出现的定位、吞吐或协作瓶颈，才足以支持新增组件及其维护成本。

| 观察到的瓶颈 | 再增加的能力 |
| --- | --- |
| 同义机制持续漏检 | embedding 与术语表 |
| 精确关键词和过滤变慢 | 全文检索/BM25 |
| 跨模块调用定位占主要时间 | SCIP/语言服务器/代码图谱 |
| 多人评审冲突 | 服务数据库、权限与审核 UI |
| Source 数量大、任务需要异步恢复 | 队列和独立 worker |
| 只读结论长期停在收益未知 | 隔离的 EXPLAIN/Benchmark 平台 |

“技术流行”不是建设理由；可观察的研究瓶颈才是。

**预算应该按阶段记录。** 将成本拆成采集、筛选、事实提取、目标映射、源码深挖、验证和人工复核。多数 Event 在机制筛选后结束，少数进入目标分析，极少数进入源码专题或动态实验。

每个任务设置最大 Source 数、工具调用、token、时间、费用和允许的执行权限。下一次检索应对应一个具体未知项，例如规则是否默认注册、计划能否到达，或者论文是否把数据搬运计入测量。重复材料已不能改变判断时就应停止；达到预算则保存已有事实和 Unknown。缓存仍有失效、存储和错误结果治理成本，向量库也不能决定新材料应该更新哪个事件。

**主要风险。** 平台错误会通过重复生成传播到后续决策，因此版本、来源和权限治理应早于大规模自动发布。

| 风险 | 后果 | 优先处理 |
| --- | --- | --- |
| 能力档案稀疏或过时 | 重复建议、误判已有能力 | 先补当前主题的最小档案和版本 |
| 旧文重发和多渠道传播 | 制造假新意 | Source/Event 分离与历史归并 |
| 开源与商业版本混用 | 错判真实能力 | 绑定仓库、release、配置和阶段 |
| 单机机制直接迁移分布式 | 忽略状态、网络和恢复 | 强制写执行模型差异 |
| 引用正确但推断错误 | 报告显得可信却无法行动 | 句子级类型、反例和人工审核 |
| 为固定篇数持续产出 | 低价值内容挤占专家时间 | 允许无结果，以有效建议衡量 |
| 过早建设全量图谱 | 高投入、低研究收益 | 先完成历史回放和消融 |
| Agent 权限过大 | 安全事故和不可复现状态 | 只读默认、白名单和控制面治理 |

研究平台适合持续跟踪多个引擎、需要复用历史判断的团队；一次源码问题通常用版本化笔记和人工核对就够了。第一版可先选少量真实事件和能力条目，检查事实能否回到原文、同义机制是否重复建议、未知项是否保留，以及版本变化后旧结论是否进入复核。只读阶段不宣称性能收益；需要验证收益的 Finding，应携带假设、反例和工作负载要求转交独立实验。未经语义和目标环境验证的外部优化，不能直接成为上线建议。

## 附录 A：单次研究检查表

结案前应同时核对事实来源、目标覆盖和未知项，避免把缺乏反例误认为结论已被证明。

1. 明确是新 Event、旧 Event 更新，还是专题基线研究。
2. 找到一手 Source，记录版本、发布日期、抓取时间和固定位置。

## 下篇 · 闭环与实验：自主优化如何验收

## 下篇 · 一、背景：为什么要把性能研究组织成闭环

数据库性能优化需要把候选生成与结果验收分离，因为一次执行成功，并不能证明候选正确，也不能证明耗时变化由候选造成。以调整 Hash 聚合策略为例：Agent 可以根据 Profile 提出“状态表过大导致 Spill”的假设，但接下来的工作至少包括确认参数生效、比较结果、测量内存与端到端耗时，以及排除缓存和排队的干扰。若提交请求恰好超时，还要先查清实验是否已在后端运行，不能直接重提。

这个例子包含两条相互依赖的链路：研究侧决定测什么、为什么测、什么结果可以推翻假设；执行侧保证候选、环境、测量和失败状态能够对应起来。LLM 可以协助分析和搜索，基准测试（Benchmark）可以产生观测，工作流系统可以恢复任务，但它们都不能单独完成验收。

### 需求与价值：降低无效实验和错误接纳的成本

持续调优的主要成本不仅是提出候选，还包括准备环境、等待作业、核对结果和重新找回上轮证据。把这些步骤串成闭环，可以减少人工交接和重复提交；但平台的价值要用有效结论及其成本衡量，不能用 Agent 运行时长替代。

本文选择的目标场景是：数据库工程师已有可运行的 Benchmark，需要持续研究参数、策略或受限实现改动；单次实验可能异步执行，资源有限，最终发布仍走独立流程。它不是面向任意数据库的自动 DBA，也不承诺每轮都能找到加速方案。以下约束是本文的设计前提，不是某个团队已经确认的生产需求。

| 编号 | 需求 | 为什么必须满足 |
| --- | --- | --- |
| R1 可复核 | 固定负载、引擎制品、配置和评价政策，能够重放一次比较 | 否则无法区分候选收益与环境变化 |
| R2 可恢复且有界 | 中断后接回外部任务；明确预算、取消和未知状态 | 响应丢失不能触发重复昂贵作业，持续等待也不能无限消费 |
| R3 独立验收 | 生成候选的 Agent 不能修改本轮正确性和性能判据 | 否则优化过程可能变成修改评分标准 |
| R4 可换场景 | 生命周期可复用，查询与增量维护有各自的验证器 | 同一 SQL、不同状态历史未必是同一实验 |
| R5 分步建设 | 先复用已有 Runner 与执行资源，不把生产发布纳入首版 | 控制投入和权限范围，先验证最小链路是否值得继续 |

这些要求决定了竞品调研的口径：既要看谁能让任务继续运行，也要看其状态与评价机制能否承接 R1—R5。只有连续、昂贵、可重复的实验任务，才更可能摊销这套基础设施；一次性的参数试验通常用脚本与人工复核就足够。

### 验收目标：平台运行成功不等于优化成功

工具调用、实验验收和 Agent 方法改进分别改变不同对象。若后两者同时进行，就无法判断收益来自数据库候选，还是评价或搜索方法的变化。

单轮工具循环发生在一个 Agent turn 内：阅读源码、搜索日志、执行允许的命令、生成配置或补丁、返回结构化提案。这些动作可由编码 Agent 承担，完成与否仍需检查工具返回和实际制品。

这一层的完成只表示：

- 工具调用结束；
- 进程返回成功；
- 结构化输出符合 Schema；
- 候选文件被生成。

它不表示候选正确，更不表示性能提升。`exit code = 0` 只是工具执行事实，不是研究结论。

实验循环把长期研究目标拆成多个假设和候选，并跨进程保存每轮的证据：

```text
读取最新证据
   → 选择下一项最有信息量的动作
   → 登记候选与实验
   → 异步执行
   → 收集并独立评价
   → 决定继续、补测、回退或结束
```

实验可能跨越分钟乃至数天，不能要求原模型调用一直存活。

方法改进循环则研究 Agent 自身：换一种提示模板、上下文压缩、工具集或搜索策略，是否能在同样预算下提出更多有效假设？

这个循环必须与线上性能任务隔离。否则 Agent 可以在结果不理想时修改自己的评分器、覆盖集合或停止条件，最终得到一个无法解释的“自我证明”。

| 循环 | 优化对象 | 权威状态 | 正确完成的含义 |
| --- | --- | --- | --- |
| 单轮工具循环 | 一次分析或实现动作 | AgentTurn | 工具和输出合同完成 |
| 实验循环 | 工作负载上的策略或实现 | Campaign、Trial、Evaluation | 在冻结政策下形成可复核结论 |
| 方法改进循环 | Agent 的提示、工具和搜索方法 | 独立任务集与评测器 | 同预算下可靠产出改善 |

这三种验收应分别保存。单次工具运行可以重试，实验结论需要补测，Agent 方法变更则需要新的独立评测；它们不能共用一个“成功”标志。

由此还要区分两种成功：**平台成功**意味着系统无需人反复输入“继续”，就能等待外部任务、恢复故障、消费结果并交付结论；**优化成功**则要求候选在规定覆盖、正确性、资源和统计条件下优于基线。一个 Campaign 最终得到“当前预算和动作范围内没有发现可信改善”，可以满足前者而不满足后者，不必靠挑选有利样本证明系统价值。

### Agent 控制项目：任务继续了，结论由谁确认

**Code Factory 将业务需求与 Agent 会话分开，适合借鉴事件交接机制。** 其架构以 Requirement、AgentSession 和 Run 组织长期软件交付；一个需求可以经历多次运行。源码中，`AgentManager` 接收触发消息后调用 `appendAgentTriggerMessage()`，后者在 `BEGIN IMMEDIATE` 事务中按 `(trigger_id, idempotency_key)` 写入回执；重复键直接返回，不再追加消息。新消息入库后才发布事件并调度待处理输入。参见 [SQLite 触发消息事务](https://github.com/luohaha/code-factory/blob/595c35e1445885f9bd5c2acdb171c63e537676f4/packages/agent-manager/src/sqlite-store.ts#L638) 与 [Manager 交接路径](https://github.com/luohaha/code-factory/blob/595c35e1445885f9bd5c2acdb171c63e537676f4/packages/agent-manager/src/agent-manager.ts#L1900)。

这条路径解决的是重复事件与消息持久化，能支持 R2 的一部分；它没有使外部 Benchmark 提交自动满足幂等性（Idempotency），也没有定义 R1/R3 的结果比较与确认测量。可以借鉴需求与运行分层，不宜把 PR 或需求完成状态直接映射为性能验收通过。

**GoaLoop 提供小型验证循环，但验证流程与编排器的信任边界需要分开看。** 项目要求在目标文件中写出具体检查，Runner 先验证、再推进；不能据此把它描述为“只让模型凭感觉判断”。在所查 `Orchestrator.run()` 中，会话身份先写入检查点，目标文件变化时不再直接恢复旧会话；Runner 返回后，编排器用 `_parse_terminator(result.text)` 读取状态，`pass` 分支结束循环。参见 [检查点与恢复](https://github.com/luohaha/GoaLoop/blob/e1ea3e0841aae8253c97eb0bafc4bd64b2b7e799/goaloop/orchestrator.py#L232) 和 [结束判定](https://github.com/luohaha/GoaLoop/blob/e1ea3e0841aae8253c97eb0bafc4bd64b2b7e799/goaloop/orchestrator.py#L365)。

可以复用其有界单轮、历史记录和续跑方式；数据库实验还需将 Runner 报告与独立采集的结果绑定。仅在提示中要求“不改评分器”，不构成 R3 所需的写权限隔离。对低成本、串行、已有确定性检查脚本的实验，这条路线可能已经足够。

**LoopX 展示了控制状态与执行宿主解耦的另一种实现。** 所查 `execute_turn_run_once()` 会将可配置的验证命令构造为 `task_validator`，再向 `run_loopx_turn_once()` 传入验证、writeback、spend 及对应的恢复查询接口。参见 [验证命令构造](https://github.com/loopx-project/loopx/blob/5cb9e4b8222a94a24a38ad2d7163e32322c11f73/loopx/cli_commands/turn_run_once.py#L104) 与 [单轮驱动连接](https://github.com/loopx-project/loopx/blob/5cb9e4b8222a94a24a38ad2d7163e32322c11f73/loopx/cli_commands/turn_run_once.py#L866)。

这一入口说明模型执行、验证和状态结算可以分别接入，但不能单凭接口连接就证明所有故障路径正确。对本文，待补的是验证命令背后的数据库语义、统计重复身份和实验预算，而不是再造一个 Agent runtime。

### Raven-Oncall：外部实验合同最接近目标场景

Raven 的 Oncall 调优辅助路径已经把候选建议与外部作业拆开，适合用来理解异步实验需要保存哪些事实。`run_adaptive_polling()` 从 Proposer 获取候选，通过 Campaign 驱动执行；`Campaign._reconcile_job()` 在没有 handle 时提交，随后 poll，终态再 fetch_result 并写入 Ledger。参见 [Runner](https://github.com/EverMind-AI/Raven/blob/3632e6040c7038a60ec418ce39ccae185c72c19f/agents/raven-oncall/plugins/oncall-flow/oncall_flow/runner.py) 与 [Campaign](https://github.com/EverMind-AI/Raven/blob/3632e6040c7038a60ec418ce39ccae185c72c19f/agents/raven-oncall/plugins/oncall-flow/oncall_flow/campaign.py)。

`JobSpec.idem_key` 区分外部提交身份，`JobBackend` 要求相同键返回同一个任务；基础设施异常与作业自身失败也分开表示。这个合同可用于 R2，但实现保证仍取决于具体后端是否兑现，而不是抽象类声明了幂等就已经成立。[JobBackend 接口](https://github.com/EverMind-AI/Raven/blob/3632e6040c7038a60ec418ce39ccae185c72c19f/agents/raven-oncall/plugins/oncall-flow/oncall_flow/backend.py)

数据库场景的关键差距出现在评价端：所查 `Campaign.best()` 从成功记录中，按配置的单个 metric 取最大值或最小值。这适合一个已经定义清楚的优化目标，却不足以直接表达“结果正确、覆盖完整、资源不越界、收益经过确认”这一组条件。因此可以借鉴 Proposer—Campaign—Backend—Ledger 分层，同时另建受控 Evaluator；这里的判断只针对该辅助调优路径，不覆盖 Raven 的所有 Oncall 工具。

### 编排、搜索与记录组件：可以组合，不能混为一个裁决者

Temporal、Optuna 和 MLflow 分别承接执行恢复、候选建议和实验记录，采用时必须明确谁拥有任务状态、谁有权晋升候选。

| 组件 | 已有功能与可复用方法 | 与本文需求的差距 |
| --- | --- | --- |
| [Temporal Activity](https://docs.temporal.io/activity-definition) | 持久工作流中的外部活动、重试和等待；文档要求 Activity 按幂等方式设计 | 重试不替外部系统实现幂等，也不定义 SQL 正确性；仍需 R1/R3 的领域合同 |
| [Optuna ask-and-tell](https://optuna.readthedocs.io/en/stable/tutorial/20_recipes/009_ask_and_tell.html) | 先建议参数，再由外部执行返回评价；建议与目标函数运行解耦 | 适用于已定义搜索空间；配置生效、覆盖和无效观测分类不能交给一个任意 score |
| [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/) | 保存 Run 的参数、指标与制品，支持查看和比较 | 记录功能不等于本文所需的目标版本、预算预留、恢复和 Promotion 权威 |

调研结果支持复用控制与执行机制，但数据库专属工作并没有消失：需要定义实验身份、观测合同、独立评价与场景语义。下一步选择的是这些职责放在哪里、由谁维护，而不是给几个产品排一个总分。

## 下篇 · 三、思路比较：从已有机制推导三条建设路线

三条路线都需要独立的数据库评价器，区别在于长期状态、恢复和搜索由谁承担。比较之前先固定 R1—R5，否则“最轻量”与“最完整”只是在回答不同问题。

| 路线 | 复用依据与组成 | 主要收益 | 主要代价与缺口 | 适用边界 |
| --- | --- | --- | --- | --- |
| A：轻量目标循环 + 验证脚本 | 借鉴 GoaLoop；目标文件、单轮 Runner、受保护的验证脚本与制品目录 | 接入少，容易先验证一条假设是否值得做 | 需要自行补齐外部提交身份、并发状态与预算记账；脚本之间容易出现隐含约定 | 单人、串行、便宜且可重建的实验；不优先用于多租户昂贵任务 |
| B：领域控制面（Control Plane）+ 可替换执行组件 | 借鉴 Code Factory/LoopX 的状态分层，以及 Raven 的异步任务合同；增加 Campaign、Evaluator、领域适配器 | 让 R1—R4 成为显式合同；Agent 与搜索器可替换，先对接已有 Benchmark | 自建状态机、迁移和故障恢复需要测试；若重复实现成熟调度功能，维护成本会扩大 | 已有执行资源，需要持续开展多轮研究，但尚无可直接复用的统一工作流底座 |
| C：持久工作流 + 搜索/记录服务 | 用 Temporal 承担持久调度，按需接 Optuna、MLflow，再实现领域活动和验收 | 可复用工作流恢复与运营能力，适合已有相关基础设施的团队 | 引入服务运维、工作流版本与状态映射；领域验证不会因此省掉 | 跨服务流程多、并发和运维要求高，或团队已在维护这些组件 |

这些路线不是互斥的终局。B 可以在内部采用 Temporal，A 也可以逐步长出数据库账本；真正需要提前固定的是**实验业务状态不能被聊天状态、工作流状态或展示状态分别裁决**。这里的比较关注首版以哪一层为建设中心。

### 当前选择：先做领域控制面，不先做通用 Agent 平台

在“已有 Benchmark、实验昂贵且异步、需要跨会话恢复、首版不自动发布”的前提下，路线 B 更符合当前目标。原因有三点：R1/R3 的主要缺口在实验与评价合同，直接包装 Agent 仍要补这些工作；R2 需要把外部任务身份独立于会话保存；R5 又要求先控制部署规模，不为尚未出现的调度压力引入完整服务栈。

这里选择的是架构分工，不是已经证明某个开源项目最值得 fork。具体采用 Code Factory、LoopX 或 Raven 的哪些模块，还要通过接口适配、依赖与许可检查。第一版可以只借鉴机制，以模块化单体连接现有 Agent Runner 和 Benchmark；有合适的稳定接口时再直接复用，不修改对方内部数据库来获得短期便利。

路线 A 不作为本场景首选，是因为一旦加入预算事务、任务核对和独立评价，它就已在承担领域控制面的责任。路线 C 不作为默认起点，是因为目前没有并发规模、恢复复杂度或团队已有运维能力的证据，不能先假定引入多个服务更省成本。若团队已稳定运行 Temporal，或者恢复编排已成为主要开发负担，应重新评估 C；若实验始终是单人串行且可低成本重跑，则退回 A。

### 执行层选型：编排 Codex / Claude Code，还是框架 + 模型 API？ {#执行层选型编排-codex--claude-code还是框架--模型-api}

执行层的选择决定平台要维护多少 Agent 运行机制，但不改变实验状态与独立验收的责任。前面的 A/B/C 比较控制面如何建设；这里比较控制面下面接什么执行器，两者是不同维度。路线 B 可以调用 Codex，也可以嵌入 pi；采用 Temporal 同样不意味着必须自行实现模型工具循环。

以下按 2026-10-08 查阅的官方资料讨论能力边界，并用本地 Codex 与前述 Code Factory 的固定提交解释接入机制。这里的 Claude 指 Claude Code 编码工具，而非仅指 Claude 模型；Hermes 指 Nous Research 的 Hermes Agent。没有实际部署这些方案做同负载测试，因此不按速度、成本或成功率给产品排名。

#### 先分清模型接口、Agent 运行时与业务控制面

调用模型 API 只解决推理请求，完整执行还需要工具调用、上下文组织、会话管理和错误处理。本文把这一组围绕模型的运行机制称为 Agent 执行宿主（Agent Harness）。框架可以提供其中一部分或大部分能力，但模型返回一个工具调用，并不意味着外部任务已经安全执行。

“编排现成工具”也不等于自动操作终端界面。Claude Code 的非交互模式提供 JSON、流式事件和按 Schema 输出的接口；Claude Agent SDK 则把 Claude Code 的循环、工具与上下文管理带入 Python/TypeScript 程序。它不同于只封装模型请求的 Client SDK，后者并不自动具有相同的编码工作流。[Claude Code 程序化运行](https://code.claude.com/docs/en/headless)、[Claude Agent SDK 概览](https://code.claude.com/docs/en/agent-sdk/overview)

Codex 同样提供 SDK，以及面向会话、事件和审批交互的 app-server。程序化集成可以复用现成运行时，不必先重写工具循环。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)、[Codex App Server](https://learn.chatgpt.com/docs/app-server)

本地 Codex 提交 `d36a3ead3c896d0552207763ef483262bce9ac73` 的 TypeScript SDK 进一步说明了这一层次：`CodexExec.run()` 构造非交互执行参数，通过 `spawn()` 启动 CLI，并以输入流和结构化事件连接调用方。SDK 在这个版本中是对执行进程的程序化封装，不是另一个独立的模型推理循环。此处说明的是已核对的实现，不应据此假定所有语言 SDK、所有后续版本都采用相同传输方式。[CodexExec.run 源码](https://github.com/openai/codex/blob/d36a3ead3c896d0552207763ef483262bce9ac73/sdk/typescript/src/exec.ts#L86)

因此至少有三种接入深度：进程级调用现成工具；通过 SDK/服务协议接入现成运行时；嵌入框架并控制模型、上下文与工具执行。中间一层通常能解决会话绑定和事件消费问题，不能因为命令行脚本不够用，就直接推导出需要自建全部 Agent 能力。

pi、OpenClaw 与 Hermes 也需要分别判断，不能并列理解成三个等价的底层 SDK：

| 项目 | 官方资料所描述的接入层次 | 对本文场景的价值与边界 |
| --- | --- | --- |
| pi | 可扩展 Harness，同时提供 CLI、RPC 和 TypeScript SDK | 适合嵌入程序、配置工具与会话；实验账本和数据库验收仍需另建。嵌入并不等于从零实现循环 |
| OpenClaw | 常驻 Gateway 连接消息渠道、客户端与 Agent 执行，提供请求和事件协议 | 当研究任务从聊天入口发起、需要持续交互时可复用入口能力；若只做批量候选生成，这些渠道与网关职责未必是首版需要的依赖 |
| Hermes Agent | 提供 CLI、Gateway 等入口，以及 Agent 循环、会话存储、记忆和定时任务 | 适合需要持续助手与跨会话经验的场景；存下会话或生成 Skill，并不能证明一项数据库优化经验已经通过独立验证 |

上表依据 [pi 项目说明](https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/coding-agent/README.md)、[OpenClaw Gateway 架构](https://docs.openclaw.ai/concepts/architecture) 和 [Hermes 架构](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)，属于文档层面的判断，不是对三个项目所有恢复路径的源码审计。尤其不要把 Code Factory 使用的 `pi-durable` 与 pi coding-agent SDK 当作同一个接口，或把前者的存储机制直接归到后者名下。

#### 差异在控制权与维护责任，而不在是否使用 API

复用成熟 Harness 可以减少编码工具与上下文管理的接入工作；深入框架则允许改变运行策略，同时把兼容性和回归验证责任带回平台。API 访问、进程部署与业务编排是三个独立选择：现成编码工具也可能使用模型 API，自部署框架也可以运行在远端 Worker 中。

| 比较维度 | 复用 Codex / Claude Code 运行时 | 嵌入框架并接模型 API |
| --- | --- | --- |
| 修改粒度 | 使用运行时公开的工具、配置、扩展与事件接口；内部循环受产品接口约束 | 可在框架开放的边界调整上下文、工具分派和模型选择；更深改动可能需要维护 fork |
| 编码能力复用 | 直接使用已有文件编辑、命令执行与项目上下文机制 | 框架可能已有这些能力，但仍需验证补丁、输出截断、工具错误和中断后的行为，不能只测试模型请求成功 |
| 状态恢复 | 绑定原生会话 ID，复用可用的续跑能力；运行环境和会话制品仍需保存 | 可选择存储与恢复策略，但必须核对框架具体保证；内存中的循环状态不是持久工作流 |
| 权限与隔离 | 复用审批和沙箱能力，再约束凭据、目录与网络；非交互运行要能处理待审批状态 | 工具暴露方式更可控，但框架内的权限检查不自动构成操作系统或服务端隔离 |
| 模型与升级 | 跟随运行时支持的模型、接口和行为变化，升级前做合同测试 | 可在所支持的供应商间适配；不同工具协议、上下文策略与模型能力仍需回归，不能把接口兼容视为行为等价 |
| 成本与运营 | 核算模型或产品额度、进程资源、失败重试与人工介入 | 核算推理、存储、宿主资源，以及运行时开发、故障排查与版本维护；省去一层封装不必然降低总成本 |

这张表比较的是责任分配，不是产品能力优劣。若现成运行时已经支持所需工具、受限执行和结构化输出，改为框架并不会直接提高候选质量；若必须控制每次模型请求的上下文组成、适配指定推理服务，或者替换运行时未开放的执行策略，框架才可能带来实质收益。反过来，只有一次参数诊断、且没有维护 Agent 基础设施能力时，不宜为了可定制性承担长期 fork。

认证和计费也不能按“CLI 用订阅、框架用 API”划线。部署前应核对实际接入方式、账号授权与额度政策，不能把个人账号可运行推导成可供团队后台无限调度。成本比较要使用相同任务与资源口径；本文没有实测数据，不给出哪条路线更便宜的结论。

#### 两种实现可以共存，但外部副作用不能跟着会话迁移

Code Factory 的固定版本已经展示了混合接入，而非要求控制面随运行时一起重建。其 `AgentProvider` 区分 `codex`、`claude-code` 与 `native-agent`；Native 路径使用 pi-durable，按保存的 conversation ID 查找会话，找不到时创建，再将会话身份回传给上层。执行环境则通过 `ExecutionEnv` 连接本地或远端工作区。[Provider 类型](https://github.com/luohaha/code-factory/blob/595c35e1445885f9bd5c2acdb171c63e537676f4/packages/agent-manager/src/types.ts#L1)、[Native 会话接入](https://github.com/luohaha/code-factory/blob/595c35e1445885f9bd5c2acdb171c63e537676f4/packages/agent-manager/src/native-agent.ts#L190)

这段实现证明了“统一管理任务、分别适配执行器”的可行形态，但没有证明不同 Harness 的会话可以无损转换。切换执行器时，适合迁移的是目标版本、代码制品和结构化证据，而不是假定对方能够继续解释原始聊天记录。一个 Hash 聚合实验可以由 Codex 阅读代码并提出候选，下一轮由另一个执行器分析 Profile；前提是候选与观测的关联来自平台账本，而非前一个 Agent 的记忆。

两条路线还有一个相同的故障边界：会话恢复无法单独解决外部作业的重复提交。假设工具已提交 Benchmark，但返回 handle 前进程退出；无论恢复 Codex 会话还是框架检查点，再调用一次提交都可能产生第二个任务。安全恢复必须查询领域控制面登记的 execution key，并核对后端状态。这也是 OpenClaw 网关请求去重、Hermes 会话存储不能被直接等同于数据库实验幂等的原因：它们记录和约束的对象不同，具体后端合同仍要验证。

工具协议也只覆盖连接的一部分。模型上下文协议（Model Context Protocol，MCP）可以复用工具描述和调用入口，但不能自动补齐 Campaign 权限、预算事务和结果验收。本文建议工具接入受控服务，由服务验证身份与预算；不能仅因为某个调用来自已授权 Agent，就允许它修改评价政策或绕过实验登记。

#### 本文的选择：先复用运行时，按已证实的缺口下沉

在已有 Benchmark、需要源码阅读与候选生成、首版不自动发布的前提下，先接一个成熟编码运行时更符合 R5。优先选择能够满足结构化输出、隔离和取消要求的公开接口；只有业务合同无法通过配置或扩展兑现时，才考虑框架替换。OpenClaw 或 Hermes 的消息入口和长期助手能力，应由实际交互需求驱动，而不是因为它们也能调用模型就默认引入。

为使这个选择可替换，设计上增加一层 Agent Adapter：输入包含 Campaign/GoalVersion、证据引用、工作区、工具权限和本轮资源上限；输出包含提案、制品引用、可获得的用量，以及完成、失败、取消或需要人工输入的状态。Adapter 保存自身的原生会话 ID，但不得用它替代 Trial、Replicate 或外部作业 ID。若运行时不提供硬预算、可靠取消或特定事件，Adapter 必须声明能力缺口，不能通过伪造统一返回值掩盖差异。

受控提案先进入 Controller 校验，再由 Benchmark Worker 提交实验，最后由 Evaluator 接纳或拒绝。Agent 退出成功仅表示本轮执行结束；JSON 格式合法也只证明结构，不证明 SQL 正确、参数生效或性能改善。框架替换应发生在这条链路的候选生成位置，不能连同评价标准一起替换。

迁移前可以做一个有界验证：给两种 Adapter 相同的源码快照、历史 Profile、允许动作和候选合同，分别测试源码定位、候选生成、错误工具返回以及会话丢失后的证据重建。模型和资源预算尽可能一致；若模型、工具或权限无法对齐，应把差异列为实验条件，不把结果解释成纯粹的框架差异。最终比较独立验收通过的候选、人工介入、恢复行为与总成本，而不是输出长度或运行轮数。没有观察到接口阻塞、可靠性缺口或可复核收益，就保留较简单的接入方式。

### 把竞品差距转成设计责任

选择路线以后，每项新增设计都应对应一个已说明的缺口。否则“通用平台”很容易扩展成与首个实验无关的功能集合。

| 需求 / 已观察到的差距 | 设计责任 | 如何验证选择有效 |
| --- | --- | --- |
| R1：任务或会话 ID 不能唯一描述一次比较 | 冻结工作负载、环境、候选与测量政策；区分 Trial 和 Replicate | 同一候选有意复测会产生新样本，网络重发不会 |
| R2：事件去重或抽象幂等合同不等于外部副作用去重 | 预算预留、Outbox、execution key、后端查询和未知状态 | 丢弃提交响应并重启控制器，不能无依据创建第二个作业 |
| R3：成功状态或单指标最优不等于数据库候选可接受 | 独立采集、正确性与覆盖检查、冻结政策、确认测量 | 更快但结果错误、覆盖缺失或越过资源约束的候选均不晋升 |
| R4：通用作业接口不包含状态历史 | 版本化场景插件（Domain Pack） | 查询与增量维护复用生命周期，但分别执行各自验证 |
| R5：自主继续不等于获得发布权限 | 受限 Runner、允许动作清单、人工发布边界 | 已通过实验的候选不能绕过原有发布流程 |

## 下篇 · 四、设计：把所选路线落实为实验合同与状态转换

路线 B 的实现核心是领域控制面：Agent 负责提出候选，Controller 管理权限、预算与实验状态，Evaluator 在冻结政策下裁决证据。下面沿合同、执行、评价和场景扩展展开，所有接口与状态机均为本文提案；竞品提供的是设计依据，不是这一完整平台已经实现的证明。

### 4.1 实验合同：对象、身份与失效条件

确定验收层次以后，还要明确一次实验由哪些对象构成。下面的身份划分直接决定网络重试是否去重，以及有意安排的复测是否被保留。

**Campaign、Hypothesis 与 Candidate。** 目标版本、解释假设和具体修改具有不同失效条件，分别建模才能在目标变化时重新解释旧实验。

- **Campaign**：一个版本化的研究任务，包含目标、约束、允许动作、工作负载、预算与验收政策。
- **Hypothesis**：可以被观测证伪的解释。例如“Hash 聚合的状态压力导致 Spill，切换算法后峰值内存应下降”。
- **Candidate**：假设对应的具体实现，可以是配置、每条查询的策略映射、代码补丁或构建制品。

“把参数调小试试”不是完整假设，因为它没有说明预期观测和反证条件。一条可执行假设至少需要：

```json
{
  "statement": "状态表过大是当前聚合阶段 Spill 的主要原因",
  "prediction": [
    "目标算子发生改变",
    "峰值内存与 Spill bytes 下降",
    "端到端耗时在确认测量中改善"
  ],
  "falsification": [
    "算子改变但 Spill 不变",
    "Spill 下降但排序或网络代价抵消收益"
  ]
}
```

**Trial、ExecutionAttempt 与 Replicate。** 三者分别标识研究问题、执行尝试和统计样本：

| 对象 | 含义 | 为什么需要独立身份 |
| --- | --- | --- |
| Trial | 在明确候选、场景和测量政策下的一次逻辑实验 | 决定要回答哪个研究问题 |
| ExecutionAttempt | Trial 的一次基础设施执行尝试 | 网络失败或机器故障可以重试，但不是新样本 |
| Replicate | 预先计划的一次独立统计重复 | 用于估计噪声，不能被候选去重删除 |

如果第一次提交成功但响应丢失，重发相同请求是传输重试，不应凭空产生第二个统计样本。如果研究者为了估计方差有意再测一次，则必须创建新的 replicate。把两者都叫 `retry`，会同时破坏幂等性和统计分析。

**Observation、Evaluation 与 Promotion。** 观测事实应保持不可变，评价可以因政策版本变化而重新计算，晋升则需要独立记录其依据。

**Observation** 是观测事实：实际配置、计划、耗时、内存、Spill、错误、环境和原始产物。

**Evaluation** 是依据冻结政策对一组 Observation 作出的判定：`ACCEPT`、`REJECT`、`INCONCLUSIVE` 或 `INVALID`。

**Promotion** 是把通过评价的候选提升为“当前最佳已验证候选”。它与把候选发布到生产环境是两种不同动作。

正确性失败可以是一条有效 Observation：实验成功证明候选不可接受。相反，结果文件丢失、环境身份不明或覆盖不完整，通常意味着 Observation 无效或证据不足，而不是候选性能差。

**Harness、Agent Runtime 与 Control Plane。** 模型执行能力与长期状态治理不能互相替代，控制面必须在原会话丢失后仍能恢复预算和外部任务。

- **Agent Runtime** 提供模型、工具调用、文件与命令执行能力。
- **Harness** 组织单次或多次 Agent 执行的上下文、权限和输出合同。
- **Control Plane** 保存长期目标、预算、事件、所有权、状态转移和恢复信息。
- **Benchmark Runner** 运行已定义的工作负载并产生观测。
- **Evaluator** 根据受控政策判断证据，不接受候选 Agent 临时改写标准。

模型接口不等于编码 Agent，编码 Agent 也不等于性能实验平台。直接调用 LLM API 时，文件工具、命令执行、上下文压缩、会话恢复和权限治理仍需要平台实现。

**Workload Snapshot 与 Environment Fingerprint。** 性能比较必须绑定负载与环境身份，否则数据分布、统计信息或引擎配置的变化可能被误归因于候选改动。至少需要记录：

```text
workload = 查询/变更序列 + 数据快照 + 统计信息 + 执行日程
environment = 引擎制品 + 配置 + 资源池 + 硬件 + 采集器版本
```

Workload Snapshot 表达“测了什么”，Environment Fingerprint 表达“在哪里、用什么版本测”。指纹一致是可比性的必要记录，却不是无噪声的保证；共享集群干扰、温度、缓存和后台任务仍可能没有被完整观测。

### 4.2 职责与权限：谁能提出、执行和裁决

候选生成、外部执行和结果评价需要独立的写入边界。Agent 可以建议补测或质疑政策，但如果能在看到结果后修改评分器，就无法再用这次实验验证原假设。

#### 状态与权限的设计约束

模型上下文会压缩，会话可能丢失，Runner 也可能升级，因此长期任务状态不能只寄存在会话里。Campaign 的目标、预算、候选、实验、证据和未解决问题必须可以在没有原会话的情况下重建。

Agent 会话适合保存局部探索连续性；平台状态负责长期事实。恢复会话是一种优化，不是正确性前提。

状态独立保存后，还需要限制谁能修改它。候选生成者若能删去失败样本，独立评价就无法成立；下面三个角色应通过受控记录交接：

```text
Agent / Searcher           Controller             Evaluator
为什么值得试？     →     是否允许执行？     →     证据支持什么？
```

Controller 检查权限、预算和状态版本；Evaluator 只消费真实观测和冻结政策。政策确需修改时，应生成新版本，不能回头更改本轮通过条件。

这些记录需要一个权威事实源。本地 Ledger、队列、工作流历史和实验展示工具可以同时存在，但不能各自决定 Trial、预算与 Promotion。否则控制器可能认为实验失败并重提，而外部协调器已经把它标记成功；两个“最佳候选”也可能在页面和报告中分叉。

控制器独立于模型以后，等待也无需占用模型轮次。外部实验运行一小时，并不需要模型每分钟询问状态。模型应在新 Observation、用户指令、依赖恢复或受控定时唤醒到来时才继续。

等待属于控制器和任务系统；分析属于 Agent。把二者分开，既降低成本，也让“没有新证据”成为合法静默状态。

此外，状态模型必须允许暂时无法判断：提交请求超时后，我们可能不知道任务是否创建；计划采集缺失时，我们可能不知道候选是否生效；区间跨过接纳边界时，我们可能不知道收益是否稳定。

成熟系统不会强迫所有状态立即二值化。`SUBMISSION_UNKNOWN`、`INCONCLUSIVE` 和 `evidence_missing` 是防止伪造确定性的安全阀。

#### 控制面如何连接执行与评价

控制面应权威管理目标、预算和实验身份，Worker 负责外部动作，Evaluator 负责冻结政策下的评价。下图是建议架构，增加了状态存储和接口维护成本。

```text
┌─────────────────────────────────────────────────────────────┐
│                    Task API / Research UI                   │
│  目标、预算、当前结论、实验矩阵、事件、人工输入、交付物      │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                     Campaign Controller                     │
│    状态机、版本、预算、租约、Outbox、继续/暂停/停止决策       │
└──────────────┬───────────────────────────────┬──────────────┘
               │                               │
┌──────────────▼──────────────┐  ┌────────────▼───────────────┐
│ Context Builder + Agent     │  │ Domain Pack + Evaluator    │
│ 读取证据、提出假设和候选      │  │ 合法性、实验编译、独立验收    │
└──────────────┬──────────────┘  └────────────┬───────────────┘
               │                               │
               └──────────────┬────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────┐
│         Build / Benchmark / Profile / Result Adapters       │
│    submit、lookup、status、collect、cancel、artifact refs     │
└─────────────────────────────┬───────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────┐
│              Relational Store + Artifact Store              │
│  任务事实、事件、评价、预算；计划/Profile/日志/补丁不可变引用  │
└─────────────────────────────────────────────────────────────┘
```

第一版可以是模块化单体：一个 API 服务、后台控制器、Agent Worker、Benchmark Worker、关系数据库和制品目录。模块边界要先清楚，进程数量不必一开始就复杂化。

**四种权威。** 同一事实的写入权必须明确，否则状态重试可能覆盖用户目标或并发晋升结果。其他组件只能提交建议或受控更新。

| 问题 | 权威组件 | 其他组件能做什么 |
| --- | --- | --- |
| 目标、预算、允许动作是什么 | GoalVersion / Campaign | Agent 可以建议，用户显式修改 |
| 外部任务实际处于什么状态 | Benchmark 系统 | 平台同步并标记未知或过期 |
| 候选是否正确、是否改善 | Evaluation Policy / Evaluator | Agent 可以解释和申请补测 |
| 是否发布到生产 | 既有发布流程与人 | 研究平台只交付证据和候选 |

“采用为任务内最佳候选”与“上线”必须分开。前者是研究判断，后者涉及更广的回归、责任和变更治理。

#### 给 Agent 什么上下文与权限

**Agent 的研究职责。** 根据已有证据，它可以承担以下任务：

- 解释计划与 Profile 的异常；
- 从源码定位配置、规则和执行路径；
- 把自然语言猜想改写为可证伪假设；
- 构造候选配置或受限补丁；
- 根据失败结果改变搜索方向；
- 判断当前证据还缺少哪个反例。

Agent 不应该直接拥有：

- 修改验收政策的权限；
- 绕过预算提交实验的权限；
- 删除失败观测的权限；
- 把候选标为已发布的权限；
- 长期轮询外部任务的职责。

**每轮上下文应该是 manifest，而不是聊天历史。** 显式上下文清单允许任务脱离原聊天会话恢复，同时保留本轮决策所需身份。Context Manifest 至少包含：

- 当前 GoalVersion 与允许动作；
- Campaign 状态版本；
- 基线和当前最佳已验证候选；
- 新增 Observation 与 Evaluation；
- 已否定假设和仍未知的问题；
- 剩余预算；
- 相关源码、计划和制品引用；
- 本轮必须回答的问题。

完整日志保持可检索，不应每轮塞进上下文。压缩结论必须保留证据引用和适用范围。这样即使原会话丢失，也能重建一次新的有界执行。

**结构化提案仍然需要语义校验。** JSON 合法不代表状态版本有效或候选可执行，控制器还需校验证据、参数与预算。

```json
{
  "schema_version": "performance_proposal_v1",
  "campaign_id": "campaign-demo",
  "goal_version": 3,
  "based_on_state_version": 18,
  "action": "run_experiments",
  "hypothesis_id": "hypothesis-07",
  "evidence_refs": ["observation-104/profile"],
  "candidate_ref": "candidate-sort-02",
  "case_ids": ["query-A", "query-B"],
  "expected_observation": "目标算子改变，Spill 与耗时下降",
  "falsification": "Spill 下降但端到端收益不足，则拒绝该解释"
}
```

提案中的 `based_on_state_version` 用于发现过期决策；`evidence_refs` 和 `falsification` 用于审查实验依据，但字段存在不代表内容有效。平台仍要检查 case 是否存在、参数是否合法、配置依赖是否满足、证据引用是否存在、状态版本是否过期以及预算是否足够。

**权限边界必须由运行时实现。** “你是只读分析员”写在提示词中，不会阻止进程写文件或访问网络。真正的边界来自：

- 隔离工作区；
- 明确的只读/可写路径；
- 独立的 Benchmark 提交身份；
- evaluator 和原始证据不可被候选修改；
- 凭据不进入提示与可下载产物；
- 源码、日志和网页中的文字都作为不可信数据，而不是指令。

源码候选的路径应是：隔离工作区 → 补丁检查 → 语义测试 → 构建 → 制品登记 → Benchmark。工作区中改了代码却测到旧制品，是自动优化平台最隐蔽也最常见的身份错误之一。

### 4.3 持久状态与异步恢复：从预算预留到结果回收

恢复的前提是辨认出原来的实验，而不只是重新启动一段代码。候选内容、统计重复和外部提交需要不同身份，状态机才能决定应该继续收集、核对提交，还是创建新的执行尝试。

#### 数据模型与观测合同

**核心实体。** 实体拆分应跟随生命周期和写入职责，避免一次执行失败使候选内容或历史评价丢失。

| 实体 | 关键字段 | 主要写入者 |
| --- | --- | --- |
| Campaign | owner、status、goal_version、state_version、budget | 用户与 Controller |
| GoalVersion | objective、constraints、allowed_actions、evaluation_policy | 受控任务接口 |
| WorkloadSnapshot | cases、data、stats、schedule、environment refs | Domain Pack |
| Hypothesis | statement、prediction、falsification、evidence refs | Agent 提案，平台登记 |
| Candidate | parent、kind、content digest、artifact ref、scope | Candidate Registry |
| Trial | candidate、scenario、replicate、measurement policy、state | Controller |
| ExecutionAttempt | attempt_no、execution_key、external job、failure class、cost | Execution Adapter |
| Observation | metrics、correctness、effective config、plan、environment | Result Collector |
| Evaluation | policy version、coverage、verdict、reason、uncertainty | Evaluator |
| AgentTurn | input manifest、runtime、proposal、usage、outcome | Agent Runner |
| Event | sequence、type、causation、payload、goal version | Controller / Inbox |
| Promotion | candidate、evaluation、effective scope | Controller |

Candidate 与 Trial 是一对多。一份配置可以在多个场景、多个环境或多个 replicate 中测试。Trial 与 ExecutionAttempt 也是一对多，因为基础设施失败可能要求新的执行尝试。

**四种身份不要压成一个哈希。** 内容相同可以复用候选，但独立统计重复必须保留不同样本身份，因此去重不能只依据配置哈希。

| 身份 | 回答的问题 | 重复规则 |
| --- | --- | --- |
| Candidate digest | 配置、补丁或制品内容是否相同 | 内容相同可复用候选对象 |
| Workload/environment fingerprint | 两次观测是否处在可比较条件 | 变化时分层或重建对照 |
| Trial + replicate_id | 是否是一项新的计划测量 | 合法统计重复必须保留 |
| execution_key | 是否在重放同一次外部提交 | 网络重发复用，确认失败后才新建 attempt |

“配置内容相同”不代表测量应被去重。相同候选在不同日期、数据快照或资源池上的实验仍然是不同证据。

**Observation 不应只保存一个 score。** 单一 score 无法解释候选是否生效或为什么被拒绝，需要同时保存原始指标、正确性和环境证据。以下 JSON 是合同示例，不是实测记录。

```json
{
  "schema_version": "observation_v1",
  "trial_id": "trial-042-r2",
  "attempt_id": "attempt-042-1",
  "case_id": "query-A",
  "candidate_digest": "sha256:EXAMPLE",
  "workload_fingerprint": "workload-v3",
  "environment_fingerprint": "engine-and-resource-v7",
  "execution_status": "succeeded",
  "correctness": {
    "status": "pass",
    "evidence_ref": "artifact://result-check/query-A"
  },
  "metrics": {
    "execution_wall_ms": {"value": 12500, "unit": "ms"},
    "queue_wait_ms": {"value": 800, "unit": "ms"},
    "peak_memory_bytes": {"value": null, "status": "missing"},
    "spill_bytes": {"value": 1048576, "unit": "bytes"}
  },
  "effective_config_ref": "artifact://effective-config/query-A",
  "plan_ref": "artifact://plan/query-A",
  "raw_result_ref": "artifact://raw/query-A"
}
```

缺失指标应保留 `missing`，不能填成 0；超时只有下界时应保留 censored 状态，不能伪装成精确耗时。原始产物不可变保存，规范化结果携带采集器版本。

#### 从预算预留到结果回收

**两层状态机。** 研究生命周期与单次实验生命周期可以独立结束，Trial 执行成功也不等于性能评价通过。

Campaign 管理研究生命周期：

```text
CREATED → ACTIVE → PAUSING → PAUSED
                ├──────────→ BLOCKED
                ├──────────→ COMPLETED
                ├──────────→ EXHAUSTED
                └──────────→ CANCELLED
```

Trial 管理一次逻辑实验：

```text
PLANNED → RESERVED → SUBMITTING → QUEUED → RUNNING
                        │                     │
                        └→ SUBMISSION_UNKNOWN │
                                              ▼
                              COLLECTING → VALIDATING
                                      ├→ SUCCEEDED
                                      ├→ FAILED
                                      └→ INVALID
```

Trial 的 `SUCCEEDED` 只表示执行完成并形成合法观测。它是否改善性能，由 Evaluation 单独判断。

**一轮控制过程。** 实验登记与预算预留应在同一事务中完成，外部提交再通过 Outbox 驱动，以缩小状态与副作用之间的不一致窗口。

1. Controller 获取 Campaign 的短租约，读取状态版本与未消费事件。
2. 优先处理新实验结果、暂停请求和目标变化。
3. 如果没有新证据和可执行动作，不调用模型。
4. 固化 Context Manifest 和 AgentTurn，释放数据库长事务。
5. Agent 返回提案后，再次校验 GoalVersion 与 state_version。
6. 在同一事务中登记 Candidate、Trial、预算预留和 Outbox 事件。
7. Worker 消费 Outbox，用 execution key 查找或提交外部任务。
8. Collector 规范化结果，Evaluator 写入判定并触发下一轮。

Outbox 解决“数据库已写入 Trial，但队列消息没有发出”的原子性缺口。它不能让外部 Benchmark 自动 exactly-once；跨系统副作用仍依赖后端幂等、查询确认和未知状态处理。

**为什么幂等不是一个布尔属性。** 幂等需要定义键、作用域和可查询结果，客户端重发同一函数名不能保证不会重复创建任务。

假设 `submit()` 超时，有三种可能：

1. 请求没有到达后端；
2. 后端创建了任务，但响应丢失；
3. 后端创建任务后自身状态尚未可查。

客户端本地没有足够信息判断是哪一种。如果立即换一个新 key 重试，就可能制造重复昂贵任务；如果永远不重试，又可能丢掉实验。因此更稳妥的顺序是：按原 key 查询 → 在有界窗口内 reconcile → 仍无法确认则进入 `SUBMISSION_UNKNOWN` → 人工或更强的后端查询介入。

[Temporal 的 Activity 文档](https://docs.temporal.io/activity-definition)也强调 Activity 应设计为幂等。工作流引擎可以重新调度代码，却不能替外部系统凭空制造幂等语义。

**租约、Fencing Token 与外部副作用。** Worker 租约到期后，旧 Worker 可能仍在运行。新 Worker 接管时，数据库可以用递增 fencing token 拒绝旧写入；但只有外部提交网关也检查 token 或幂等键，才能阻止旧 Worker 再次触发外部副作用。

这说明：本地“只有一个 owner”与跨系统 exactly-once 是两回事。可靠设计不轻易承诺 exactly-once，而是明确哪些操作幂等、哪些可查询、哪些必须人工核对。

**暂停、取消与目标修改。** 控制指令具有不同副作用，必须由控制器处理，不应等待模型下一轮解释用户意图。

- **暂停**：停止新提交，默认允许在途任务完成并保留结果。
- **取消**：主动终止可取消任务，不再继续研究。
- **修改目标**：生成新的 GoalVersion；旧结果保留，但按新政策重新评价后才能晋升。

控制命令由 Controller 直接处理，不必等 Agent 在下一轮读到。否则一个等待中的模型会话就变成系统控制面的单点故障。

### 4.4 评价与搜索：先固定比较，再分配预算

搜索策略只有消费可比较的评价结果才有意义。若覆盖、基线或失败处理随候选变化，再聪明的建议器也可能只是在寻找评价口径的漏洞。

#### 测量、覆盖与独立确认

评价必须固定覆盖、指标与失败处理，并为最终候选保留独立确认测量，否则选择过程本身会制造乐观偏差。

**先冻结问题，再测量。** 评价政策必须先于候选测量确定，否则删去慢查询或修改分母就可能制造虚假收益。Campaign 开始时冻结：

- 主目标与硬约束；
- 必需 case 和覆盖定义；
- 正确性判据；
- 超时、OOM 与缺失结果的处理；
- 环境分层；
- replicate 和停止政策；
- 最小有意义收益。

探索过程中可以换候选、换假设，但不能因为结果不好就删除退化查询、修改分母或切换指标。确需改变目标时，应创建新版本并说明旧实验如何解释。

多轮优化还需要同时保存两个基线，分别衡量净收益和边际改善：

- **B0**：Campaign 启动时冻结的原始基线，用于报告净收益。
- **B\***：当前最佳已验证候选，用于判断边际改善。

候选相对 B\* 有改善，不代表它仍满足相对 B0 的所有资源和回归约束。不同环境下多轮小收益也不能机械相乘。

**多查询指标不能只剩一个平均数。** 几何平均加速比描述相对变化，不等于完整工作负载耗时。令第 `i` 条查询的基线与候选耗时为 `B_i` 和 `C_i`，可将其作为辅助指标：

$$
S_{geo}=\exp\left(\sum_i w_i\log(B_i/C_i)\right),\qquad \sum_i w_i=1
$$

但它不等于整套 wall time，也会隐藏关键查询的严重回归。若目标是串行总时长，可以报告：

$$
S_{sum}=\frac{\sum_i B_i}{\sum_i C_i}
$$

若目标是并发 makespan，则必须测真实并发日程，不能用前两种公式替代。完整报告至少包含：主指标、每 case 比值、最差回归、关键约束、资源变化和覆盖率。

**噪声、配对与选择偏差。** 数据库实验常受缓存、共享资源、编译、排队和后台负载影响。对接近接纳边界的候选，可以在相同资源块中交替或随机安排基线与候选，再使用配对比值或块级 bootstrap 估计不确定性。

固定“每个候选跑三次”并不是通用统计保证。样本是否独立、噪声多大、最小收益是多少，都会改变需要的测量量。多次尝试后只挑最小值会产生 winner's curse，因此最终候选需要未参与选择的新测量确认。

**失败与缺失如何进入评价。** 超时、错误结果与缺少证据不能统一记为一个惩罚分，否则搜索器无法区分候选缺陷和基础设施问题。

| 情况 | 合理处理 |
| --- | --- |
| 临时机器或服务故障 | 记录 infrastructure failure，按政策重试并记成本 |
| 候选真实 OOM、超时、错误结果 | 按固定规则拒绝或标为受限，不能移出分母 |
| 缺少 Profile 但结果与正确性可信 | 可保留性能结论，根因解释受限 |
| 缺少正确性或生效配置证明 | 标记无效或证据不足 |
| 超时只有耗时下界 | 保存 censored observation |
| 引擎、容量或数据发生漂移 | 新环境分层或重建对照 |

无法区分候选错误与基础设施异常时，保留 `UNKNOWN`，不要向搜索器输入一个伪造的惩罚分数。

#### 根据缺失证据选择下一步

语义分析决定哪些变量值得探索，数值搜索则在固定空间分配测量预算；二者应通过候选与评价接口衔接。

**Agent 不是贝叶斯优化器，搜索器也不懂源码。** Agent 擅长发现新的变量、解释非线性交互和构造反例；网格、随机或贝叶斯搜索擅长在稳定的结构化空间内系统取样。二者可以通过统一接口组合：

```text
suggest(context, history, budget) -> candidates
observe(evaluations)              -> updated search state
```

第一阶段可以让 Agent 提出小而合法的参数空间，再由确定性枚举验证主要因素。历史足够以后，使用 [Optuna ask-and-tell](https://optuna.readthedocs.io/en/stable/tutorial/20_recipes/009_ask_and_tell.html)一类接口把建议器和昂贵外部执行解耦。

**什么时候不应该继续增加实验。** 缺少生效证据时继续扫参数不会解释收益，应先补齐因果链或停止当前方向。

| 当前证据 | 更合理的下一步 |
| --- | --- |
| 配置未生效、计划未变化 | 查作用域、依赖和代码读取路径 |
| 局部收益清楚但覆盖不足 | 扩展同类查询与反例 |
| 结果波动大且接近阈值 | 在预设预算内补充配对测量 |
| 两个参数单独有效、组合退化 | 检查交互、资源峰值和计划变化 |
| 有状态场景小批有效、大批退化 | 测量转换边界与回退路径 |
| 现有参数无法表达有效策略 | 形成源码问题；有权限时再生成补丁 |
| 多轮没有新增证据 | 切换假设或停止 |

重复改写总结不算研究进展。新增证据、排除假设、缩小边界或明确停止，才是一次有效轮次。

即使候选筛选可靠，局部收益仍需回到组合负载确认。每条查询单独最快的配置，组合后可能提高并发内存峰值、网络争用或 makespan。多个物化视图（Materialized View）各自最省资源的刷新计划，也可能在共享源表和存储上相互冲突。

因此，候选可以先按 case 筛选，但 Promotion 必须回到任务定义的真实组合方式。把单查询耗时简单相加，不能替代并发工作负载的真实测量。

### 4.5 场景适配：查询策略与增量维护

生命周期可以复用，数据库语义必须由具体场景定义。查询策略主要比较固定输入上的计划与资源变化，增量维护还依赖状态历史、提交边界和新鲜度；把两者都压成一次运行和一个 score 会丢失关键条件。

#### 用 Domain Pack 声明场景合同

“通用平台”不意味着所有工作负载都被压成一个浮点数。通用的是生命周期、身份、预算、证据和恢复合同；场景语义由版本化 Domain Pack 定义。

**Domain Pack 的六部分。** 场景语义必须版本化，否则更换结果比较器或刷新日程后，旧实验仍可能被误认为可比。

1. **Manifest**：场景名称、支持动作、参数 Schema 和资源需求。
2. **Context**：如何把计划、Profile、源码与历史组织给 Agent。
3. **Candidate**：候选合法性、依赖、作用域和是否需要构建。
4. **Execution**：如何编译 Trial、提交 Benchmark 和恢复环境。
5. **Evaluation**：正确性、指标单位、覆盖、回归与结果分类。
6. **Knowledge**：常见机制、失败边界和经验适用范围。

接口可以保持很小：

```python
class DomainPack:
    def build_context(self, campaign, evidence_index) -> dict: ...
    def validate_candidate(self, candidate, goal) -> dict: ...
    def compile_trials(self, proposal, workload_snapshot) -> list: ...
    def normalize_result(self, raw_result) -> dict: ...
    def evaluate(self, observations, frozen_policy) -> dict: ...

class BenchmarkAdapter:
    def submit(self, request, execution_key) -> str: ...
    def lookup(self, execution_key) -> dict: ...
    def status(self, job_id) -> dict: ...
    def collect(self, job_id) -> dict: ...
    def cancel(self, job_id) -> dict: ...
```

`lookup` 很重要：提交响应丢失后，系统必须先确认任务是否已经创建。如果后端无法按幂等键查找，可以用可搜索标签或提交网关补足；仍然无法确认时，应进入未知状态并停止盲目重提。

**可支持的场景。** 不同场景可以复用生命周期，但不能复用同一验收函数；查询策略与增量维护尤其需要不同的状态身份。

| Domain Pack | 候选 | 关键验收 |
| --- | --- | --- |
| query_strategy_tuning | 全局参数、每查询映射、特征规则 | 全集覆盖、配置生效、组合工作负载回归 |
| incremental_view_maintenance | 刷新参数、维护策略、候选实现 | 快照正确、新鲜度、状态历史、回退路径 |
| optimizer_rule_validation | 规则开关、代价阈值、代码补丁 | 语义正确、规则命中、计划变化、运行收益 |
| resource_policy_tuning | 并发、内存、并行度和队列策略 | 延迟、吞吐、资源成本与公平性 |
| source_diagnosis | 源码假设和验证计划 | 区分事实与推断；无运行证据不声称收益 |

一个无状态查询 Trial 可以是一次运行；一个增量视图 Trial 可能包含初始化、重放变更、刷新、检查点验证和清理。核心状态机无需知道每个步骤的数据库语义，但插件必须声明哪些步骤可重试、哪些副作用不可重复。

#### Hash/Sort：从局部机制回到组合负载

Hash/Sort 实验必须先绑定算子与完整数据路径，因为 Join、Aggregation、Distinct 和 Shuffle partitioning 的状态及成本结构不同。下文以分析查询集为假设场景，不将流程示例当成实测收益。

**候选的四个层级。** 交付物的作用域决定结论范围，每查询映射不能直接证明未见负载上的策略收益。

| 层级 | 交付内容 | 可以声称什么 |
| --- | --- | --- |
| 全局配置 | 全部查询采用相同策略 | 在当前工作负载中是否有更好默认值 |
| 每查询映射 | query/template → 配置 | 固定工作负载是否能进一步提速 |
| 特征规则 | 根据可得计划特征选择策略 | 是否可能推广到未参与搜索的查询 |
| 引擎实现 | 代价模型、算子或运行时修改 | 是否形成更通用、可维护的能力 |

每查询映射是合法的工程交付，但它的适用范围就是固定工作负载。若要声称策略具有泛化性，必须使用搜索阶段未见过的模板或参数变体，并确保特征在决策时可获得，而不是偷看运行后信息。

**一条可审阅的实验路径。** 先验证候选改变了目标路径，再扩大负载与测量规模，可以避免对未生效参数进行昂贵比较。

1. 固定引擎、数据、统计信息、资源和查询日程。
2. 从基线识别耗时贡献、Spill、倾斜、估计偏差和资源峰值异常。
3. 按执行机制分组，先选少量正例与反例。
4. 验证参数真实生效、目标算子和计划确实改变。
5. 观察峰值内存、Spill、排序、网络与端到端耗时，而非只看一个局部指标。
6. 对有希望的候选扩展覆盖，检查交互和最差回归。
7. 在原定组合/并发方式下运行完整候选。
8. 用独立新测量确认并交付适用边界。

如果 Sort 降低了 Hash 状态压力，却增加排序与网络开销，那么“Spill 下降”只支持局部机制判断，不能支持最终性能结论。

筛选规模也会改变结论：Hash 表容量、Spill 阈值、倾斜和网络拥塞都有明显的规模效应。小数据上的赢家可能在目标规模进入完全不同的执行区间。便宜的低保真场景可以用于筛选，但 Promotion 必须回到任务规定的规模和覆盖。

#### 增量物化视图：把状态历史纳入实验

增量物化视图不是“把一条查询多跑几次”。它的结果依赖初始状态、变更顺序、事务边界、刷新日程和长期维护历史。

**有状态实验的最小身份。** 同一 SQL 在不同变更历史下可能面对不同状态，因此有状态实验还需固定初始数据、提交日程和观察窗口。

```text
(D0,
 view_definition,
 delta_sequence,
 transaction_schedule,
 refresh_schedule,
 query_checkpoints,
 horizon)
```

其中 `D0` 是初始逻辑数据，`delta_sequence` 是有序变更，`horizon` 是观察窗口。是否计入初始构建和状态准备成本必须提前声明，不能在候选之间使用不同口径。

**必须同时记录的维度。** 刷新完成只证明作业结束，不证明走了增量路径或满足新鲜度；记录必须覆盖状态和回退行为。

| 维度 | 需要记录 | 常见错误结论 |
| --- | --- | --- |
| 变更模式 | 插入、删除、更新、分布和事务边界 | 插入有效就声称所有增量模式有效 |
| 规模 | 基表量、增量比例、热点和分区变化 | 小批次优势直接外推到大批次 |
| 计算路径 | 纯增量、部分重算、全量回退 | 刷新成功就认为增量路径成功 |
| 状态历史 | 状态大小、累计次数、整理和清理 | 一次空状态刷新代表长期成本 |
| 一致性 | 提交边界、可见版本、验证时间点 | 比较两个不同快照的结果 |
| 新鲜度 | 提交到可查询的延迟 | 通过少刷新制造表面成本下降 |

缺少可观测性时应报告 Unknown，不能由 Agent 猜测回退原因。

**正确性与恢复。** 每个检查点都应在相同逻辑提交边界上，将增量结果与参考结果比较。验证器必须明确重复行、NULL、类型、排序和数值容差语义。若参考查询也可能被优化器重写到待验证物化视图，就会形成循环验证，需要显式关闭该路径或采用独立参考。

候选使用不同私有状态格式时，应从同一逻辑 `D0` 各自初始化，不能直接复制另一候选的内部状态。中途失败后，读指标可以重试；已经提交的非幂等变更不能无条件重放。无法确认提交边界时，重建隔离环境比盲目继续更安全。

**单次刷新更快并不代表长期更好。** 单次刷新缩短可能来自推迟维护或降低新鲜度，因此必须在固定观察窗口内同时衡量总成本与服务约束：

- 正确性；
- 分位与最坏刷新延迟；
- 新鲜度 SLA；
- 状态占用；
- 全量回退频率；
- 清理与维护成本。

当时间、CPU、存储和金钱没有统一权重时，保留指标向量比随意相加更诚实。

### 4.6 研究记忆：保留可复核结论及其前提

研究记忆应保存结论依赖的版本与证据，不应将不同验证层级压缩为永久可信的摘要。

**证据不是单调增加的置信分。** 源码支持、计划生效与性能验证证明的是不同命题，不能累加成无条件可信分。可以区分四种证据：

- **SOURCE_SUPPORTED**：源码或文档支持机制判断；
- **PLAN_CONFIRMED**：计划或实际配置证明候选生效；
- **MEASURED**：产生了合法运行观测；
- **VALIDATED**：满足任务的确认政策。

它们不一定严格逐级。例如运行时调度策略可能没有明显计划变化，却有真实测量收益；纯源码诊断任务也可能在第一层完成。报告应展示证据类型，而不是强行压成一个 0–100 的“可信度”。

**失败经验也要可检索。** 失败经验只有绑定版本和前提才能阻止重复试错，否则新负载可能被旧结论错误排除。至少记录：

- 适用的引擎与工作负载版本；
- 采取的动作；
- 观测与评价；
- 失败边界；
- 证据引用；
- 未来何时值得重新验证。

如果知识库只保存成功故事，Agent 会反复踩过被摘要删除的坑。新版本或数据分布明显变化时，旧经验应降级为“待复验”，而不是无限期传播。

**研究记录不是模型思维链。** 每轮保存的应是可审阅决策：当前问题、引用证据、可选动作、选择、预期观测、反证条件、成本估计与最终判断。工具调用、补丁、实验和评测才是执行证据；平台不需要保存或展示模型的内部推理过程。

### 4.7 实施顺序：先接通可验证实验，再接入自主建议

实现依赖顺序应从确定性合同开始，因为 Agent 只有在执行、观测和评价可信后，才有可消费的反馈。以下是拟议步骤与验收门槛，不是已完成的开发记录，也不是工期承诺。

| 步骤 | 实现内容 | 依赖与阶段出口 |
| --- | --- | --- |
| D0 固定实验合同 | 选一个引擎和负载；冻结正确性、覆盖、主指标与约束 | 基线能重跑，能区分一次复测和一次执行重试；否则先修采集链路 |
| D1 接入真实后端 | 实现 submit / lookup / status / collect / cancel；登记 Candidate、Trial、Attempt | 单个合法候选可脱离 Agent 完成；提交结果未知时停止盲重试 |
| D2 建立恢复与独立评价 | 事务预算、Outbox、原始制品、Evaluator 和状态竞争检查 | 重启不丢任务；错误结果、配置未生效和证据缺失有不同判定 |
| D3 接入受限 Agent | 根据版本化上下文生成提案，经控制器校验后执行 | 不再需要人工反复输入“继续”；无新证据时不调用模型，过期提案被拒绝 |
| D4 完成一个查询策略闭环 | 有限候选筛选、完整覆盖与独立确认，输出 B0/B* 对照 | 在同预算下与简单枚举或人工流程比较，报告有效结论与总成本 |
| D5 扩展场景与部署规模 | 再接增量维护、参数搜索服务和团队并发 | 每次扩展先证明原合同仍成立；必要时将调度迁入持久工作流 |

首个概念验证（Proof of Concept，PoC）只需要一个版本化 Campaign、一个 Domain Pack、一个 Agent Runner、一个 Benchmark Adapter、独立 Evaluator、关系数据库和制品目录。界面可以先展示状态与证据，不必先建完整协作系统。有状态维护与代码补丁路径用于检查可扩展边界，不作为第一轮必须同时交付的功能。

## 下篇 · 五、可行性分析：先证明前提，再扩大自主范围

这套方案在组件层面有实现依据，但尚不能宣称已经具备端到端可行性。公开源码证明了检查点、事件去重、任务协调和验证接口能够实现；目标 Benchmark 是否支持可恢复提交、是否能独立检查结果，仍决定本设计能否成立。

### 哪些可复用，哪些必须补齐

复用范围应落实到接口和测试，而不是“接入一个框架”这种描述。下表区分已有依据、计划工作与阻塞条件。

| 设计部分 | 已有依据或基础能力 | 需要新增的工作 | 不满足时的处理 |
| --- | --- | --- | --- |
| 单轮分析与候选生成 | 编码 Agent 的程序化接口；GoaLoop 的单轮组织 | Agent Adapter、证据上下文、参数白名单、提案版本校验及运行时能力声明 | 先由人工提交候选，验证器与执行链仍可工作 |
| 控制状态与去重 | Code Factory 的事务回执；LoopX 的验证与结算接口 | Campaign 状态、预算预留、事件消费与版本竞争测试 | 不开放并发自主提交，先保证单任务恢复 |
| 外部作业协调 | Raven 的 Backend 合同；已有执行系统的任务接口 | 后端适配、幂等键查找、取消与费用核对 | 无法核对提交结果时进入未知状态；不以重试掩盖接口缺失 |
| 数据库验收 | 参考结果、执行计划、实际配置与 Profile 采集能力，需逐项确认 | 结果语义、覆盖政策、测量分层与独立确认 | 缺正确性或生效证据时只能做诊断，不接纳性能候选 |
| 有状态维护 | 目标引擎提供的快照、提交边界和隔离环境，尚待验证 | 变更重放、检查点对照、恢复和清理 | 无法重建同一逻辑状态时暂不接入该场景 |
| 团队化运行 | 数据库存储与现有权限体系 | 租户隔离、凭据最小授权、审计与容量测试 | 首版限定单团队、隔离环境和人工发布 |

这里最需要尽早验证的是外部任务可查询性与观测合同。两者缺失时，继续完善 UI 或增加模型轮次都无法解决重复提交和错误接纳问题。反过来，若现有 Benchmark 已经提供这些能力，平台只需适配，不应重新建设执行基础设施。

### 用故障与反例检验最小闭环

正常候选跑通，只能证明接口连接成功；恢复与验收必须用会使错误实现失败的测试来验证。先用可控假后端注入故障，再在隔离的真实后端上复核，不能将假后端结果当作生产保证。

| 检查 | 设计依据 | 必须看到的结果 |
| --- | --- | --- |
| 后端创建任务后丢弃响应，再重启 Controller | R2 / execution key | 找回原任务，或保留未知状态；不得无依据新建任务 |
| 回调重复、乱序，旧 Worker 晚到 | R2 / 回执、状态版本与 fencing | 不重复扣预算或晋升；拒绝过期写入，外部副作用另查 |
| 更快但结果错误、覆盖缺失或配置未生效 | R1/R3 / 独立 Evaluator | 错误候选被拒绝；缺证据与真实退化分开记录 |
| GoalVersion 改变时旧提案或旧实验返回 | R1/R3 / 政策版本 | 旧证据保留，但不能未经新政策评价直接晋升 |
| 预算耗尽、取消与完成同时发生 | R2/R5 / 预算和控制状态 | 停止新提交，记录在途任务及实际费用，不把取消请求等同于任务已终止 |
| 有意复测同一候选 | R1 / Replicate | 保留独立样本，而不是被候选内容去重 |
| Agent 会话丢失、运行时升级或更换 Adapter | R1/R2/R5 / 执行层与业务账本解耦 | 从结构化证据重建上下文；不重提已登记的外部实验；先通过输出、权限和取消合同测试 |
| 变更可能已提交但响应丢失 | R4 / 逻辑提交边界 | 先核对或重建隔离状态，不能盲目重放非幂等变更 |

权限测试也必须包含 Agent 尝试修改评价政策、删除失败观测、读取不必要凭据或直接发布的情况；拦截应发生在服务与运行时权限层，而不是依赖模型遵守提示。这样才能把“候选提出者不裁决结果”从文档约定变为可验证的边界。

### 成本与收益：统计有效结论，不统计运行轮数

平台是否值得建设，需要比较相同目标和预算下获得的有效结论，而不是只看搜索到的最好样本。原稿没有团队规模、机器价格、实验时长与失败率数据，因此这里不估算交付周数或给出虚构的 ROI。

应分开记录模型 token/费用、编译与测试资源、Benchmark 资源、确认测量、失败恢复、制品存储和人工介入。wall time、CPU-hours 与金额不是同一单位；只有明确换算口径以后，才讨论总成本。预算也应区分已消耗、已预留和剩余额度：能阻止新提交不代表能即时停止所有在途计费，后端缺少硬配额或可靠取消时，要明确可能超出的风险。

建设判断可以写成一条待测的不等式，而不是预设结论：

```text
在同一服务约束与核算周期内：
节省的人工介入成本 + 避免的重复/无效实验成本 + 已确认优化的使用收益
    > 控制面开发与维护成本 + 新增模型、验证、存储和恢复成本
```

各项必须使用同一价值口径；无法货币化时，就分别报告人工时间、资源消耗和可靠性，不强行相加。优化收益还要与原有人工或枚举流程比较，不能把本来就会发现的改进全部计为 Agent 的新增价值。

平台层面至少跟踪独立确认通过率、错误接纳与回归漏检、每个有效结论的资源和模型成本、重复提交、恢复成功率，以及人工介入原因。固定小规模候选集先提供对照，之后才比较更复杂搜索器；多提候选会增加探索与确认成本，不保证净收益增加。

### 继续、退回或停止的条件

自主范围应随证据扩大，而不是随框架功能数量扩大。若不能绑定制品、工作负载与实际配置，就先停在诊断和人工执行；若无法确认外部提交，暂停自动重试；若结果不稳定且预算不足以完成确认，则保留 `INCONCLUSIVE`；若简单枚举在同预算下已经足够，不必为此引入更重的 Agent 搜索。

只有首个隔离场景通过正确性、恢复和预算测试，并展示可接受的总成本，才扩展到有状态维护与团队并发。本文选择的路线 B 是这些前提下的设计建议，尚无平台实测结果；实验 `ACCEPT` 也不授予生产发布权限。

## 下篇附录 A：单次 Campaign 检查表

交付前应按实验身份、独立评价和恢复边界核对证据，不能只检查报告是否完整。

1. 目标、硬约束、允许动作和停止条件是否已版本化？
2. Workload Snapshot 与 Environment Fingerprint 是否完整？
3. 假设是否包含预期观测和反证条件？
4. Candidate、Trial、Attempt 与 Replicate 是否正确区分？
5. 配置、计划或制品是否证明候选真实生效？
6. 正确性、覆盖和性能指标是否由独立 Evaluator 判断？
7. 基础设施失败、候选失败、证据缺失和未知是否分开？
8. 提交响应丢失时能否按 execution key 查询？
9. 基线和候选是否处于可比较的环境分层？
10. 最终候选是否使用了未参与选择的新测量确认？
11. 失败经验、成本和适用边界是否进入交付物？
12. 发布是否仍由独立、受控流程决定？
