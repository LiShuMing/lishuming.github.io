## 面试主线：技术判断必须能被追问复核

面试官问 review，考察的是三件事：判断力（什么该阻塞）、影响力（怎么让别人接受意见）、机制化（怎么让质量不依赖个人）。面向 OLAP 数据库内核的 Senior / Staff / Tech Lead 岗位，回答先交代版本与改动契约，再展开反例、状态变化、验证和合入取舍；有真实数据才报数据，没有就说明证据边界。下面的“高频题”是备考题目分类，不表示已统计公司题库。

## 1. 高频题与答法要点

**Q1：你 review 时看什么？顺序是什么？**
先看描述和测试，弄清意图和边界；再看接口、兼容性和语义；最后看实现细节。阻塞默认针对正确性、并发、资源、分布式语义，以及严重的设计/复杂度问题；纯风格偏好标 Nit。引用 Google “improve code health 而非 perfect” 的标准（见第一篇）。

**Q2：PR 太大怎么办？**
要求按可独立编译、可独立测试的步骤拆分：先做无行为变化的重构，再做语义变更，最后补开关和清理。若协议或状态迁移不能独立成立，就先澄清兼容契约与设计边界；拆分困难本身不能证明设计没想清楚。

**Q3：和作者意见冲突，尤其对方更资深时？**
拿事实说话：复现用例、benchmark、故障场景。意见分成阻塞和非阻塞两类；两轮评论还没谈拢就转同步沟通，结论写回 PR 留痕。Apache 规定 veto 必须附技术理由，这个原则可以当作答题依据。

**Q4：review 拖慢交付怎么办？**
先量化：首次响应时延、轮次、PR 大小分布。再从机制上治理：小 PR、SLA（比如一个工作日内回应）、CODEOWNERS 分流、机械检查前移到 CI、AI 做初筛。不要靠降低标准换速度。

**Q5：AI 写的代码 / AI reviewer 怎么用？**
AI reviewer 可作辅助读者，不能代替人工合入责任；仓库规则里写明不变量（Invariant）；作者必须能解释 AI 生成的代码。可以引用 DORA 2025 的“AI 是放大器”说明前提是工程基础要扎实。

**Q6：如何通过 review 带新人？**
用 Mentor 式评论，每条都讲原因；把重复出现的问题沉淀成 checklist 或 lint 规则；让新人先 review 资深成员的 PR，以读代码来学习。依据是 MCR 研究：知识传递本身就是 review 的主要产出。

**Q7：线上事故，事后发现 review 漏了，怎么复盘？**
复盘对事不对人。追问三点：这类问题能不能被工具捕获（sanitizer、fuzz、SQL 回归测试）？检查项是否缺失？PR 是不是太大？最后落地成机制，而不是加一条“review 要更仔细”。

**Q8（内核向）：review 一个 optimizer 新规则，你重点看什么？**
看语义等价性：NULL 和外连接、重复行、相关子查询；看规则的触发条件与终止性（会不会在 memo 里循环）；看代价模型的影响和计划回归（plan diff 测试）；看开关和回退路径。

## 2. STAR 叙事

STAR = Situation / Task / Action / Result。素材优先取自已公开写过的工作。

- **素材方向（博客中已有内容）**：外连接下的 dynamic filter（见 [dynamic-filter-outer-join](/2026/08/24/dynamic-filter-through-outer-join/)）、StarRocks optimizer（见 [dive-starrocks-optimizer](/2026/09/01/dive-starrocks-optimizer/)）。这两篇可以作为技术复习入口，具体结论应回到各自的版本和条件核对；文章存在不证明作者参与了相关评审，下面的 review 情节是【模板】。
- 【模板】S：社区 PR 把 runtime filter 推过 left outer join。T：作为 committer 判断能否合入。A：（填：实际过滤方向、连接保留侧、过滤器用途与 NULL 行为）；构造能区分改写前后的反例 SQL，记录实际错误结果和安全条件，要求补回归测试。不能仅凭“推向补 NULL 侧”判断丢行，需按具体语义推演。R：（填：实际是否合入、修改内容及验证结果）；只有确有记录时才填写后续同类问题数。
- 【模板】性能回归：PR 声称提升 X%，review 时要求附上 TPC-H/SSB 前后对比和 profile；（填：实际发现了什么，以及对应负载和 profile）；（填：最终合入、延期或拒绝及原因）。开关合入、默认关闭只是可选处置，不得当成已发生结果。（填真实数据）
- 【模板】机制化：团队 PR 首次响应时延中位数从（填）降到（填），措施包括 CODEOWNERS、PR 模板、CI 前置 sanitizer。

## 3. 追问链：将参考答法推进到可验证的细节

下面是【推断】性质的模拟问答。现场先给短答，再沿追问展开；不要一上来背完整清单。

| 可能的问题 | 精简强答 | 面试官可能继续追问 | 常见差答与缺口 |
|---|---|---|---|
| 优化器（Optimizer）规则通过结果测试，为什么还不批准？ | 先核对适用条件是否覆盖 NULL、重复行和连接语义，再检查规则交互、搜索终止与计划成本；已有测试不能穷尽输入。 | 给一个反例；随机 SQL 如何约束非确定性？参考结果来自哪里？ | “多跑回归即可”：没有说明断言与语义条件的对应关系。 |
| C++ 取消路径用了 RAII，为什么仍可能泄漏？ | RAII 约束析构时释放，但异步引用或引用环可能使析构不发生；须证明任务退出与最后引用释放。 | 哪个线程完成清理？取消和完成同时发生如何只处理一次？ | “智能指针自动管理”：未解释生命周期和调度依赖。 |
| 存储格式上线后发现问题，关开关够吗？ | 先查新格式是否已持久化及旧版本能否读取；停止新写入不等于回退存量格式，需明确迁移与恢复方案。 | 如何验证混合版本读取？失败迁移能否续做？ | “回滚二进制”：忽略数据与程序的兼容方向。 |
| RPC 已超时，为什么不能直接报告事务失败？ | 提交状态可能已持久化而响应丢失，应按协议查询最终状态或用稳定标识安全重试。 | 节点重启后去重还有效吗？取消撞上提交怎么返回？ | “超时就是失败”：混淆调用结果与持久状态。 |
| 性能提升但内存峰值上升，如何取舍？ | 先确认同等资源和负载条件，分析是否扩大单查询或并发内存需求，再决定优化适用范围、资源限制和启用条件。 | 吞吐与尾延迟是否一起测？倾斜数据会怎样？ | “延迟下降所以合”：没有计算资源成本与适用范围。 |
| 交付前发现争议，TL 怎么决策？ | 把争议写成可证伪的风险，明确决策人和验证截止条件；不可逆风险未澄清先阻塞，可隔离风险才讨论受控启用。 | 你具体让谁补了什么证据？延期成本由谁确认？ | “我拍板兜底”：责任承诺不能降低技术风险。 |

## 4. 经验叙事：用证据承接 STAR，而非填充英雄故事

**可能的问题**：“说一次你通过 review 改变了方案的经历。”

**精简强答框架**：只选真实可披露案例，先说原方案想解决什么、自己承担什么角色，然后用一个关键反例或失败时序说明为何修改，最后说实际修订和验证。若自己只审了执行器（Executor）部分，就明确优化器或存储由其他人确认；读过 PR、提出评论、批准合入和主导设计是不同的贡献。

**追问**：“把 PR 打开，你指出哪条评论？修复前的测试为什么没拦住？作者提出了什么反驳？最终还有什么风险？”准备时应能对应提交版本、关键代码位置、评论与断言；不能披露时，说明保密边界，用不包含敏感信息的机制推演解释技术判断，不伪造公开 PR。

**常见差答**：“我拦住了一次重大事故”“团队因此提升很多”。若没有已确认故障或测量，最多说识别到某个可触发风险、补齐了某项检查；不能把潜在风险折算为避免的事故数量，也不能把团队结果全部归给个人。

【模板】证据卡：背景与版本（填）→ 本人角色和审阅范围（填）→ 原实现及预期不变量（填）→ 评论中的触发条件与反例（填）→ 作者回应和实际修订（填）→ 验证环境、断言或测量结果（填）→ 本人未验证部分与残留风险（填）。没有可核验记录的格子保留“未确认”，不要为了叙事完整而补故事。

对于 Staff / Tech Lead，可以在这张卡后补一层：同类风险是否横跨模块、哪项检查可自动化、哪项必须保留人工判断、谁维护这些规则，以及后来是否真的被使用。只有实施记录时才说“建立了机制”；尚未执行时说“建议这样做”。这能区分个人技术深度与组织影响，避免把写一份 checklist 等同于改进已生效。

## 5. 模拟面试的验收方式

让同伴从一个真实案例出发，依次追问语义反例、C++ 所有权、存储恢复或分布式失败中的相关路径，再问为何这样分工和决策。不要求每个案例覆盖所有方向，但每项结论都应有条件、证据和边界。

复盘只记录三类缺口：机制讲不清就回到代码或协议，证据接不上就补核验或降低结论强度，贡献边界混淆就重写角色说明。通用参考答法不能替代目标团队的具体架构，也不能替代真实 review 材料；没有亲历案例时，明确展示源码复核与模拟评审能力即可。

## 6. 反问面试官

- 团队 PR 的规模和首次响应时延大概是多少？
- 设计评审和代码评审怎么衔接？谁有否决权？
- AI 编码和 AI review 现在用到了什么程度，有什么约束？
