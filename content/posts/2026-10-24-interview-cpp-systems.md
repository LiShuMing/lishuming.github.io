## 一、对象模型的第一道关：地址存在，不等于对象仍然有效

### 1. 对象生命周期：内存池复用后，旧指针还能不能读？

**题目**：执行器把一块内存反复用于不同批次。地址没有变化，类型也一样，为什么保存的指针仍可能出错？如何判断能否使用 `memcpy` 搬运对象？

**强答要点**：先分开存储期（Storage Duration）、对象生命周期（Object Lifetime）、指针有效性和业务代次。内存池保留的是存储；某个对象的初始化完成和析构开始决定另一组边界；批次编号则属于业务身份。这三种边界不能由地址相同替代。

【事实】一般对象的生命周期开始要求获得大小与对齐合适的存储，并完成相应初始化，联合体与隐式生命周期类型等另有规则。类对象的生命周期在析构调用开始时结束，而存储可能稍后才释放。见工作草案 [basic.life](https://eel.is/c++draft/basic.life)。

```cpp
#include <cstddef>
#include <memory>
#include <string>

struct Cell { std::string value; };

void rebuild() {
    alignas(Cell) std::byte storage[sizeof(Cell)];
    auto* first = std::construct_at(
        reinterpret_cast<Cell*>(storage), Cell{"batch-1"});
    std::destroy_at(first);
    auto* second = std::construct_at(
        reinterpret_cast<Cell*>(storage), Cell{"batch-2"});
    // 使用 second；是否可以用 first，要另查透明可替换条件。
    std::destroy_at(second);
}
```

还应区分 `new` 表达式和 `operator new`：前者组织分配与初始化，后者只承担相应分配职责；正常抛出式分配失败、`nothrow` 版本和定位构造（Placement New）的契约不同。构造失败时的清理也不是简单“没有析构，所以必泄漏”。`malloc` 不调用用户构造函数，但对隐式生命周期类型的规则不能用“绝不创建任何对象”一笔带过。

这个例子证明“释放对象”和“释放存储”可以分开；它没有证明并发读者可以越过重建时刻。透明可替换（Transparent Replaceability）满足条件时，旧指针可自动指向新对象；条件不满足时需要按具体规则重新取得指针，`std::launder` 也不能让已经结束的生命周期复活。更稳妥的接口直接返回新构造结果，并禁止外部保留跨批次借用。

【推断】对于带 `std::string` 或锁的结构，不能以整块字节复制代替正常复制；可平凡复制类型（Trivially Copyable Type）在满足对象及存储条件时有对象表示复制保证，见 [basic.types](https://eel.is/c++draft/basic.types)。自指针本身不排除可平凡复制，但复制后的指针仍指向原地址，可能破坏业务不变量。即便某类型允许复制对象表示，业务身份仍需单独检查：旧批次的下标可能恰好落在新批次的有效区间，越界检测也抓不到这一类错误。

**追问链**：

1. 第一层：内存池只调用 `free`，不调用析构，会丢什么？答成员拥有的资源；回收原始字节不会替你执行对象协议。
2. 第二层：同址重建后读者为什么不能继续读？答必须先证明读者退出或持有有效保护，否则可能与析构、重建并发冲突。
3. 第三层：把指针换成 `{slot, generation}` 呢？可以检测陈旧句柄，但版本检查与访问之间仍需要同步或生命周期保护。

**常见差答／陷阱**：“内存没有释放，所以对象还在”“强转以后就是目标类型”“加 `launder` 可以解决悬空”。这些回答混淆地址、语言对象与业务对象；追问一次异步回调跨批次执行就会失效。

### 2. 虚函数与 ABI：为什么 sizeof 题回答完还不够？

**题目**：一个算子接口只有虚函数，没有数据成员，其对象是否必定是八字节？插件新增一个虚函数是否安全？通过基类指针释放派生对象有什么要求？

**强答要点**：对象布局要同时注明架构、编译器和应用二进制接口（Application Binary Interface，ABI）。虚表（Virtual Table）与虚表指针（Virtual Table Pointer）是常用实现机制，不能当成语言强制规定的固定字段。继承布局、对齐、编译选项和 ABI 都可能影响大小。

【事实】[Itanium C++ ABI 的数据布局与虚表章节](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#vtable)规定了采用该 ABI 时的布局规则，包含次级虚表、调整量和构造期间的虚表；“每个对象只有一根虚指针”不足以解释多重继承。这里引用的是 ABI 规则，不是全部平台的共同承诺。

普通空类的完整对象必须有非零大小，但标准不要求所有空类都恰好是一字节。空基类优化（Empty Base Optimization）和 `[[no_unique_address]]` 成员又允许特定子对象不额外占空间；不能用“所有对象地址永远唯一”概括布局规则。

通过普通基类指针删除派生对象时，非虚基类析构通常导致未定义行为（Undefined Behavior，UB），不能只描述成“少调一次析构”。若接口允许这种删除，就提供公开虚析构；若禁止，则可以采用受保护的非虚析构并让实际所有者按具体类型销毁。这里不讨论特殊的 destroying delete 设计。

构造函数不能声明为虚函数是语言规则，不应只用“此时还没有虚指针”解释。构造和析构期间可以发生虚调用，但派发按当前构造或析构阶段的类处理；调用纯虚函数还涉及更严格的限制。公开基类、对象构造和释放策略应一起设计，不能分别背诵。

【推断】插件新增虚函数即使在某套 ABI 下看似只追加表项，也不能直接宣布兼容：旧插件的表长度、调用方使用的索引、内联代码和对象构造方可能不一致。需要支持长期二进制兼容时，显式版本号、能力查询或稳定的 C 接口更容易形成可验证契约。

**追问链**：

1. 第一层：为什么不能把含虚函数对象直接写盘？布局与指针值依赖进程和工具链，应序列化稳定字段而不是对象表示。
2. 第二层：热循环虚调用慢在哪里？可能是间接分支、难以内联或数据布局；先看生成代码与采样，不能把所有成本归到一次查表。
3. 第三层：改成模板是否一定更快？可能改善内联，也可能放大代码体积和指令缓存压力，要控制实例化组合。

**常见差答／陷阱**：“64 位就是八字节”“所有基类都必须虚析构”“模板零成本”。这些结论遗漏平台假设、删除契约或机器码成本。

### 3. RAII 与失败路径：析构成功不代表提交成功

**题目**：资源获取即初始化（Resource Acquisition Is Initialization，RAII）如何覆盖打开文件失败、部分构造、异常、提前返回和查询取消？析构中能不能做最终提交？

**强答要点**：把资源生命周期绑定到一个明确的所有者，使构造后的对象始终满足不变量（Invariant），析构完成不抛异常的清理。获取失败可以抛异常，也可以由工厂返回 `std::expected<Resource, Error>`；选哪种取决于项目错误模型，不能构造一个未标记的半有效对象。

【事实】[C++ Core Guidelines 的 R.1、C.35、C.36 与 CP.52](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)分别讨论资源管理、基类析构、析构失败和跨挂起持锁问题。这些是工程指南，不能替代具体系统的持久性或线程安全证明。

```cpp
#include <memory>
#include <utility>

struct Batch { /* 拥有列缓冲，省略具体定义 */ };

void consume(std::unique_ptr<Batch> batch);

void submit(std::unique_ptr<Batch> batch) {
    // consume 按值接收，所有权在调用处转移。
    consume(std::move(batch));
    // 这里不再通过 batch 访问批次。
}
```

该接口把释放责任交给 `consume`，但没有证明 `consume` 内部排队、失败回调和取消路径都正确。若它只保存 `batch.get()` 然后返回，RAII 会立即暴露悬空，而不会自动延长借用。应继续沿队列元素和回调的字段追踪所有权。

【推断】需要向调用者报告的动作应有显式接口，例如 `commit()`、`flush()`、`finish()`；析构只做兜底清理。理由是析构通常无法可靠回传提交失败，栈展开期间再抛异常还可能终止进程。RAII 证明的是离开作用域时执行清理，不是磁盘写入、远端提交或设备任务已经成功。

查询取消也应区分“请求停止”和“全部工作已经结束”。停止提交新任务后，还必须等待已发布的工作收敛，再释放其依赖对象；进程被强制终止时不保证运行 C++ 析构。跨挂起点持有线程互斥锁还可能在另一线程恢复后解锁，违反锁的线程归属要求。

**追问链**：

1. 第一层：构造函数中第二个资源获取失败，谁释放第一个？已完成构造的成员会析构；应先用成员包装器接管资源。
2. 第二层：析构中的关闭失败怎么办？设计显式可报告的结束操作，析构清理只记录或忽略可接受错误，不能假装提交成功。
3. 第三层：取消后还有完成回调怎么办？用任务所有权、完成计数或显式汇合协议，证明最后一个回调结束早于依赖对象释放。

**常见差答／陷阱**：“全部改智能指针就安全”“析构里做一次提交即可”“取消后直接释放”。它们都没有给出异步工作的完成边界。

## 二、所有权进入接口：移动、借用和泛型如何形成约束

### 4. 移动语义：为什么 std::move 可能触发拷贝，甚至让代码变慢？

**题目**：批次进入队列时加上 `std::move`，是否证明没有复制？返回局部对象时是否也应该加？容器扩容会怎样处理可能抛异常的移动构造？

**强答要点**：`std::move` 只改变表达式的值类别，使其可参与相应重载；具体移动、拷贝或报错由重载和类型能力决定。`const T` 通常不能绑定普通 `T&&` 移动构造，因此对常量调用 `move` 仍可能拷贝。命名的右值引用变量本身是左值表达式。

```cpp
#include <string>
#include <utility>

std::string make_name() {
    std::string name = "scan";
    return name;                 // 允许 NRVO；不要机械加 move。
}

void example() {
    const std::string frozen = "scan";
    std::string copy = std::move(frozen); // 通常调用拷贝构造。
    std::string moved = make_name();
}
```

返回值优化（Return Value Optimization，RVO）与命名返回值优化（Named Return Value Optimization，NRVO）不是同一个保证。C++17 的特定纯右值初始化场景不需要中间移动；返回命名局部对象的 NRVO 仍不是一概强制。不能通过“返回大对象用了移动”解释所有高效返回。

【推断】移动的成本也取决于资源布局：短字符串可能复制内联字节，分配器不兼容的容器移动赋值可能逐元素迁移，自引用结构可能需要修复内部指针。应该回答调用哪个重载、是否分配、是否逐元素处理，而不是把移动等同于三次指针赋值。

对可拷贝元素，容器重分配时常用不抛异常的移动或选择拷贝，以维持异常保证。只提供可能抛异常移动的不可拷贝类型，会使部分保证受限；不能通过随手加 `noexcept` 掩盖真实异常，否则抛出时会终止程序。资源类优先采用零法则（Rule of Zero），让标准成员承担复制和移动；自行管理原始资源时再审查五个特殊成员。

移动后的标准库对象通常处于有效但未指定状态（Valid but Unspecified State），允许调用满足其前置条件的操作；这不等于“禁止再使用”，也不等于“一定为空”。`unique_ptr` 的移动后为空则有具体契约。用户自定义类型需要自己说明移动后不变量。

**追问链**：

1. 第一层：`return std::move(local)` 有何风险？可能妨碍 NRVO；先判断返回规则，不以显式 `move` 作为优化证据。
2. 第二层：为什么完美转发不能都写 `move`？转发引用（Forwarding Reference）的调用方可能传左值，应按推导结果使用 `std::forward<T>` 保留值类别。
3. 第三层：怎样证明减少复制？记录构造、分配和字节搬运路径，结合优化后机器码及目标负载；调试日志本身会改变优化条件。

**常见差答／陷阱**：“有 `&&` 就一定是转发引用”“移动后不能碰”“`emplace_back` 永远优于 `push_back`”。是否直接构造、是否重分配以及输入是不是已有对象，决定实际成本。

### 5. 智能指针与视图：三个线程安全问题不能合并回答

**题目**：多个线程共享 `shared_ptr<Batch>`，是否可以同时修改批次？一个线程重置指针，另一个读取是否安全？`span` 和 `string_view` 能不能放进异步队列？

**强答要点**：分开控制块、智能指针句柄和被管理对象。不同 `shared_ptr` 句柄共享控制块时，所有权计数有并发保证；对同一非原子句柄并发读写需要同步；对象内部字段是否可并发访问是第三个独立问题。

【事实】共享所有权与删除器等契约见 [util.smartptr.shared](https://eel.is/c++draft/util.smartptr.shared)。`std::atomic<std::shared_ptr<T>>` 可以用于并发发布句柄，但它不保证 `T` 的内部操作安全，也不承诺无锁实现。

```cpp
#include <atomic>
#include <memory>

struct Snapshot { int version; };
std::atomic<std::shared_ptr<const Snapshot>> current;

void publish() {
    current.store(std::make_shared<const Snapshot>(Snapshot{7}),
                  std::memory_order_release);
}

int read_version() {
    auto owned = current.load(std::memory_order_acquire);
    return owned ? owned->version : -1;
}
```

读者持有局部所有者，因此发布新版本不会销毁它正在访问的旧版本。这里还依赖快照发布后不再变动；`const` 接口不能阻止其他可写别名，应在构造和发布流程中消除这样的别名。该示例没有证明更新吞吐、回收时延或原子共享指针的锁自由性。

`weak_ptr` 不增加强引用计数，但并非“没有控制块参与”。`lock()` 将存活检查与取得强引用结合起来；先调用 `expired()` 再使用裸指针，会留下检查到使用之间的窗口。最后一个强引用销毁对象，控制块则要等相应弱引用也消失；合并分配还可能让对象所在那块分配随控制块保留。

【推断】借用视图应携带可审计的有效期。`std::span` 是连续区间视图，`std::string_view` 是字符视图，它们都不拥有底层数据；把视图复制进队列并不会复制所有者。可以让队列元素同时拥有缓冲，或使用明确的批次租约，但必须证明租约覆盖消费和取消清理。

**追问链**：

1. 第一层：为什么 `use_count() == 1` 不能用来证明无并发访问？它只是瞬时所有权观测，不约束裸指针和随后的句柄变化。
2. 第二层：`shared_ptr` 按值传参有什么语义？表达需要保留共享所有权；仅同步借用可用引用或指针，但不能把异步延寿需求优化掉。
3. 第三层：怎样消除热路径引用计数竞争？考虑批次级所有权、线程归属和分片，不先牺牲生命周期证明。

**常见差答／陷阱**：“计数原子所以对象线程安全”“`const shared_ptr<T>&` 保证 T 只读”“`weak_ptr` 完全没有计数成本”。三个说法分别混淆对象、句柄常量性和控制块成本。

### 6. 模板与 concepts：编译通过能证明哪些事情？

**题目**：为向量化执行器设计通用聚合接口，如何使用概念约束（Concepts）？为什么符合 `requires` 的用户类型仍可能破坏并行聚合结果？

**强答要点**：模板把类型和常量差异推到编译期；概念约束参与候选筛选和重载排序，让接口要求可表达。它们能检查表达式、返回类型和部分静态性质，却不能自动证明关联律、确定性、线程安全或业务空值语义。

```cpp
#include <concepts>
#include <cstdint>

template<class A>
concept Mergeable = requires(A a, const A b, std::int64_t x) {
    { a.add(x) } -> std::same_as<void>;
    { a.merge(b) } -> std::same_as<void>;
};

template<Mergeable A>
void combine(A& dst, const A& src) {
    dst.merge(src);
}
```

此概念只验证两种调用形式；一个把 `merge` 实现为空操作的类型也可以通过。若算法要求“分区后合并等价于顺序处理”，就需要写清语义契约并测试不同分区、合并顺序和边界值。浮点加法在通常机器算术下不满足数学上的精确关联律，不能由接口名称推导可任意重排。

【事实】约束的满足、规范化与偏序规则见 [temp.constr](https://eel.is/c++draft/temp.constr)。约束包含关系不是任意数学定理证明；复用命名概念与复制看似相同的布尔表达式，可能产生不同的原子约束身份，影响重载选择。

【推断】把类型、空值模式、排序模式和指令集全部作为模板维度，会按组合数放大实例化。只对证据明确的热路径做静态专门化，在外层用运行时分派约束代码体积，通常更容易控制编译时间、链接时间和指令缓存占用；这里是设计判断，不是普适性能结论。

**追问链**：

1. 第一层：concept 比替换失败非错误（Substitution Failure Is Not An Error，SFINAE）改善什么？主要是显式表达约束与诊断，不能凭此保证生成代码更快。
2. 第二层：为什么两个重载都满足约束还会歧义？说明偏序与约束身份，再检查是否通过同一个命名概念建立包含关系。
3. 第三层：何时采用类型擦除（Type Erasure）？需要稳定边界、减少实例化或支持运行时插件时；接受间接调用及可能的存储成本。

**常见差答／陷阱**：“concept 是运行时接口”“模板自动向量化”“编译器验证了 merge 的数学性质”。语法可调用性和语义正确性必须分开证明。

## 三、并发证明必须覆盖发布、修改和回收

### 7. 内存模型：release/acquire 到底连接了哪两段代码？

**题目**：生产者写普通字段后设置原子标志，消费者看到标志就读字段。如何选择内存序（Memory Order）？把所有操作改成顺序一致是否解决全部并发错误？

**强答要点**：先找冲突访问，再建立先行发生（Happens-before）关系。原子变量上的修改顺序、不同操作之间的同步关系和其他普通对象的访问是三个层面；“CPU 会刷新缓存”不能替代语言层面的证明。

```cpp
#include <atomic>
#include <cassert>

int payload = 0;
std::atomic<bool> ready{false};

void producer() {                 // 整个实验仅调用一次。
    payload = 42;
    ready.store(true, std::memory_order_release);
}

void consumer() {
    if (ready.load(std::memory_order_acquire)) {
        assert(payload == 42);
    }
}
```

【事实】如果获取操作读到了对应释放操作发布的值，就形成同步关系，连接发布前写入与获取后读取。若把标志的两端都改为宽松内存序（Relaxed Ordering），对标志本身仍是原子访问，但不再建立这里所需的跨对象同步；普通 `payload` 的冲突访问可能形成数据竞争（Data Race），导致未定义行为。依据见 [intro.races](https://eel.is/c++draft/intro.races) 和 [atomics.order](https://eel.is/c++draft/atomics.order)。

这个证明依赖“一次发布后不再写 payload”。生产者第二轮直接覆盖数据，消费者可能仍在第一轮读取；布尔标志无法表达槽位是否已归还。正确循环队列还要证明消费者读取完成后，生产者才可以复用槽位，通常需要反向的发布关系或代次协议。

【推断】面试画图时应给每条边命名：同线程的程序次序、读到了哪个原子写、哪条同步边把普通读写连起来。若无法指出某次 acquire 读到了哪个发布，就不能只说“用了 acquire，所以看得见”。

进一步追问可讨论释放序列（Release Sequence）：按 C++20 规则，释放操作之后连续的原子 RMW 可以接续释放序列，让读到相应结果的获取操作承接原来的发布；不能把任意后续普通原子 store 都当成仍在传递发布。多个生产者覆盖标志时，应逐次确定消费者读自哪次写，不能因为值相同就假定同步来源相同。

顺序一致（Sequential Consistency）为相关原子操作提供更强的排序约束，但无法修复悬空指针、先检查后修改的业务竞态或不受同步保护的普通数据访问。宽松计数适合只需要原子累计、不承担其他对象发布责任的场景；精确的一致快照需要另外设计。

**追问链**：

1. 第一层：把 `payload` 也改成原子就行吗？可以消除其数据竞争，但不自动建立“看见 ready 必须看见指定版本 payload”的跨对象契约。
2. 第二层：硬件缓存一致性是否足够？一致性约束缓存行或位置的可见行为，不能替代 C++ 抽象机对跨位置同步的要求。
3. 第三层：x86 上压测没失败，能推出什么？只能说明该二进制在已运行条件下未观察到错误；编译优化与其他架构仍需语义证明。

**常见差答／陷阱**：“`volatile` 防重排，所以可同步”“release 立即刷回主存”“任何 acquire 都会读到最新值”。它们没有给出读取关系与对象复用边界。

### 8. CAS 与锁：原子操作组合起来，也可能丢更新

**题目**：为什么 `counter.store(counter.load() + 1)` 会丢更新？如何写一个基本自旋锁？比较交换失败后为什么要重新处理 `expected`？

**强答要点**：原子加载和原子存储各自不可分割，不代表两者组成的读改写（Read-Modify-Write，RMW）不可分割。计数应使用 `fetch_add`，有条件的状态迁移才考虑比较交换（Compare-and-Swap，CAS），多字段不变量仍可能更适合互斥锁。

```cpp
#include <atomic>

class TeachingSpinLock {
    std::atomic<bool> held_{false};
public:
    void lock() noexcept {
        bool expected = false;
        while (!held_.compare_exchange_weak(
            expected, true,
            std::memory_order_acquire,
            std::memory_order_relaxed)) {
            expected = false;
        }
    }
    void unlock() noexcept {
        held_.store(false, std::memory_order_release);
    }
};
```

关键是成功时把 `false` 改成 `true`；原料写成 `false → false`，多个线程可以同时“成功”。失败时 CAS 会更新 `expected`，循环必须恢复本次希望比较的值；弱比较交换还允许伪失败，所以需要正确重试。

这里成功获取用 acquire，释放用 release，失败只需要观察原子状态而无需读取临界区数据，因此使用 relaxed。CAS 的失败路径是加载，不能为其指定 release 或 acq_rel；涉及旧版标准时还需核对成功与失败内存序的组合约束。

【推断】这个教学锁不适合作为默认生产锁：所有等待者反复执行 RMW，竞争同一缓存行；线程被抢占或 CPU 配额不足时，其他线程仍会忙等。可以讨论先读后尝试、处理器暂停指令、退避、排队锁或 `atomic::wait`，但每一步都要重新分析唤醒、饥饿和停机行为。

C++20 的 `atomic::wait/notify` 可以用于等待原子值变化；修改值后还需配套通知，不能保证仅靠 store 唤醒已阻塞的等待者，见 [atomics.wait](https://eel.is/c++draft/atomics.wait)。等待的是值，不是任意事件历史。短暂的 A→B→A 变化可能被错过；如果语义是“必须观察每一次任务完成”，就需要序号或其他状态协议。条件变量同样需要谓词循环，通知不代替受保护的状态。

**追问链**：

1. 第一层：弱 CAS 失败是不是说明别人推进了？不一定，可能伪失败，不能把这个结论直接用于进度证明。
2. 第二层：原子是否必定无锁？不是，需核查目标类型与平台的 `is_lock_free()` 或 `is_always_lock_free`。
3. 第三层：为什么短临界区也可能不适合自旋？持锁线程是否运行、是否超额订阅、是否跨插槽竞争，决定等待成本。

**常见差答／陷阱**：“原子一定比锁快”“CAS 循环就是无等待”“加超时就不会死锁”。超时后的资源释放、重试与公平性仍是协议的一部分。

### 9. 无锁与 ABA：比较的是地址，回收的是对象

**题目**：一个用 CAS 实现的栈，弹出节点后立即 `delete`，为什么不安全？加版本号是否就能同时解决 ABA 和内存回收？

**强答要点**：分开线性化（Linearizability）、进度保证和安全内存回收（Safe Memory Reclamation）。CAS 成功可以是逻辑操作的线性化点，但读者可能在 CAS 前已经读取旧节点；把节点从结构里摘除，并不代表所有潜在访问者都退出了。

```text
初始：head -> A -> B -> C
T1：读取 head=A，并已保存 A.next=B，然后暂停
T2：弹出 A，再弹出 B，把 A 重新压回，令 A.next=C
T1：仅比较 head 是否为 A，CAS(A, B) 成功
结果：把已经不属于当前栈的 B 错误放回 head
```

这个时序先假定节点存储仍安全，且 A.next 的读取先于改写，以便隔离 ABA：地址经历 A→其他值→A，地址比较看不出历史。若换一种交错：T1 只读到 head=A 就暂停，T2 随即释放 A，那么 T1 恢复后读取 `A.next` 就可能先发生释放后使用（Use-after-free），根本不必等到 ABA 的 CAS。

【事实】危险指针（Hazard Pointer）用于延迟回收仍可能被读者访问的节点，C++26 相关接口与动机见 [P2530R3](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/p2530r3.pdf)。这不是让原子指针自动拥有对象；保护、校验与退役仍需遵循具体库协议。

常见的回收选择有不同成本归属：危险指针让读者显式保护节点并重新校验源指针；基于纪元的回收（Epoch-based Reclamation，EBR）让读者进入受保护区间，推迟到旧读者退出才回收；读复制更新（Read-Copy-Update，RCU）则围绕读侧临界区和宽限期建立回收协议。这里比较的是机制，不声明它们是标准库中完全等价的接口。

【推断】选型首先看最慢读者是否有上界。纪元读者长期停顿可能积压大量退役节点；危险指针需要保护记录、扫描和重试；版本标签存在回绕、表示宽度与双宽 CAS 支持问题。回收方案决定了延迟和内存上限，不能只比较读侧指令数。

危险指针可以防止其保护协议覆盖期间的释放与复用，但不自动阻止“同一个尚存活节点被移除再插入”的逻辑 ABA。版本号也不能使解引用一个已释放对象合法。必须说明允许怎样的节点复用，并分别证明地址可访问与历史可区分。

**追问链**：

1. 第一层：线性化点在哪里？逐一指出 push、pop 成功和空栈返回的判定点，不只给成功 CAS 一个答案。
2. 第二层：保护指针为什么要再读一次 head？保护发布前节点可能已经被移除；必须确认保护对象仍与源一致后再解引用。
3. 第三层：保护记录用 relaxed store 就行吗？不能凭直觉决定；扫描者与读者的排序必须满足库算法证明，本文不提供可替换的手写实现。
4. 第四层：线程退出或被取消时谁清理保护？运行时必须有注册、退出和停机协议，且不能跳过仍可能访问节点的读者。

**常见差答／陷阱**：“CAS 成功所以一定安全”“双宽 CAS 解决全部问题”“指针读到后马上加引用就好”。最后一种会在取得所有权之前触碰已释放对象。

### 10. 无锁队列的选型：进度保证不能由名字推出

**题目**：为查询调度器选择单生产者单消费者（Single Producer Single Consumer，SPSC）环形队列，还是多生产者多消费者（Multiple Producer Multiple Consumer，MPMC）队列？什么情况下应保留有锁版本？

**强答要点**：先固定参与者、容量、满队列行为、元素生命周期与关闭语义，再讨论算法。无锁（Lock-free）要求系统总体持续推进；无等待（Wait-free）要求每个参与操作在有界自身步骤内完成；无阻塞命名或“使用 atomic”本身都不是这些保证。

在固定容量 SPSC 环上，生产者写槽位后发布写游标，消费者获取写游标后读槽位；消费者完成读取后发布读游标，生产者获取它再复用槽位。两个方向都需要证明，不能只画生产者到消费者的一条边。

```text
生产者：构造 slot[i] → 发布 write
                              ↓ 消费者观察该发布
消费者：读取并结束使用 slot[i] → 发布 read
                              ↓ 生产者观察该发布
生产者：下一轮才可重建 slot[i]
```

这张图说明谁授予复用权限，但不规定某个队列的具体游标编码。实现还要处理整数回绕、满空判定、缓存游标和析构；有些算法以模运算，有些保留空槽，不能把一个方案的判定式移植到另一个方案。

【推断】有界容量使内存上限更清楚，但队列满时必须背压（Backpressure）、拒绝或由上层处理。生产者预留槽位后暂停，可能阻挡按顺序消费；某些声称“无锁”的有界 MPMC 算法因此不能满足严格锁自由定义。候选人应说明自己选用算法的实际进度属性。

关闭不是一个简单布尔变量：需要禁止新增提交，决定是否排空已有元素，唤醒等待者，并在全部访问结束后析构槽位。让调用者忙等到有位置会把队列问题转化成 CPU 和延迟问题；让调用线程直接执行任务又可能破坏线程归属或锁顺序。

**追问链**：

1. 第一层：无锁为何不保证低尾延迟？某个线程仍可能长期输掉竞争；总体推进与个体公平不同。
2. 第二层：`malloc` 在入队路径上，会影响什么？它可能阻塞，也可能使算法宣称的端到端进度保证失效。
3. 第三层：怎样公平比较两种队列？固定容量、满队列策略、生产消费比例、工作量与 CPU 预算，报告尾延迟及失败次数。

**常见差答／陷阱**：“MPMC 通用，直接用它”“无锁不会阻塞，所以没有停顿”“吞吐高就该替换”。接口语义、回收成本和公平性都可能不同。

## 四、内存预算与硬件局部性：性能成本由谁承担

### 11. jemalloc 与 mimalloc：分配器优化先解释 RSS 为什么没降

**题目**：查询结束后对象已经释放，进程常驻集大小（Resident Set Size，RSS）仍然很高。怎么区分泄漏、线程缓存、碎片和页面归还？换分配器能解决什么？

**强答要点**：建立分层账本：业务存活字节、分配器实际分配字节、活跃页、映射和驻留页；再检查线程缓存、尺寸分级、跨线程释放、空闲页保留与操作系统记账。`free` 结束对象分配的可用性，不承诺立即减少进程 RSS；RSS 也不是堆存活对象的同义词。

【事实】[jemalloc 官方手册](https://jemalloc.net/jemalloc.3.html)描述了 arena、线程缓存、尺寸类别、衰减与统计接口，例如 `stats.allocated`、`stats.active`、`stats.resident` 和 `stats.retained`。这些指标口径不同；其中 resident 是分配器统计，也不能直接当成操作系统对整个进程的 RSS。读取统计还需按手册刷新 `epoch`，并确认构建启用了相关能力。

【事实】[mimalloc v3.0.1 的固定版本说明](https://github.com/microsoft/mimalloc/blob/v3.0.1/readme.md)介绍空闲链表分片、跨线程释放与页面管理，并保留 2024–2025 的演进记录。其早期 v3 描述为实验分支；不能把该标签说明替换成所有 v3 发布的稳定性结论。本文只据该固定版本说明讨论机制，不把其历史实验状态当作 2026 年发布状态，也不把作者基准排名推导成数据库负载结论。

| 观察维度 | 应检查的机制 | 不能直接推出的结论 |
|---|---|---|
| 存活对象持续增长 | 所有权、队列积压、引用环 | 全部是分配器碎片 |
| allocated 回落，active 高 | 活跃页被少量对象占住、尺寸类别 | purge 可以移动存活对象 |
| 活跃页回落，驻留仍高 | 缓存、空闲页状态、归还策略 | 一定泄漏 |
| 跨线程释放多 | 所有者归属、远端回收批量 | 线程缓存越大越好 |
| 吞吐提高但峰值内存变大 | 缓存保留与归还延迟 | 新分配器全面更优 |

【推断】更大的缓存可能降低锁与系统调用频率，也可能在大量工作线程上放大保留内存。更积极归还页面可能压低驻留量，却增加下轮缺页和清零成本。应把空闲后内存曲线与恢复负载时的延迟一起看，否则只是把成本从当前时刻移到下一轮查询。

选型实验至少包括：实际对象尺寸和存活期分布；同线程与跨线程释放比例；稳态、突发和空闲后恢复；线程数与配额；透明大页（Transparent Huge Pages，THP）和非一致内存访问（Non-Uniform Memory Access，NUMA）策略；分配器版本、编译参数及配置。没有这些条件，不报告“替换后提升百分之几”。

**追问链**：

1. 第一层：为什么归还空闲页不能消除所有碎片？同一页还有存活对象时，通用原生指针分配器不能随意搬迁这些对象。
2. 第二层：设置更多 arena 能解决什么？可能减竞争，也可能增加分散与保留；需结合线程数、尺寸分布和实际绑定验证。
3. 第三层：如何确认替换生效？核对动态链接、覆盖方式、静态库和自定义内存池，避免只替换了部分分配路径。
4. 第四层：达到容器上限前怎么办？业务预算和准入应覆盖存活数据与系统余量，不能把分配器回收调参当作内存上限协议。

**常见差答／陷阱**：“jemalloc 没碎片”“mimalloc 在所有场景更快”“`malloc_trim` 可以整理全部存活对象”。这些说法把保留策略、可归还页和可移动对象混为一谈。

### 12. arena 与批次内存：批量释放如何跨过异步边界？

**题目**：为列式批次使用 arena（区域分配）或多态内存资源（Polymorphic Memory Resource，PMR），能否在查询结束时一次释放？嵌套容器和异步输出有什么风险？

**强答要点**：区域分配适合共享生命周期的一组对象；将逐对象释放成本移到区域重置，但要求所有借用者已经退出。资源对象、容器和容器元素的析构顺序必须明确，单调内存资源（Monotonic Buffer Resource）释放存储并不代替执行其中业务对象的析构。

```cpp
#include <array>
#include <cstddef>
#include <memory_resource>
#include <vector>

void local_batch() {
    std::array<std::byte, 4096> buffer;
    std::pmr::monotonic_buffer_resource arena(
        buffer.data(), buffer.size());
    std::pmr::vector<int> values{&arena};
    values.resize(100);
    // 离开时先析构 values，再析构 arena，最后结束 buffer 存储期。
}
```

这个顺序让容器先于资源销毁；如果 `values.data()` 被保存进外部回调，局部顺序正确仍然无法阻止回调悬空。若提前执行 `arena.release()` 后再访问 `values`，同样破坏了容器有效性。需要“批次所有者”覆盖资源与所有消费任务，而非把裸地址发出去。

4096 只是示例缓冲大小，不是性能推荐。默认上游资源允许缓冲耗尽后继续分配；如果想验证严格预算，应提供受限上游或明确的失败路径。否则所谓“栈上 4 KiB 批次”可能实际上向上游申请更多内存。

【推断】区域方案能减少释放动作和元数据成本，也可能让一小段慢输出拖住整个大批次；拆分区域可以缩短保留时间，却增加区域数量和管理成本。对于有非平凡析构的对象，必须安排析构调用或证明可以不构造这种对象。

**追问链**：

1. 第一层：`pmr::vector<std::string>` 的字符串缓冲也用 arena 吗？不自动如此；元素类型与分配器传播规则决定嵌套分配路径。
2. 第二层：跨资源移动一定转移缓冲吗？不能这样保证，资源不兼容时可能逐元素处理，要核对构造和赋值的具体操作。
3. 第三层：异步发送如何避免整批滞留？可以复制小结果、转移独立缓冲或持有批次租约，按字节与尾延迟证据选。

**常见差答／陷阱**：“有 arena 就不需要析构”“PMR 自动覆盖所有子分配”“查询返回就可以 reset”。最后一个说法遗漏仍在执行的远端或设备消费者。

### 13. cache、false sharing 与 NUMA：线程越多为什么越慢？

**题目**：每个工作线程只更新自己的计数器，扩展到更多核心后吞吐反而下降。怎样区分伪共享、带宽饱和和远端内存访问？

**强答要点**：缓存行（Cache Line）是常见一致性粒度。伪共享（False Sharing）指线程修改不同逻辑变量，却竞争同一缓存行；真实共享是多个线程争同一逻辑状态。填充只能针对前者，不能解决所有线程反复更新一个全局计数器的问题。

```cpp
#include <atomic>
#include <new>

struct alignas(std::hardware_destructive_interference_size) Counter {
    std::atomic<unsigned long long> value{0};
};
```

该写法表达隔离意图，不证明所有机器恰好 64 字节，也不证明没有其他共享行。应核对工具链常量、布局和分配地址；若这个类型暴露在二进制接口中，还需要固定并检查布局，避免编译目标差异。填充会增加工作集，可能伤害缓存和地址转换后备缓冲（Translation Lookaside Buffer，TLB）的覆盖率。

【事实】Linux v6.12 的 [perf c2c 文档](https://github.com/torvalds/linux/blob/v6.12/tools/perf/Documentation/perf-c2c.txt)提供缓存行共享分析入口。相关事件受硬件支持和采样方式限制；缓存到缓存传输或修改态命中等证据，只能定位候选共享位置，仍要映射到字段与访问者才能区分真共享和伪共享。

NUMA 要同时考虑线程在哪运行、物理页在哪分配以及数据被谁访问。首次触页（First Touch）解释的是一定策略下实际页分配的常见行为，不是 `malloc` 返回地址时一定绑定到调用线程的承诺；共享页、预触页、迁移和内存策略都会改变结果。

【事实】[Linux NUMA 内存策略文档](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)说明默认、本地、绑定和交错策略，以及策略与 cpuset 限制的关系。仅绑定 CPU 不会自动修复已经位于另一节点的数据；策略也不能越过允许节点集合。

【推断】对线程私有构建的大哈希表，可以让所属节点工作线程初始化并使用；对所有节点共同扫描的只读数据，交错放置或按节点复制可能更合理。前者减少远端访问但可能负载不均；后者增加内存或跨节点流量，必须按访问模式验证。

**追问链**：

1. 第一层：用了 relaxed 为何仍有竞争？它削弱排序约束，不取消原子 RMW 对同一缓存行的所有权竞争。
2. 第二层：线程绑核后变慢说明什么？可能失去负载均衡、受拓扑或配额限制；需同时查页分布与线程运行状态。
3. 第三层：每线程计数再合并有什么代价？减少共享写，但实时读到的是滞后或不一致汇总；精确快照需要额外协调。
4. 第四层：缓存未命中升高是否就是 NUMA？不是，还可能容量、冲突、预取无效或访问随机性；需要远端访问与带宽证据。

**常见差答／陷阱**：“每个字段后加 64 字节”“MESI 保证程序没有竞态”“NUMA 一律 interleave”。它们没有说明实际拓扑、读写归属和负载约束。

## 五、协程把控制流写直，却把生命周期问题留给运行时

### 14. C++20 协程：挂起以后，谁拥有协程帧，谁有权恢复？

**题目**：把异步扫描改为 `co_await`，为什么仍可能悬空、重复恢复或无法取消？协程是否等于轻量线程？

**强答要点**：C++20 协程（Coroutine）提供无栈协程转换机制，编译器把跨挂起点存活的状态组织进协程帧（Coroutine Frame），由承诺对象（Promise Object）和等待器（Awaiter）协议控制行为。它没有内置通用调度器、网络轮询器和完整取消协议。

【事实】语言转换中的参数副本、promise、初始挂起、最终挂起与异常处理规则见 [dcl.fct.def.coroutine](https://eel.is/c++draft/dcl.fct.def.coroutine)。帧可能动态分配，也可能满足条件后被优化消除；不能保证每次调用都分配，也不能保证一定零分配。

```text
调用 → 建立帧和 promise → initial_suspend
     → 执行函数体 → await_ready
                     ├─ 就绪：继续
                     └─ 未就绪：await_suspend 注册恢复路径
     → await_resume 获取结果 → return_value / return_void
     → final_suspend → 由协议指定的所有者销毁帧
```

图中的销毁策略不是统一固定：若最终挂起保留帧，任务对象需要承担销毁；若设计为完成时自行销毁，就不能再让外部持有者无条件 `destroy()`。`coroutine_handle` 是操作句柄，不天然拥有帧；对已销毁帧使用句柄或同时恢复同一协程，都需要被协议排除。

【推断】审查一个异步等待器，应该按“注册完成 → 完成可能立即发生 → 取消同时发生 → 运行时关闭”逐项推演。`await_suspend` 把句柄交给其他线程后，对方可能立即恢复并使等待器失效；发布后再访问等待器成员，不能假设它仍存活。把完成与取消串行化、或设定一个唯一完成者，是运行时必须证明的状态迁移。

协程按值参数可以成为帧的一部分，引用参数仍只是引用。成员协程中的 `this` 不延长对象生命周期；带捕获的协程 lambda 也不能假定闭包成员自动按值搬进帧。让闭包在协程挂起后销毁，可能留下对已销毁捕获的访问，通常应把依赖作为有所有权的参数传入。

持锁跨 `co_await` 除了放大临界区，还可能阻止完成者取得同一把锁；若恢复到另一个线程，还涉及线程互斥锁的解锁约束。正确做法通常是锁内提取状态，锁外挂起，恢复后重新校验版本，而不是简单把锁换成自旋锁。

**追问链**：

1. 第一层：`co_await` 会自动切线程吗？不一定，是否挂起、由谁恢复和在哪恢复由等待器及调度器决定。
2. 第二层：取消后能直接 destroy 吗？只有证明底层操作和回调都不会再访问帧，且没有并发恢复，才可以销毁。
3. 第三层：超时和成功同时到达怎么办？需要唯一终结状态、结果归属和迟到回调处理，超时不是底层任务已经停止的证明。
4. 第四层：怎样降低帧成本？缩短跨挂起存活的对象、减少捕获和分配，检查生成代码；同时保留所有权和关闭协议。

**常见差答／陷阱**：“协程自动多核并行”“`handle.destroy()` 就是取消”“RAII 保证回调不悬空”。语言机制没有替运行时决定这些事情。

### 15. 从数据库调度到 AI runtime：完成事件必须覆盖真实使用期

**题目**：把同一套 C++ 异步组件用于数据库远端扫描和模型推理请求，资源何时可以回收？主机函数返回是否意味着加速设备已经不用缓冲？

**强答要点**：对每一类资源定义“最后一次可能访问”的完成条件。数据库输入缓冲可能被解码或输出任务继续持有；设备提交接口返回也可能只说明工作已经入队。主机所有权结束与设备完成事件不是同一个时刻。

【推断】这里是跨岗位设计练习，不声称某个 vLLM 版本采用此实现。缓冲释放前，必须确认所有使用者都已完成访问，或接口已完成复制、转移所有权；不能仅凭提交函数返回判断。以 [CUDA 12.6 的同步行为文档](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-runtime-api/api-sync-behavior.html)为例，内核启动相对主机异步，而内存复制的同步行为取决于方向、内存类型和具体接口，不能仅凭 `Async` 名称判断。

```text
请求接纳 → 取得预算 → 构建输入 → 提交底层任务
                               ↓
取消请求 → 停止新增派生任务   等待真实完成或安全撤销
                               ↓
                    汇合回调 → 归还预算与输入缓冲
```

预算覆盖期应包含排队和取消后的收敛窗口，否则大量超时请求可能在账本里消失，却继续占用真实资源。队列、协程帧、输出片段和底层在途任务都要有责任人；只统计当前可见请求数，无法证明内存上限。

【推断】可以优先建立结构化并发（Structured Concurrency）的任务树，让父任务退出前汇合子任务；若采用脱离父任务的后台工作，则必须另建明确所有者和停止协议。前者增加汇合等待，后者增加运维与回收复杂度，不能只用代码行数决定。

**追问链**：

1. 第一层：请求超时后还能不能回传结果？由接口契约决定，但结果不能被交给已经销毁的接收对象。
2. 第二层：底层无法取消怎么办？逻辑取消后保留必要资源直到完成，限制在途规模，并把这部分占用计入预算。
3. 第三层：完成回调运行在哪个线程？若回调只能在受限线程执行，就不能在那里无界析构大对象或阻塞等待其他任务。

**常见差答／陷阱**：“协程析构就会停止设备任务”“客户端断开就不用记内存”“换语言可以消除异步资源问题”。资源使用方的完成契约仍然存在。

## 六、性能剖析：先解释时间去了哪里，再决定改什么

### 16. perf 与火焰图：宽度、等待和尾延迟分别说明什么？

**题目**：查询延迟变高，CPU 使用率却不高；另一组查询 CPU 满载，但火焰图找不到单个大热点。分别怎么排查？

**强答要点**：把墙钟时间（Wall-clock Time）、运行中时间（On-CPU Time）、离开 CPU 的时间（Off-CPU Time）和可运行却未被调度的等待分开。线程 CPU 总时间可以因并行而大于一次请求耗时，不能把所有线程样本直接相加当成请求关键路径。

【事实】Linux v6.12 的 [perf record 文档](https://github.com/torvalds/linux/blob/v6.12/tools/perf/Documentation/perf-record.txt)描述采样事件和调用链采集方式。栈回溯要匹配实际二进制，保留符号，并按构建情况选择帧指针或 DWARF 调试信息；高采样频率与更复杂回溯都会改变观测开销。

```bash
# 以下为实验命令模板，不是本文已经执行的生产采样。
# PID 替换为目标进程号；事件、权限和线程覆盖范围先查本机版本。
perf stat -p PID \
  -e task-clock,cycles,instructions,cache-misses,context-switches -- sleep 30
perf record -F 99 -g --call-graph dwarf -p PID -- sleep 30
perf report
```

30 秒和 99 Hz 只是便于复述的示例窗口与频率，不是采样充分性的保证。进程线程是否全部纳入、容器可见性、硬件计数器复用和符号匹配都要核对；不能拿两种不同采样配置的宽度变化直接证明函数变快。

【事实】[火焰图（Flame Graph）作者的说明](https://www.brendangregg.com/flamegraphs.html)将横向宽度解释为所聚合样本的权重，普通火焰图横轴不是时间顺序。CPU 图中宽函数可能是被频繁调用，也可能是单次昂贵；离 CPU 图则按相应等待数据解释，不应混用。

【事实】[Off-CPU Analysis](https://www.brendangregg.com/offcpuanalysis.html)用阻塞与等待分析补足 CPU 采样。线程的离 CPU 区间还需结合调度状态区分阻塞与可运行等待；阻塞栈说明在哪里睡下，不自动指出是谁持锁或哪个远端请求导致等待。

【推断】CPU 不高时，先检查是否锁等待、输入等待、背压、CPU 配额节流或单线程串行阶段；CPU 高但热点分散时，检查重复工作、全局共享计数、内存带宽与吞吐退化。低每周期指令数（Instructions Per Cycle，IPC）只是现象，可能来自等待、分支或执行资源限制，不能直接断言“内存瓶颈”。

尾延迟要按慢请求选时间窗口或保留请求关联：全局平均样本会被大量正常查询淹没。端到端关键路径还可能跨线程、进程和设备；线程级采样与请求时间线互相校验，才知道优化是否碰到了慢请求的约束。

**追问链**：

1. 第一层：CPU 火焰图能否看网络等待？通常看不到阻塞期间消耗的时间，需要等待和请求时间线证据。
2. 第二层：锁函数很宽就应该换无锁吗？先识别持锁者、锁保护的不变量与竞争来源，可能应缩小临界区或分片。
3. 第三层：怎么看优化是否真实？固定负载、资源与构建，检查绝对 CPU 时间、吞吐和延迟，而不只看占比下降。
4. 第四层：生产环境不能采完整调用栈怎么办？使用低开销计数和阶段埋点逐步缩小范围，明确证据不足，不能虚构热点归因。

**常见差答／陷阱**：“火焰图越平越好”“最宽函数就是最慢请求”“cache-misses 多就加预取”。它们都缺少采样口径和因果验证。

### 17. 性能与正确性验证：怎样推翻自己的第一个解释？

**题目**：你认为瓶颈是分配器，替换后微基准变快，却使线上高分位延迟上升。如何复盘并决定是否回退？

**强答要点**：先保留可比较的构建、参数、输入与时间线，拆成可证伪的假设。例如“跨线程释放竞争增加 CPU 时间”应预测相关栈和事件下降；“归还更积极导致恢复期缺页”则应预测空闲后恢复阶段的缺页与延迟一起上升。不同预测对应不同采集方法。

【推断】只看平均吞吐无法排除队列积压和资源转移。固定到达负载、逐级加压，同时记录成功率、拒绝率、队列长度和尾延迟；若新方案靠拒绝更多请求换吞吐，必须把这种语义变化显式纳入比较。这个实验设计不包含任何已测量的提升数值。

| 假设 | 支持它的候选证据 | 使它变弱的观察 |
|---|---|---|
| 分配竞争主导 | 分配栈 CPU 成本、并发扩展、跨线程释放路径 | 替换后分配成本下降但总耗时不变 |
| 伪共享主导 | 热缓存行映射到独立写字段，布局实验后扩展改善 | 分离缓存行后竞争仍集中在同一逻辑状态 |
| NUMA 远端访问主导 | 页归属、线程位置与远端访问匹配 | 本地化后瓶颈仍是同样的带宽上限 |
| 锁导致长尾 | 慢请求窗口中存在长阻塞，能关联到持锁者 | 大量离 CPU 时间其实是可运行等待 |

【事实】地址消毒器（AddressSanitizer，ASan）可以发现多类越界与释放后使用，线程消毒器（ThreadSanitizer，TSan）用于检测数据竞争，能力与限制分别见 [ASan 文档](https://clang.llvm.org/docs/AddressSanitizer.html)和 [TSan 文档](https://clang.llvm.org/docs/ThreadSanitizer.html)。两类检测通常使用不同构建，不能把插桩构建的性能直接与生产构建对比。

即便所有字段都是原子变量，仍可能发生 ABA、错误状态迁移或重复完成，这些不是 TSan 无报告就能证明正确的内容。应补确定性交错测试、取消与停机测试、回收延迟测试；小型状态机还可以穷举关键交错，但要说明模型包含了哪些动作。

【推断】验证应在合入前确定失败判据：正确性出现反例直接停止；性能退化按团队事先定义的延迟、内存和错误预算决定回退。阈值必须来自实际业务要求，不在文章里替 候选人 编造一个“统一提升或退化百分比”。

**追问链**：

1. 第一层：微基准还有什么价值？隔离机制与发现上限，但要把线程、尺寸、缓存和生命周期条件带回真实负载验证。
2. 第二层：复现不了线上长尾怎么办？收集慢窗口上下文和对照条件，逐步复现负载阶段，不把“没复现”写成“已经排除”。
3. 第三层：回退后该保留什么？失败假设、二进制标识、配置、输入特征和时间线，便于下次定位，而不是只留一张图。

**常见差答／陷阱**：“跑一遍压测更快就合”“TSan 通过所以无锁算法正确”“线上环境复杂，结论只能靠经验”。经验可以选择假设，不能替代可核验观察。

## 七、2024–2026 的增量：按工程问题选择标准特性

### 18. C++23：新接口能减少哪些错误，不能替你决定什么？

**题目**：一个仍以 C++17 为主的内核，值得为哪些 C++23 能力升级？如何避免把语言升级变成大规模重写？

**强答要点**：从具体错误和接口成本出发，而不是罗列语法。先区分编译器前端支持、标准库支持、部署机器兼容与 ABI；升级编译开关只是其中一项。选一两个局部模块验证，保留与旧代码可互操作的边界。

【事实】[libc++ 的 C++23 状态页](https://libcxx.llvm.org/Status/Cxx23.html)列出 `expected`、`mdspan`、`move_only_function`、`generator` 等库能力及实现进度；语言特性另查 [Clang 状态页](https://clang.llvm.org/cxx_status.html)。下表描述能力的用途，不宣称所有部署工具链已完整支持。

| 能力 | 可以直接改善的问题 | 仍需单独证明的边界 |
|---|---|---|
| `std::expected<T, E>` | 将可预期失败显式放进返回类型 | 错误传播、资源清理、调用方是否处理 |
| `std::move_only_function` | 保存捕获独占资源的可调用对象 | 是否分配、何处析构、空调用前置条件 |
| `std::mdspan` | 分离多维索引、布局和访问策略 | 存储所有权、尺寸及布局的实际合法性 |
| `std::generator` | 以同步拉取方式表达逐项生成 | 不提供通用异步调度与取消 |
| 显式对象形参 | 减少某些成员重载重复，表达值类别 | 工具链支持、接口可读性和代码体积 |

【推断】对任务队列，允许移动型可调用对象可以避免为了闭包复制而引入共享所有权；但不能因此声称所有任务都不分配。对解析和计划构建，`expected` 能统一可恢复错误表示，却不会自动处理部分结果撤销。升级收益应以减少的错误状态和实际代码路径说明。

`mdspan` 的非拥有性尤其要与前面的视图题连接：它能表达布局，并不延长底层缓冲有效期。`generator` 同样不能替代前面的异步任务类型；“基于协程”只是实现机制的共同点，调用和调度契约仍然不同。

**追问链**：

1. 第一层：用了 `expected` 就完全不会抛异常吗？不是，值类型的构造、分配或其他操作仍可能抛，取决于具体操作契约。
2. 第二层：怎样防止库支持不完整？使用特性测试宏（Feature-test Macro）、实际编译链接探针和目标平台测试，避免只比较编译器版本号。
3. 第三层：什么时候暂不升级？依赖库、编译器插件或部署平台尚未满足要求时，局部封装能先保持接口边界，不强推全量改造。

**常见差答／陷阱**：“C++23 都是语法糖”“打开标准开关就都能用”“generator 就是异步流”。回答必须落到所有权、错误与实现支持。

### 19. C++26：execution、回收、SIMD 和反射怎样进入答题？

**题目**：2024–2026 应补哪些系统编程新知识？为什么了解提案仍不能直接承诺用它重构生产引擎？

**强答要点**：按四个工程问题准备：异步组合如何表达完成与停止；节点回收由谁承担；数据并行如何表达；元数据生成如何减少重复。用固定提案解释机制，用实现状态确认可用性，不把历史提案代码当成最终 API。

【事实】2024 年 [P2300R10：std::execution](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/p2300r10.html)以发送者／接收者（Sender/Receiver）模型组合异步操作，涉及值、错误、停止完成及操作状态。协程负责可挂起控制流，execution 讨论异步组合协议；两者并非互相替代，也不意味着标准库附送所有设备后端。

【推断】对运行时岗位，值得追问的是连接后操作状态由谁持有、启动后如何完成、停止请求如何到达底层、调度器切换是否改变线程归属。停止完成信号不是强制终止正在执行的任意操作；接入真实网络或设备仍要处理无法取消的工作和迟到事件。

【事实】C++26 的危险指针方向与前文节点回收相连，见 P2530R3。2024 年 [P1928R15](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/p1928r15.pdf)讨论标准数据并行类型，即单指令多数据（Single Instruction Multiple Data，SIMD）抽象。提案提供表达能力，不保证任意算子自动更快，也不保证浮点归约与原顺序逐位一致。

【事实】静态反射（Static Reflection）可以围绕类型与成员元数据生成代码，机制参考 2025 年 [P2996R13：Reflection for C++26](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p2996r13.html)。这是编译期反射方向，不能直接理解为运行时扫描任意对象，也不能由成员枚举结果推导稳定的持久化格式。

| 面试切入口 | 可以讨论的收益 | 应主动补上的代价 |
|---|---|---|
| execution | 统一完成通道与异步组合 | 状态有效期、适配层、调试与实现成熟度 |
| 危险指针 | 将回收保护协议形成库接口 | 保护开销、退役扫描、停机与内存上限 |
| 标准 SIMD | 减少部分平台相关向量表达 | 尾部、掩码、对齐、指令集与数值语义 |
| 静态反射 | 生成字段访问与诊断代码 | 编译时间、代码体积、字段演进与外部格式契约 |

【推断】数据库中的可持久化元数据需要独立版本和字段编号，不能把 C++ 成员声明顺序当作长期格式。数据并行优化也应固定目标指令集、输入长度与分布；带宽受限、分支选择性或短批次下，表达成向量并不保证消除主要瓶颈。

**追问链**：

1. 第一层：知道 execution 名称后应该讲什么？选一个有取消的异步操作，画状态所有权和三种完成结果，而不是背算法名称。
2. 第二层：某标准特性已进入草案，为什么还要探针？前端、库和适配后端可以分别缺失；历史版本与当前修订也可能有差异。
3. 第三层：怎样安排试点？在可替换的局部边界验证语义、成本和工具链，保留回退方案，再决定是否扩展使用范围。

**常见差答／陷阱**：“C++26 已经让 C++ 内存安全”“有 reflection 就不用格式版本”“标准 SIMD 等于最佳汇编”。这些承诺都超出了接口与提案证据。

### 20. Rust 对比：把哪些证明交给类型系统，哪些仍留给工程师？

**题目**：新运行时该用 C++ 还是 Rust？已有 C++ 内核能否通过 Rust 包装获得线程安全与内存安全？两种语言的移动与异步有什么区别？

**强答要点**：Rust 的所有权、借用与析构规则能在安全代码中拒绝多类悬空和别名冲突；C++ 更多依赖类型约定、代码审查和动态检查。比较应落到需要维护的证明数量、已有生态和边界成本，而不是预设某语言必然更快。

【事实】Rust 的 `Send` 表达值可安全跨线程转移，`Sync` 表达共享引用可安全跨线程使用，定义与不安全实现责任见 [Rustonomicon：Send and Sync](https://doc.rust-lang.org/nomicon/send-and-sync.html)。`Arc<T>` 提供共享所有权，并不自动把任意 `T` 的内部操作变成线程安全；这与 C++ 的控制块／对象区分可以相互对照。

Rust 中的移动主要是所有权语义，不存在 C++ 那样可自由自定义的移动构造函数。地址敏感状态则需单独约束；[标准库 Pin 文档](https://doc.rust-lang.org/std/pin/)解释固定（Pinning）与 `Unpin` 的条件，不能把 `Pin` 误读成“指针变量不能移动”或“对象永远不析构”。

【推断】C++ 协程的句柄、promise 和帧所有者，与 Rust 的未来对象（Future）及执行器，都需要运行时安排轮询或恢复、唤醒和关闭。安全类型可以约束接口，却不会替你决定公平调度、队列上限或远端操作何时停止；丢弃 future 也不必然取消已经提交的外部工作。

【事实】[Rust 1.85 发布说明](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)宣布 Rust 2024 Edition 在 2025 年稳定。新版要求更显式地标记不安全边界：[`unsafe extern` 块](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-extern.html)强调外部声明正确性由作者负责；[`unsafe_op_in_unsafe_fn`](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html)默认警告促使函数体中的不安全操作使用显式块。Edition 名称不是稳定发布年份，也不是 C++ ABI 兼容保证。

| 比较维度 | C++ 的常见证明责任 | Rust 带来的约束与剩余责任 |
|---|---|---|
| 借用有效期 | 接口契约、所有者、审查和检测 | 安全引用受借用规则约束；外部裸指针仍需证明 |
| 跨线程所有权 | 明确同步和对象有效期 | Send/Sync 约束；不安全实现必须正确 |
| 节点回收 | 原子协议与回收协议分别证明 | 原子、unsafe 与回收库仍需协议证明 |
| 跨语言调用 | ABI、异常、分配与释放配对 | 外部函数接口（Foreign Function Interface，FFI）包装不能验证 C++ 内部 |
| 异步关闭 | 帧、回调、任务树汇合 | future、执行器和外部资源仍需关闭契约 |

【推断】适合渐进引入的边界通常具备清晰所有权与低频跨语言调用；例如一个独立解析模块可以先把输入、输出和错误封装起来。跨每行数据频繁调用、复杂回调和双向共享对象会放大包装成本，应先测边界，不把整引擎重写当成默认选项。此处为候选设计，未指向候选人的项目改造经历。

**追问链**：

1. 第一层：安全 Rust 是否排除死锁和业务竞态？不排除；锁顺序、原子状态机和协议仍可能错误。
2. 第二层：FFI 必须写清什么？分配与释放方、长度和对齐、别名与可变性、回调有效期、线程归属及异常或 panic 边界。
3. 第三层：为什么安全包装也可能有缺陷？若内部 unsafe 或外部实现违反包装承诺，调用者遵守安全接口也可能触发错误。
4. 第四层：怎样证明引入值得？对比缺陷类型、维护成本、边界开销和交付约束，用小模块证据决定下一步，不宣称语言替换本身带来收益。

**常见差答／陷阱**：“Rust 没有内存泄漏”“加 Arc 就能随便共享”“包装一层就能验证 C++”“借用检查器解决所有并发问题”。这些说法把类型约束扩大成了系统级保证。

## 八、把强答变成可核验材料

### 21. 综合题：给一次查询取消后的崩溃与长尾，怎样组织答案？

**题目**：一个查询使用区域内存，批次通过队列交给协程输出；取消后偶发崩溃。修复后内存峰值上升，吞吐下降。请给出排查顺序与可上线方案。

**强答要点**：先把对象和事件画完整：查询对象、区域资源、批次、队列元素、协程帧、底层在途操作；标出谁引用谁和谁拥有谁。崩溃先验证是否存在资源重置早于最后使用，再检查完成与取消是否重复终结。修复正确性以后，再比较保留内存和调度成本。

【推断】一种待验证方案是让输出任务持有批次所有者，取消后禁止新增派生任务，等在途操作完成才回收资源；同时用有界队列和字节预算限制保留量。它解决的是释放时序与上限，不保证吞吐不降：每批共享所有权、汇合和背压都可能新增成本，必须测量。

**追问链**：

1. 第一层：用什么反例证明旧实现不安全？构造“输出已拿到视图但未消费 → 查询取消并重置区域 → 输出恢复”的确定性交错。
2. 第二层：为什么峰值上升可能是修复后的真实成本？旧实现可能过早归还账面预算，新方案才把在途资源完整计入；仍要排除无界队列与引用环。
3. 第三层：吞吐下降怎样拆分？分别观察引用计数、队列满比例、CPU 时间、等待和恢复期缺页，不同时改分配器、线程数和内存布局。
4. 第四层：上线条件是什么？反例不再成立、关闭路径能收敛、预算满足真实约束，并保留灰度与回退条件；具体数值由业务要求填写。

**常见差答／陷阱**：“给所有对象加 shared_ptr”“直接扩大队列”“换成无锁和新分配器”。这些改法可能掩盖根因、放大内存，或者在生命周期未证明时引入第二套错误。

**【模板】个人案例证据卡**：仅填写允许披露且本人能核实的材料。没有真实案例时，将这张卡标为复核练习，不把设计推演改写为生产经历。

- 环境与版本：【填写编译器、标准库、引擎版本、CPU 拓扑与内存配置】。
- 具体触发：【填写输入、并发度、取消／超时条件和可观察后果】。
- 本人责任：【填写本人提出的判断、实现或验证；团队成员的工作单列】。
- 初始假设与反证：【只有实际存在时填写，不能为了叙事编造一次误判】。
- 关键证明：【填写所有权图、同步边或回收边界，以及对应提交／记录】。
- 验证与结果：【填写测量口径、实际结果、未覆盖条件与回退方式】。

【推断】用于 Staff 面试时，再补一句“如何让同类错误不依赖我亲自发现”：可以是受约束的所有权接口、统一关闭协议、确定性交错测试或性能采样规范。应选择实际做过且有效的一项；没有落地证据就明确说是下一步方案。

2. **多份原料的“原子操作最高效”排序**：删除固定性能排名；原子类型可能不无锁，RMW 有缓存行竞争，锁和原子只能在同等语义、参与者与负载下比较。
3. **原始文件中以单例或局部 static 修复 `i++` 的回答**：初始化线程安全不等于后续操作安全；并发冲突需要同步，普通变量数据竞争不只意味着少加一次。
4. **某 C++ 题库 与详解的空类和虚类大小**：普通空完整对象大小非零，不是标准强制恰好一字节；带虚函数对象的大小依赖 ABI、布局和对齐，不能无条件断言四或八字节。
5. **虚析构解释**：通过普通非虚基类析构路径删除派生对象通常是未定义行为，不仅是派生析构没有执行；禁止该删除路径的基类也可以采用受保护非虚析构。
6. **构造与虚表解释**：构造函数不可声明为虚函数属于语言规则；构造／析构期间可以虚调用，但派发有阶段限制，不能用“虚指针还没初始化”概括。
7. **某题目详解 的 weak_ptr 示例**：原例在内层作用域声明 w1、w2，出作用域后又调用它们，代码不可编译；本篇改为描述对象与控制块的两个释放边界。weak_ptr 不增加强计数，不等于无控制块或无弱引用管理。
8. **简化 shared_ptr 实现**：普通 `int* ref_count` 既不满足并发计数要求，也没有覆盖赋值、弱引用和删除器等语义，不能作为可用实现；同一句柄与被管理对象的同步分别讨论。
9. **移动语义解释**：移动后的标准库对象并非“一概不能使用”，应遵守有效但未指定状态及操作前置条件；返回对象也不必发生移动，需区分保证的复制消除与可选 NRVO。
10. **vector 失效表**：`reserve` 只有实际重分配才使元素引用与迭代器全部失效；`pop_back` 还使被删除元素的引用和迭代器失效，不只影响 end；插入／擦除要区分位置与是否重分配，见 [vector.modifiers](https://eel.is/c++draft/vector.modifiers)。扩容倍数属于实现策略，不是 GCC 或某标准库永久不变的承诺。
11. **brk/mmap 的 128 KiB 二分法**：原料将特定默认值写成固定规则；glibc 的 mmap 阈值可配置且有动态调整，已有空闲块也会影响路径，见 [mallopt 官方手册](https://man7.org/linux/man-pages/man3/mallopt.3.html)。`free` 是否立即归还还取决于块来源与分配器策略。
12. **`mallinfo2().mmap_threshold`**：原料的这个成员不存在，不能用它读取阈值，成员定义可核对 [mallinfo2 手册](https://man7.org/linux/man-pages/man3/mallinfo.3.html)。本文不提供虚构查询接口，也不沿用原料未经实验说明的纳秒级分配与系统调用数字。
13. **“全局 map 不能用原子解决”**：不能把一般 `std::map` 简单包成原子来支持任意并发修改，但可以设计不可变快照加原子发布，或采用有独立证明的并发结构；适用语义与成本不同。
14. **缓存一致性与 volatile**：硬件一致性协议不等于 C++ 线程同步，volatile 也不建立普通线程间的发布关系；本文按数据竞争与先行发生关系分析。
15. **原始文件对 deque 与 array 的归类**：deque 不保证整体连续，array 的大小固定且没有常规插入／删除接口；不能把它们都套进 vector 的“连续容器插删”失效说明。
