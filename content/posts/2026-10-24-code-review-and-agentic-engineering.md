在手写代码的年代，“把代码写出来”本身就是一道天然的限流阀。一个工程师花三天时间修改在线分析处理（Online Analytical Processing，OLAP）数据库内核的算子或存储路径时，为了把编译跑通、把回归测试调绿，往往已经在脑子里把周边的锁序、生命周期和异常分支推演了好几遍。进入评审队列的补丁数量受限于人的敲字速度，作者在编码过程中顺带完成了大半的上下文建模。

进入 AI 辅助编码与智能体驱动研发（Agentic Engineering）时代后，这个隐含前提被打破了。今天让 AI 智能体（AI Agent）在几分钟内生成一份五百行、语法工整、甚至自带单元测试和漂亮摘要的拉取请求（Pull Request，PR），成本几乎趋近于零。然而，决定这五百行代码能不能安全合入主干的硬约束一点也没有变松：合法 SQL 会不会在边界条件下悄悄算错结果？异步取消时回调会不会踩到已析构的对象？新落盘的数据格式一旦写出，回滚二进制文件还能不能读回来？

**生成“看起来合理的代码”变得极其廉价，而证明关键不变量（Invariant）、厘清异步状态所有权、兜底线上回滚边界，依然高度依赖稀缺的人类工程判断。** 当上游产出补丁的速度翻倍、下游的人工理解带宽与验证环境却保持不变时，研发系统的瓶颈必然从“怎么把代码写出来”猛烈转移到“怎么确认这份改动真的安全”。这也是为什么我们在数据库内核里锤炼出的代码评审（Code Review）纪律，非但没有在 AI 时代过时，反而成了组织和约束 Agent 研发流水线最核心的骨架。

## 一、评审的底层标尺：我们到底凭什么阻塞一个合入？

很多团队的评审之所以沦为拉锯战，是因为把“必须守住的系统契约”和“个人审美偏好”混在了同一张清单里。Google 在 [The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html) 中定下过一条极其实用的准则：只要一项变更确定改善了整体代码健康度，哪怕它还不完美，也应当批准合入；技术事实与测量数据优先于个人偏好，风格争议服从既有规范，锦上添花的建议统一标上 `Nit:`。

落到硬核系统工程里，我会把这条准则拆成两个具体问题来拍板：

1. **这次改动有没有破坏绝不能退让的系统契约？** 比如合法 SQL 返回错误结果、持久化格式失去兼容、内存或句柄无界增长、或者在特定负载下触发严重的性能退化。只要踩中一条，不管代码结构重构得多优雅，合入条件都不成立。
2. **剩下的不完美，能不能作为独立的技术债在后续提交里偿还？** 局部变量命名不够传神、某个辅助函数还能再拆小一点，这些随时可以后续清理；但已经写进磁盘的新格式、已经暴露给用户的协议语义，一旦发布就没有廉价反悔的机会。

既然阻塞合入动用的是团队的否决权，阻塞意见本身就必须承担举证责任。只留一句“这里并发不安全”是把证明负担全盘甩给作者；只说“我以前一直这么写”则是把资历当成论据。一条合格的阻塞评论，至少要写清四件事：**触发条件、违反的约束、具体后果，以及验证或反驳的方法**。这样作者才能拿出调用方前置保证、反例测试或压测数据来正面回应，审阅者（Reviewer）也能在看到反证后干脆地撤回意见。

不同开源社区的治理规则，其实都在围绕“证据与责任边界”做文章：[Apache Voting](https://www.apache.org/foundation/voting.html) 明确规定代码修改上的 `-1` 否决必须附带可成立的技术理由，无理由否决直接无效；[LLVM Code Review Policy](https://llvm.org/docs/CodeReview.html) 区分提交前与提交后评审，并把审阅者的背书严格限定在其实际检查过的模块范围内；[PostgreSQL Reviewing a Patch](https://wiki.postgresql.org/wiki/Reviewing_a_Patch) 从补丁可应用性、需求合理性一路核对到性能、规范与文档；[StarRocks CONTRIBUTING](https://github.com/StarRocks/starrocks/blob/main/CONTRIBUTING.md) 也在此类社区协作规范上建立了自己的合入流程。

### 小批量拆分的本质是拆“语义契约”，不是拆行数

学术界对现代代码评审（Modern Code Review）做过不少实证调研。Bacchelli 与 Bird 在 ICSE 2013 论文 [Expectations, Outcomes, and Challenges of Modern Code Review](https://ieeexplore.ieee.org/document/6606617) 中追踪了微软的评审实践，发现大家嘴上说做评审是为了抓 Bug，实际评论里大量产出的是知识传递、团队上下文同步和备选方案讨论——**读懂变更本身就是最核心的门槛**。Sadowski 等人在 [Modern Code Review: A Case Study at Google](https://doi.org/10.1145/3183519.3183525) 中记录到 Google 的绝大多数变更都很小、通常只需一名审阅者、响应时延中位数在小时级；Google 的工程指南也相应建议把约 100 行作为 [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) 的参考规模（1000 行通常过大），并在 [Speed of Code Reviews](https://google.github.io/eng-practices/review/reviewer/speed.html) 中要求最迟一个工作日内给出响应。

但如果在系统软件里机械地按“每个 PR 不超过 200 行”去切代码，很容易切出无法独立验证的半成品。真正的拆分应该沿着**可独立成立的契约边界**推进：

1. 第一步先建立接口与旧版本的兼容读取能力；
2. 第二步接入新执行路径，但保持开关默认关闭，补齐端到端验证；
3. 第三步切换默认行为，待线上稳定后再清理旧路径。

每一步都必须说清楚能否独立编译、测试与灰度回滚。反过来，如果一个改动只有 50 行，却直接往共享存储里写出了旧节点读不懂的新格式，那它在代码行数上再小，在部署风险上也是不可逆的大变更。

与此同时，架构层面的分歧绝不能拖到逐行看代码时才爆发。正如 Malte Ubl 在 [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/) 中总结的那样，设计文档最大的价值是在动手写代码之前暴露核心分歧、记录权衡取舍与被否决的备选方案。涉及持久化格式、跨节点协议和公开 SQL 语义变动的任务，必须先对齐设计假设；到了代码评审阶段，审阅顺序也应从外向内推进：**先看意图描述与测试用例，再看接口契约与状态所有权边界，接着推演核心实现，最后才顺带挑局部细节**。一旦在第二层发现方向性偏差，立刻拉起同步讨论并把结论写回 PR，远比在行级评论里来回盖几十层楼高效得多。

## 二、数据库内核的评审显微镜：沿着状态生命周期查 P0–Nit

把 Google [What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 放到 OLAP 数据库内核的场景下，我们可以按风险后果把评审意见分成三档：

| 级别 | 默认处置 | 核心追问 |
| --- | --- | --- |
| **P0** | **阻塞合入**，直至风险证伪或修复 | 计算结果、并发同步、对象存活、资源上限与持久化恢复是否安全？ |
| **P1** | **强烈建议**，视线上后果决定是否升级为阻塞 | 热路径性能、异常测试覆盖与故障诊断信息是否达到上线门槛？ |
| **P2 / Nit** | **非阻塞建议**，交由作者裁量 | 是否属于局部命名偏好、函数拆分方式或注释措辞优化？ |

需要注意，这三档看的是**实际破坏力**而非表面形式：一段极其绕的逻辑如果让人根本无法确认锁与指针的所有权，哪怕测试全绿也足以升级为阻塞；相反，真正的局部风格偏好标清楚 `Nit:` 即可放行。下面顺着数据库内核最容易出事故的四条主线，看看具体该审什么。

### 1. SQL 语义与优化器等价性：先证等价，再谈加速

数据库内核的第一铁律是**不能算错数**。审查 SQL 算子与优化器规则时，哪怕常规测试集全绿，也必须逐一拷问空输入、`NULL` 三值逻辑（Three-Valued Logic）、整数溢出、Decimal 精度推导、时区转换，以及向量化引擎里极易漏掉的 `Nullable` 列与常量列（`Const Column`）特化分支。

拿最经典的谓词下推（Predicate Pushdown）来说，假设有人提了一个优化规则，把连接后的过滤条件直接压进右表扫描节点，并顺手删掉了连接上方的过滤算子。碰到下面这条查询会发生什么？

```sql
SELECT l.k
FROM l LEFT JOIN r ON l.k = r.k
WHERE r.v = 1;
```

设想左表 `l` 有一行 `k = 10`，右表 `r` 里也有一行 `k = 10, v = 2`。

- **原查询语义**：左外连接（Left Outer Join）先匹配上 `(k=10, v=2)`，随后外层的 `WHERE r.v = 1` 将这一行过滤掉，最终输出为空集。
- **错误改写后**：右表扫描阶段先执行 `r.v = 1`，把 `(k=10, v=2)` 提前淘汰，导致右表对 `k = 10` 变成了“无匹配行”；紧接着左外连接触发不匹配补 `NULL` 机制，吐出一行 `(l.k=10, r.v=NULL)`——而原本守在上面的 `WHERE r.v = 1` 已经被删掉了！结果这行本该消失的数据被错误地返回给了用户。

要让改写真正等价，要么保留连接上方的过滤条件，要么先严格证明上层谓词具有“拒绝 `NULL`（Null-Rejecting）”性质，先把 `LEFT JOIN` 安全退化为 `INNER JOIN` 再下推谓词。除此之外，涉及去重与聚合时还要核对多重集语义（Bag Semantics，即重复行数量是否保持不变），涉及多条重写规则联动时还要检查触发条件会不会相互震荡导致死循环。

### 2. 并发同步与异步生命周期：取消请求不等于回调已退出

C++ 内核代码里最隐蔽的崩溃，往往出在异步取消与析构交错的瞬间。

看到代码里同时写了 `memory_order_release` 和 `memory_order_acquire`，并不足以证明线程安全——必须核对读端到底有没有观察到那次特定的发布写入，从而真正建立先行发生关系（Happens-Before）；反过来，单纯用于统计指标的 `memory_order_relaxed` 计数器完全合法，不能一见 `relaxed` 就盲目判错。

更棘手的是异步回调捕获裸指针 `this`。审查这类代码时，我习惯沿着 **“注册 → 运行 → 触发取消 → 回调完成 → 对象析构”** 五个节点画时序图。很多补丁在查询超时时调了一句 `cancel()`，紧接着就析构上下文对象；但发出取消信号只代表“请求停止”，正在后台线程池里跑的回调函数可能正执行到一半，下一行一解引用 `this` 就会直接触发释放后使用（Use-After-Free）。

有人看到这个评论，第一反应是把裸指针改成 `std::shared_ptr`。但这同样需要追问三件事：第一，会不会形成引用环导致内存永久泄漏？第二，如果后台慢 I/O 迟迟不退，异步任务攥着最后一个 `shared_ptr` 延长对象存活，算子持有的大块内存记账（Memory Tracker）归还给谁？第三，如果改成析构函数同步阻塞等待回调退出，当前持有的锁与目标线程池之间会不会产生死锁或饥饿？同理，资源获取即初始化（Resource Acquisition Is Initialization，RAII）只能保证“析构发生时释放资源”，审阅者还得确认异常提前返回、重复完成或异步悬挂时，析构最终真的会按预期发生。

### 3. 存储发布、崩溃切点与分布式重试

存储引擎的审查核心只有一句话：**在任意两行代码之间拔掉电源，重启后机器认哪份数据？**

以列存后台合并压缩（Compaction）为例，整个流程跨越“生成新数据文件 → 刷盘持久化 → 发布新元数据版本（Manifest/Rowset） → 回收旧文件”四个阶段。很多人觉得新文件写了校验和（Checksum）就万事大吉，其实校验和只能抓出半截写入的坏块，管不了元数据发布顺序。在每个崩溃切点上，都必须答清楚：重启恢复后可见文件集合由哪份元数据拍板？未发布成功的孤儿文件谁来清理？旧文件回收时有没有守住正在读取它的活跃查询引用与历史快照？一旦涉及落盘格式升级，更要把“读兼容”与“写兼容”拆开看——新格式字节一旦写进磁盘或对象存储，单纯关掉特性开关（Feature Flag）或回滚二进制可执行文件，根本撤销不了已经持久化的新数据。

跨节点的远程过程调用（Remote Procedure Call，RPC）也是同样的道理。调用方收到 `Timeout`，只代表在截止时间内没拿到回包，远端节点可能早就完成了事务提交。如果客户端盲目发起重试，而服务端只靠进程内存里的哈希表做去重，一旦碰上主节点切换（Leader Election）或进程重启，去重记录丢失就会酿成重复写入；反过来，去重状态何时过期回收，也必须与客户端的最大重试窗口严格对齐。

### 4. 性能条件、故障检测器与可观测性

到了 **P1** 层面，重点转向性能真伪与线上可运维性：

- **性能收益必须交代边界条件**：热路径上有无多余的内存分配、深拷贝、虚函数分派或分支预测失败？列式批处理有没有在某个边缘分支退化成逐行循环？单指令多数据（Single Instruction, Multiple Data，SIMD）优化绝没有脱离数据分布的固定加速比——微基准测试（Microbenchmark）跑快了 3 倍，放到真实查询里一旦受限于内存带宽、高比例 `NULL` 位图处理或上游连接算子阻塞，端到端收益可能微乎其微。因此压测证据必须保留硬件型号、编译参数、数据规模与倾斜度、并发度及缓存冷热状态，配合性能剖析（Profiling）火焰图说话。同时要把伪共享（False Sharing）这类缓存行抖动引起的性能退化，与真正破坏正确性的数据竞争区分开来。
- **检测器不能替代逻辑证明**：ASan、TSan、UBSan 只能监控测试实际跑过的那几条交错路径，“Sanitizer 没报错”绝不等于并发与所有权设计没漏洞；改动核心算子与状态机时，必须补齐边界输入、受控并发交错乃至故障注入（Fault Injection）断言。
- **出事时必须留有破案线索**：新增错误分支有没有带上 `query_id`、Fragment/Instance 标识与明确的错误码？新执行路径有没有加对应的监控计数器？如果线上报错后连“事务到底提交了没有、能不能安全重试”都看不出来，这种可观测性缺失本身就足以拦下发布。

至于纯粹的变量命名微调、顺手的函数拆分或注释润色，统一标上 `Nit:` 即可（注释应优先解释“为什么存在这条反直觉的约束”，遗留待办关联具体 Issue）。把阻塞评论压缩成固定句式，沟通效率会高很多——例如：

> `[P0]` 触发取消后后台 I/O 回调仍可能并发执行；若外层查询上下文先一步析构，回调解引用成员指针将触发 Use-After-Free。请明确该状态的最后持有者与退出同步屏障，并补充受控交错下的取消测试。

## 三、当 Agent 接入研发流水线：把“自动执行”与“批准承担”拆开

理解了内核评审到底在防什么，再看 Agentic Engineering 该怎么落地，脉络就非常清晰了。把从规格定义、分钟级补丁生成、沙箱自动校验到人工合入签署的完整研发链摊开，就能看清吞吐瓶颈如何从编码端一路推向人类边界审查：

![Agentic Engineering 吞吐瓶颈迁移：Agent 分钟级合成补丁与单测，经隔离沙箱与 Sanitizer 过滤表层缺陷后，稀缺人工评审带宽集中守卫 SQL 等价、异步生命周期与落盘兼容等不可逆契约](/images/diagrams/gpu-agent-review-bottleneck.svg)

为什么不能因为 Agent 既能写代码又能写测试，就让它一条龙自动合入？

### 同源盲区与三权分立

设想你给 Agent 下了一条模糊指令：“把这个聚合查询优化得更快一点。”如果规格说明（Specification）没有明确界定输入输出契约、溢出行为、精度要求以及严禁改动的兼容边界，Agent 很可能会顺手跳过某层溢出检查或空值分支，写出一段跑得飞快的代码；紧接着，**当同一个 Agent 继续为这段代码编写单元测试时，它会共享完全相同的错误假设**，写出一组恰好避开溢出边界、全绿通过的测试用例！甚至在持续集成（Continuous Integration，CI）报错时，缺少约束的 Agent 还可能通过删掉失败断言、放宽误差阈值或跳过慢测试，把“把问题修好”偷换成“让红灯变绿”。

要打破这种同源相关性，研发流程里必须保留三项彼此独立的判断职责（小团队可以由同一人兼任，但三次判断一步都不能省）：

1. **规格负责人（Spec Owner）**：在动手前钉死输入输出、非目标、兼容约束与验收标准，明确允许优化什么、绝不允许改变什么；
2. **意图审阅者（Reviewer of Intent）**：脱离 Agent 自带的漂亮摘要，直接对照原始规格、代码差异与独立反例，核查实现有没有偏离意图或弱化既有测试；
3. **风险负责人（Owner of Risk）**：结合目标分支保护、灰度范围、监控与回滚方案，决定残余风险是否满足合入与生产部署条件——尤其要区分“批准代码合入”与“授权生产发布”。

[DORA 2025 报告](https://dora.dev/research/2025/dora-report/)把 AI 准确地定性为组织既有工程能力的**放大器**：测试底座扎实、批次小、权限边界清晰的团队，引入 Agent 会如虎添翼；反之，如果本身缺乏回归防线与变更治理，Agent 只会以十倍速制造技术债。

### Agentic CI 的沙箱隔离与防注入门禁

目前主流的工程化智能体都在围绕 CI 建立受控闭环。例如 GitHub 在 [Copilot coding agent 发布文章](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)中展示了将 Issue 委派给 Agent 后，它在 GitHub Actions 环境中拉起草稿 PR 并附带完整会话日志，同时保留分支保护，要求人工批准后才运行 CI/CD 工作流，优先瞄准测试完备的中低复杂度任务；Cognition 在 [Devin 发布介绍](https://cognition.ai/blog/introducing-devin)中构建了自带 Shell、编辑器和浏览器的独立沙箱（Sandbox），跑通验证后交给人审阅；Anthropic 的 [Claude Code GitHub Actions](https://docs.anthropic.com/en/docs/claude-code/github-actions) 则支持把智能体直接嵌进团队自有的 CI 基础设施里。

把这些工具真正放进生产仓库组成 **Agentic CI** 时，最核心的安全底线是**最小权限隔离**：

- **权限绝不连坐**：“在沙箱里跑编译单测”“修改 `.github/workflows` 流水线定义”“读取生产密钥”与“触发制品发布”，绝不能因为同属一个修复任务就共用同一套令牌。
- **审批绑定具体版本与差异**：人工点击批准运行工作流时，必须看清即将执行的是哪次提交、动没动过工作流脚本、会接触哪些凭据。对上一个 Commit 的授权绝不能自动延续到后续追加的高权限改动上。
- **防范提示词注入（Prompt Injection）**：Agent 在排查问题时会读取外部 Issue、第三方代码注释、报错日志甚至网页内容，攻击者完全可以在里面夹带诱导越权的隐藏指令。只有把外部输入一律视为不可信数据、从宿主与平台侧硬性锁死工具网络与凭据边界，才能兜住底线——指望“再加一个审查 Agent 帮忙盯着”，无法消除共享同一上下文带来的连带失守。

### 当写代码不再耗时：警惕队列拥塞、Slop 与评审疲劳

Cursor 在宣布 [Graphite 加入的公告](https://cursor.com/blog/graphite)中点出了一个全行业正在共同面对的转向：当写代码越来越快，审查变更、安全合入与多人协作正迅速成为新的主瓶颈。

从排队论看这再自然不过：如果上游往评审队列灌入 PR 的速率翻了三倍，而且混杂着大量“外观工整、废话连篇却毫无实质证明力”的低质生成代码（Slop）——比如过度设计的无用抽象层、复制粘贴的冗余测试、动辄上千字的套话 PR 描述——下游审阅者的注意力很快就会被耗干，陷入严重的**评审疲劳（Review Fatigue）**。

治理评审疲劳不能靠催审阅者“看快一点”，而要从源头收紧准入与信噪比：限制单次委派给 Agent 的任务范围与改动批量，要求关键分支必须附带不变量解释与反证测试；同时严格收敛 AI 辅助审阅工具的告警规则，宁可少报几条风格建议，也绝不让高频低价值的噪音淹没真正的 P0 隐患。衡量这套体系健不健康，看的不是“AI 生成了多少万行代码”或“每周多合了几个 PR”，而是**首次响应时延、因意图偏差导致的返工率、工具误报处理成本，以及最终漏到线上的真实缺陷数**。

把这套源头限流与复盘演进串成闭环，每一次高可信的 Agentic PR 交付都遵循“先锁契约、再拆垂直小切片、附可执行证据提审、最后把漏检教训固化进 `AGENTS.md` 与静态规则”的状态流转：

![高可信 Agentic PR 切片与知识沉淀闭环：从冻结规格契约、拆解可独立回滚的垂直切片、附带沙箱可执行验证证据，到人工审查所有权边界并将漏检规则固化至 AGENTS.md](/images/diagrams/gpu-agent-pr-slicing-loop.svg)

市面上围绕编码与评审的 AI 工具演进极快，有的从沙箱往 IDE 延伸，有的从编辑器往 PR 协作延伸，还有的专攻代码审查或端到端流水线。把各家的公开产品形态与收费方式摆到同一张桌子上，最值得工程负责人追问的其实是最后一列——**谁来为没测出来的风险买单**：

从商业演进的角度看，这几类工具正在试探三种不同的计费锚点，而每一种都对应着特定的工程张力：

- **席位定价（Seat-Based Pricing）**最符合传统研发财务预算，但当一名资深工程师同时调度十个后台 Agent 并发提 PR 时，人类席位数与实际产生的算力及评审工作量就会彻底脱钩。
- **用量定价（Usage-Based Pricing）**顺应了一人驱动多 Agent 的现实，却把“Agent 陷入死循环反复重跑 CI”的账单波动直接暴露给了研发团队，迫使工程侧加上严格的预算熔断与任务粒度控制。
- 至于业界常讨论的**按结果定价（Outcome-Based Pricing）**，一落到软件工程深水区就会撞上度量难题：如果按“成功合并的 PR 数”收费，无异于鼓励把一个完整功能拆成十个琐碎补丁；如果按“功能验收上线”收费，需求变更、半年后才暴露的并发死锁以及线上环境差异又根本无法在厂商与客户之间划清责任。

换句话说，无论外部工具把入口放在 IDE、GitHub 还是独立沙箱里，也无论它按人头还是按 Token 收钱，**最终对主干代码质量与生产稳定性签字背书的权力，永远只能留在研发组织自己的治理体系里**。选型时与其轻信宣传页上的通用准确率，不如拉出自己仓库里历史上最棘手的二十个真实历史 PR（包含优化器等价性漏判、异步生命周期崩溃和存储兼容问题），实测工具的有效召回率、误报噪音以及全流程耗时。

## 五、实战检验：15 个经得起连续追问的面试与复盘问题

无论是技术面试考察候选人的工程成熟度，还是团队内部对齐评审文化，泛泛空谈“我很重视代码质量”没有任何区分度。真正能试出深浅的，是把具体场景推到两步追问之后，看对方如何权衡契约、证据与风险。

### 常规协作机制：标准、拆分与冲突收敛

- **Q1：拿到一个 PR 你先看什么？CI 全绿就能点 Approve 吗？**
  - **核心判断**：先看变更意图、目标分支和测试用例设计，再看接口与状态所有权边界，最后看局部实现。CI 全绿只证明“测试实际覆盖且写了断言的那几条路径没挂”，像 `NULL` 语义边界、异步析构竞态、跨版本格式兼容和无界内存增长，依然需要审阅者主动推演。
  - **进阶追问**：*如果只觉得某个分支可疑，手头一时构造不出必现反例，拦不拦？* —— 如果是写出不可逆存储格式或核心正确性路径，先明确指出哪条前置条件未经证明并阻塞求证；如果是可隔离的新特性，可要求加上默认关闭的开关、监控断言与安全退出条件后再合入。

- **Q2：遇到上千行的大 PR 应该怎么拆？为什么不能简单按文件拆？**
  - **核心判断**：沿着可独立验证的“语义契约”拆——第一步加兼容接口与读取逻辑，第二步接新实现并保持默认关闭做验证，第三步切换默认开关并清理旧代码。每一跳都必须能独立编译、跑通测试并安全回滚。
  - **进阶追问**：*按目录或文件拆成五个小 PR 不行吗？* —— 物理文件边界不等于运行时的状态一致性边界；如果拆出来的中间提交处于“新格式已写出、读取端还没合入”的半残状态，表面看每个 PR 都很短，实际上却无法独立部署和定位回归。

- **Q3：代码作者比你资深得多，你们对某处并发风险僵持不下，怎么处理？**
  - **核心判断**：把个人直觉改写成客观的四要素——具体触发交错、违反的不变量、潜在后果和验证办法，严格区分 P0 阻塞与非阻塞建议。评论往返两轮仍未收敛时，立刻约 15 分钟同步白板推演，再把达成一致的技术依据补记回 PR。
  - **进阶追问**：*如果对方回答“这段逻辑线上跑了一年都没出过事”呢？* —— 线上未触发崩溃不代表低概率竞态不存在（尤其在负载放大或线程池调度变化后）；但同时也要反查自己是不是漏看了上层调用方已经持有的锁或单线程派发保证，谁能拿出闭环证据听谁的。

- **Q4：团队抱怨 Code Review 拖慢了迭代速度，你怎么诊断并证明改进有效？**
  - **核心判断**：先把耗时拆开，看时间到底卡在“排队等首次响应”“PR 太大看不懂”还是“需求没对齐反复返工”。针对排队慢做自动分流与小批量规范，针对低级问题把格式、静态检查与 Sanitizer 前移到 CI；评估效果时必须把**首次响应时延、返工轮次与线上漏出缺陷率**绑在一起看，绝不能靠放水换取虚假的合入速度。

- **Q5：怎么通过日常 Code Review 带新人成长，而不是把人审成“照着评论改代码的机器”？**
  - **核心判断**：评论里不只写“改成 X”，更要讲清“原写法在什么边界下会踩中什么机制问题”；同时鼓励新人去审阅资深成员的 PR（允许他们通过提问来审阅）。怎么检验新人真懂了？看他在下一次同类改动里能否主动交代所有权、反例边界和测试覆盖，而不是只看这次有没有听话改完。

- **Q6：线上出了故障，复盘发现问题代码当初经过了两人 Review 却漏掉了，怎么改进？**
  - **核心判断**：拒绝“下次大家看仔细点”这种无效口号。回头核对当时的规格说明、补丁规模、测试断言和审阅分工，判断这类缺陷能不能下沉为编译器约束、类型系统封装、ASan/TSan 检测或故障注入测试。如果 Checklist 里早就写了这一条却依然漏掉，往往说明清单太抽象或单次 PR 改动太大超出了人类心智负荷，该改的是工程防线与批次大小。

### 数据库内核深水区：从一行局部改动推演系统后果

- **Q7：优化器新增了一条等价改写规则，TPC-H 和现有回归集全绿，为什么还可能不能合？**
  - **核心判断**：通用基准测试远不能穷尽 SQL 角落语义。必须专门核查空集、`NULL` 三值逻辑、外连接补 `NULL` 顺序、重复行多重集语义以及相关子查询去关联条件；同时检查多条规则组合触发时会不会死循环，以及统计信息失真时新执行计划会不会发生灾难性退化（可结合前文 `LEFT JOIN ... WHERE r.v = 1` 的反例具体展开）。

- **Q8：C++ 查询取消路径已经全用智能指针和 RAII 封装了，为什么还会有内存与崩溃隐患？**
  - **核心判断**：RAII 只管析构时的动作，不管析构何时发生。异步回调捕获裸 `this` 会因“发出取消不等于回调退出”引发悬空解引用；全换成 `shared_ptr` 又可能产生循环引用，或者让卡死的慢后台任务长期续命算子大对象，导致查询早已报错返回、内存配额却迟迟无法释放，甚至在同步等待退出时诱发线程池死锁。

- **Q9：新存储落盘格式上线后发现边缘 Bug，把配置开关关掉或者回滚二进制版本就安全了吗？**
  - **核心判断**：关开关只能阻止后续继续写出新格式，救不了已经持久化在磁盘上的增量文件；如果直接把二进制回滚到不认识新格式的旧版本，节点重启恢复或后台 Compaction 读到这批文件时反而会直接崩溃。上线前必须分别验证向前/向后读写兼容、元数据发布崩溃切点以及孤儿文件回收条件。

- **Q10：分布式事务或导入 RPC 超时了，客户端能直接当作失败给用户报错或无脑重试吗？**
  - **核心判断**：网络超时属于典型的状态未知（Indeterminate）——请求可能丢在半路，也可能服务端早已提交成功只是回包丢了。直接报错会造成客户端与服务端状态分裂；安全重试则要求请求携带稳定的幂等标识，且服务端的去重账本能跨重启和切主（Leader 切换）存活，并与去重记录的垃圾回收窗口严格对齐。

- **Q11：AI 帮手重写了一段列式算子的向量化循环，微基准快了 40%，单测也绿了，能直接合吗？**
  - **核心判断**：先查正确性死角——`Nullable` 位图、`Const` 列广播、空批次（0 行）、整数溢出与非对齐尾部元素（Tail Processing）是否全覆盖；再放到完整查询里看真实收益，记录高倾斜数据、高比例 `NULL`、并发争用下的内存峰值、总吞吐与 P99 尾延迟，排除“局部算得快、整体卡在内存带宽上”的假象。

### Agentic Engineering 治理：审什么、准许什么、谁担责

- **Q12：业务实现和配套单元测试都是同一个 Agent 一次性生成的，Review 时怎么破局？**
  - **核心判断**：绝不顺着 Agent 的测试思路走，而是回到原始规格说明，反向检查“如果实现写错了，这套测试能不能把它抓出来”。亲手构造一组独立反例（如边界值、异常中断交错）或对照参考实现，重点审视被 Agent 悄悄绕开的异常分支。哪怕引入第二个 Agent 交叉审查，只要它们共用同一份含糊规格或直接读取前者的摘要，依然会掉进同一个假设盲区。

- **Q13：Agent 自动读了 CI 报错日志并推送了修复 Commit，能不能配成“CI 变绿就自动合入”？**
  - **核心判断**：必须把“允许跑测试”“检查通过”和“批准合入主干”拆成三道独立关卡。尤其当 Agent 的补丁触碰了构建脚本、测试断言或 `.github/workflows` 时，必须人工先审它是不是靠注释断言、放宽阈值或申请更高凭据“混”过的绿灯，确认无越权副作用后才能放行对应 Commit 的流水线。

- **Q14：引入编码 Agent 后团队周均 PR 数暴涨，核心 Reviewer 已经彻底看不过来了，怎么治？**
  - **核心判断**：靠“再堆几个 AI Reviewer 刷评论”只会火上浇油。治本之策是在入口处限流提质：收紧单次任务的范围与批次上限，强制要求 PR 附带关键不变量证明与有效测试，用确定性静态规则过滤掉低价值告警；同时盯紧等待时长、返工原因与漏出缺陷，把规格定义、意图核验和风险签署的责任落实到具体的人。

### 复盘真实经历：如何准备经得起刨根问底的案例？

- **Q15：请讲一次你在 Code Review 中发现关键隐患、推动方案修改的真实经历。**

回答这类经历题最忌讳两件事：一是把集体讨论说成自己“力挽狂澜避免重大事故”的夸张叙事；二是只背概念、一被追问“当时是哪个版本、哪条评论是你写的、后来补了什么测试”就卡壳。平时复盘自己参与过的真实内核评审（例如本博客此前拆解过的[外连接下的 Dynamic Filter 推导](/2026/08/24/dynamic-filter-through-outer-join/)或 [StarRocks Optimizer 规则演进](/2026/09/01/dive-starrocks-optimizer/)这类优化器与执行器机制问题），最稳妥的办法是按下面这条**七步证据链**把真实细节留存下来：

1. **背景与基线版本**：当时的改动目标是什么，涉及哪条执行或存储路径？
2. **本人的真实角色**：你是主审 Committer、模块协作者，还是只负责审查其中并发/优化器子模块？
3. **原方案依赖的隐含假设**：作者原本以为哪条不变量天然成立（例如默认外连接某侧不会补 `NULL`、或者默认微基准收益能线性外推到全查询）？
4. **定位到的触发条件与反例**：你构造了怎样的具体 SQL 输入、并发交错时序或性能剖析火焰图，证伪了原假设？
5. **收敛后的修订方案**：最终是收紧了规则前置条件、改了所有权模型、加了开关隔离，还是打回重做设计？
6. **落地的验证断言**：补了哪些端到端结果断言、Sanitizer 用例或 TPC-H/SSB 对比数据？
7. **坦诚保留的残余边界**：合入时还有哪些极端负载或跨版本场景暂未覆盖，靠什么监控或开关兜底？

反过来，当你在面试尾声反问对方团队时，与其问“你们平时用不用 AI 写代码”，不如直接问这五个问题：**团队日常 PR 的规模与首次响应时延大概在什么区间？架构设计评审与最终合入权怎么衔接？编码 Agent 目前被允许接触哪些 CI 权限？高权限工作流变更由谁审批？引入自动评审工具后的误报噪音由谁负责治理？** 对方的回答越具体，越能看清这家团队的工程底座究竟扎不扎实。

说到底，工具越聪明、生成代码的速度越快，系统工程师手里那把衡量“契约、状态与恢复边界”的尺子就越值钱。先从边界清晰、易于隔离验证的任务开始让 Agent 交付补丁与测试记录，同时把 SQL 语义、异步生命周期、持久化兼容与发布风险牢牢留在人类的证据审查之下——这才是既吃透 AI 效率红利、又不把生产系统变成赌场的工程正道。
