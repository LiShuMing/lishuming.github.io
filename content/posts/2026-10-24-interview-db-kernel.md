读者是在线分析处理（Online Analytical Processing，OLAP）数据库内核，以及可能转向人工智能基础设施（AI Infrastructure）的高级工程师、资深工程师（Staff Engineer）、技术负责人（Tech Lead）候选人。Kevin Li 的 StarRocks / MaxCompute 背景决定选材优先级，但本文没有把他的任何未公开实现写成事实；需要个人证据的位置统一使用【模板】。

## 一、优化器：先证明等价，再比较代价

### 1. 逻辑等价与物理代价为什么必须拆开？

**题目**：“优化器把谓词下推到 Scan，为什么有时正确、有时错误？你如何向面试官证明这次改写是等价的？”

**强答要点**：先声明改写的输入输出关系是否保持同一多重集语义（或多集基数、空值与列顺序约定），再讨论代价。谓词下推（Predicate Pushdown）在内连接（Inner Join）上通常安全；一旦出现外连接（Outer Join）、反连接（Anti Join）、窗口函数分区边界或非确定性函数，就必须证明谓词是空值拒绝（Null-Rejecting）的，以及它落在保留侧还是空值供给侧。

【事实】生产 Cascades 路径会把逻辑扩展、物理实现与 Enforcer（如 Exchange/Sort）放进同一代价闭环；教学实现若只有单个 Winner、未接入物理属性，就不能声称已覆盖分布式排序与分布联合选择。对照 [optd Cascades 源码剖析](/2026/09/01/dive-optd-cascades-optimizer/) 与 [StarRocks Optimizer：Property 与 Enforcer](/2026/09/01/dive-starrocks-optimizer/)。

【推断】面试回答应显式给出：(1) 改写前后的关系代数或算子树；(2) 一条使语义变化的反例 SQL；(3) 用什么测试或断言挡住该反例。没有反例的“一般都能下推”不能作为 Staff 答案。

**追问链**：

1. 第一层：“`WHERE coalesce(t2.x, 0) > 0` 能否下推过 `t1 LEFT JOIN t2`？”答：该谓词拒绝 `t2.x` 为 NULL 的补行，可能把外连接变成内连接语义，通常不能直接下推到 null-supplying 侧。
2. 第二层：“代价模型显示下推后更便宜，是否足以合入？”答：代价只在等价成立后才有意义；不等价的便宜计划是错误计划。
3. 第三层：“规则在单测通过，线上某客户计划回归，你查什么？”答：统计信息、约束（非空/外键）、会话选项、以及规则准入条件是否依赖这些元数据。

**常见差答／陷阱**：“外连接也能随便下推”“CBO 选出来的一定对”“加了单元测试就等价”。单元测试覆盖的是已想到的形状，不等价于语义证明。

### 2. Cascades / Memo 与 System R 式动态规划差在哪里？

**题目**：“用一分钟说明 Cascades 相对经典 System R 自底向上动态规划（Dynamic Programming，DP）多解决了什么问题？”

**强答要点**：System R 风格 DP 主要在固定算子集合上按连接顺序枚举并复用子问题最优解。Cascades 用备忘录（Memo）把逻辑等价类（Group）与组内表达式（Group Expression）分开，让规则探索与物理实现交错发生，并用当前最优代价做分支限界（Branch-and-Bound）。父节点还可提出物理属性要求（分布、排序），子计划不满足时插入 Enforcer 并计入代价。

【事实】大规模连接顺序搜索在实践中常配合启发式或受限枚举；PostgreSQL 对超过阈值阈值的连接使用遗传查询优化器（Genetic Query Optimizer，GEQO），见 [PostgreSQL GEQO 文档](https://www.postgresql.org/docs/current/geqo-intro.html)。[Leis 等人 PVLDB 2015《How Good Are Query Optimizers, Really?》](https://www.vldb.org/pvldb/vol9/p204-leis.pdf) 用真实基数误差展示：代价模型与基数估计的偏差往往比“枚举算法名词”更能解释计划质量。

【推断】Staff 回答应能指出：搜索空间、剪枝上界、超时降级策略各自决定什么；“我们用了 Cascades”本身不是证据。

**追问链**：

1. 第一层：“同一个 Group 为什么可能有多个 Winner？”答：不同 Required Property 对应不同最优物理计划。
2. 第二层：“规划超时后怎么保证还能给出可执行计划？”答：保留当前上界、启发式初始计划或阶段降级；需说明是否可能返回次优但语义正确的计划。
3. 第三层：“统计信息过期时，你更信任规则还是代价？”答：给出具体负载下的验证方法（A/B、回放、强制 hint）与回退开关，而不是抽象站队。

**常见差答／陷阱**：把 Memo 说成“缓存 SQL 文本”；声称遗传算法一定优于 DP；用“工业界都用 Cascades”回避基数误差。

### 3. 空值拒绝谓词与外连接：Dynamic Filter 能不能穿？

**题目**：“父 Join 的 Runtime Filter / Dynamic Filter 能否穿过下层 Outer Join？你的判据是什么？”

**强答要点**：分开讨论**生成**与**穿越**。Filter 只能无假阴性地缩小 Probe 集合；一旦 Outer Join 改变匹配状态并补 NULL，上层谓词若依赖这些补行，穿越就可能改语义。典型反例是对补 NULL 仍为真或仍可通过的表达式（如某些 `coalesce` / `IS NOT DISTINCT FROM` 组合）。

【事实】工程对照与统一判据见已发表笔记 [Dynamic Filter 穿越 Outer Join](/2026/08/24/dynamic-filter-through-outer-join/)：生成侧通常不当自己的保留侧 Producer；穿越要求落到保留侧后再有向派生，并显式处理 Null-Safe 等值。

**追问链**：

1. 第一层：“Inner Join 上 DF 的正确性条件是什么？”答：Build 摘要可有假阳性、不可有假阴性（对等值过滤语义而言）。
2. 第二层：“Left Join 的保留侧与 null-supplying 侧，谁可以接收父 DF？”答：先画保留/供给，再套判据表，不背系统名。
3. 第三层：“如何写回归？”答：构造补 NULL 行仍能通过上层谓词的最小 SQL，断言结果集基数与具体行。

**常见差答／陷阱**：“过滤越多越正确”“某引擎下推更深所以更优”。深度不是正确性指标。

### 4. Join Reorder：何时穷举，何时启发式？

**题目**：“十表连接还要不要做完整动态规划？你怎么向业务解释偶尔的坏计划？”

**强答要点**：连接数、图形状（链式 / 星型 / 环）、是否有外连接与谓词依赖，共同决定搜索策略。穷举 DP 在表数上升时组合爆炸；贪婪、GOO 类启发式或 GEQO 用可接受的次优换规划时延。坏计划的对外解释应落到基数估计、相关谓词、数据倾斜与超时降级，而不是“优化器随机”。

【事实】[Neumann & Radke, PVLDB 2018《Adaptive Optimization of Very Large Join Queries》](https://www.vldb.org/pvldb/vol11/p1573-neumann.pdf) 讨论超大连接查询的自适应优化思路；与 [Leis et al. 2015](https://www.vldb.org/pvldb/vol9/p204-leis.pdf) 一并说明：枚举能力不等于真实基数下的最优。

**追问链**：

1. 第一层：“星型模型为何常比环状好搜？”答：维度表选择性与 FK 结构可大幅剪枝。
2. 第二层：“外连接顺序能自由交换吗？”答：一般不能；关联与空值生成顺序受语义约束。
3. 第三层：“线上强制 hint 后变快，说明什么？”答：说明估计或搜索在该形状失败；下一步是固化统计 / 改写 / 限制定时器，而不是永久人工 hint 神话。

**常见差答／陷阱**：断言“我们永远最优”；把一次 TPC-H 数字当成所有客户负载。

### 5. 查询改写与 MV Matching：匹配成功不等于可以透明替换

**题目**：“优化器把查询改写到物化视图上，你如何证明结果仍正确？哪些情况必须拒绝改写？”

**强答要点**：改写要同时满足结构匹配（Join / Grouping / 输出列）、补偿谓词可推导、聚合滚上（roll-up）合法，以及新鲜度（Freshness）策略允许。视图定义含非确定性函数、不完全覆盖的 WHERE、外连接方向不一致、或刷新尚未追上查询所需快照时，应拒绝或走 query-time 校验路径。

【推断】面试应准备一张“可改写 / 不可改写”对照表，每条配最小 SQL。Staff 还会说明：改写失败时的可观察指标（候选 MV 数、拒绝原因码）如何用于产品化。

**追问链**：

1. 第一层：“`COUNT(*)` 的 MV 能否回答带额外 WHERE 的查询？”答：仅当过滤可下推到保存的明细粒度或存在可补偿结构。
2. 第二层：“基表刚写入，MV 延迟 2 分钟，查询要不要用 MV？”答：由会话一致性 / 最大陈旧时间 SLA 决定，不是优化器单方面决定。
3. 第三层：“改写后计划更贵，还会选吗？”答：代价比较应包含扫描 MV 与扫基表；若规则强制改写，需说明产品优先级。

**常见差答／陷阱**：“命中 MV 一定更快”“刷新成功就语义正确”。刷新成功只说明维护路径完成，不说明与任意查询快照对齐。


### 5b. 基数估计错了，代价模型还可信吗？

**题目**：“直方图、抽样与上界方法各解决什么？相关谓词为什么经常把计划打崩？”

**强答要点**：代价是在估计基数上的相对比较。单列直方图对独立假设友好；列相关、连接跨列相关会系统性低估或高估。抽样受倾斜影响；上界/稳健优化在最坏情况与平均情况之间取舍。面试官要听的是：你如何发现估计误差、如何用反馈或强制统计修复，而不是背公式。

【事实】[Leis et al., PVLDB 2015](https://www.vldb.org/pvldb/vol9/p204-leis.pdf) 表明真实负载中基数误差可跨数量级，且对计划质量影响往往大于枚举算法差异。后续工作继续讨论何时需要自适应或端到端学习估计，但生产合入仍要可回退。

**追问链**：

1. 第一层：“两个谓词 `AND` 时为何不能直接乘选择率？”答：独立性假设常不成立。
2. 第二层：“连接后基数如何估计？”答：基于 FK/唯一性、直方图拼配或采样；说明失败时的保守策略。
3. 第三层：“学习型优化器何时不该上？”答：可解释性、冷启动、漂移、与确定性回归的冲突。

**常见差答／陷阱**：把代价数字的绝对值当成物理时间；否认相关谓词。

### 5c. 物理属性：排序、分布与 Enforcer 成本

**题目**：“为什么‘同一个 Group 的最优计划’这句话在分布式优化器里不完备？”

**强答要点**：父算子可能要求孩子按某键排序或按某方式分布。孩子局部最优若不满足属性，需要 Exchange/Sort 等 Enforcer，其成本必须计入。缺少属性维度的 Winner 表会漏掉全局更优组合。详见 [StarRocks Optimizer 笔记](/2026/09/01/dive-starrocks-optimizer/)。

**追问链**：

1. 第一层：“Hash 分布与 Range 分布各利哪类操作？”答：等值连接 vs 范围/有序聚合等。
2. 第二层：“CTE 物化与属性传递如何互相影响？”答：物化点改变可复用属性与重复计算权衡。
3. 第三层：“Enforcer 插入位置错误的症状？”答：多余 Shuffle、重复排序、或错误地假设有序。

**常见差答／陷阱**：只比较算子 CPU 忽略网络；认为排序属性可以“事后再说”。


## 二、向量化执行与 SIMD：批处理赚的是解释开销，不是魔法倍数

### 6. 为什么向量化，而不是一次一行？

**题目**：“解释向量化执行（Vectorized Execution）相对火山模型一次一行（Tuple-at-a-Time）的收益来自哪里？什么时候收益消失？”

**强答要点**：收益主要来自减少虚调用与解释开销、提高指令与数据局部性、让编译器/SIMD 有机会作用在紧凑循环上。批大小（如数百到数千行）是缓存与流水线的折中。当表达式极简单且数据已在缓存，或当每行都要做复杂字典解码、大量分支、宽行物化时，向量化优势会缩小甚至被物化成本抵消。

【事实】列式分析引擎普遍以批 / 块为接口；具体批大小与算子融合（Operator Fusion）策略因系统而异，不能把某一博客的加速比当成通用常数。

【推断】回答中应主动区分：解释开销下降、缓存命中、SIMD、多核流水线四类来源；面试官追问“你们最快多少倍”时，回到负载与剖析证据，而不是背数字。

**追问链**：

1. 第一层：“批太大会怎样？”答：缓存失效、延迟尾部变差、内存峰值上升。
2. 第二层：“选型选算子间物化还是流水线融合？”答：融合减物化，但增大寄存器压力与代码生成复杂度。
3. 第三层：“如何证明某算子慢在解释而非 I/O？”答：CPU 剖析、CPI、缓存未命中、与 Scan 等待时间对比。

**常见差答／陷阱**：“上了 SIMD 就十倍”“向量化等于编译执行”。编译执行（JIT）与向量化解释是不同轴。

### 7. SIMD 何时值得写？Null 位图与字典编码怎么干扰？

**题目**：“给过滤算子加 AVX2/AVX-512 有没有必要？Null 与字典列怎么处理？”

**强答要点**：先测量标量紧凑循环是否已受限于内存带宽。SIMD 对均匀、无分支、定长类型最友好；Null 位图强制掩码合流，字典编码可能先解码再比较或在字典空间比较。错误的“先解码成行存再 SIMD”可能比标量列式更慢。

【推断】Staff 应能讲清：剩余谓词、选择率、是否可延迟物化（Late Materialization）。没有剖析的 SIMD 补丁在评审里应被要求补基准与正确性（对齐、尾块、页面边界）。

**追问链**：

1. 第一层：“选择率极低时 SIMD 过滤仍有用吗？”答：可能；但更应考虑下推、索引、zonemap / 统计跳过。
2. 第二层：“变长字符串怎么 SIMD？”答：通常先固定长度化、结束符扫描或自动机；很多路径保持标量。
3. 第三层：“补丁在开发机快、客户机慢？”答：核对指令集降级、频率墙、NUMA、以及数据编码是否一致。

**常见差答／陷阱**：用合成全非空 int32 基准推广到生产宽表；忽略尾部不足一个向量的标量收尾。

## 三、物化视图、IVM 与 Dynamic Table：增量是能力，也是状态债务

### 8. 增量维护的代数直觉与非单调算子

**题目**：“用 Join 的 delta 公式说明为什么多表增量会‘状态爆炸’？哪些算子让你倾向全量重算？”

**强答要点**：对视图 \(V=Q(DB)\)，增量维护试图用 \(\Delta DB\) 计算 \(\Delta V\)。选择/投影等较易线性化；Join 展开为 \(\Delta R \bowtie S\)、\(R \bowtie \Delta S\) 与高阶交叉项，多表时中间状态急剧变大。`MIN`/`MAX`/`COUNT DISTINCT`/部分窗口函数等非单调算子在撤回（Retraction）时可能需要历史细节，空间换时间或退回分区全量。

【事实】工业界常见产品化形态是：声明新鲜度目标 + 自动调度刷新 + 有限算子覆盖。Snowflake 文档描述 Dynamic Table 以目标延迟等参数管理刷新，见 [About dynamic tables](https://docs.snowflake.com/en/user-guide/dynamic-tables-about)。Databricks 文档将物化视图与 Delta Live Tables / 声明式流水线关联，见 [Delta Live Tables](https://docs.databricks.com/aws/en/dlt/)。具体算子矩阵以各云当前文档为准，面试时应声明阅读日期。

【推断】xlab IVM 调研中的竞品对照可作阅读线索，但其中未核对的版本号与 Issue 进展不得直接写成【事实】。对 StarRocks，可公开讨论的产品概念是异步 MV、分区变更追踪（Partition Change Tracking，PCT）等文档化能力；行级 IVM 是否落地要以当时版本发行说明为准。

**追问链**：

1. 第一层：“只有 INSERT 的 append-only 流水线，哪些聚合可以安全增量？”答：如 SUM/COUNT 等可交换聚合；注意 NULL 与溢出。
2. 第二层：“来了一条 DELETE，MAX 怎么维护？”答：保留多重集 / Top-k 结构，或标记失效后重算该组。
3. 第三层：“DAG 上多个 MV 刷新不等时，用户读到什么一致性？”答：定义新鲜度 SLA、是否快照对齐、跨表读是否允许混版本。

**常见差答／陷阱**：“IVM 总是比全量便宜”“流式系统没有一致性问题”。增量省的是平均代价，最坏情况与状态存储往往更贵。

### 9. 查询时用 MV 的正确性与运维接口

**题目**：“客户投诉‘改写到 MV 后结果旧了’，你如何分层排查？”

**强答要点**：分层： (1) 改写是否在语义上合法；(2) MV 刷新水位与表快照；(3) 会话要求的一致性；(4) 分区部分就绪时的可见性；(5) 是否存在 query-time 回退扫基表。把“旧”说成优化器 bug 之前，先拿出刷新任务状态与版本号。

**【模板】**：案例〔项目〕；暴露的 SLA〔填写〕；水位落后原因〔填写〕；本人改动〔检测 / 拒绝改写 / 调度〕；验证〔填写〕；未覆盖〔填写〕。

**追问链**：

1. 第一层：“如何向用户解释 TARGET_LAG / interval？”答：用最大可接受陈旧时间，而不是“实时”。
2. 第二层：“刷新失败会不会继续提供旧数据？”答：产品策略：失败开放旧数据、失败即不可用、或混合。
3. 第三层：“如何防止错误 MV 定义进入生产？”答：创建时检查、刷新试跑、改写金丝雀、血缘与权限。

**常见差答／陷阱**：只调大刷新频率；不测量状态存储成本就承诺秒级全面增量。

## 四、存算分离：计算节点“无状态”仍拥有什么？

### 10. 缓存、粘滞与冷启动

**题目**：“存算分离（Disaggregated Storage and Compute）之后，计算节点宕机会丢数据吗？会丢什么？”

**强答要点**：持久数据在共享存储；计算节点仍拥有：内存缓存、临时溢写、执行中算子状态、锁/租约、本地计划缓存与连接。宕机丢失的是未提交的中间态与缓存热度，不是已提交表数据——前提是写入路径的持久化语义被正确实现。

【事实】云数仓公开工程叙述常强调多计算集群共享一份存储、弹性扩缩；例如 Amazon Redshift 的演进讨论见 [arXiv:2212.03970](https://arxiv.org/abs/2212.03970)。具体产品保证以官方文档为准，不能把论文架构图当成所有引擎的行为。

**追问链**：

1. 第一层：“缓存一致性如何维护？”答：版本号 / 世代 / 租约；更新后如何让旧缓存失效。
2. 第二层：“粘滞调度（sticky assignment）的收益与风险？”答：收益是缓存命中；风险是热点与故障转移变慢。
3. 第三层：“冷启动为什么慢？你怎么验收扩容？”答：元数据加载、缓存填充、连接池、代码/JIT 预热；用分位数而非平均。

**常见差答／陷阱**：“计算完全无状态所以随便杀”“存算分离等于没有本地盘”。溢写与操作系统页缓存仍影响性能与故障模式。


## 四（续）、执行层还要能讲清的连接与倾斜

### 10b. Hash Join、Shuffle 与倾斜

**题目**：“Build 侧远超内存时怎么办？数据倾斜时你如何证明该换计划而不是加机器？”

**强答要点**：先区分分区倾斜与值倾斜。Hash Join 在内存不足时溢写（Spill）；Shuffle Join / Broadcast Join 的选择应回到基数与网络代价，而不是“大表小表”口诀。倾斜时加机器可能放大 Shuffle 热点；更有效的是隔离热键、两阶段聚合、临时统计或强制分散。

【推断】用一次真实慢查询说明：热键占比、Spill 字节、网络等待与 CPU 占比。没有这三项，不建议谈“优化了 Join”。

**【模板】**：查询〔〕；原计划〔〕；热键证据〔〕；改写 / hint / 统计修复〔〕；结果分位数〔〕。

**追问链**：

1. 第一层：“Broadcast 的正确性条件？”答：被广播侧在该片段语义下可复制；外连接方向与空值仍要单独检查。
2. 第二层：“Spill 到本地盘与存算分离是否冲突？”答：临时状态仍可能本地化；节点丢失会重算该片段。
3. 第三层：“为何不用永远 Sort-Merge？”答：有序代价、延迟物化与选择率共同决定；有序输入可省排序但不能假设总存在。

**常见差答／陷阱**：只说“加并行度”；把 Spill 成功当成性能成功。

### 10c. 资源组、排队与取消

**题目**：“大查询占满集群，小查询饿死，你如何设计隔离？取消后内存何时可回收？”

**强答要点**：隔离维度包括 CPU、内存预留、并发槽位与扫描带宽。排队策略要公开可观测。取消必须能传播到远程片段并保证回调不再访问已释放批；否则会出现 use-after-free 式崩溃，这与 C++ 篇的生命周期题是同一类证据。

【推断】AI 推理服务的取消与 KV 缓存回收可以类比，但不能直接等同：模型状态语义不同。迁移叙事见系列第⑥篇。

**追问链**：

1. 第一层：“硬限与软限的差别？”答：硬限拒绝/杀死；软限降级或延后。
2. 第二层：“如何证明取消安全？”答：故障注入 + 地址消毒 / 生命周期断言。
3. 第三层：“多租户之间如何避免优先级反转？”答：预留、老化、避免持有关键锁时睡眠。

**常见差答／陷阱**：“杀掉会话就行”；不考虑远程 fragment 仍在写共享缓存。


## 五、湖仓与 Iceberg：表格式契约，不是执行引擎本身

### 11. 快照隔离与提交冲突

**题目**：“Iceberg 如何让读请求看到一致快照？两个作业同时改同一分区，谁赢？”

**强答要点**：读计划基于表元数据中的快照（Snapshot）；数据文件列表与删除文件在规划时确定，执行期通常不追逐并发写入者的最新提交。写路径通过原子提交元数据实现乐观并发；冲突粒度在分区/文件/删除向量等层，取决于操作类型与规格版本。

【事实】[Apache Iceberg 规格](https://iceberg.apache.org/spec/) 定义了快照、清单、分区演化与删除文件等概念。V3 用删除向量（Deletion Vector，DV）替代新写的位置删除（Position Delete）路径（equality delete 仍有独立规则）；**格式 v4 是否 formal adopt 必须以社区公开材料为准，本文不宣称已采纳**。细节笔记见草稿向 [Iceberg V3 DV 与 V4 进行中变更](/2026/10/18/iceberg-v3-dv-and-v4-wip/)（若仍为 draft，面试只引用规格已写明部分）。

**追问链**：

1. 第一层：“position delete 与 equality delete 的读代价差在哪？”答：位置删除指向文件内行；等值删除需按表达式匹配，规划与运行期代价不同。
2. 第二层：“DV 让删除更便宜后，并发语义有什么新风险？”答：冲突/合并粒度变化；不相交行更新仍可能在文件级冲突——以规格与实现为准。
3. 第三层：“引擎与湖格式版本倾斜时如何兼容？”答：读老写新、特性旗标、清单字段演进；混合版本集群的验收用例。

**常见差答／陷阱**：把 Iceberg 说成“另一种存储引擎”；声称“湖仓自动解决所有一致性”；把未采纳的 v4 提案写成现状。

### 12. 引擎读 Iceberg：规划期决策与运行期残余

**题目**：“规划时剪枝了 99% 文件，为什么执行仍可能很慢？”

**强答要点**：剩余文件的脚注删除、DV 合并、残余谓词、加密/压缩解码、对象存储尾延迟、以及运行期过滤都可能主导。规划剪枝是必要非充分。

**追问链**：

1. 第一层：“清单文件太多会怎样？”答：规划 CPU/RPC 成为瓶颈。
2. 第二层：“近实时写入下快照爆炸如何治理？”答：合并压缩、快照过期、水位与读写分离。
3. 第三层：“同一份表，Trino 与 Spark 结果不一致，你查什么？”答：时区、类型提升、读时点快照、未提交数据可见性、引擎各自的残留删行实现。

**常见差答／陷阱**：只优化执行算子，不看规划元数据路径。

## 六、分布式正确性：重试、幂等与版本倾斜

### 13. RPC 至少一次与幂等

**题目**：“后端执行 RPC 超时，前端重试，如何避免重复写入或重复计费式副作用？”

**强答要点**：网络常见至少一次（at-least-once）投递。幂等键、去重表、正好一次语义通过“至少一次 + 去重/事务状态机”逼近。查询只读路径也要考虑：重试是否重复扫描计费、是否重复取消、是否让同一请求附着两个查询 ID。

【推断】OLAP 写入（导入、刷新 MV、提交湖表）比只读 Scan 更需要显式幂等设计；面试应用一个真实导入/刷新例子画状态机。

**【模板】**：请求 ID〔填写〕；服务端去重状态存活期〔填写〕；超时与成功并发的处理〔填写〕；观测指标〔填写〕。

**追问链**：

1. 第一层：“谁生成幂等键？客户端还是服务端？”答：各有代价；关键是冲突检测窗口。
2. 第二层：“去重状态丢了会怎样？”答：可能双写；需存储级别的持久去重或可重收敛数据结构。
3. 第三层：“取消已发出的重试？”答：协作取消、世代号、服务端查询注册表。

**常见差答／陷阱**：“TCP 保证正好一次”“我们用了 Raft 所以业务幂等”。共识复制不等于业务操作幂等。

### 14. 版本倾斜：FE/BE、规划器/执行器、滚动升级

**题目**：“集群滚动升级时，新 FE 旧 BE 混跑，你最担心哪些不兼容？”

**强答要点**：序列化协议、计划片段字段、函数签名、分布方式枚举、错误码。需要：版本门闸、特性旗标、双读/双写窗口、以及“旧节点拒绝新计划”的明确错误而不是静默错结果。

【推断】与代码评审中的“混版兼容”检查同一条线：合入前问能否滚动，而不是只问单测是否绿。见 [代码评审与 Agentic 研发](/2026/10/24/code-review-series-index/)。

**追问链**：

1. 第一层：“向前兼容与向后兼容你保证哪边？”答：滚动方向决定；通常先升级能理解旧协议的节点。
2. 第二层：“遇到未知 plan node 怎么办？”答：失败要响亮；默认忽略会导致错结果。
3. 第三层：“如何设计兼容性测试？”答：N 与 N-1 混部矩阵、计划回放、导入/刷新烟测。

**常见差答／陷阱**：假设“protobuf 加字段永远兼容”；用生产集群当第一次混版实验。


### 12b. 元数据服务与规划延迟

**题目**：“湖上表分区上万，规划比执行还慢，你怎么拆？”

**强答要点**：规划路径上的 RPC、清单迭代、串行加锁与重复反序列化常被忽视。优化方向包括清单缓存、分区统计摘要、并行 listing、以及把部分剪枝下推到元数据过滤表达式。要用规划阶段火焰图，而不是只盯着 BE CPU。

**追问链**：

1. 第一层：“规划缓存的失效键是什么？”答：表版本 / 快照 ID / 会话时区与目录配置。
2. 第二层：“缓存击穿时如何保护元数据服务？”答：单飞（singleflight）、限流、降级扫描策略。
3. 第三层：“正确但过时的规划缓存会导致什么？”答：读到旧快照或错过新文件；必须绑定快照世代。

**常见差答／陷阱**：一上来改执行算子；用扩大超时掩盖规划算法问题。

### 14b. 导入 Exactly-once 与 EOS（End of Stream）

**题目**：“流式导入如何做到不重不丢？恰好一次是口号还是状态机？”

**强答要点**：端到端 exactly-once 通常由“可重放源 + 幂等汇 + 对齐检查点”组成。OLAP 侧要定义：事务标签、分区提交、失败重放窗口。EOS 标记与延迟数据（late data）策略要写进契约，否则“不丢”与“实时”互相打架。

【推断】可把检查点与 MV 刷新水位类比，但存储语义不同，不能共用一套故障故事。

**追问链**：

1. 第一层：“源端至少一次时，汇端如何去重？”答：主键 / 幂等键 / 序列号窗口。
2. 第二层：“检查点成功但下游未可见？”答：可见性与提交分离；读需等待发布。
3. 第三层：“迟到数据修正已发布聚合？”答：撤回、修订表或接受窗口外丢弃并度量。

**常见差答／陷阱**：把 Kafka offset 提交等同于表提交；忽略跨分区事务。


## 七、OLAP 语境下的事务与隔离：少谈写偏斜，多谈快照与新鲜度

### 15. 分析读需要哪种隔离？

**题目**：“OLAP 查询要不要可串行化？快照读够不够？”

**强答要点**：多数分析读需要的是点内一致快照：同一查询看到的基表/文件集合不中途换成另一提交。写偏斜、幻读等 OLTP 考题要会，但不是每天主导 OLAP 故障。真正高频的是：长查询与并发导入之间的快照选择、MV 与基表混读的新鲜度、以及湖表提交后多久对引擎可见。

【事实】MySQL InnoDB 的 MVCC / 隔离级别材料见 xlab `database-interview-questions.md`；它们证明你理解读写并发，但回答 OLAP 岗位时应主动切换到快照、分区与刷新 SLA。

**追问链**：

1. 第一层：“查询开始后导入提交，结果包不包含新数据？”答：取决于快照时点（语句开始 / 事务开始 / 引擎特定）。
2. 第二层：“两个查询是否需要彼此同一快照？”答：报表一致性需求；通常要额外协议。
3. 第三层：“OLAP 系统提供事务 API 的意义？”答：多语句脚本、流式摄入 exactly-once、元数据多表提交等；不是为了高竞争行锁。

**常见差答／陷阱**：把 RR/RC 背诵当作内核深度；否认分析系统存在一致性问题。

## 八、把机制回答变成可核验材料

### 16. 如何用一个项目贯穿优化、执行与维护？

**题目**：“请用同一条业务查询，串起优化器决定、执行瓶颈与 MV 策略。”

**强答要点**：【推断】选一条真实查询：展示改写前后计划、一次剖析火焰图、一次刷新/导入失败复盘。三层证据分别证明语义、性能与运维。避免三层各讲一个互不相关的故事。

**【模板】**：

| 字段 | 填写 |
|---|---|
| 查询 / 负载 | 〔〕 |
| 语义风险与反例 | 〔〕 |
| 计划关键决定 | 〔〕 |
| 执行瓶颈证据 | 〔〕 |
| MV / 湖表策略 | 〔〕 |
| 本人改动边界 | 〔〕 |
| 他人贡献 | 〔〕 |

**追问链**：

2. 第二层：“为什么不采用更简单方案？”给出代价与否决证据。
3. 第三层：“后任如何维护？”文档、开关、测试与告警。

**常见差答／陷阱**：用团队总加速替代个人贡献；只有设计 PPT 没有回放数据。
