## 一、先回答谁能运行，再讨论线程数量

### 1. 线程池扩容后，为什么吞吐不涨而长尾变差？

**题目**：一个扫描服务运行在容器内，增加工作线程后，主机中央处理器（Central Processing Unit，CPU）没有打满，请求第 99 百分位延迟（P99 Latency）却上升。如何区分调度、锁竞争和 I/O 等待？

**强答要点**：先确定容器实际可用的处理器集合、带宽配额和任务到达率，再看线程是在运行、可运行但未被调度，还是睡眠等待。主机平均利用率不能代表该容器的可运行预算；同样，睡眠线程多也不能直接推出磁盘慢。

【事实】Linux 使用任务表示可调度的执行实体，同一进程的线程通常共享地址空间和文件描述符表。跨进程切换可能更换地址空间；同进程切换仍有寄存器、栈、调度器和缓存局部性成本，不能概括为“只切寄存器”。任务模型与共享关系参见 [clone(2)](https://man7.org/linux/man-pages/man2/clone.2.html)。

把一次请求拆成接入排队、执行器排队、CPU 执行、锁等待、设备等待和完成回调六段。可运行队列等待增长支持调度竞争假设；锁持有者长时间不能运行则可能是配额或抢占放大了锁等待；读请求耗时增长还要区分提交前排队与设备服务时间。

【推断】工作线程数至少受三个预算约束：可用 CPU、下游可承受的在途操作、每个在途任务占用的内存。I/O 等待占比只能提供起始估计；如果增加线程导致内存回收、争用或下游排队，原来的等待占比也会改变，固定公式就失效了。

调度还必须说明版本。完全公平调度器（Completely Fair Scheduler，CFS）是经典背景；现代公平调度路径还需理解最早合格虚拟截止期优先（Earliest Eligible Virtual Deadline First，EEVDF）。【事实】该算法以公平份额的欠账判断资格，在合格任务中选择虚拟截止期较早者；虚拟截止期不是业务请求的真实截止时间。参见 [EEVDF 官方说明](https://docs.kernel.org/scheduler/sched-eevdf.html)。

**追问链**：

1. **第一层：线程都处于运行状态，为什么仍慢？** 运行状态包括正在运行与等待调度。测量唤醒到实际运行的间隔，核对亲和性、容器节流和同核竞争；不要把状态字母当成 CPU 计时器。
2. **第二层：换成用户态协程是否解决？** 协程可以减少阻塞时占用的内核线程，但承载线程被节流或被阻塞调用占住，协程仍无法推进。CPU 密集计算也不会因协程数量增加获得更多执行预算。
3. **第三层：短临界区是否应统一自旋？** 取决于持锁线程能否及时运行。超额订阅或配额耗尽时，等待线程可能把剩余 CPU 都用于自旋，反而延迟持锁者；应比较等待分布、缓存争用与睡眠唤醒成本。
4. **第四层：如何批准线程数调整？** 固定负载与资源限制，比较完成吞吐、排队时间、超时比例、单位请求 CPU 和内存峰值；如果收益只是把积压转移到下游，就不算解决瓶颈。

**常见差答／陷阱**：“线程数等于核数”“I/O 密集就无限加线程”“CPU 不满说明没有 CPU 瓶颈”。这些回答忽略了有效配额、局部热点和排队位置。把进程看成永远不能调度的抽象也不准确，单线程进程同样存在可调度任务。

【模板】填一例真实线程池调整：内核与容器配置、原先判断、支持或推翻判断的指标、最终并发预算、本人负责部分。没有可披露数据时保留定性结论，不填虚构百分比。

### 2. 为什么容器有“空闲 CPU”和“可用内存”，请求仍会被卡住？

**题目**：容器控制组第二版（Control Group v2，cgroup v2）限制了一个服务。应用看到很多逻辑核，线程池也按此扩容，但延迟呈周期性尖峰；另一实例没有触及硬内存上限，却持续变慢。你会读哪些控制文件？

**强答要点**：区分资源权重、资源上限和资源放置。`cpu.weight` 决定竞争时的相对份额，`cpu.max` 限制周期内 CPU 时间，`cpuset.cpus.effective` 描述可用 CPU 集合；三者不能互相代替。这里的 CPU 带宽推演按普通公平调度任务讨论，不能直接套用到实时调度任务或任意 sched_ext 策略。

【事实】内存的 `memory.high` 是节流和回收压力边界，`memory.max` 是硬限制，无法通过回收降低占用时可能触发组内内存不足终止（Out-of-Memory Kill，OOM Kill），但占用在某些情况下可暂时超过该值；文件缓存等也可能进入控制组内存记账。具体接口与层级约束参见 [cgroup v2 官方文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。子组配置不能绕过祖先组的资源限制。

【推断】假设 `cpu.max` 为 `200000 100000`，仅用于说明平均两核的时间预算。在没有其他限制时，八个线程同时执行 CPU 工作可能约 25 毫秒消耗完该周期预算，然后等待补充。实际节流时长受执行分布、层级和突发配置影响，这不是每个周期都会出现的实测曲线。

因此，周期性尖峰要对齐 `cpu.stat` 中节流相关计数的增量与请求时间线。内存变慢要对齐 `memory.events`、匿名页与文件页分布、回收活动和压力停顿信息（Pressure Stall Information，PSI），而不是只比较进程常驻内存与上限。

【事实】压力停顿信息描述 CPU、内存和 I/O 资源争用造成的停顿；`some` 表示至少部分任务受影响，内存与 I/O 的 `full` 可表示所有非空闲任务同时停顿的时间。系统级 CPU `full` 没有定义，自 Linux 5.13 起为兼容性报告为零；控制组级 CPU `full` 才有相应停顿统计。参见 [PSI 文档](https://docs.kernel.org/accounting/psi.html)。

**追问链**：

1. **第一层：CPU 限制为两核，绑定两个核是否等价？** 不等价。配额是时间带宽，绑定是放置限制；后者影响缓存与迁移，前者允许短时在多个核上消耗预算。还要说明是否与其他任务共享物理核。
2. **第二层：`memory.high` 上升为什么影响网络请求？** 分配可能进入直接回收，使接入或回调线程停顿；如果接收缓冲和应用队列继续增长，停顿又反过来延长缓冲占用。需要分配栈与控制组事件支持这条因果链。
3. **第三层：只给容器提高内存上限是否够？** 不一定。父组也可能限制它，或瓶颈来自不可回收、被固定的缓冲。先识别记账项和生命周期，再决定减少并发、收缩缓存或调整上限。
4. **第四层：多租户如何治理？** 应用内按租户分配并发和字节预算，控制组约束进程组的最终资源使用。每请求成本相差很大时，单一请求数限额无法可靠映射到 CPU 与内存成本。

**常见差答／陷阱**：“容器是轻量虚拟机，所以有独立内核”“`cpu.weight` 等于核数”“只要没到 `memory.max` 就不会受内存限制”。这些说法把隔离、记账和节流混成了一件事。

把容器总预算传给执行器、RPC 接入层和缓存管理器，是应用层治理建议；本文不声称 Linux 会自动替这些组件建立统一预算。

## 二、地址空间不等于物理内存，分配成功不等于访问便宜

### 3. 分配成功后第一次扫描变慢，如何解释缺页和内存承诺？

**题目**：查询启动时申请大块内存很快，第一次写入或扫描明显慢，偶尔还被终止。请解释虚拟内存（Virtual Memory）、地址转换与缺页的关系，并给出排查顺序。

**强答要点**：先分开地址保留、实际物理页、页表映射和资源记账。申请返回只说明某个分配路径成功，不保证未来访问所有页面都有足够物理内存或控制组预算；是否允许过量承诺还取决于系统策略。

【事实】快表（Translation Lookaside Buffer，TLB）未命中通常触发页表遍历，不等于缺页。缺页可能只是为匿名页分配和清零、建立已有文件页的映射或执行写时复制（Copy-on-Write，COW），也可能需要读取后备存储。Linux 的次缺页与主缺页计数按是否需要 I/O 区分，参见 [getrusage(2)](https://man7.org/linux/man-pages/man2/getrusage.2.html)。

【事实】内存过量承诺（Memory Overcommit）有独立策略，参见 [Linux 内存承诺文档](https://docs.kernel.org/mm/overcommit-accounting.html)。大地址空间可以依赖按需映射与稀疏访问存在，但持续活跃工作集超过可承受内存时，性能与生存性都没有保证。

排查要保留匿名映射还是文件映射、首次读还是首次写、是否存在交换空间、容器预算、分配器行为和非统一内存访问（Non-Uniform Memory Access，NUMA）拓扑。只报“缺页很多”不能区分初始化清零、远端访问和回收后的重新读取。

【推断】在可控启动阶段预先触碰页面，可以把部分缺页成本从请求路径移走，同时提前暴露预算不足；代价是启动更慢、预占更多物理内存，也可能在错误 NUMA 节点建立放置。它不适合无差别触碰远大于实际工作集的地址空间。

**追问链**：

1. **第一层：`mmap` 是否意味着零拷贝且没有 I/O？** 文件映射建立访问关系，实际访问仍可能缺页读取；应用省掉显式读入私有缓冲的动作，不代表磁盘数据凭空进入内存。
2. **第二层：`fork` 为什么快，之后为什么可能突然变慢？** 页表复制与写时复制避免立即复制所有数据；后续写入触发复制。并发写入量、页表规模与大页行为决定尖峰，不能把 `fork` 宣称为完全不阻塞。
3. **第三层：释放对象后常驻内存为什么不降？** 对象销毁、分配器归还空闲块、解除映射或回收物理页是不同阶段。先核对分配器保留与碎片，再判断泄漏；不能仅凭常驻内存不降定案。
4. **第四层：如何验证预触碰有效？** 比较冷启动和稳定阶段的延迟分布、缺页增量、常驻内存、NUMA 放置及启动成本。把首次访问移出计时区，只能证明预热后的性能。

**常见差答／陷阱**：“虚拟内存就是磁盘上的交换区”“TLB 未命中一定读盘”“分配成功就保证不发生内存不足”。这些解释无法处理匿名页、共享文件页与容器独立限制。

原料中把 `brk` 与 `mmap` 的选择阈值固定为 128 KB，也不足以支撑现场分析。分配器版本、调优参数和动态阈值都会改变路径；本篇不把该数值当成通用规则。

### 4. 大页为什么能改善吞吐，也可能制造长尾？

**题目**：一个大哈希表服务准备启用透明大页（Transparent Huge Pages，THP）。面试官要求你证明收益，并解释为什么有服务会限制它。你如何设计判断依据？

**强答要点**：先说明目标是减少地址翻译开销，而不是泛称“内存更连续所以所有访问更快”。大页扩大单个地址翻译项覆盖范围，但分配、清零、规整、合并和内部浪费可能提高请求路径成本。

【事实】在基础页为 4 KiB、页大小为 2 MiB 的例子中，一页覆盖的基础页数量为 512；这只是覆盖范围的算术关系，不是查询加速倍数。显式预留大页与透明大页的分配、回收和管理方式不同，参见 [HugeTLB 文档](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)。

【事实】2024 年 Linux 6.8 文档已描述多尺寸透明大页（Multi-size Transparent Huge Pages，mTHP）：匿名内存可使用介于基础页和传统大页之间的粒度，而且可继续通过页表项映射。较小粒度减少单次清零量，但具体地址翻译收益依赖架构。参见 [Linux 6.8 透明大页文档](https://docs.kernel.org/6.8/admin-guide/mm/transhuge.html)。

【推断】长期存活、访问密集且地址翻译开销明显的内存池，是优先实验对象；大量稀疏访问、短命分配或极严尾延迟场景要更谨慎。先对选定内存范围提出建议，再讨论全机策略，避免让一个服务的吞吐目标替所有租户决定内存策略。

验证必须同时看翻译事件、CPU 时间、实际大页覆盖、规整与回收活动，以及请求延迟。只看透明大页开关不能证明目标映射已经使用大页；只看吞吐提高也无法解释内存峰值是否超出了服务预算。

**追问链**：

1. **第一层：开启后为什么没变化？** 可能工作集不受地址翻译限制，目标映射不符合条件，或未实际获得大页。先确认映射与硬件事件，不能直接判定功能无效。
2. **第二层：大页越大越好吗？** 越大，覆盖收益可能越高，但分配与清零粒度、稀疏使用浪费也越大。多尺寸选择需要结合架构与真实访问分布，不能只比较页数量。
3. **第三层：能否预留所有内存为显式大页？** 需要评估预留导致的其他工作负载可用内存下降、启动失败与容量变更成本；不能把预留池视为普通可随时回收的缓存。
4. **第四层：如何与 NUMA 配合？** 保留分配线程、首次触碰位置和访问线程分布；若换页大小时同时改变节点放置，就不能把全部收益归因于大页。

**常见差答／陷阱**：“大页固定是 2 MB”“开启透明大页就保证使用”“任何数据库都应关闭或开启”。这些结论没有限定架构、分配路径与延迟目标。

不要把模型服务中缓存注意力键和值张量的键值缓存（Key-Value Cache，KV Cache）逻辑块与操作系统页面混为一谈；例如 [PagedAttention 论文](https://arxiv.org/abs/2309.06180)借用了分页思想，但其逻辑块由模型运行时管理。二者都涉及粒度和碎片，但管理对象、地址空间与回收协议不同，不能直接互推效果。

## 三、I/O 接口改变了什么，又没有改变什么

### 5. 数据库已有缓存，是否应该使用 O_DIRECT？

**题目**：存算分离节点从本地缓存文件读取压缩列块，应用另有解压缓存。你会保留页缓存（Page Cache），还是改成直接 I/O（Direct I/O，`O_DIRECT`）？日志写入能否沿用同一判断？

**强答要点**：先画清各层缓存存的是什么。压缩文件页和解压列块不是完全重复的数据；是否值得保留双层缓存，取决于复用率、解压成本、内存预算和顺序扫描对其他租户的干扰。

【事实】`O_DIRECT` 的缓冲地址、长度和偏移约束依赖文件系统与内核；Linux 6.1 起可在支持的文件上通过 `statx` 的 `STATX_DIOALIGN` 查询对齐信息。直接 I/O 也不等于 `O_SYNC`，不能据此宣布数据已持久化。参见 [open(2)](https://man7.org/linux/man-pages/man2/open.2.html)。

页缓存路径提供内核缓存、预读和写回机制，应用仍可能受复制与回收成本影响。直接路径减少数据经页缓存的缓存过程，却把缓冲复用、对齐、预取和并发组织交给应用。这里的成本迁移才是方案比较的核心。

【事实】`fsync` 与 `fdatasync` 用于同步文件状态，但创建或重命名后的目录项持久性需要另行考虑父目录同步。参见 [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)。日志协议还要说明顺序、错误传播和设备缓存语义，不能只换一个打开标志。

【推断】一次性大扫描可能污染缓存，重复小读可能受益于页缓存；但缓存污染也可通过访问建议和容量管理缓解。应用具备成熟块缓存、预取和内存治理时，直接 I/O 才更容易形成完整方案；这些是选型条件，不是所有数据库的固定答案。

**追问链**：

1. **第一层：如何公平比较两条路径？** 固定文件系统、设备、请求大小、队列深度、读写比例、数据压缩状态和总内存预算；分别记录冷缓存与热缓存，避免一边重复读缓存，一边持续读设备。
2. **第二层：可以混用缓存读写、直接读写与映射吗？** 重叠范围会引入一致性与协调成本，也可能损害性能；应优先统一访问策略，确需混用时按文件系统支持验证，不把它当成免费并行优化。
3. **第三层：异步直接写完成能立即返回提交成功吗？** 先定义成功契约。I/O 完成、持久化与数据库事务提交是不同边界；如果协议要求断电恢复，必须证明相应同步、顺序和恢复步骤。
4. **第四层：为什么不用清空系统缓存做线上验证？** 全局操作会影响其他服务，也改变正在测量的共享环境。应在隔离环境准备冷数据集或专用实例，线上用可归因观测判断。

**常见差答／陷阱**：“数据库有缓存所以必须直接 I/O”“直接 I/O 完全绕过内核”“写成功即落盘”。三句话分别忽略缓存内容差异、内核仍参与请求和持久性边界。

对增量视图维护（Incremental View Maintenance，IVM），小批写入的确认顺序可能比扫描吞吐更重要。不要把扫描缓存的测量结论直接用于增量提交日志。

### 6. io_uring 是完成接口，为什么仍可能消耗很多线程和 CPU？

**题目**：把阻塞文件读换成 io_uring 后，单个调用看起来更轻，但服务出现完成积压与取消后的内存错误。请解释它的执行方式，并设计请求状态机。

**强答要点**：io_uring 是通过共享环组织提交与完成的异步接口，不保证每项操作都由设备原生异步完成，也不保证零系统调用、零复制或按提交顺序完成。

【事实】提交队列（Submission Queue，SQ）承载请求，完成队列（Completion Queue，CQ）返回结果；完成项的结果字段按操作类型表达返回值，例如读写的字节数、accept 的新描述符或某些操作成功时的零；失败通常为负错误码。需要阻塞执行的路径可转由工作线程处理。参见 [io_uring(7)](https://man7.org/linux/man-pages/man7/io_uring.7.html)。

应用需给请求稳定标识，区分准备、已提交、业务超时、取消请求已提交、目标操作终结和资源可回收。业务超时可以结束对调用者的等待，但不能据此判断内核已停止访问缓冲。

【事实】取消请求本身也有完成结果，并与目标请求存在竞态；目标可能已完成、正在执行或成功被取消。参见 [io_uring_prep_cancel(3)](https://man7.org/linux/man-pages/man3/io_uring_prep_cancel.3.html)。取消结果必须与目标操作的终结事件共同解释，不能只等取消项就释放目标上下文。

【推断】最小安全不变量是：调用者完成状态只提交一次，资源须等其对应的底层访问与必要释放通知结束后才能归还；请求上下文还须保留到所有仍会引用它的事件处理完毕。引用计数只是实现工具，还必须防止请求标识被过早复用、完成项命中新对象，以及回调线程与取消线程同时完成用户承诺。

```text
准备 → 提交 → 等待目标完成 → 目标终结 → 回收
              │
              └→ 业务超时 → 请求取消 ─┘
                 调用者可返回，资源继续由运行时持有
```

这张图只表达普通单次操作的生命周期。多次完成操作、零拷贝通知和跳过部分完成项的选项，需要扩展终结条件；不能照搬“一次提交一定一个完成项”的简化假设。

**追问链**：

1. **第一层：队列越深，吞吐越好吗？** 超过设备有效并行度后，新增请求主要增加排队与缓冲占用。分别测提交等待、底层服务和完成消费时间，限制在途请求与字节数。
2. **第二层：开启提交轮询是否免费减少系统调用？** 提交轮询（Submission Queue Polling，SQPOLL）用轮询线程换取部分提交开销下降；需要计入其 CPU、唤醒与容器资源预算，不能只统计业务线程。
3. **第三层：固定缓冲区是否可以随时释放？** 注册与解除注册有独立约束，应用也必须遵守在途操作的访问期。固定缓冲降低重复注册成本，不能取消所有权与内存预算。
4. **第四层：如何处理完成消费跟不上？** 观察完成积压与消费者调度，缩小提交预算，保证完成推进不会依赖已被业务任务占满的线程池；容量与溢出行为按特性和内核版本确认。

**常见差答／陷阱**：“io_uring 比 epoll 新，所以全面替换”“业务超时后立刻释放缓冲”“每个请求只可能收到一个事件”。这些答案容易在竞态和多次完成路径失效。

2026 年面试中还应主动询问部署是否允许该接口、是否有系统调用过滤以及实际支持的操作。可用性是部署事实，不应从内核主版本或本机样例成功推断整个生产集群。

### 7. epoll 的边缘触发如何兼顾不漏事件和公平性？

**题目**：一个连接持续可读，事件线程每次都读到 `EAGAIN`，其他连接延迟开始增长。改为每次只读固定字节后，又出现连接“有数据但不处理”。怎样修正？

**强答要点**：先区分就绪通知与数据完成。epoll 返回某文件描述符（File Descriptor，FD）可读，不保证后续读取不遇到竞争，也不保证一次读能得到完整应用消息。

【事实】水平触发（Level-triggered，LT）与边缘触发（Edge-triggered，ET）是不同通知方式；边缘模式应使用非阻塞描述符，并在等待下一次内核通知前把当前就绪状态处理到不能继续。参见 [epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html)。

【推断】若为公平性设置每轮字节或时间预算，预算用完但尚未读至 `EAGAIN` 时，把连接放入用户态就绪队列，主动安排后续轮次。只有确认暂时不可继续，才把推进责任交还内核事件；否则应用把“主动暂停”误写成了“等待新边缘”。

写路径也需状态机：处理部分写入，剩余数据保留偏移；遇到暂不可写才等待可写通知，发送队列清空后撤销不必要的关注。否则长期可写的连接可能制造无意义唤醒。

【事实】epoll 维护关注与就绪集合，但返回多个事件、复制事件数组和处理这些事件都有成本；不能把整个服务的复杂度标成 O(1)。它仍受描述符上限、内存及内核资源限制，同一手册也描述了相关监控限制。

**追问链**：

1. **第一层：收到可读后另一个线程先读走数据怎么办？** 非阻塞读取允许返回 `EAGAIN`，应用应回到等待状态；事件不是对字节的独占承诺。最好明确单连接的读取所有者。
2. **第二层：`EPOLLONESHOT` 能解决所有并发吗？** 它可以帮助控制事件交付，但重新启用、关闭、超时和对象回收仍需同步；不能靠一个标志替代连接状态机。
3. **第三层：关闭描述符后数字被复用会怎样？** 旧事件若只保存整数，可能误操作新连接。用稳定连接标识、代际或受控引用识别事件归属，并延后释放仍被引用的对象。
4. **第四层：为什么不永远用边缘触发？** 它可能减少重复通知，却增加暂停恢复与公平性管理成本；是否值得取决于连接活跃比例、处理预算和实现质量，水平模式同样能支撑高并发。

**常见差答／陷阱**：“边缘触发只通知一次，所以更可靠”“没读完会丢掉 TCP 数据”“epoll 无限 FD 且没有任何复制”。前两句混淆通知丢失与数据驻留，最后一句混淆注册集合与就绪结果。

网络消息分帧属于连接状态机：长度前缀需要校验最大长度与整数溢出，累计读取需要限制内存。单独使用 Protocol Buffers（协议缓冲序列化格式）并不能自动定义 TCP 字节流上的消息边界。

### 8. 零拷贝省掉哪一次复制，谁负责缓冲区的后半生？

**题目**：跨节点交换要发送大批列块，团队建议用零拷贝（Zero-copy）。请分别解释文件发送、内存发送与接收路径，并说明为什么小请求可能变慢。

**强答要点**：在图上标出文件、页缓存、用户缓冲、套接字缓冲和网卡，再指出省掉的边。设备直接内存访问（Direct Memory Access，DMA）仍然搬运数据；少一次 CPU 复制不意味着没有数据传输、协议处理或生命周期成本。

【事实】`sendfile` 可在内核中组织文件到输出描述符的传输，避免先读入用户缓冲再写回的路径；它不等于所有平台、文件系统与发送配置都没有内部复制。参见 [sendfile(2)](https://man7.org/linux/man-pages/man2/sendfile.2.html)。

【事实】`MSG_ZEROCOPY` 以页固定和完成通知等开销换取复制规避，调用返回后不能立即修改仍在使用的缓冲；应用需消费错误队列中的释放通知，路径也可能回退到复制。参见 [Linux MSG_ZEROCOPY 文档](https://docs.kernel.org/networking/msg_zerocopy.html)。

【推断】是否获益取决于消息大小、内存带宽、页管理与完成消费成本。小消息不能摊薄固定开销，大消息在慢接收方下又会长期占用页；所以应同时限制未释放字节数，不能只限制发送调用次数。

【事实】io_uring 的零拷贝发送有普通发送完成与缓冲释放通知的区别；后续是否有通知需检查完成标志，不能无条件假定恰好两次完成。参见 [io_uring_prep_send_zc(3)](https://man7.org/linux/man-pages/man3/io_uring_prep_send_zc.3.html)。

**追问链**：

1. **第一层：发送完成是否表示对端已经处理？** 不是。发送接口完成、缓冲可重用、TCP 确认和对端业务提交分别属于不同契约；必须明确这次优化关注哪个边界。
2. **第二层：加密与压缩后还可以零拷贝吗？** 要看变换发生在用户态、内核还是设备，以及输出是否必须重新物化。先画变换后的路径，不能把明文文件发送结论移植到任意加密链路。
3. **第三层：接收端也有对应优化吗？** 有不同机制，但不是给普通读取加一个通用零拷贝标志。需核对注册区域、网卡能力、队列分配与缓冲归还协议。
4. **第四层：慢消费者如何拖垮服务？** 未完成的发送与未归还的接收区域挤占缓冲池；若上游继续生产，零拷贝只是让这些内存更久不能复用。限额必须覆盖真实占用期。

**常见差答／陷阱**：“DMA 就是零拷贝”“少两次复制一定快”“完成回调后所有内存都能回收”。这些说法没有识别具体接口与通知类型。

【事实】Linux 6.15 文档已经给出 io_uring 零拷贝接收：报头仍由内核 TCP 栈处理，负载直接进入注册的用户内存；要求网卡支持报头与数据分离、流量定向和接收侧扩展（Receive Side Scaling，RSS）。参见 [Linux 6.15 零拷贝接收文档](https://docs.kernel.org/6.15/networking/iou-zcrx.html)。这不是任意旧网卡都可启用的软件开关。

【事实】2024 年 Linux 6.12 的设备内存 TCP（Device Memory TCP）文档描述了负载直接进入设备内存、报头进入主机内存的接收路径。参见 [Linux 6.12 设备内存 TCP 文档](https://docs.kernel.org/6.12/networking/devmem.html)。该路径要求兼容的网卡及驱动支持报头分离、流量定向和 RSS，需将 DMA-BUF 绑定到接收队列，并由应用通过 `recvmsg(MSG_SOCK_DEVMEM)` 接收和按接口归还缓冲；不能仅凭升级内核就认定已有通用 GPU 直收能力。它与用户内存零拷贝接收有共同的路径拆分思路，但目标内存与接口不同。

【推断】模型服务跨机传输时，应先问最终数据要进入主机还是设备，以及拓扑是否支持直接路径；不能把“采用 TCP”与“必须经过主机负载复制”画等号，也不能由此宣称任何部署都优于 RDMA。

## 四、网络吞吐由多个控制环共同决定

### 9. 换成 BBR 后，为什么吞吐与长尾仍可能没有改善？

**题目**：远端扫描吞吐低，链路标称带宽很高。有人提议统一改用 BBR（基于瓶颈带宽与往返传播时间建模的拥塞控制算法）。你如何证明瓶颈在拥塞控制，而不是窗口、应用或主机？

**强答要点**：区分应用生产速率、连接发送缓冲、接收方通告窗口、拥塞窗口与实际链路容量。TCP 提供有序字节流，但不能保证应用及时生产、消费或提交。

【推断】稳态近似下，吞吐受可用带宽、有效在途窗口除以往返时间（Round-trip Time，RTT）、应用供给和消费速率中的较小者限制。这个近似帮助选择观测，不适用于直接预测短流启动过程或突发丢包恢复。

例如假设路径为 100 Gbit/s、往返时间 1 毫秒，则带宽时延积（Bandwidth-delay Product，BDP）约为 12.5 MB。这是单位换算后的推演，不是某云产品参数；若目标在途量远小于它，即使链路无拥塞，也难持续填满该假设路径。

【事实】BBR 根据瓶颈带宽与传播往返时延建立模型，调节发送节奏和在途数据；不同代际对丢包、显式拥塞通知及探测有不同处理。Google 官方提供 v3 测试分支和文档，不能从模块名 `bbr` 推断实现就是 v3。参见 [Google BBR 官方入口](https://github.com/google/bbr)与 [BBRv3 发布说明](https://github.com/google/bbr/blob/v3/README.md)。

【推断】方案比较要保留短流与长流、往返时延、随机损失与排队损失、竞争流、接收端处理速度和 CPU 配置。单连接吞吐提高不代表共享瓶颈上公平性或请求长尾改善，也不证明拥塞控制替应用解决了过载。

**追问链**：

1. **第一层：如何区分接收窗口小与拥塞窗口小？** 结合连接状态、通告窗口、在途字节、重传和接收队列；如果接收应用长期不读，提高拥塞窗口并不能创造接收容量。
2. **第二层：看到重传就能认定网络拥塞吗？** 不能。损失、乱序、路径变化与观测位置都影响解释；还要排查主机丢包、网卡队列和对端处理，不能只数某一个计数器。
3. **第三层：增大所有套接字缓冲是否稳妥？** 它可能帮助覆盖带宽时延积，也会在大量连接下扩大内存和排队；需要按活跃连接、消息规模和目标延迟配置预算。
4. **第四层：如何做 BBR 对照？** 核实内核源码或发行版包、实际算法与队列配置，固定负载并保留竞争场景；设置回退条件，避免把同时更换硬件的收益归给算法。

**常见差答／陷阱**：“BBR 不看丢包”“BBR 永远比 CUBIC 快”“Linux 默认算法在任何环境都一样”。这些回答忽略版本、默认配置可变和应用受限连接。

TCP 报头至少 20 字节不意味着所有段都固定 20 字节；常见以太网 1500 字节最大传输单元（Maximum Transmission Unit，MTU）也不是所有路径的常数。卸载会改变抓包视图，不能把抓到的大包直接解释为线上违反 MTU。

### 10. TIME_WAIT 太多，应先调哪个参数？

**题目**：客户端出现连接建立失败，机器上有大量 `TIME_WAIT`。另一实例有很多 `CLOSE_WAIT`。如何判断是端口耗尽、关闭泄漏还是正常连接周转？

**强答要点**：先定位主动关闭者、连接方向、失败错误、地址四元组与周转率。连接数量本身不是故障结论；监听端可以通过不同对端共享同一本地端口，客户端到固定目的地的临时端口约束却可能成为瓶颈。

【事实】TCP 的关闭状态机保留半关闭能力，结束不要求恰好四个独立报文；确认与结束标志可以合并。`TIME_WAIT` 用于处理关闭末尾的重传与旧报文问题，同时关闭也可使双方进入该状态。参见 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

【事实】`tcp_fin_timeout` 针对孤儿连接的 `FIN_WAIT_2` 行为，不是通用的 `TIME_WAIT` 调节器；`somaxconn` 也不是该状态数量的上限。参见 [Linux IP 参数文档](https://docs.kernel.org/networking/ip-sysctl.html)。调整前先确认参数管的是哪个对象和状态。

【推断】如果每秒关闭连接数为 λ，状态平均驻留时间为 T，稳态数量约为 λT。这个关系只能用于解释连接周转，不应把协议中的两倍最大报文生存时间（Maximum Segment Lifetime，MSL）硬写成所有系统统一的分钟数。

`CLOSE_WAIT` 表示本端已收到对方结束发送的通知，而应用尚未完成本地关闭；重点查对象生命周期、异常路径和任务是否仍持有连接。`TIME_WAIT` 则通常先检查连接复用、短连接周转与临时端口压力，二者不能用相同“快速回收”方案处理。

**追问链**：

1. **第一层：服务端只能接受 65535 个连接吗？** 不能这样推断。连接按本地与远端地址、端口区分；实际限制还包括描述符、套接字内存、跟踪表、代理和应用预算。端口数量不是监听端连接总数。
2. **第二层：`SO_REUSEADDR` 是否清除旧连接？** 不是。地址绑定复用与连接状态管理是不同机制；它不能无条件保证相同四元组立即重新连接，也不替应用修复泄漏。
3. **第三层：提高网速或改成非阻塞能缩短驻留吗？** 它们不直接修改协议状态的计时规则。应减少不必要的建连关闭，核对连接池空闲超时与代理策略，再分析特定内核的复用条件。
4. **第四层：如何证明端口耗尽？** 保留客户端建连错误、临时端口范围、目的地分布、连接状态与网络地址转换（Network Address Translation，NAT）设备观测；有些瓶颈实际在代理或转换设备上。

**常见差答／陷阱**：“把 `tcp_fin_timeout` 调小”“加大 backlog”“重启机器”“用新网卡缩短两倍 MSL”。这些措施都没有建立失败与具体资源约束的联系。

连接池也有边界：池过大扩大内存与后端连接压力，池过小使调用排队，过期策略不一致又会产生批量重连。修复后要观察成功请求、连接建立速率和后端负载，而不只观察 `TIME_WAIT` 是否减少。

### 11. TCP 有流量控制，应用为什么仍会内存不足？

**题目**：下游消费者变慢，TCP 已经降低发送进度，但扫描线程仍在生产结果，发送端内存持续上涨。如何设计端到端背压（Backpressure）？

**强答要点**：TCP 约束字节进入连接的速度，不会自动限制已生成的列块、序列化对象、线程池任务或等待重试的请求。应用只要不断把数据移入用户队列，就可以绕开网络上的流量限制。

【推断】首先建立字节信用：下游可接纳多少有效数据，上游才生产多少；信用的返还应绑定真实资源释放，而非某个提交函数返回。多个队列可以有各自局部额度，但所有未释放字节必须归入明确的总预算。

```text
扫描器 → 编码队列 → RPC 在途数据 → 接收队列 → 算子消费
  ↑                                              │
  └──────────── 释放容量后返还信用 ────────────────┘
```

这条反馈链要求暂停能停到扫描器，而不是只让编码线程在满队列上等待。若暂停仍持有下一阶段必须取得的锁或全部执行线程，就可能把限流变成死锁。

【事实】gRPC 的流式流量控制会影响消息发送进度，但写入框架不代表数据已离开主机。双方大量写入而不推进读取时也可能相互等待。参见 [gRPC 流量控制](https://grpc.io/docs/guides/flow-control/)。对单次请求的接入预算仍要在应用层另行设计。

【推断】队列必须同时限制数量、字节与最大等待时间。单条消息大小差异很大时，数量限额会漏掉内存风险；无限等待则把已经不可能按时完成的任务留在系统里，继续挤占新请求预算。

**追问链**：

1. **第一层：所有队列都设为有界，是否就安全？** 不一定。若生产和消费共用耗尽的线程池，生产者阻塞会让消费者无法运行；需要保证关键推进路径有执行预算，或采用可挂起的等待。
2. **第二层：信用用字节还是行数？** 网络缓冲按编码后字节更直接，执行器还要估计解压后或构建状态的内存。应明确预算覆盖哪一阶段，不能只用压缩大小保护膨胀后的算子。
3. **第三层：取消时如何归还信用？** 幂等地关闭生产，撤销未提交数据，等待在途对象完成其释放协议，再返还相应额度；取消通知本身不等于内存已经不再被访问。
4. **第四层：重试如何避免破坏限额？** 所有尝试共享原请求预算，取消无用尝试，限制放大系数与剩余时间。不能让每次重试重新获得一份完整资源额度。

**常见差答／陷阱**：“交给 TCP”“给队列多加一点内存”“发送 API 返回就返还信用”。这些回答没有跟踪真实占用，也没有证明反馈最终能让上游停下来。

迁移到模型服务时，要限制的不只是输出文本，还可能是等待执行的输入、主机缓冲和设备状态；迁移到智能体运行时，则要给工具调用和子任务传播同一截止时间与预算。这里是设计推导，不是对某个框架当前实现的描述。

## 五、RPC 与 RDMA 要回答语义，不能只比较接口速度

### 12. 如何比较 brpc 与 gRPC，并解释超时后的结果不确定性？

**题目**：为跨节点数据交换选择 RPC 框架。面试官继续问：多路复用是否消除阻塞，超时是否代表没有执行，备用请求是否可以直接开启？

**强答要点**：建立共同维度：协议兼容、序列化与缓冲、执行模型、连接与流复用、截止时间与取消、重试、接入控制和诊断能力。没有相同消息大小、连接数、加密、并发与业务开销的测量，不能宣布框架普遍更快。

【事实】brpc 的 bthread 是多对多（M:N）用户态线程机制；阻塞承载线程的操作与可协作挂起的等待不能视为相同。参见 [bthread 官方说明](https://brpc.apache.org/docs/bthread/bthread/)。同步写法不自动等于每请求独占内核线程，也不保证任意阻塞库调用都被自动改造成异步。

【事实】gRPC 官方性能指南指出连接上的并发流限制可能使调用排队。参见 [gRPC 性能指南](https://grpc.io/docs/guides/performance/)。超文本传输协议第二版（HTTP/2）允许多流复用，但共享 TCP 的有序交付仍会让丢失字节影响后续字节交付；应用流隔离不能消除传输层队头阻塞（Head-of-Line Blocking）。

【事实】gRPC 默认不替业务指定一个合理的截止时间（Deadline）；超时传播与服务端取消还需语言支持及应用配合。参见 [gRPC 截止时间指南](https://grpc.io/docs/guides/deadlines/)。应用代码应检查取消并停止后续工作，但已经产生的外部副作用不能靠取消自动撤销。

【推断】“超时”描述调用者没有按时获得结果，可能发生在发送前、服务端执行中，或提交之后回复丢失。具有副作用的请求需要操作标识、幂等处理或可查询结果；网络层的可靠传输不提供业务恰好执行一次。

**追问链**：

1. **第一层：重试放在哪里？** 明确框架、代理和业务分别是否重试，保留尝试标识与原始截止时间。多层各自重试会放大流量，必须计算最坏尝试数并统一预算。
2. **第二层：收到响应头后还会不会透明重试？** 按具体框架重试契约判断。gRPC 的提交点与重试策略有明确条件，不能把某个错误状态一律等同于安全重放，参见 [gRPC 重试指南](https://grpc.io/docs/guides/retry/)。
3. **第三层：备用请求为何可能恶化长尾？** 它能用额外副本机会绕开慢实例，也会加重共享瓶颈；过载时扩大请求数可能使所有实例更慢。需要触发阈值、比例预算、幂等性和取消机制。
4. **第四层：接入上限为何不等于线程数？** 在途请求占用缓冲和下游资源，即使没有占着线程，也需要限额。brpc 提供并发限制机制，参见 [Auto ConcurrencyLimiter](https://brpc.apache.org/docs/server/auto-concurrencylimiter/)；应用仍需验证成本差异和反馈稳定性。

**常见差答／陷阱**：“brpc 用协程所以一定更快”“gRPC 写成功说明对端收到”“超时之后直接再执行一次”“HTTP/2 消除了所有队头阻塞”。这些回答无法说明完成、提交和取消各自的边界。

【模板】填一条真实 RPC 链路：调用者、框架版本、代理、服务端、幂等键、截止时间传播与取消收敛时间。本人没实现过幂等协议，就明确这是待验证设计，不叙述为上线经验。

### 13. RDMA 为什么既不是远程函数调用，也不是远程事务？

**题目**：远程直接内存访问（Remote Direct Memory Access，RDMA）能减少数据路径的 CPU 参与，为什么不直接用它替换所有 TCP RPC？请设计一个远程块读取协议。

**强答要点**：先区分双边消息与单边内存操作。双边发送需要接收端提供接收资源；单边读写使用远端授权的内存区域，可减少远端 CPU 在搬运路径上的参与，但远端应用仍要建立、管理并撤销这些区域。

【事实】RDMA 使用内存区域（Memory Region，MR）、保护域（Protection Domain，PD）、队列对（Queue Pair，QP）和完成队列；访问权限、操作类型与传输模式有具体契约。参见 NVIDIA 的 [RDMA 编程手册](https://docs.nvidia.com/rdma-aware-networks-programming-user-manual-1-7.pdf)。本文所述单边读写主要按可靠连接的常见使用方式讨论，不推广到所有传输模式。

【推断】读取协议至少需要控制面返回块标识、地址、长度、访问凭据和版本，并保证读取期间内存不会被复用为另一块。完成后验证版本或校验信息，失败则重新解析；地址有效不等于它仍属于原来的逻辑对象。

缓冲固定、注册缓存和连接状态也占资源。注册池过大降低其他工作负载可用内存，池过小导致回收或重新注册；大量队列与完成轮询还可能把节省的协议处理成本转成轮询和连接管理成本。

【推断】需要分别写出本地完成、远端可见、远端应用已消费与持久化的契约。即使某项操作已经满足传输完成语义，也不能推出数据库事务已经提交，或多个远端对象已经原子更新。

**追问链**：

1. **第一层：接收端不及时提供资源怎么办？** 双边操作可能遭遇接收资源不足；应用仍需信用和缓冲管理，不能因为使用硬件队列就放弃背压。
2. **第二层：远端进程重启后旧地址还能用吗？** 需要失效旧访问凭据、连接或会话，并用代际阻止旧请求误命中新资源。重建连接本身不能证明业务对象身份正确。
3. **第三层：以太网 RDMA 是否必须依靠绝对无损网络？** 不应下绝对结论。融合以太网 RDMA（RDMA over Converged Ethernet，RoCE）的部署需结合优先级流量控制、显式拥塞通知、端点拥塞算法与重传能力；具体能力受版本和硬件约束。
4. **第四层：什么时候保留 TCP RPC？** 控制消息多、消息小、网络条件不可控、跨地域或语义复杂时，成熟 RPC 的运维与失败处理可能更重要。先量出搬运成本占比，再考虑独立数据通道。

**常见差答／陷阱**：“RDMA 不用 CPU”“单边写完成就事务成功”“访问凭据等于完整租户认证”“使用 RoCE 就不会拥塞”。它们分别省略控制面、提交协议、授权范围与网络治理。

【推断】对于模型服务的跨机缓存搬运，可以考虑“RPC 管控制与对象身份，专用传输管大块数据”的分层设计；必须同时证明取消、租户隔离和资源回收，不把它称为对任意工作负载都成立的最佳方案。

## 六、最后用可归因观测检验前面的每个判断

### 14. 用 eBPF 定位长尾：如何从相关性走到可证伪的因果链？

**题目**：数据库扫描、RPC 与模型服务都出现偶发长尾。你准备使用扩展伯克利包过滤器（Extended Berkeley Packet Filter，eBPF）观测。如何选挂载点，避免得到一张无法指导行动的火焰图？

**强答要点**：先提出竞争假设，再选择观测。请求慢可能因为无法获得 CPU、锁持有者未运行、直接回收、设备排队、网络重传或回调消费延迟；单看 CPU 栈只能解释正在 CPU 上执行的部分。

【推断】将应用请求标识与时间段关联到线程和控制组，再对照调度唤醒与切换、分配回收、块请求提交完成、连接状态。异步请求可能跨线程，设备与网络事件也未必带原始进程上下文，因此“按进程号过滤”不自动形成完整请求追踪。

【事实】libbpf 提供程序加载、挂载与对象管理，加载时的验证由内核验证器执行；它还支持一次编译、跨内核运行（Compile Once–Run Everywhere，CO-RE）的结构适配机制。参见 [libbpf 官方概览](https://docs.kernel.org/bpf/libbpf/libbpf_overview.html)。结构重定位不保证任意挂载点在所有版本存在，更不保证内部函数语义稳定。

【事实】BPF 环形缓冲可共享跨 CPU 事件存储并保留相应顺序，但容量仍有限，预留失败必须处理。参见 [BPF ring buffer 文档](https://docs.kernel.org/bpf/ringbuf.html)。观测中应记录丢失或预留失败，不能把采集空白解释成系统没有发生事件。

【推断】用低成本直方图先定位等待类型，再对少量实例短时采集栈和关联事件；同时记录采样、事件速率和额外 CPU。观测开销若改变排队与长尾，就需要降低范围，并重新验证原始现象是否仍然存在。

**追问链**：

1. **第一层：如何区分运行队列等待与锁等待？** 前者从可运行到实际调度，后者要识别阻塞与唤醒来源。持锁者的运行队列等待可能放大另一线程的锁等待，所以需要时间线而非两个独立总量。
2. **第二层：设备完成慢是否就是磁盘硬件慢？** 先定义挂载点覆盖的是块层排队、驱动还是设备服务；映射层、合并与重试会影响关联。应用端等待还可能发生在提交前和完成后。
3. **第三层：采不到事件怎么办？** 核对权限、内核配置、BPF 类型信息、挂载点与过滤条件，再退回应用埋点、进程统计或已有跟踪工具；采不到不等于假设被证伪。
4. **第四层：怎样证明修复有效？** 只改变关键变量，保持负载、配置和观测范围，检查预期中间量是否下降，再看成功吞吐与长尾；同时排除错误率上升或过早拒绝造成的表面提速。

**常见差答／陷阱**：“装一个 eBPF 工具就能自动找到根因”“有验证器就没有开销”“CO-RE 保证所有版本兼容”。这些回答没有观测模型、丢失处理或版本边界。

【事实】2024 年 Linux 6.12 提供可扩展调度类（Extensible Scheduler Class，sched_ext），可由 BPF 程序定义调度行为，并在错误或任务停滞等条件下回退。参见 [Linux 6.12 sched_ext 文档](https://docs.kernel.org/6.12/scheduler/sched-ext.html)。它属于执行策略，不是普通观测探针；把它引入生产需要独立验证，不能在排障中顺手替换调度器。

## 七、把十四题收敛成一次完整的故障答辩

**综合题**：一个容器内的分布式查询节点，远端数据读取变慢，内存上升，超时后仍有 CPU 活动。面试官要求你先止损，再定位，最后决定是否采用 io_uring、BBR 或 RDMA。

**强答要点**：首先限定是题设，没有给定真实测量，不直接认定某项技术能解决。先确认服务级目标（Service-level Objective，SLO）、错误率、影响租户与变化时间，再冻结可回滚变更，减少新请求和在途字节，保证取消与完成推进仍有预算。

第一步检查容器实际 CPU 带宽、处理器集合、内存事件与压力信息。如果 CPU 节流与超时对齐，先解释为什么接收、完成和取消不能及时运行；不能因主机平均空闲就跳过这一层。

第二步拆请求时延。若远端读请求尚未真正提交，换拥塞控制没有针对性；若底层已完成但回调长时间排队，增加设备并发可能扩大积压；若接收应用不消费，先解决消费预算与背压。

第三步核对内存归属。对象在扫描器、编码队列、RPC 框架、未释放零拷贝缓冲或解压算子中有不同释放条件。把“超时已返回”与“底层资源已回收”分别观测，定位泄漏、正常延迟释放或取消未收敛。

第四步再选择实验。文件读提交开销或并发组织占主导时试 io_uring；持续长流且窗口与拥塞行为支持网络假设时比较 BBR；确实受大块搬运 CPU 或内存带宽约束、且网络与运维条件满足时试专用传输。每次只验证一个主要假设。

**追问链**：

1. **第一层：无法立即复现，如何止损？** 降低新增在途资源，隔离受影响租户，保留最小必要指标与配置快照；拒绝策略应计入错误率，不宣称“延迟下降”即恢复。
2. **第二层：业务要求不拒绝任何请求怎么办？** 有限服务能力与持续超额到达无法同时保证有限排队与无限接收。需要协商排队上限、可重试响应、优先级和上游降速，这是容量约束的直接推论。
3. **第三层：技术方案局部指标变好，是否发布？** 还要验证端到端目标、资源总账、失败恢复与租户影响；若只是把工作移到轮询线程、远端节点或不可回收缓冲，就需重新计算收益。

**常见差答／陷阱**：把三个技术都列为“优化方向”，没有排除条件；只看平均时延，不看失败与取消后的资源；直接归因于内核老旧，却拿不出版本差异和触发路径。

【模板】实际答辩材料填写如下，不要求每例覆盖所有机制：

| 需要本人补充 | 证据边界 |
|---|---|
| 版本、机器与容器配置 | 可披露的真实信息；未知项明确写未知 |
| 请求类型、数据规模、并发与消息大小 | 保留冷暖缓存、持续时间与负载发生方式 |
| 初始判断及被推翻的理由 | 只写真实出现过的判断变化 |
| 本人决策、实现与他人贡献 | 分清主导、参与、复核与阅读练习 |
| 变更前后结果及误差 | 无原始记录不补写具体收益 |
| 回退条件、遗留问题与不适用场景 | 说明仍未验证什么 |

复核材料时，把异步对象、取消与资源归还写成代码评审（Code Review）问题，再组织真实证据。源码阅读练习与线上故障处理属于不同证据，不要求把前者包装成后者。

## 八、验证方案：面试中说清如何测，别把建议写成实验结论

【推断】比较系统方案时，首先固定成功契约和资源总账。吞吐统计成功完成的业务量，延迟从请求进入被测边界开始计算；排队、重试和失败不能被悄悄移出计时范围。

以下是待执行的验证矩阵，不是本文已经完成的实验：

| 待验证假设 | 保持不变的条件 | 主要观测 | 反例与停止条件 |
|---|---|---|---|
| 工作线程过多导致调度竞争 | CPU 配额、请求分布、下游容量 | 可运行等待、锁等待、完成吞吐 | 减线程后设备不足或吞吐显著下降 |
| 大页降低地址翻译成本 | 分配器、NUMA、数据与并发 | 翻译事件、大页覆盖、缺页与长尾 | 覆盖不足，或规整成本超过收益 |
| 直接 I/O 改善内存治理 | 文件系统、缓存总额、请求大小 | 缓存复用、回收、读延迟 | 小读放大，预取不足，内存总账不降 |
| io_uring 减少提交开销 | 队列深度、批量、缓冲和持久性 | 总 CPU、提交与消费等待 | 完成积压、取消异常或工作线程成本上升 |
| 零拷贝减少搬运开销 | 负载字节、连接、加密与接收速率 | CPU、带宽、未释放字节 | 小消息回退多、缓冲池耗尽 |
| BBR 改善目标路径 | 实现版本、流量、时延与竞争流 | 吞吐、排队、重传与公平性 | 业务受限，或其他流退化 |
| RDMA 数据通道值得建设 | 对象协议、消息规模、可靠性要求 | 端到端成本、注册与轮询开销 | 控制与恢复复杂度超过可证明收益 |

请求发生器也属于实验条件。若只在前一请求完成后发下一请求，服务变慢时发生器会自动降速，可能低估过载和长尾；需要同时说明到达模式、实际请求率与最大在途数。反过来，无上限开放发送又可能测成发生器或队列崩溃，而不是目标稳态能力。

观测命令只作为入口，必须解释字段。下面读取当前进程所属路径、压力与系统统计；应在真实目标进程和对应控制组下执行，不从一次命令推断根因。

```bash
cat /proc/self/cgroup
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
vmstat 1
ss -tin
```

这些命令没有替你测出请求归因，也不证明设备、驱动和框架具体路径。控制组文件需根据目标进程路径与挂载位置定位，不能假设本机根目录就是目标容器的有效限制；计数器应比较时间窗口内增量，避免拿累计值关联一次尖峰。

对于 Linux 内存回收，也不要把教材中的最近最少使用（Least Recently Used，LRU）顺序直接当成当前系统实现。【事实】Linux 提供多代 LRU（Multi-Gen LRU）实现，其是否启用依赖配置和运行时开关，参见 [官方回收文档](https://docs.kernel.org/admin-guide/mm/multigen_lru.html)。淘汰策略、物理页分配和应用缓存淘汰分别解决不同层的问题。

### 白板推演：同一份资源只能归还一次

这一练习对应第 6、8、11 题，不增加另一套接口教程。面试官可以要求你写出“业务结束但底层尚未终结”的状态，并构造乱序事件；只画正常路径不足以证明安全。

【推断】把用户结果与资源状态分开，可以避免一个 `done` 同时承担超时、取消、I/O 完成和内存释放四种含义。下面是单线程事件归并器上的伪代码，不是可直接用于并发环境的 C++ 实现；跨线程事件必须先由明确的同步协议串行化。

```text
Request:
    user_result = pending
    payload_terminal = false
    release_notice_required = false
    release_notice_seen = false
    credits_returned = false
    buffer = owned

on_business_timeout(req):
    if req.user_result == pending:
        req.user_result = timeout
        request_cancel(req.id)
    # 业务返回不修改底层终结与缓冲状态

on_cancel_result(req, result):
    record_cancel_result(result)
    # 取消项的结果不能替代目标项的终结证据

on_target_completion(req, result, flags):
    req.payload_terminal = is_final_target_event(flags)
    req.release_notice_required = needs_release_notice(flags)
    if req.user_result == pending and req.payload_terminal:
        req.user_result = map_business_result(result)
    try_release(req)

on_release_notice(req):
    req.release_notice_seen = true
    try_release(req)

try_release(req):
    if not req.payload_terminal:
        return
    if req.release_notice_required and not req.release_notice_seen:
        return
    if not req.credits_returned:
        req.credits_returned = true
        return_credits_for_owned_bytes(req)
        release_buffer(req)
```

其中决定性的分支是“目标已终结”与“附属释放条件已满足”的合取。即使用户结果已超时，两个条件不满足时仍由运行时持有缓冲；真正归还的字节必须与仍归该对象所有的字节一致。

这段伪代码仅示意一种状态表达方式，不构成正确性证明；普通目标完成与释放通知须先分类分派，不能把释放通知再次当作目标完成更新状态。它尚未解决部分发送、多次完成操作、已提交数据与未提交数据分段、连接销毁和通知错误。用于零拷贝接口时，要按该接口检查通知标志及失败路径；用于普通文件读时，不应凭空等待不存在的释放通知。

面试官可用四条事件序列检验状态机：正常完成后超时、超时后正常完成、取消找不到目标但目标完成已排队、业务已返回而释放通知延后。对每条序列，应说明用户结果、缓冲和信用各变化几次，而不是只答“加引用计数”。

再加入一个关闭事件：旧请求完成项到达前，连接数字已被新连接复用。若事件只按描述符查对象，上面的释放保护仍无法防止误命中新对象；稳定请求标识与对象持有关系必须在事件进入归并器之前成立。

最后检验异常：归还信用后，如果销毁缓冲触发回调或提交新工作，是否重入同一对象？若有，应先提交不可重复的状态，再执行外部动作，或将动作放入后续事件，避免递归路径再次归还额度。

这个练习的合格产物是状态表、反例序列和明确的适用范围。没有实现及并发验证，就只把它称为设计推演；不能因伪代码看起来顺序正确，就宣布真实运行时已经没有释放竞态。

## 九、勘误：从原料中的简化和错误到可追问的边界

这里列出实际修订对象。未在本文展开的密码存储、语言对象模型等原料错误，不借本篇范围做无关扩展；新增技术与纠正原料分开看，避免把扩写冒充原文已有内容。

1. **“线程切换只保存寄存器，进程切换必然刷新全部快表”。** 改为区分执行上下文、地址空间与间接缓存成本；地址空间标识和体系结构会影响翻译缓存行为，不能给出一律全刷的结论。本文不提供未测量的切换耗时。

2. **“进程不是调度单位”。** 改为 Linux 调度执行任务，线程与进程的共享关系需要结合创建方式解释；单线程进程也具有可调度执行实体，不能用概念表格否认它被调度。

3. **“原子操作永远最快，自旋锁次之”。** 删除统一性能排序；争用、持锁者调度、缓存行迁移和临界区决定成本。原料 某题目详解 的自旋示例把成功写入值写为 `false`，无法建立独占，本文不复用该代码。

4. **“`std::lock` 原子获得多把锁”。** 原料使用“原子”容易被理解为单条不可分割操作；应理解为采用避免死锁的多锁获取算法，其内部可多次尝试。参见 [C++ 工作草案的锁算法契约](https://eel.is/c++draft/thread.lock.algorithm)。本文用状态与锁顺序推演，不沿用该错误表述。

5. **“虚拟内存让大于物理内存的程序总能运行”。** 增加工作集、后备存储、过量承诺和控制组条件。映射存在不保证所有页面可同时驻留，缺页也不一定读磁盘。

6. **“`brk` 小于 128 KB，`mmap` 大于等于 128 KB”。** 改为分配器版本和参数相关的策略，不能把某个初始默认阈值当成所有分配路径不变的分界；对象释放与常驻内存下降也不等价。动态阈值的官方说明见 [mallopt(3)](https://man7.org/linux/man-pages/man3/mallopt.3.html)。

7. **“epoll O(1)、无限描述符、只发生一次复制”。** 改为避免每轮扫描完整关注集合，但返回及处理就绪事件有成本；仍有描述符、内存与监控限制，事件结果也需要传给用户态。

8. **“边缘触发更可靠，没一次读完就会丢数据”。** 改为通知语义与推进责任；未读取数据并不会因此从 TCP 缓冲消失，应用可能因等待新通知而停住。加入主动就绪队列与每轮公平预算。

9. **“非阻塞 I/O 就是异步 I/O，异步一定最快”。** 改为区分调用是否等待、通知就绪还是完成，以及实际执行位置；io_uring 也可能使用工作线程，轮询也消耗 CPU。新增接口不能凭名称判定收益。

10. **“TCP 最大连接数是 65535”。** 改为按地址四元组与资源限制分析；监听端本地端口可以承载不同远端连接，客户端到固定目的地的临时端口约束另算。

11. **“`tcp_fin_timeout` 缩短 `TIME_WAIT`，`somaxconn` 控制未完成握手数量”。** 前者应解释为孤儿 `FIN_WAIT_2` 的超时参数；后者限制监听连接积压上限。半连接队列与应用请求队列也不能混为一谈。

12. **“换更快网卡、使用非阻塞可以缩短 `TIME_WAIT`”。** 删除因果关系；它们不直接改变状态驻留规则。地址复用选项也不自动清除旧连接，优先检查连接周转与失败资源。

13. **“`TIME_WAIT` 固定 1—4 分钟且只可能在主动关闭方”。** 保留协议两倍最大报文生存时间的解释，具体计时核对实现，同时关闭需单独处理；不把某个示例时长写成普遍事实。

14. **“TCP 关闭必须恰好四个包，HTTP/2 消除了全部队头阻塞”。** 改为独立关闭两个发送方向，确认可合并；HTTP/2 多流仍共享 TCP 有序交付，应用层与传输层阻塞分别说明。

15. **“Protocol Buffers 自动解决 TCP 消息边界，20 字节 TCP 头与 1500 字节 MTU 都固定”。** 增加外层分帧、长度校验、可选头部、路径与卸载条件，避免把序列化格式和特定链路示例当成协议通则。

16. **原料没有覆盖的新机制。** 多尺寸透明大页、sched_ext、设备内存 TCP 与 io_uring 零拷贝接收作为 2024—2025 年补充，分别注明版本文档与部署条件；cgroup v2、RDMA 与 eBPF 以资源和失败边界组织，不冒充它们都是最近两年出现的新技术。

本文没有复现内核调度、大页、拥塞控制或 RDMA 的性能实验。若拿本篇作为面试材料，下一步应选择一个允许披露的真实案例，补齐版本、资源配置和证据，然后让同伴沿取消、复用与过载方向追问三层；任何缺失的数据保留【模板】，不能以通用原理填补个人履历。
