> **系列导航**：这里是[面试系列索引](/2026/10/24/interview-series-index/)，七篇正文入口见下文；代码判断与团队评审案例可配合 [Code Review 系列](/2026/10/24/code-review-series-index/)准备。本文是导航与练习协议；七篇正文已作为同系列一并发布，阅读时仍以机制证据为准，而不是以发布状态代替掌握程度。

这个系列解决一个具体问题：有十年以上数据库内核经验，如何在有限面试时间内，证明自己能够负责一个复杂子系统、推动跨团队决策，或者把已有能力迁移到人工智能基础设施（AI Infrastructure）岗位。准备产物应包括可以追问的机制解释、可核验的个人贡献，以及明确的适用边界；阅读进度和术语数量不足以证明这些能力。

【推断】对 Kevin Li 而言，准备主线应从在线分析处理（Online Analytical Processing，OLAP）、优化器（Optimizer）、物化视图（Materialized View，MV）与增量视图维护（Incremental View Maintenance，IVM）展开，再连接向量化执行（Vectorized Execution）、资源管理和失败恢复。理由是：沿一个熟悉的请求或状态变化解释正确性，比同时复习多个陌生系统更容易形成可核查的深度证据。

StarRocks 核心开发者与代码提交者（Committer）、以及大型分布式 SQL 引擎与增量视图维护相关工作，是选材起点。开源身份与过往职级都不能直接换算成另一家公司的职级，也不能替代本人职责、代码位置和结果条件。涉及项目成绩、事故处理和组织影响的叙述，都应由 Kevin 补充允许披露的真实材料。

## 先选岗位路径，再决定在哪一篇停下来深挖

下面的高级工程师（Senior）、资深技术专家（Staff）、技术负责人（Tech Lead，TL）划分，是本系列的备考框架【推断】，不是各公司的统一职级定义。技术架构师也应按实际决策范围选择路径，而不是仅按职位名称备考。

| 目标岗位 | 建议阅读顺序 | 需要提交给自己的证据 | 最容易遗漏的边界 |
|---|---|---|---|
| Senior 数据库／系统工程师 | ①方法 → ②数据库 → ③C++ → ④系统网络 → ⑤算法设计 → ⑦行为 | 一个模块的正确性推演、一次定位过程、一份可运行的编码练习 | 只讲成功路径，不解释取消、异常和恢复 |
| Staff／技术架构师 | ①方法 → ②数据库 → ⑤算法设计 → ⑦行为，再按短板补③④⑥ | 两种可替代方案、跨模块契约、迁移与回退条件 | 把系统规模当作本人影响范围 |
| TL | ①方法 → ⑦行为 → ②数据库 → ⑤算法设计，再补③④⑥ | 决策记录、责任划分、分阶段交付和团队复用的验收标准 | 把亲自解决问题等同于让团队持续解决问题 |
| AI 基础设施／智能体运行时 | ①方法 → ⑥AI → ⑤算法设计 → ③C++ → ④系统网络 → ⑦行为，用②解释迁移基础 | 一张请求生命周期图、一组失败注入方案、一份尚未验证的假设清单 | 把数据库缓存与模型状态缓存当成同一种语义 |

智能体运行时（Agent Runtime）方向还要区分推理服务与工具执行：前者关心调度、内存、算子和延迟，后者关心持久状态、外部副作用、重试与权限。两者可以共享基础设施，面试时仍须先确定自己负责哪条执行链。

如果目标岗位的主要职责是模型训练或算法研究，本系列只能覆盖部分系统能力；需要另补训练数值稳定性、优化算法和对应实验。若岗位主要做应用交付，也应先确认是否需要深入图形处理器（Graphics Processing Unit，GPU）算子，避免把两周都花在与职责无关的底层细节上。

## 七篇正文：每篇回答一个主问题

1. **[方法与策略：把经历整理成可验证的回答](/2026/10/24/interview-method-and-strategy/)**：从岗位描述反推材料、分配技术深挖与编码时间，并用模拟追问发现叙述中的证据缺口。
2. **[数据库内核：沿查询、视图维护与恢复解释正确性](/2026/10/24/interview-db-kernel/)**：围绕优化等价条件、增量状态、执行成本与存算分离（Disaggregated Storage and Compute），把产品经验展开为机制判断。
3. **[C++ 与系统编程：所有权、并发与性能边界](/2026/10/24/interview-cpp-systems/)**：从对象生命周期和内存序（Memory Ordering）切入，追问分配器、容器、单指令多数据（Single Instruction Multiple Data，SIMD）优化与故障诊断。
4. **[操作系统与网络：请求为什么排队、阻塞和超时](/2026/10/24/interview-os-network/)**：把线程调度、虚拟内存（Virtual Memory）、输入输出（Input/Output，I/O）和传输控制协议（Transmission Control Protocol，TCP）放回端到端请求中解释。
5. **[算法与系统设计：从资源预算推导数据结构和架构](/2026/10/24/interview-algorithms-system-design/)**：把限时编码与容量估算连接起来，讨论倾斜、外部计算、背压（Backpressure）、缓存和失败时的成本归属。
6. **[AI 时代的基础设施与智能体：迁移能力，也验证新边界](/2026/10/24/interview-ai-era-infra-agents/)**：围绕 vLLM 推理引擎、CUDA Graph（CUDA 执行图）、检索增强生成（Retrieval-Augmented Generation，RAG）与智能体，区分调度性能、检索质量和工具副作用。
7. **[职业、行为与 Staff 叙事：证明决策和组织影响](/2026/10/24/interview-career-behavioral-staff/)**：从真实项目、技术分歧和失败案例提取本人贡献，并把求职选择落到职责、资源和可持续的工作条件。

每篇正文都应沿“题目 → 强答要点 → 追问链 → 常见差答／陷阱”组织主题。索引只演示两条入口追问，具体机制留在正文展开，避免七篇重复回答同一组基础定义。

## 入口练习：能否从技术深度走到责任范围

### 题目一：为什么这个岗位应该相信你的内核经验？

**题目**：“从你做过的一项优化出发，说明为什么它足以支持你应聘 Staff。”

**强答要点**：【推断】先给问题与约束，再选一个决定性的机制展开：原方案在哪个条件下失败，替代方案为何成立，验证排除了什么，谁承担迁移成本。Staff 部分继续解释接口如何约束其他模块、意见如何收敛、自己离开后谁能维护。技术深度与组织影响需要分别举证，不能把参与项目的全部结果计入个人贡献。

**追问链**：第一层，“拿掉这项优化，哪个负载先退化，为什么？”→ 第二层，“修正代价估算与改变执行策略，为什么选后者？”→ 第三层，“收益只出现在部分客户时，谁决定默认启用、如何回退？”每层都应给证据或承认尚无证据；最后一层需要真实决策记录，不能临时编造组织故事。

**常见差答／陷阱**：“我是核心开发者，系统吞吐提升很多”“我们做了全链路优化”。前者缺少负载与本人角色，后者无法定位决定性改变。若只是参与实现，应如实说明负责的部分，并解释对上游设计的理解。

**【模板】**：项目／版本：〔填写〕；原始问题与约束：〔填写〕；本人修改与其他人贡献：〔分别填写〕；决定性反例或实验：〔填写〕；未采用方案：〔填写〕；跨团队决策与维护责任：〔填写〕；仍未覆盖的场景：〔填写〕。

### 题目二：数据库经验如何迁移到 AI 基础设施？

**题目**：“你熟悉查询引擎，但没有足够的推理服务生产经验，为什么能负责相关系统？”

**强答要点**：【推断】先说明已有经验覆盖资源生命周期、批处理、排队、取消和恢复，再明确新系统还需验证的模型状态语义、设备执行与评价指标。用一条请求从进入、调度到释放资源的路径对照，说明哪些判断可迁移、哪些只能算设计假设。若尚未部署过，就展示源码复核与实验计划，不声称已取得生产收益。

**追问链**：第一层，“数据库执行批次与逐步生成请求的调度约束有什么差异？”→ 第二层，“客户端取消后，何时能安全回收仍在设备上使用的状态？”→ 第三层，“工具调用超时但外部写入可能成功，恢复时如何避免重复副作用？”第三层已从推理进入智能体运行时，需要单独给出业务操作的幂等性（Idempotency）或结果核对机制。

**常见差答／陷阱**：“都是缓存和调度，换一下接口即可”“用了智能体框架就能恢复”。类比只帮助提出问题；它不能证明状态可共享、取消已完成、外部操作可重放，也不能证明质量与成本达标。

## 2024—2026 的补充：用新材料检验旧经验

【事实】2024 年的 [FlashAttention-3 论文](https://arxiv.org/abs/2407.08608v2)围绕 Hopper 架构，讨论异步计算与数据搬运的重叠及低精度机制；2026 年的 [FlashAttention-4 论文](https://arxiv.org/abs/2603.05451v1)针对 Blackwell 架构重新安排流水线并减少部分非矩阵计算。【推断】因此第⑥篇应要求解释硬件变化如何改变瓶颈，不能把“做过 SIMD”直接当作已掌握 GPU 优化。两篇论文的算子实验也不能直接推出完整服务的吞吐收益。

【事实】[vLLM V1 官方架构文章](https://vllm.ai/blog/2025-01-27-v1-alpha-release)发表于 2025 年 1 月，说明执行循环、调度器、前缀缓存和分段 CUDA 执行图等改动；文章描述的是当时的早期版本。【推断】面试练习应记录实际阅读的版本与代码路径，再讨论主机调度和设备执行如何重叠，不能把这篇发布说明当作 2026 年所有配置的行为保证。

【事实】Anthropic 的 [Building effective agents（构建有效智能体）](https://www.anthropic.com/research/building-effective-agents)区分预定义代码路径的工作流（Workflow）与由模型动态决定流程、工具使用的智能体（Agent），并讨论复杂度、延迟与成本的取舍。【推断】第⑥篇据此先问“是否需要动态决策”，再讨论恢复和工具接口；供应商的工程经验不等于所有业务中智能体都优于固定流程的实验结论。

这些材料分别补充硬件、服务架构和控制流程三个维度，不组成“热门项目必考清单”。本索引不复现论文或服务基准；具体实验要另保留模型、硬件、精度、请求分布、并发、版本和测量方法。

## 与代码评审系列共用案例，承担不同任务

例如，在[代码评审与 Agentic 研发一文](/2026/10/24/code-review-series-index/)里，一个异步资源释放问题需要落实阻塞条件、修复和断言；到本系列第③④篇，要解释对象、线程、请求和设备之间的生命周期；到第⑦篇，要补充争议如何处理、谁负责修复和后续维护。

【推断】两组系列共用一个真实案例档案即可：代码或设计版本、触发条件、本人判断、验证记录、决策过程、剩余限制。不能把阅读公开补丁的复核练习写成自己参与的评审；个人表达可参考[代码评审面试篇](/2026/10/24/code-review-series-index/)，技术证据仍由案例本身提供。

**【事实】**表示有可追溯依据的行为或记载。源码结论需要版本、位置和调用路径；论文结果需保留实验条件；官方文章只支持其明确陈述的机制或经验，不证明 Kevin 参与过该工作。

**【推断】**表示从约束推导出的判断、备考安排或尚未验证的设计。需要说明假设、代价与可推翻判断的观察；它不表示“虽然没有证据，但可以当作事实背诵”。

## 两周冲刺：每天留下可复查的产物

【推断】下面按已有内核经验、每天可投入约两小时设计，是可调整的练习预算，不是“两周达到 Staff”的承诺。每天约一小时处理主题，半小时脱稿回答与追问，半小时核查证据；发现基础缺口时，优先减少覆盖面，保留验证时间。

| 天数 | 阅读与练习 | 当天产物与验收条件 |
|---|---|---|
| 第1天 | ①，拆解两份真实岗位描述 | 职责—证据对照表；不能拿职级名称代替职责 |
| 第2天 | ①⑦，盘点两个真实项目 | 两张案例卡，区分本人修改、团队贡献和未验证结论 |
| 第3天 | ②，优化器与查询语义 | 一个带成立条件的优化推演及反例；说明版本 |
| 第4天 | ②，视图维护与恢复 | 一张状态变化图；解释删除、重试与恢复边界 |
| 第5天 | ③，所有权与并发 | 一段最小代码或真实补丁；解释取消和异常路径 |
| 第6天 | ④，排队、内存与网络 | 一份诊断假设表；每个工具观察都对应一个待排除原因 |
| 第7天 | ①—⑤，第一轮模拟 | 保存追问记录；只选三个有证据缺口的问题进入下周 |
| 第8天 | ⑤，限时编码 | 一道代表题的实现、边界用例及复杂度；不用题量充当验收 |
| 第9天 | ⑤，系统设计 | 容量估算、两种方案和故障场景；分清请求率与并发数 |
| 第10天 | ⑥，推理引擎请求路径 | 标明版本的调度与资源生命周期图；列出需实验确认之处 |
| 第11天 | ⑥，检索与工具执行 | 一个超时后的恢复推演；分别验收答案质量与副作用处理 |
| 第12天 | ⑦，技术分歧与影响 | 两个真实叙事；能回答谁决策、谁实现、谁维护 |
| 第13天 | 目标岗位主路径，第二轮模拟 | 将第7天的缺口重新追问；无法解释的内容从能力声明中移除 |
| 第14天 | ①⑦，收敛材料与反问 | 一份面试前速查页、待验证清单与针对目标团队的反问 |

Senior 路径可把第11天换成模块调试；Staff／TL 路径应让第9、12天共用一个跨团队案例；AI 基础设施路径可以减少第4天的复习时间，补充设备状态管理，但应保留一项数据库深度案例。【推断】这些调整让已有证据与岗位缺口同时得到准备，比把所有题都平均过一遍更容易发现不匹配。

## 勘误

以下仅说明本索引相对原料的处理，不声称已修订其他七篇或修改原始文档。

- `how-to-interview(raw).md` 中“数据库、数据结构、算法”原本是某位作者的个人面试习惯；`interview-guide.md` 将其扩展成“必问三项”。本索引恢复为按岗位取舍的建议，不把个人习惯写成行业统一规则。
- `how-to-interview.md` 的“简历通过率约 20—30%”“顶尖公司录取率低于 5%”没有在相关段落提供样本、口径和统计来源。本索引不沿用这些数字，也不据此安排投递数量。
- `how-to-interview.md` 将 Committer 身份直接列作技术深度证明。本索引改为用本人贡献、机制解释和可核验材料建立判断；身份本身无法说明具体参与范围。
- 原料中的请求率与并发数混写被拆开：第9天需分别估算单位时间到达的请求数与同时在系统中的请求数。二者量纲不同，不能把“每秒请求数”写成“并发查询数”。
- `career-philosophy.md` 中“最终答案一定会让人流泪”等表述属于经验主张，本索引不把情绪反应作为职业选择的有效性标准；历史海外求职流程、费用及签证规则也未被沿用为当前操作指南。

冲刺结束时，只保留能够说明机制、验证条件和本人贡献的能力声明。两周计划适用于整理已有经验与定位缺口；若目标岗位要求的关键能力尚无实践证据，就继续做有明确验收条件的小实验，并在面试中说明其验证范围。
