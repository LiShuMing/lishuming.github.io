## 一、先固定问题，再决定展示哪一层能力

### 1. 开场题：面对陌生问题，如何建立可检验的回答

**题目**：给你 45 分钟，设计一个高并发数据服务，或者实现一个海量数据算法。你先问什么，何时开始写代码或画图？

**强答要点**：先固定输入、输出及错误条件，再给最低可行解；用一个约束排除明显不可行方案，然后选择一个关键路径深入。算法题需要循环不变量和复杂度前提，系统题需要成功确认点、持久化边界及超时后的行为。二者都应给出推翻自己方案的反例。

可以把开场压缩成四句话：

1. 输出要求是精确结果、近似结果，还是在期限内返回可用结果？
2. 输入规模、分布和更新方式是什么，是否允许修改输入或落盘？
3. 时间、内存、带宽及一致性约束中，哪一个必须优先满足？
4. 我先构造一个可证明正确的基线，再根据瓶颈选择优化。

“先写暴力解”是思考基线，不意味着任何题都要现场实现低效版本。若排序基线已经明显超过时间预算，说明原因即可；把剩余时间留给边界、代码与验证。复杂度比较必须以相同输出要求为前提，返回无序前 K 个元素与返回有序结果并非同一任务。

【推断】45 分钟设计练习可按约 5 分钟澄清、8 分钟估算与主路径、20 分钟深挖、8 分钟故障与验证、4 分钟收束安排。面试官已经给定规模或要求编码时，应直接调整，不把时间分配当作流程规范。

**追问链**：

1. 面试官不提供规模怎么办？提出两组假设，例如内存可容纳与不可容纳，说明跨越哪条边界会改变算法。
2. 对方要求立即给方案怎么办？先声明一个最小假设并给主路径，再明确最可能推翻选型的条件。
3. 讨论进入实现细节，如何判断该停？回到当前瓶颈：若细节不能改变正确性、容量或故障结果，就先记录为待展开项。

**常见差答／陷阱**：“先上分布式”“所有请求最终一致即可”“按经验用某产品”。这些回答跳过了成功的定义；即使组件都能运行，也无法判断业务目标是否满足。

### 2. 数量题：每秒请求数与并发数如何约束架构

**题目**：原料要求“日增 10 TB、历史 1 PB、1000 并发、P99 小于 1 秒”，这些条件足够设计实时分析服务吗？

**强答要点**：不够。在线分析处理（Online Analytical Processing，OLAP）要区分点查、固定报表和任意交互查询。每秒查询数（Queries Per Second，QPS）描述到达率，并发数描述在途数量；P99 是 99 分位延迟，不能直接当成平均延迟代入排队公式。

【事实】在稳定、统计口径一致的系统中，利特尔定律（Little's Law）给出平均在途数 L = 到达率 λ × 平均停留时间 W。若到达率是 1000 次／秒，平均停留时间为 0.2 秒，则平均在途约 200；这不能推出 P99，也不能保证突发时只有 200 个请求。

按十进制单位演算，10 TB／日约为 116 MB／秒平均原始输入。如果题设再给 5 倍峰值，则峰值约 580 MB／秒；压缩、索引、复制和后台重写要分别计量。不要先乘一个没有依据的“数据库膨胀系数”，也不要把平均摄入吞吐当成峰值写入能力。

假设单条查询实际读取 1 GB，1000 次／秒意味着约 1 TB／秒的逻辑读取需求。是否可行取决于裁剪、压缩、共享缓存和机器规模；只知道历史总量无法得出结论。固定报表若能命中预聚合，成本模型又完全不同。

**追问链**：

1. CPU 利用率只有 40%，为什么 P99 很高？检查队列等待、单核串行路径、热点分片、远端读取与锁等待，不能只看整机均值。
2. 扩容两倍，吞吐能否翻倍？识别可并行部分与共享瓶颈，检查元数据、网络、热点及后台维护是否也增加容量。
3. 如何留下安全余量？用节点失效、峰值到达和维护重叠三种场景验算，余量由容错目标决定，不背固定百分比。

**常见差答／陷阱**：把“1000 并发”等同“1000 QPS”；用 P99 替代平均值；给每个组件分配同样的 P99 后相加。端到端尾延迟需要联合分布或实际链路观测，分位数不能一般性直接相加。

## 二、通用算法题要展示可迁移的不变量

### 3. 二分与窗口：何时可以删除一半搜索空间

**题目**：实现有序数组的左边界查找，再解决“最长连续区间满足某条件”。怎样证明边界和窗口收缩不会漏解？

**强答要点**：二分查找（Binary Search）依赖单调判定，滑动窗口（Sliding Window）依赖扩展与收缩对合法性的可预测影响。先说明性质，再写模板；代码形状相似不意味着成立条件相同。

左边界采用半开区间 [lo, hi)，保持 lo 左侧都小于目标，hi 及右侧都不小于目标。终止时 lo = hi，返回的是插入位置，范围是 0 到 n。使用无符号长度时，空数组上不要先计算 n - 1。

```cpp
#include <cstddef>
#include <span>

std::size_t lower_bound_index(std::span<const int> a, int target) {
    std::size_t lo = 0;
    std::size_t hi = a.size();
    while (lo < hi) {
        const auto mid = lo + (hi - lo) / 2;
        if (a[mid] < target) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    return lo;
}
```

这个片段使用 C++20，只建立左边界语义；没有验证输入已排序，也没有承诺并发修改安全。现场测试至少覆盖空数组、全部相等、目标小于最小值和大于最大值。若题目要“是否存在”，还要检查返回位置小于 n 且元素等于目标。

对于正数数组的区间和约束，扩展右端不会使和下降，可以据此收缩左端。加入负数后该性质失效，应考虑前缀和、单调队列或其他结构。对乘积约束，还需要处理 0、负数和溢出；不能仅把“和”改成“乘积”。

**追问链**：

1. 如何找最大可行资源配置？先证明可行性随参数单调，再把答案搜索转化为二分；存在离散跳变不影响单调性，但多峰目标不适用。
2. 窗口最大值为什么能线性完成？单调队列中，每个下标最多入队和出队一次，总操作次数为 O(n)，不是每个循环都只做常数工作。
3. 数据乱序到达怎么办？数组窗口的下标顺序不等于事件时间顺序；要增加缓冲和迟到策略，问题已经变成流处理语义设计。

**常见差答／陷阱**：背“左闭右开”但无法说出不变量；把任意区间约束套成双指针；把原料中返回“最后一个 ≤ 目标的位置”的函数叫作标准 `upper_bound`。标准语义是第一个大于目标的位置。

### 4. 堆与选择：Top K 的答案在哪里完成聚合

**题目**：1 TB 文本、1 GiB 内存，求精确词频前 10；若改成多节点分别上报局部前 10，是否仍然正确？

**强答要点**：前 K 项（Top K）先区分按数值选元素与按频次选键。前者可用选择算法；后者必须先完成同键计数。小顶堆只解决从完整计数结果中保留候选，不解决统计状态超内存。

【推断】精确离线方案可以先按完整词键做哈希分区，使同一个词只属于一个分区，再逐分区计数、选局部前 10，最后归并候选。哈希碰撞只让不同词进入同一分区，分区内仍比较完整键；不能用哈希值替代原词判等。

分区数由唯一键数、平均键长、装载因子、计数器和分配开销决定。一个 1 GB 原始文件不保证能放进 1 GiB 哈希表；超过预算时应递归分区或外排。单一高频词会使文件很大但状态很小，不能把文件大小倾斜与唯一键状态倾斜混为一谈。

同键已经归到唯一分区时，局部前 K 可覆盖全局前 K：一个键若在自己的分区严格落后于 K 个键，它也无法进入全局前 K。遇到频次相同，必须统一第二排序键；若要求“所有并列第 K 名”，候选数量可能超过 K。

任意按行切分则不成立。取 K = 1：分片 A 为 x:6、a:7，分片 B 为 x:6、b:7；各取局部第一只得到 a、b，但全局第一是 x:12。这个反例足以说明需要先做跨分片同键归并。

**追问链**：

1. 只选数组前 K 个数呢？小堆 O(n log K)、原地快速选择期望 O(n)、排序 O(n log n)；需要有序输出时还要对候选排序。
2. 哈希分区遇到攻击性键分布怎么办？保留分区统计、限制单分区资源，换种子只能缓解某些碰撞，必要时回退外排；不能保证把同一个键拆散后仍直接取局部前 K。
3. 允许近似能省什么？可用频次草图保留候选并给出误差界，但某些草图本身不保存键，还需要候选集合；要求精确结果时需要重扫确认。
4. 如何验证实现？小输入与完整计数排序对照，增加跨分片热点、相同频次、超长键、空输入和计数溢出案例。

**常见差答／陷阱**：“固定切 1000 份即可”“先算每个机器的前 10 再合并”“用 HyperLogLog 找热点”。最后一种把基数估计与频次估计混淆了。

### 5. 图与动态规划：状态压缩必须保持未来决策所需信息

**题目**：实现有依赖关系的任务调度，再说明动态规划题中的状态为什么足够。二者如何迁移到查询计划或智能体任务？

**强答要点**：有向无环图（Directed Acyclic Graph，DAG）调度先维护未完成前驱数，只有前驱全部成功的任务才能进入就绪队列。拓扑排序（Topological Sort）只是依赖顺序，不负责并发额度、失败恢复和外部副作用。

【事实】按邻接表存图，入度法处理所有点边的时间为 O(V + E)。若处理点数少于 V，只能推出剩余子图存在环或被环阻塞；要给出环上具体节点，还需要进一步搜索，不能把所有剩余节点都标为环成员。

任务失败时必须定义下游是取消、重试还是使用补偿。重试需要任务标识和代际；旧执行结果回来时，不能覆盖新一代状态。智能体（Agent）调用外部工具后丢失响应，重跑图节点可能重复执行付款或发送动作，DAG 本身没有恰好一次的保证。

动态规划（Dynamic Programming，DP）则要先说明状态是否覆盖未来决策。0/1 背包一维数组按容量倒序更新，是为了让本轮读取仍来自上一轮物品状态；正序会让当前物品在同一轮被重复使用，变成另一个问题。

最长递增子序列（Longest Increasing Subsequence，LIS）的尾值数组保存各长度下的最小末尾，不必形成原数组的一条真实子序列。若要恢复路径，还需前驱及索引信息。能说清“压缩掉了什么”比复述转移公式更能证明理解。

**追问链**：

1. 图很深，递归搜索有什么风险？调用栈可能随深度增长；用显式栈保留状态，同时仍需访问标记避免重复与环。
2. 查询优化器能直接用普通背包吗？连接重排涉及关系子集、物理属性和语义约束，状态要覆盖后续组合所需条件，不能只保留一个最便宜标量。
3. 任务执行成功但提交状态失败怎么办？区分可安全重放的纯计算与外部副作用，后者需要接收端幂等或可查询的操作记录。

**常见差答／陷阱**：把拓扑序当成完整调度系统；把“用了 DP”当成最优性证明；看到状态很大就任意丢弃维度。压缩只有在保留支配关系或充分状态时才安全。

### 6. LRU 与线程池：常数复杂度不等于有界服务时间

**题目**：实现最近最少使用缓存（Least Recently Used，LRU），再把它或一个线程池放进高并发服务。原料代码还缺什么？

**强答要点**：哈希表定位加双向链表维护次序，查找与更新是期望 O(1)；哈希退化、内存分配、锁竞争不属于这个常数承诺。容量为 0 时直接拒绝存储，不能从空链表取尾节点。生产缓存通常按字节计费，并把过期与淘汰分开。

返回值也有契约：用 -1 表示未命中会排除合法的 -1 数据，泛化接口可以返回可选值。若返回内部对象引用，需要说明淘汰、并发删除和生命周期；复制结果虽然更简单，但大对象复制有成本。

分片锁可以减少争用，却把全局严格 LRU 改成分片内近似策略。访问本身会修改链表，因此读多也可能争抢锁。是否值得维持严格次序，要比较命中收益与元数据写入成本。

线程池同样要先约束队列。无界任务队列只把过载延迟成内存耗尽；提交接口应返回接受或拒绝，携带截止时间，并定义关闭后的行为。任务异常必须捕获并传播到结果通道，不能任由异常穿出工作线程函数。

【事实】Redis 官方说明其 LRU 淘汰采用采样近似，并通过配置调整精度；这支持“策略存在实现成本”的论点，不支持“近似策略总比严格策略好”。见 [Redis 淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)。

**追问链**：

1. 工作线程向同一线程池提交子任务并阻塞等待，会发生什么？全部工作线程都等待尚未执行的子任务时可能饥饿死锁，需异步依赖或执行策略调整。
2. 取消任务时如何释放资源？区分未开始、执行中和已完成状态；协作式取消需要算子检查点，不能假设删除队列元素就终止了执行。
3. 缓存加过期时间用什么结构？惰性检查配合小顶堆、时间轮或周期扫描；更新过期时间时，旧堆条目要用版本号识别，避免删掉新值。

**常见差答／陷阱**：“get／put 都 O(1)，所以性能不会有问题”“析构时 join 就能优雅退出”“队列满了让调用者一直等”。等待策略若没有截止时间，会把池内过载传播到整个调用链。

## 三、数据库算法要沿着内存、I/O 与语义展开

### 7. 哈希连接：线性复杂度有哪些隐藏条件

**题目**：实现哈希连接（Hash Join），构建侧 80 GB，可用内存 16 GB；连接键严重倾斜，如何保持正确并控制尾延迟？

**强答要点**：先指定连接类型和键语义，再决定构建侧。内连接通常优先考虑过滤后体积较小的一侧，但选择受连接方向、外连接输出规则和物理属性约束；不能只按原表行数选。

【事实】在哈希分布合适、探测代价可控的条件下，工作量可表示为期望 O(B + P + Z)，其中 B、P 是两侧行数，Z 是输出行数。多对多热点会使 Z 远大于输入，“哈希连接是 O(n)”不能隐藏输出成本。

内存预算应包括键、载荷或行引用、桶目录、装载空隙、空值信息和分配开销。输入压缩后大小不等于构建结构大小。多个连接与聚合同时执行时，16 GB 还必须明确是单算子、单查询还是整个进程额度。

超内存可以做分区哈希连接（Grace Hash Join）：两侧按相同规则分区，逐对装载处理；过大分区继续划分或回退。分区和读回增加临时写入与读取，外溢（Spill）需要磁盘配额、取消清理及错误传播，不是一个布尔开关。

热点键会使相同哈希分区持续超限，换更多分区也不会把同键自动分开。可识别热点单独处理，或者在保证配对覆盖且不重复的前提下分块。网络倾斜与输出爆炸要分别解决；结果本来就有数十亿行时，调度无法把它变成轻量查询。

运行时过滤（Runtime Filtering）从构建侧键生成候选过滤器，可减少探测及下游处理；能否进一步减少底层读取或网络传输，取决于过滤器的下推位置、就绪时间及存储裁剪能力。内连接通常容易说明，但外连接保留侧、反连接和空值感知语义不能照搬。过滤器未就绪或失效时，应退化为多做工作，不能丢合法结果。

**追问链**：

1. 广播连接与分区连接如何选择？广播构建结构到每个接收端，网络总量及每节点内存随副本数增加；分区会重分布两侧，保留本地性可改变成本。
2. `NULL = NULL` 是否匹配？普通 SQL 等值不匹配；空值安全等值连接另有语义。字符串还要固定排序规则及哈希与相等比较的一致性。
3. 外溢后能否恢复？同一查询内读回与跨进程故障恢复是两个要求；后者需持久化分区清单、版本和完成状态，或明确选择重跑。
4. 如何评估单指令多数据（Single Instruction, Multiple Data，SIMD）收益？分离哈希计算、随机访存和比较成本，保留键宽、命中率、重复度及批大小，不把指令数减少等同整体加速。

**常见差答／陷阱**：“小表 build 大表 probe”“分区足够多就不会倾斜”“加 Bloom 就能解决连接成本”。这些回答没有处理构建结构膨胀、热点输出和 SQL 语义。

### 8. 外部排序：归并路数由内存和设备共同决定

**题目**：给 1 TiB 无序记录，排序阶段实际可用内存 8 GiB。如何估计外部排序（External Sorting）的轮次、临时空间和取消成本？

**强答要点**：先生成有序段，再多路归并。若 8 GiB 全部可用于输入排序且忽略元数据，初始约有 128 段；这是理想下界式估算。实际要扣除排序键展开、指针数组、压缩缓冲和执行框架预留。

设有 R 个段，归并扇入为 F，归并轮数约为向上取整的 log_F(R)。F 受每段输入缓冲、输出缓冲、文件句柄和并行任务限制；在共享磁盘或远端对象存储上，也受请求数量和带宽竞争约束。不能默认“开 128 个文件同时读”就是最快方案。

【事实】若每一轮都完整读写 N 字节、记录布局不变，生成段加 p 轮归并的读写量约为 2N(1 + p)。最终结果流向下游时可省最后一次物化写入；压缩、变长布局或提前终止会改变字节数。这是简化成本推导，不是设备耗时预测。

临时空间不能只给一个倍数：归并时旧输入段何时删除、输出何时确认、失败是否保留重试材料，决定峰值。设计可以在一组输入成功替换后删除旧段，但要明确失败清单，防止半成品被当成完整段读取。

【事实】DuckDB 在 2025 年 9 月介绍了随 v1.4.0 发布的排序重设计，复用可外溢的页布局并重做执行路径。它说明工程优化会跨越内存管理与算子边界；不意味着经典归并成本模型失效。见 [DuckDB 排序重设计](https://duckdb.org/2025/09/24/sorting-again)。

**追问链**：

1. 仅需要 `ORDER BY ... LIMIT 100` 呢？先考虑有界堆或局部候选，不能默认完整外排；大偏移分页和并列语义会增加所需候选。
2. 多路归并用堆还是败者树（Loser Tree）？二者都可做到每条记录 O(log F) 更新，比较器成本、分支与布局决定常数，按实际键类型验证。
3. 如何处理字符串和空值？固定排序规则、空值位置、升降序及稳定性要求；编码排序键必须与逻辑比较一致。
4. 节点被取消时怎么做？停止预取与新写入、等待在途 I/O 安全结束、释放文件引用并按查询清单回收临时段，防止残留长期挤占磁盘。

**常见差答／陷阱**：“归并排序 O(n log n)，所以选它”“内存用满即可”“临时空间永远等于输入两倍”。这些描述缺少外存成本和资源竞争条件。

### 9. Bloom 与 Cuckoo：允许假阳性，不能偷换集合语义

**题目**：为负查询多的存储或连接构建布隆过滤器（Bloom Filter）；若需要删除，是否直接换成布谷鸟过滤器（Cuckoo Filter）？

**强答要点**：先明确过滤器只做成员资格预判。标准 Bloom 在正确构建、查询且未错误清位时，可以判定“一定不存在”或“可能存在”；后者仍需精确存储确认。过滤器不返回原元素，也不能作为精确去重集合。

【事实】对 m 位、n 个插入元素、k 个近似独立均匀哈希，假阳性率近似为 `(1 - exp(-kn/m))^k`；最佳 k 近似为 `(m/n) ln 2`。给定目标误判率 p，每元素位数近似为 `-ln(p)/(ln 2)^2`。这些近似依赖模型，不覆盖恶意输入和错误并发实现。

【推断】若 n = 10 亿、p = 1%，约需 9.6 bit／元素，位数组约 1.2 GB，k 约为 7。这个预算不含构建临时结构和版本副本；如果每次请求都远端读取过滤器，预判的网络成本可能吞掉收益。

删除不能直接清 Bloom 的位，因为其他元素可能共享它。计数布隆过滤器（Counting Bloom Filter）用计数器支持受约束删除，但增加空间并需防溢出。不可变文件常可在重写时重建过滤器，未必需要可删除结构。

【事实】Cuckoo Filter 存储短指纹并检查候选桶，支持插入和删除，但接近容量时插入可能失败。删除要求有正确的成员管理，不能仅凭一次阳性就删除任意未插入键，否则可能误删碰撞指纹。见 [CoNEXT 2014 论文](https://www.cs.cmu.edu/~dga/papers/cuckoo-conext2014.pdf)。

**追问链**：

1. 更新期间如何避免新键被误判为不存在？先发布覆盖新键的版本，或对未覆盖时间段旁路查询；“理论无假阴性”不能替代发布协议。
2. 如何决定是否启用过滤器？比较负查询比例 × 可省精确读取成本，与哈希、访问过滤器、构建和分发成本。
3. 多个过滤器能否合并？兼容 Bloom 可按位或，但需同尺寸和同哈希规则，合并后占用率及误判率不会降低，通常会上升；不能据此推断 Cuckoo 指纹数组可直接逐位或。
4. 误判率达标为何还是慢？检查随机访存次数、缓存行访问及下游读取大小；概率指标并非延迟指标。

**常见差答／陷阱**：“过滤器有误判，所以可能把真实数据漏掉”“Cuckoo 支持删除，因此任意阳性都可以删”“1% 假阳性等于整体准确率 99%”。假阳性率的分母是不存在的查询，不是所有查询。

### 10. HyperLogLog：可合并的统计状态不等于可撤回的统计状态

**题目**：每天十亿事件，统计不同用户数，跨分片合并并支持最近 7 天窗口；为什么选 HyperLogLog，删除怎么办？

**强答要点**：HyperLogLog（基数估计草图，HLL）把均匀哈希分桶，保存各桶观察到的秩，再通过估计器还原基数。它估计不同值数量，不回答“用户 x 是否存在”，也不提供用户频次。

【事实】经典分析给出相对标准误差约为 `1.04/sqrt(m)`，m 为寄存器数。若 m = 16384，约为 0.81%；这不是每一次估计都落在 ±0.81% 的硬保证。小基数修正、哈希宽度与实现细节还会影响实际误差。见 [HLL 原始论文](https://algo.inria.fr/flajolet/Publications/FlFuGaMe07.pdf)。

合并时对兼容状态逐寄存器取最大值。这里的兼容包括哈希函数、种子、精度及编码约定；不能把两个最终估计数相加当作并集，因为用户可能重复。数据库聚合接口应该传递可合并状态，而非只传递最终数字。

【推断】日窗口可以每天保存一份草图，查询 7 天时合并对应桶。窗口滑动不从总草图中“减去昨天”，而是重新合并仍有效的桶，或维护可重算的层级聚合。分钟级窗口可以按时间桶折中，边界精度与状态数量由业务选择。

普通 HLL 的最大值更新丢失了次大值和元素归属，因此不能直接撤回任意元素。这一点对物化视图（Materialized View，MV）与增量视图维护（Incremental View Maintenance，IVM）很关键：插入可合并不代表删除可逆。

**追问链**：

1. 精确账单能否用 HLL？若合同要求逐用户精确结算，应使用精确集合或可核验明细；近似仪表盘与财务口径分离。
2. 所有分组都分配固定草图会怎样？总内存是分组数乘单组状态；高基数分组可能让小草图也失控，需要稀疏表示、限制或外部状态。
3. 两个群体交集很小怎么办？直接用并集估计做容斥，误差可能淹没交集；需评估专用估计器或换精确方法，不能宣称相同相对误差。

**常见差答／陷阱**：“HLL 是一种稀疏／密集矩阵”“12 KB 是所有 HLL 的固定内存”“删除时减计数”。Redis 的具体空间和误差属于其实现，见 [Redis HLL 文档](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)，不能泛化为算法常量。

### 11. 跳表、LSM 与 B+ 树：把成本归到前台和后台

**题目**：为高写入、点查与范围扫描混合负载选索引，如何比较跳表、日志结构合并树和 B+ 树？

**强答要点**：三者层级不同。跳表（Skip List）是有序查找结构，日志结构合并树（Log-Structured Merge-Tree，LSM Tree）组织多层有序状态及合并，B+ 树（B+ Tree）是多路平衡查找树，在数据库中通常采用页式布局。LSM 的内存表可以用跳表，不能把它们当作互斥产品。

【事实】随机层级跳表在通常独立随机假设下，查找和更新期望 O(log n)，最坏情况可退化。并发跳表还需要节点发布、删除和安全回收机制；有多层指针不等于天然无锁或安全。

B+ 树以页为单位提高扇出，内部节点通常保存分隔键和子页引用，叶子保存记录或记录定位信息。页容量要扣页头、槽目录及空隙；叶子记录宽度和内部键宽度不同，不能用同一容量直接推算所有层。

【推断】若内部有效扇出约 500、叶子平均容纳 200 条，100 万条需要约 5000 个叶子页，再约 10 个中间页和一个根页，形成三层。这个例子展示计算方法；缓存命中后，查找并不必然产生三次物理 I/O。

LSM 以顺序追加和批量合并改变写入路径，同时承担写放大、读放大和空间放大。后台合并（Compaction）必须有持续预算；写入突发超过可消化能力时，积压最终会反压前台。把随机写转顺序写，没有消除重写字节。

【事实】RocksDB 的官方概述说明了内存表、有序文件、写前日志及合并结构，可作为 LSM 实现例子；具体合并策略与参数需另行固定版本。见 [RocksDB Overview](https://github.com/facebook/rocksdb/wiki/RocksDB-Overview)。

| 比较维度 | 跳表作为内存结构 | LSM 组织的存储 | 页式 B+ 树 |
|---|---|---|---|
| 更新路径 | 查找并修改节点链接 | 内存追加、刷写、后台合并 | 定位页、修改，必要时分裂 |
| 范围读取 | 沿底层有序链访问 | 合并多个来源并处理版本 | 定位叶子后遍历相邻叶子 |
| 关键成本 | 指针与回收、缓存局部性 | 合并带宽、版本与墓碑 | 页访问、分裂、并发控制 |
| 持久性来源 | 需额外设计 | 取决于日志与提交配置 | 取决于日志与恢复设计 |

**追问链**：

1. LSM 删除为何没有立即省空间？墓碑必须阻止旧值复活，安全清理需要覆盖相关旧版本且满足快照保留要求。
2. B+ 树在固态盘上是否失去意义？扇出、缓存局部性、范围读取和更新协议仍有价值，设备变化改变成本权重，不自动淘汰结构。
3. 如何选择合并策略？明确点查、扫描、更新比例与空间预算，再比较层级和分层合并的成本分配；不给脱离负载的唯一答案。
4. 内存有序数组是否更好？静态或批量构建场景可能因连续布局受益，频繁插入的移动成本则增加；先明确更新方式。

**常见差答／陷阱**：“B+ 树每层固定 1024 个节点”“红黑树有 20 层就要 20 次磁盘读取”“LSM 写入是 O(1)，后台免费”。结构高度、物理读取和系统吞吐是三个不同指标。

## 四、系统设计需要一个贯穿五道题的约束框架

### 12. 通用设计题：把成功确认点和状态所有权画出来

**题目**：如何证明一张架构图已经覆盖正确性，而不是只覆盖正常数据流？

**强答要点**：沿请求标出接收、排队、执行、持久化、提交、返回六个时刻，并为每段状态指定所有者。组件图之外，至少补一张失败状态表；每个重试都要回答是否可能重复执行，每个缓存都要回答版本来自哪里。

```text
接收 → 准入 → 排队 → 执行 → 提交 → 返回
         │       │       │       │
       拒绝    截止超时  可取消   结果可能已生效
                                 ↓
                         重试先查询操作状态
```

上图是设计骨架，不是要求所有请求都持久化。只读查询可能直接重跑；产生外部副作用的操作则要记录操作标识、业务结果和恢复策略。超时只说明调用方未得到结果，不能推导服务端没有提交。

资源预算也要沿同一条路径走：入口持有连接和请求体，队列持有待执行对象，执行持有内存、计算和 I/O，提交持有日志或元数据锁，返回阶段仍可能受慢客户端反压。只限制工作线程数量会漏掉其他状态。

| 失败位置 | 必须定义的问题 | 可检验的不变量 |
|---|---|---|
| 接收后、入队前 | 是否已承诺接受 | 未接受请求不能伪装成功 |
| 执行中断 | 能重放什么 | 重放不会重复已确认副作用 |
| 提交后、返回前 | 如何确认最终状态 | 同一操作标识对应同一业务结果 |
| 控制面不可用 | 数据面能工作多久 | 旧配置不会越过授权及租约边界 |

**追问链**：

1. 主节点失联是否立即失去主身份？不一定；需要协议任期、租约或隔离令牌约束有效操作，不能靠“它自己知道失联”保证安全。
2. 重试如何避免放大故障？设置总体截止时间、有限次数、退避与抖动，并只重试可重放操作；重试流量计入容量。
3. 方案如何演进？先定义兼容读写和版本切换，再灰度与回退；回退若无法读新格式，二进制降级并不等于数据可恢复。

**常见差答／陷阱**：“所有服务无状态”“消息队列保证恰好一次”“网络分区时兼顾全部一致与可用”。先说清状态、一致性和故障模型，再讨论产品能力。

### 13. 实时 OLAP：新鲜度必须和可见性一起定义

**题目**：设计日增 10 TB、历史 1 PB 的实时 OLAP，支持摄入、更新、报表和交互查询，目标报表 P99 小于 1 秒。

**强答要点**：先把目标约束到报表集合、数据新鲜度和资源配额。任意 SQL、任意扫描范围与固定秒级尾延迟，不能仅靠列存和并行承诺。对于不可控交互查询，应提供单独的资源池和超时语义。

【推断】可选择“持久输入日志 → 解析与幂等摄入 → 可查询列式分片 → 查询协调与执行”的主路径。控制面管理表、分片与版本；数据面处理扫描、连接、聚合和交换。存储是否与计算分离，取决于恢复目标、缓存命中与远端带宽。

变更数据捕获（Change Data Capture，CDC）要保留源位置、主键、更新顺序及删除语义。主键更新不能只做追加，否则聚合会重复计入旧值。跨源没有天然全局顺序时，要说明使用源内顺序、业务版本还是冲突规则。

成功确认至少区分“已持久接收”“已写入可查询状态”“所有目标报表已追上”。若产品只承诺第一种，客户端应能读取摄入位置与可见位置，不能从一个成功响应推断所有查询已包含新数据。

MV 用空间和维护成本换查询成本，IVM 则要求明确哪些表达式可增量维护。计数与求和可在保留足够状态时处理撤回，去重计数和连接更新可能持有大量状态；维表变更还可能使大量历史结果失效。先说明可维护子集，再讨论自动改写。

性能路径按实测瓶颈分解：扫描裁剪减少读取，列裁剪减少解码，运行时过滤减少探测，局部聚合减少交换。向量化执行（Vectorized Execution）降低逐行调度开销，但批次大小、变长数据和高选择性路径仍需测量。

【事实】DuckDB 2024 年的内存管理说明把流式执行、临时外溢及缓冲管理共同纳入资源控制。这是“多个算子共享预算”的公开工程例子，不是分布式 OLAP 的完整方案。见 [Memory Management in DuckDB](https://duckdb.org/2024/07/09/memory-management)。

**追问链**：

1. 源端重复发送会怎样？以源分区和位置或稳定业务标识去重，固定去重状态保留期；过期后重放需另有批次或重建协议。
2. 一个节点崩溃，如何确保查询不混读版本？协调器固定查询快照或可见版本，重试分片仍使用该版本；无法取得时明确失败或整体重跑。
3. IVM 落后 30 分钟还能用吗？根据报表容忍度返回新鲜度标记、回退基表或阻塞；优化器不能把过期视图无条件当作等价结果。
4. 如何验收 P99？固定查询组合、扫描范围、到达模型、并发摄入、缓存状态及单节点失效条件，分别报告成功率、新鲜度和尾延迟。

**常见差答／陷阱**：“Kafka 加 StarRocks 就完成设计”“向量化就是 SIMD”“建 MV 后所有查询都秒级”。组件选择不能代替可见性协议与维护预算。

**【模板】个人案例**：填写一个允许披露的查询或 MV／IVM 问题：版本、业务目标、原始计划、本人负责边界、反例数据、方案比较、验证条件及尚未解决的限制。没有完整指标时保留定性结论，不补造提升倍数。

### 14. 分布式缓存：故障期间的源站预算先于命中率

**题目**：设计每秒 100 万次读取的分布式缓存，支持热点、过期、扩容和节点故障。数据库最多可承受每秒 2 万次回源。

**强答要点**：题设下，如果所有未命中都回源，稳定期至少需要 98% 命中率才能不超过源站预算；这只是平均条件。节点丢失与集中过期时，必须限制回源总量，并允许拒绝或返回被业务许可的旧数据。

【推断】先划分本地一级缓存与共享缓存，明确是否允许旧读。读路径做鉴权、缓存查找、同键请求合并及受限回源；写路径选定源站为真相来源，再通过版本化值、失效通知或变更流控制旧值窗口。

缓存旁路（Cache-Aside）有读写竞争：旧读在新写失效后才回填，会重新放入旧值。版本比较、回填条件和通知顺序需要共同设计；“先写数据库再删缓存”只描述动作，未消除竞态。

过期时间（Time To Live，TTL）加随机抖动可缓解集中到期，不能解决单热点。请求合并要有等待上限，持锁重建者死亡后要能恢复；允许旧读时可以先返回旧值再刷新，但授权、余额等场景未必允许。

一致性哈希（Consistent Hashing）减少成员变化时的键归属迁移，不自动解决热点请求。虚拟节点改善键分布及容量加权，某一个键的流量仍可能压垮归属节点。热点可以复制或本地缓存，但增加失效与版本协调成本。

**追问链**：

1. 加一台节点到底迁移多少？在均匀、等权的理想模型下，新节点接收约总键数的 1／(节点数 + 1)，实际受权重、虚拟节点与分布影响；迁移字节和请求负载不一定同比。
2. 旧节点恢复后会不会返回旧数据？路由代际及迁移状态要控制读写责任，不能把节点存活视作数据已追平。
3. 缓存全部失效怎么办？全局及租户级回源预算、优先级与降级协同，不能只依赖随机过期时间。
4. 使用过滤器挡穿透有什么更新风险？未覆盖新插入键的过滤器可能错误拒绝合法请求，需版本覆盖或旁路策略。

**常见差答／陷阱**：“一致性哈希只影响相邻物理节点”“缓存命中率 99% 就稳定”“加锁避免所有击穿”。虚拟节点使一个物理节点分布在多段区间；命中率也不能说明故障瞬间的流量。

### 15. 日志检索：摄入、可搜索和保留是三种不同承诺

**题目**：每天 100 亿条日志，支持租户隔离、最近 15 分钟全文检索、30 天保存，以及按请求标识追踪。

**强答要点**：先问平均与高分位事件大小、峰值、字段结构、可搜索延迟、检索语法及删除要求。100 亿条／日约为平均 11.6 万条／秒；若每条按 1 KB 十进制原始大小估算，是约 10 TB／日，30 天约 300 TB，尚未计算压缩和索引。

【推断】输入先落可重放日志，解析后写入不可变检索段；段清单发布决定可搜索状态。按租户、时间和容量组织分区，保留期通过段或对象生命周期执行，不能仅把一条过期标记写进元数据就宣称物理数据已经删除。

倒排索引（Inverted Index）适合词项到文档的映射，列式字段适合过滤、聚合与读取；分词器、词位置与规范化决定全文、短语和大小写语义。请求标识应优先保留精确字段，不能把高熵标识任意分词后再声称可精确定位。

对任意子串、正则和大范围聚合，要说明能否利用索引，必要时拒绝或转异步。热门错误码可能命中大量文档，即使定位词项很快，读取与合并结果仍有成本。时间范围与结果上限应尽早收紧。

写入确认要区分日志持久化与检索可见；解析失败进入可观察的隔离通道，不能悄悄丢弃。若重放可能重复，采用稳定事件标识或明确“至少一次、查询侧去重”的语义，并核算去重状态成本。

**追问链**：

1. 消费速度长期小于生产速度怎么办？算积压增长与日志保留耗尽时间，临时扩容、降低非关键索引或受控拒绝；缓冲不会解决长期能力不足。
2. 段合并为何影响 P99？合并和查询争抢 I/O、CPU 与缓存，需要独立预算；减少小段的收益必须扣掉重写成本。
3. 深分页如何保证结果稳定？固定快照及排序键，使用游标；如果索引持续刷新而游标无快照，跨页可能重复或漏项。
4. 恢复中发现某段损坏怎么办？校验段与清单，从副本或输入日志重建，并报告可见缺口；不能让损坏静默表现为“未检索到”。

**常见差答／陷阱**：“按时间分表就行”“所有字段都建倒排”“全文检索延迟等于摄入延迟”。存储保留、索引构建和查询服务分别有资源与语义边界。

### 16. 湖仓查询：一致的文件集合是计划执行的前提

**题目**：设计基于对象存储的湖仓查询服务（Lakehouse Query Service），支持多租户 SQL、弹性计算、更新删除和重复查询加速。

**强答要点**：先固定表格式、读取快照、目录服务与引擎兼容版本，再谈缓存和调度。对象存储中“文件都存在”不等于它们属于同一次表提交；读取必须从表元数据确定一致文件集合。

【事实】Apache Iceberg 以快照及元数据描述表状态，提交通过元数据变更建立新状态；实现需要使用相应目录的原子提交机制。见 [Iceberg 规范](https://iceberg.apache.org/spec/)。本文设计范围固定在 v2／v3 能力，不把页面中更高格式版本的内容混入结论。

【推断】协调器在准入后固定快照，读取清单并裁剪文件，生成扫描任务；工作节点从对象存储读取并在本地缓存不可变数据块，交换中间结果并受内存预算控制。缓存键要覆盖对象身份、版本或内容标识及范围，防止路径重用带来的错读。

元数据可能成为主成本：大量小文件增加清单解析、任务调度与远端请求，即使压缩后数据很小也会慢。文件合并、分区设计与统计维护属于服务的一部分；后台重写与前台扫描需要分配不同预算。

结果缓存必须覆盖 SQL 参数、表快照、会话语义、权限上下文与相关函数行为。跨租户共享相同数据块可能可行，跨租户共享未经权限约束的查询结果则可能泄漏信息；两类缓存不能使用同一安全假设。

【事实】Iceberg 1.9.0 于 2025 年 4 月发布，发行记录包含为 v3 表写入删除向量（Deletion Vector）的支持。格式支持与每个查询引擎的读写支持是两层兼容性，不能仅升级目录就启用新格式。见 [Iceberg 发行记录](https://iceberg.apache.org/releases/)。

删除向量将指定数据文件中的行位置标为删除；读取仍需正确关联文件与删除状态。是否能减少删除文件开销，要按删除密度、更新模式及引擎实现测量；不能推导为“删除免费”或“任意更新都不需维护”。

**追问链**：

1. 查询进行时快照被过期清理怎么办？保留期必须覆盖在途查询或有引用保护；仅固定快照编号而文件已删，仍会失败。
2. 计算节点随时可回收，外溢文件放哪里？选择失败后重跑或持久中间结果；临时本地盘便宜，但不能同时承诺不重算恢复。
3. 如何控制远端费用？分别计量扫描字节、请求次数、交换及结果传输，控制小文件、重复读取和低命中预取。
4. 一个租户提交数千个大扫描怎么办？按租户准入、并发与扫描预算隔离，规划任务也要限额，不能只给工作节点设置 CPU 上限。

**常见差答／陷阱**：“对象存储强一致，所以多文件表更新天然原子”“数据不变所以结果缓存永远有效”“升级文件格式会自动让所有引擎支持删除向量”。对象、表提交及执行兼容性需要分别论证。

### 17. LLM 服务平台：先算每个请求占用多少状态

**题目**：设计大语言模型服务（Large Language Model Serving，LLM Serving）平台，兼顾聊天、长上下文、检索增强生成和智能体工具调用，支持多租户与弹性扩容。

**强答要点**：先按模型版本、输入输出长度分布、到达模式和交互目标分组。检索增强生成（Retrieval-Augmented Generation，RAG）会引入检索及上下文装配，智能体可能反复请求模型；一次业务请求不等于一次模型推理。

首词元延迟（Time To First Token，TTFT）、词元间延迟（Inter-Token Latency，ITL）及端到端完成时间要分别定义，并固定客户端或服务端测量边界；请求内平均的每输出词元时间（Time Per Output Token，TPOT）不能替代逐词元 ITL 的尾延迟。指标实现可参见 [vLLM v0.10.2 Production Metrics](https://docs.vllm.ai/en/v0.10.2/usage/metrics.html)。有效吞吐（Goodput）应只统计满足服务目标的工作量，并固定是请求数还是词元数；增加总吞吐但让大部分交互超时，不能视作达标。

【推断】入口做鉴权、模型路由、长度限制和租户配额；调度器做准入与批处理；执行节点负责预填充（Prefill）和逐步解码（Decode）；平台管理模型版本、权重分发、健康、指标与扩缩容。先用同节点执行建立基线，再决定是否分离两阶段。

对于采用标准注意力的自回归模型，且各层 K、V 缓存均符合下列形状的情况，可用下面的逻辑大小估算键值缓存（Key-Value Cache，KV Cache）：

```text
每个词元的 KV 字节 ≈ 2 × 层数 × KV 头数 × 每头维度 × 每元素字节数
请求 KV 字节 ≈ 上式 × 当前缓存词元数
```

这里的 2 表示键与值。这个估算不覆盖多头潜在注意力（Multi-head Latent Attention，MLA）、滑动窗口、混合架构、缓存量化元数据及分页空隙，也不能直接得出张量并行后的每卡占用；是否复制 KV 头要看实际实现。

假设 32 层、8 个 KV 头、每头 128 维、每元素 2 字节，逻辑缓存约为 128 KiB／词元。8192 个词元约需 1 GiB，一个实例的可并发请求数因而可能先受显存约束，而不是先受连接数约束。这是架构演算，不对应某个指定模型的实测。

分组查询注意力（Grouped-Query Attention，GQA）可以减少 KV 头数量，但具体容量还要扣权重、运行时工作区、图执行预留、碎片和安全余量。扩容也包含权重加载、编译、预热与缓存变冷，不能按新增进程数立刻折算可用吞吐。

**追问链**：

1. 请求排队时是否预留全部最大输出缓存？全量预留更保守，动态分配提高利用率但增加运行中抢占风险；需要明确输出上限和不足时策略。
2. 长请求是否应该独立队列？隔离可保护短请求，但可能降低总体利用率；按长度分组、优先级及公平性共同评估，不能只按请求条数限额。
3. 流式返回中连接断开怎么办？将断连传播为引擎取消，并在在途计算安全结束后回收状态；是否保留会话、已生成内容如何计费，由产品契约决定。
4. 模型节点失效能否透明续传？重新计算缓存可能恢复计算，但采样状态、输出确认和随机性也需处理；不能无条件承诺逐词元一致续传。

**常见差答／陷阱**：“加一个自动扩容器即可”“QPS 相同所以负载相同”“KV 缓存就是普通结果缓存”。输入长度、生成长度和已占用缓存决定请求成本，缓存内容也依赖模型与前缀。

### 18. 推理调度追问：分块、分离与缓存路由分别解决什么

**题目**：长输入使短请求变慢，应该采用分块预填充、预填充／解码分离、前缀缓存，还是 CUDA Graph？

**强答要点**：这些机制控制不同成本。分块预填充（Chunked Prefill）把长输入分成可调度块；两阶段分离控制资源干扰；前缀缓存复用已经计算的状态；CUDA Graph（CUDA 执行图）减少重复执行时的主机调度开销。先定位等待来自哪里，再比较方案。

【事实】Sarathi-Serve 在 2024 年提出结合分块预填充的调度，研究吞吐与延迟的权衡。论文支持“长预填充与解码混排需要调度控制”，不支持任意块大小都最优。见 [Sarathi-Serve](https://arxiv.org/abs/2403.02310)。

【事实】DistServe 在 2024 年研究预填充与解码分离，按两阶段延迟目标及通信条件配置资源。它支持“隔离干扰可能提升达标服务能力”，不是“分离总是更快”。见 [DistServe](https://arxiv.org/abs/2401.09670)。

【推断】若一次请求需转移前节估算的 1 GiB 缓存，假设该请求独占有效吞吐为 25 GiB／秒的传输路径，且实际转移量恰为 1 GiB，单纯传输时间约为 40 毫秒，尚未计排队、协议与争用。分离节省的干扰成本必须超过传输和调度新增成本；同机高速互连与跨机网络不能共用结论。

【事实】vLLM v0.10.2 的自动前缀缓存文档按块组织复用状态，并说明哈希键还包含前驱信息和附加身份信息；其 V1 引擎可通过可选的请求级 `cache_salt` 限制复用范围，V0 不支持该机制；该选项不自动识别租户；【推断】服务端应按信任域控制盐值，不能把客户端任意提供的盐当作授权凭据。见 [Automatic Prefix Caching](https://docs.vllm.ai/en/v0.10.2/design/prefix_caching.html)。

前缀命中只减少可复用部分的预填充，不免除后续解码。路由到缓存最多的实例也可能排很长队，决策应比较排队、传输与重算的总成本。高命中率并不自动等于低 TTFT，更不能让租户通过共享缓存探测其他租户的提示内容。

【事实】vLLM v0.15.1 的 CUDA Graph 文档区分完整图与分段图等模式，涉及后端兼容和运行形状选择。见 [CUDA Graphs 设计](https://docs.vllm.ai/en/v0.15.1/design/cuda_graphs/)。应按捕获形状、填充浪费、显存与回退路径验证，不把“打开执行图”当作消除所有开销。

【事实】NVIDIA 在 2026 年 3 月发布的 Dynamo 1.0 官方技术文章把多节点推理、KV 感知路由和缓存管理放在平台层讨论，并支持对接 vLLM 等执行引擎。这里仅引用功能与架构定位，不引用其特定硬件上的营销性能倍数。见 [Dynamo 1.0 官方技术博客](https://developer.nvidia.com/blog/nvidia-dynamo-1-production-ready/)。

**追问链**：

1. 如何做可信比较？固定模型和精度、硬件与拓扑、输入输出长度分布、到达模型、缓存冷热和软件版本，同时报告达标率及成本。
2. 连续批处理（Continuous Batching）为何不等于无限加大批次？大批次可能增加调度等待和词元间延迟，显存压力还会触发抢占与重算。
3. RAG 更新后能否沿用前缀缓存？只有模型权重、适配器、多模态输入、位置编码及缓存格式等计算条件兼容，且隔离策略允许时，相同词元前缀才可复用；文档版本或权限变化后需重新检查装配内容与授权，检索结果缓存也要独立失效。
4. 工具调用超时能否重试整个智能体？模型推理可重算不代表外部操作可重放；工具操作需要幂等标识、状态查询及授权边界。

**常见差答／陷阱**：“数据库流水线可以直接套到模型推理”“解码一定只受带宽限制”“执行图支持所有动态路径”。可以迁移资源预算与状态管理思路，硬件瓶颈和调度结论仍要按实际批次与模型验证。

**【模板】迁移叙事**：填写一个已做过的数据库资源控制案例，再列出能迁移的预算、反压和版本原则；AI 推理部分分别注明已经实现、仅做源码阅读或准备验证的范围。不得把阅读 DistServe 或调试样例说成运营过大规模推理平台。

## 五、评估标准要落在可观察证据上

### 19. 综合题：怎样区分记住方案与能够负责方案

**题目**：一名候选人可以讲出全部组件，但未提供容量和失败路径；另一名只深入一个子系统，如何评价？

**强答要点**：按岗位要求评估已证明的能力，不按术语数量打分。局部深入能支持 Senior 判断，但 Staff 还应把局部决策连接到其他团队的契约、资源分配和演进条件。覆盖全图但没有不变量，同样不足以证明整体设计能力。

下面是本文练习用的评估量表，不是任何公司的录用标准。每个维度都要记录具体答复或反例；“表达自信”“名企背景”不能替代证据。

| 维度 | 可工作的基础答案 | 资深强答 | Staff／负责人增量 |
|---|---|---|---|
| 问题定义 | 复述功能 | 固定规模、输出与约束 | 识别冲突目标并协商范围 |
| 正确性 | 正常路径可运行 | 不变量、反例、异常语义 | 明确跨组件及跨团队契约 |
| 成本 | 给渐进复杂度 | 算内存、字节、到达与服务率 | 将预算归属到租户和维护任务 |
| 故障 | 有副本和重试 | 区分提交、超时与重放 | 定义故障演练与恢复责任 |
| 演进 | 能扩容 | 有兼容和回退条件 | 明确分阶段投入与退出条件 |
| 证据 | 叙述设计 | 固定版本和验证条件 | 让团队持续执行检查与复盘 |

【推断】不能用总分掩盖关键正确性缺口。若缓存方案允许越权读、统计方案漏键、重试方案重复副作用，应先修正这些问题；高吞吐估算不能抵消业务语义错误。

对 Kevin 的准备，可以选一条熟悉主线深挖到代码与测试，再用一个陌生场景验证迁移。比如先讲连接外溢的预算和取消，再讲 KV 缓存的容量与抢占；后者应主动指出模型结构和硬件数据尚需确认的部分。

**追问链**：

1. 未做过该系统，如何证明能力？标明设计假设，给成本推导、最小实验和反例；不把推演包装成线上结果。
2. 无法在面试现场完成压测怎么办？给可执行的验证计划和失败判据，承认性能尚未证实；现场能做的是检查数量级与逻辑一致性。
3. 作为负责人如何阻止范围失控？把第一阶段承诺、延期能力及触发扩展条件写清，说明谁承担数据和兼容风险。

**常见差答／陷阱**：“Staff 就是比 Senior 懂更多系统”“只要能推动团队就不必写代码”“系统设计没有标准答案所以都对”。方案不唯一，不意味着容量矛盾和错误语义无法检验。

### 20. 验证题：怎样设计能推翻方案的实验

**题目**：你的设计声称更快、更省内存且不影响正确性，怎样安排最小验证？

**强答要点**：先分开正确性、资源与性能假设。用小规模精确基线验证语义，用可控分布观察资源增长，再在固定环境验证吞吐与尾延迟。任何一个维度失败，都应能定位到具体假设，而不是只得到“综合跑分下降”。

算法验证包括空输入、极值、相同键、倾斜与最坏排列；系统验证再增加超时、重复、乱序、部分提交、节点失效和恢复。近似算法需要在多次试验中观察误差分布，单个样本准确不能证明估计器稳定。

性能实验保留数据生成方式、分布、热身、缓存状态、输入输出大小及并发背景。固定并发闭环压测会在服务变慢时自动降低到达率，可能掩盖排队失控；要验证过载，应另设独立到达率及明确拒绝策略。

| 假设 | 能推翻它的输入或故障 | 必须记录的量 |
|---|---|---|
| Top K 候选不会漏 | 同键跨分片、边界并列 | 与精确基线的差异 |
| 哈希连接资源可控 | 单热点、多对多、高基数 | 峰值内存、外溢、输出量 |
| 缓存保护源站 | 节点丢失与热点到期同时发生 | 回源峰值、拒绝、旧读窗口 |
| OLAP 达标 | 摄入与合并叠加、冷缓存 | 新鲜度、成功率、尾延迟 |
| 推理分离有收益 | 长短混合、低带宽、冷前缀 | TTFT、ITL、达标吞吐及成本 |

这些是实验设计建议，本文没有实际运行所述系统或复现论文。博客构建只能验证文章渲染，不能充当算法实现、数据库压测或模型服务实验的证据。

**追问链**：

1. 平均值变好而 P99 变坏怎么办？按长度、租户、查询类和缓存状态分组，判断收益是否由一类请求占用另一类资源换来。
2. 新方案只在热缓存下更好怎么办？报告适用条件，测预热成本与故障后恢复时间；不要隐去冷态结果。
3. 结果与论文不同怎么办？先核对版本、模型、数据分布和指标口径，再定位机制差异；不能只归因“硬件不够好”。

**常见差答／陷阱**：“跑一遍基准”“流量回放没有报错”“CPU 降了所以成本降了”。缺少正确性断言、故障覆盖或资源总账，结论都不完整。

## 六、把准备材料压缩成可复核的决策记录

每个主题准备一页材料即可，但页内必须形成闭环：题设、假设、正确性不变量、两个候选方案、数量级预算、最危险失败、验证方法及适用边界。代码只保留决定性的状态转换，长结构清单和无关字段不占口头回答时间。

通用算法优先练边界查找、窗口与单调队列、精确 Top K、依赖图和状态压缩；数据库专项至少完整讲通哈希连接外溢、外部归并、概率结构和索引成本。练习目标是改变约束后仍能解释为什么改算法，不能只在原题输入上复述答案。

系统设计优先选择一题作为主练，再用另外两题测试迁移。数据库岗位可选实时 OLAP 为主、缓存与湖仓为迁移；AI 基础设施岗位可选 LLM 平台为主，再用日志检索和线程池检查准入、取消及状态所有权。没有证据的扩展点应保留为验证计划。

**【模板】决策记录**：在【版本／时间】、【可披露负载】下，我负责【明确边界】。原方案在【观测】上不满足【目标】，我比较【方案 A／B】，依据【不变量与预算】选择【方案】；由【本人／协作者】完成【验证】，结果是【真实数据或定性结论】，仍不适用于【限制】。

对于缺少生产经历的 AI 主题，可把模板中的“负责”改成“阅读／原型验证”，把“结果”限定为实际观测。开源身份和历史职级提供背景，具体判断仍由调用路径、数据和反例支撑；他人面经与公开论文不属于个人交付证据。
