**数据库内核工程师转向 AI 基础设施，最有说服力的能力是把调度、内存、状态和失败处理落实为可验证的系统契约。** 熟悉项目名字只能建立讨论入口；能算出资源边界，解释优化何时失效，并设计有对照的实验，才足以支持高级工程师（Senior）、资深技术专家（Staff）或技术负责人（Tech Lead）岗位的判断。

本文为 Kevin Li 的备考草稿：按已提供背景，他有十余年数据库内核与在线分析处理（Online Analytical Processing，OLAP）经验，是 StarRocks 核心开发者与代码提交者（Committer），现从事阿里巴巴（Alibaba）MaxCompute 的结构化查询语言（Structured Query Language，SQL）引擎及增量视图维护（Incremental View Maintenance，IVM）相关工作。下文把这些能力与新岗位连接，但不推定他参与过任何推理平台、图形处理器（Graphics Processing Unit，GPU）内核或 Agent 生产系统。

## 一、先定义推理服务的目标，再谈优化开关

【推断】同一项优化可能提高总产出，却让交互请求超时。面试应先建立延迟与成本模型，再依次讨论批处理、KV 内存和算子优化；否则所有“加速”都缺少可比较的分母。

### 题 1：吞吐上涨，为什么用户反而觉得更慢？

**题目**：一个大语言模型（Large Language Model，LLM）服务扩大批量后，每秒生成量增加，但聊天投诉上升。你如何判断问题、定义优化目标？

**强答要点**

先区分首词延迟（Time to First Token，TTFT）、词间延迟（Inter-Token Latency，ITL）、端到端时延，以及服务级别目标（Service Level Objective，SLO）。本文的服务端 TTFT 从请求到达服务边界计至首个输出词元返回，包含边界内的排队、分词和预填充；客户端 TTFT 还包含网络等开销。不同基准的计时边界可能不同，比较时必须对齐，不能只报 GPU 上的一段执行时间。

预填充（Prefill）处理输入前缀，解码（Decode）逐步生成后续词元（Token）。常见密集 Transformer（变换器模型） 在较长输入的预填充阶段有较高计算强度，小批量解码则经常受权重和状态访存限制；这只是瓶颈假设，必须结合模型结构、上下文长度、并行方式和实际设备验证。

【事实】DistServe 把优化目标设为在首词延迟和每请求平均输出词元耗时（Time per Output Token，TPOT）约束下、达到指定 SLO 达标比例的每 GPU 有效吞吐（Goodput），而不是仅追求生成总量。TPOT 是首词之后的平均值，不能保证每个词间间隔都达标。这给出了讨论服务容量的统一入口。[DistServe，OSDI 2024](https://arxiv.org/abs/2401.09670)

【推断】可以把“合格请求数／设备时间”作为一个目标，再同时报告拒绝率、取消率和每个成功任务的成本。只排除慢请求而不报拒绝率，会把过载隐藏成好成绩；只报 token/s，又会让长输出请求主导结果。

**追问链**

1. **第一层：延迟从哪里开始计时？** 客户端和服务端分别打点；流式连接建立不等于首个有效词元到达。明确网络是否包含在服务承诺内。
2. **第二层：如何发现排队主导？** 分解入口队列、调度等待、实际执行和回传；按输入长度与输出长度分桶看尾延迟，不只看全局平均值。
3. **第三层：持续过载时怎么做？** 以资源需求和截止时间做准入，给出有界队列、租户配额与可解释的拒绝；扩容启动期间也要保护在途请求。
4. **第四层：怎样比较两个版本？** 固定模型、精度、到达过程与长度分布，记录完成、失败、拒绝和成本，画出负载增加时的容量曲线。

**常见差答／陷阱**

“GPU 利用率越高越好”没有说明有多少工作在截止时间内完成。“把批量调大”没有区分排队等待和算子效率；“平均耗时下降”也可能只是短请求占比变化。模型服务的资源利用率是解释变量，用户目标才是验收变量。

**可交付证据**：一张分阶段时延图、一张到达负载与合格完成量曲线，以及一份完整的失败分母。没有线上数据时，明确这是负载生成实验。

### 题 2：连续批处理为什么有效，又为什么会饿死请求？

**题目**：解释连续批处理（Continuous Batching），并设计一个同时接收短对话和长文档请求的调度器。

**强答要点**

连续批处理在生成迭代的边界调整活跃集合：完成的请求退出，新请求获得位置。静态批处理需要等同批长尾结束才能整体换批；迭代级调度减少空闲位置，但不消除请求之间的计算与显存竞争。

【事实】vLLM 的 PagedAttention 工作把迭代调度与按需 KV 分配结合，允许不同长度请求更有效地共享显存。[PagedAttention，SOSP 2023](https://arxiv.org/abs/2309.06180)

【推断】调度预算至少包括本轮处理词元数、活跃序列数和可分配 KV 块。只有序列数上限时，一条超长输入仍可能占用整轮计算；只有词元预算时，又可能产生过多序列管理、采样和回传开销。

公平性应落在可执行规则：等待时间增加优先级、租户获得资源份额、长输入有最低推进额度。若永远优先处理短请求，短请求尾延迟可能漂亮，长请求却没有完成保证。

**追问链**

1. **第一层：调度单位是什么？** 区分一次生成迭代、一个预填充片段和整个请求；只有明确可抢占边界，才有公平性的实现基础。
2. **第二层：解码突然需要更多显存怎么办？** 为增长预留余量，或在明确边界暂停、换出、重算；不能在内核已经引用地址时任意回收块。
3. **第三层：短请求优先是否最优？** 它依赖长度估计和目标函数；估计错误或长请求占比高时，应报告饥饿和截止时间违约。
4. **第四层：如何处理取消？** 停止未来调度，等待在途设备操作结束，再回收状态；取消信号到达不代表 GPU 已停止访问。

**常见差答／陷阱**

“动态 batch 就是不断加请求”遗漏退出、增长和资源回收。“线程越多并发越高”混淆 中央处理器（Central Processing Unit，CPU）控制并发与 GPU 可容纳的工作量。一个活跃序列也可能因为上下文很长而承担极高的单步成本。

**可交付证据**：调度器伪代码应返回已选请求、资源扣减和未选原因；用长短混合、突发到达与取消测试验证是否有饥饿。

### 题 3：分块预填充如何缓解干扰？

**题目**：一个长提示词进入系统，正在流式输出的请求出现明显停顿。分块预填充（Chunked Prefill）能解决什么，不能解决什么？

**强答要点**

分块把一次长预填充拆成多个有序片段，使调度器能在片段之间推进已有解码。它控制一次迭代的工作量，减少长输入形成的大停顿；不减少输入本身必需的注意力计算，也不让后续片段脱离此前上下文。

【事实】Sarathi-Serve 在 2024 年提出以分块预填充构造减少解码停顿的调度，并研究吞吐与延迟的折中。其收益依赖模型、设备及延迟约束，不能直接迁移为所有引擎的固定倍数。[Sarathi-Serve，OSDI 2024](https://arxiv.org/abs/2403.02310)

【推断】片段越小，单次阻塞通常越短，但调度、内核启动和中间状态管理次数可能增加。片段太大则重新接近长预填充；应把片段大小作为策略参数，而不是把某个词元数当作通用常量。

**追问链**

1. **第一层：每块是否只关注块内词元？** 否；因果注意力（Causal Attention）仍需访问此前合法位置的状态。分块改变执行安排，不能任意改变模型语义。
2. **第二层：优先解码会伤害谁？** 新请求首词可能等待更久；需要对首词和逐词目标分别分配预算。
3. **第三层：怎么动态调节？** 利用迭代耗时和排队情况估计可容纳工作量，同时限制反馈震荡；先以固定策略建立对照。
4. **第四层：能替代 PD 分离吗？** 两者处理干扰的方式不同；分块仍共享设备，分离额外引入状态传输与资源池配比问题。

**常见差答／陷阱**

“切成小块后计算复杂度变低”把调度优化说成算法复杂度优化。“解码永远优先”遗漏新请求的首词饥饿。回答应能展示一条长输入在多轮调度中如何前进，而不是只画一个大 batch。

**可交付证据**：固定总输入，比较不分块与不同片段策略下的首词、词间延迟和调度开销，并保留到达负载条件。

## 二、把 KV cache 当作派生状态管理系统

KV 缓存（Key-Value Cache，KV cache）保存模型注意力的键和值，不是业务数据库中的通用键值对。它可以从输入与模型重新计算，但其重算成本和容量增长决定推理服务的可用并发。

【推断】数据库经验可以迁移到容量估计、共享引用和分层管理；迁移边界是模型状态的语义兼容性。两个看起来相同的文本，并不自动对应可以互用的设备状态。

### 题 4：PagedAttention 到底把什么“分页”了？

**题目**：请解释 PagedAttention（分页注意力）的地址映射、共享和碎片，并估算一个请求的 KV 占用。

**强答要点**

【事实】PagedAttention 把逻辑上连续的 KV 序列映射到不必物理连续的固定大小块，使用块表定位。共享前缀或生成分支可共享块，并在需要修改共享状态时采用写时复制（Copy-on-Write）。它借鉴操作系统分页思想，但不是让 GPU 自动通过 CPU 页表按需取回 KV。[PagedAttention 论文](https://arxiv.org/abs/2309.06180)

对于各层配置相同、使用常规键值头的模型，未分片的 KV 原始字节数可按下式估算：

```text
KV_bytes = 2 × 层数 × KV头数 × 每头维度 × 上下文词元数 × 每元素字节数
```

【推断】设模型有 32 层、8 个 KV 头、每头 128 维，采用每元素 2 字节表示。每个词元是 `2 × 32 × 8 × 128 × 2 = 131072` 字节，即 128 KiB；8192 个词元的原始 KV 为 1 GiB。这是算例，不包含块表、对齐、工作区、图捕获内存和共享收益。

分组查询注意力（Grouped-Query Attention，GQA）下应使用 KV 头数，不能套用查询头数。多卡部署还需看 KV 头如何分片或复制；不能默认用总大小除以卡数得到每卡占用。

【事实】DeepSeek-V2 的多头潜在注意力（Multi-head Latent Attention，MLA）使用压缩潜在表示改变 KV 状态组织，因此上述普通 KV 头公式不应原样套用。[DeepSeek-V2，2024](https://arxiv.org/abs/2405.04434)

**追问链**

1. **第一层：分页是否消灭碎片？** 减少大段连续分配造成的浪费，但尾块仍有内部碎片，元数据和块粒度也有成本。
2. **第二层：共享块能直接写吗？** 应由所有权和引用计数决定；共享部分必须保持不可变，独占尾部才能按规则追加。
3. **第三层：进程崩溃如何恢复？** KV 可丢弃重算；已输出内容和请求重试语义另行管理，不能把缓存可重算等同于请求透明恢复。
4. **第四层：怎么找到真正容量瓶颈？** 同时测权重、KV、临时张量及图内存，并解释峰值与稳定值；原始 KV 算式只提供下界附近的预算线索。

**常见差答／陷阱**

“PagedAttention 把 KV 存进磁盘”“它让注意力变成线性复杂度”“所有卡均匀分摊 KV”都跳过了关键条件。分页改善状态布局，未自动改变注意力计算量或部署拓扑。

### 题 5：前缀复用为什么既是索引问题，也是隔离问题？

**题目**：比较前缀缓存（Prefix Caching）与 SGLang 的 RadixAttention（基数树注意力缓存机制）。哪些请求可以复用，怎样避免跨租户错误？

**强答要点**

前缀复用保存已经计算的中间状态，匹配的是模型实际接收的词元序列及其兼容上下文。语义相近不等于前缀相同；同一段文字放到不同历史后面，其位置和注意力上下文可能不同。

【事实】SGLang 的 RadixAttention 用基数树（Radix Tree）组织可共享的前缀状态，利用程序中重复出现的提示前缀；缓存感知调度把复用机会纳入请求安排。[SGLang，NeurIPS 2024](https://arxiv.org/abs/2312.07104)

【事实】vLLM v0.10.1 的设计文档说明基于块哈希的前缀缓存，哈希依赖父块、当前块词元和额外信息，并涉及适配器、多模态输入及缓存隔离；该实现只缓存完整块，匹配前缀不代表所有匹配词元都能免于重算。这是该版本机制的依据，不把它等同于所有版本的接口承诺。[vLLM v0.10.1 前缀缓存设计](https://docs.vllm.ai/en/v0.10.1/design/prefix_caching.html)

【推断】服务设计还应把模型权重版本、位置编码配置、词元化及提示模板的变化纳入兼容性判断。租户共享必须显式授权：即使返回内容正确，缓存命中造成的延迟差也可能暴露其他租户是否使用过某段输入。

路由也有成本。让请求总去缓存最热的副本可以省计算，却可能排在长队后面；应比较省下的预填充时间与增加的等待时间，而不是最大化命中率本身。

**追问链**

1. **第一层：后缀相同为什么不够？** 因果模型的中间状态依赖此前序列；普通前缀缓存没有证明任意片段拼接的等价性。
2. **第二层：命中能加速哪些部分？** 主要减少可复用输入的预填充；后续生成仍需运行模型，并访问已有上下文。
3. **第三层：哈希碰撞如何处理？** 说明碰撞风险模型、哈希方案与必要校验；不能仅凭一个短整数就承诺语义正确。
4. **第四层：如何评估缓存价值？** 除请求命中率外，统计省下的词元计算、设备时间、占用字节与尾延迟；不同长度命中不能等价计数。

**常见差答／陷阱**

“相似问题共享 KV”混淆语义答案缓存与前缀状态缓存。“RadixAttention 是新的近似注意力”误解了索引作用。“统一 system prompt 一定可以跨用户共享”则跳过租户与隐私策略。

### 题 6：KV 放到 CPU 或 SSD，何时比重算更贵？

**题目**：设计 GPU 显存、主存与固态盘（Solid-State Drive，SSD）三级 KV 管理，解释准入、淘汰和失败恢复。

**强答要点**

【推断】先比较重算与取回的关键路径成本：`取回时间 ≈ 定位与排队 + 字节数／有效带宽 + 格式转换与同步`。只有预计节省的计算超过这条路径，外部缓存才可能帮助当前请求；高命中率不能替代时间估算。

设需要取回 1 GiB，端到端有效传输带宽为 25 GiB/s，仅数据移动下界就是 40 ms，尚未计排队与同步。这个示意值不能冒充网络实测；如果同一前缀重算只需更短时间，取回将延迟首词。

【事实】Mooncake 把 KV 作为中心状态组织分离架构，并利用 CPU、主存及 SSD 资源构建缓存，调度同时考虑延迟目标与过载处理。[Mooncake，2024 预印本](https://arxiv.org/abs/2407.00079)

【推断】淘汰可以按“预计复用次数 × 每次可节省的关键路径成本／占用字节”排序，但这是设计候选，尚需在线验证。活跃且仍被设备引用的块必须固定；已落盘的块只有在内容完整且兼容性元数据发布后才能进入可发现状态。

普通缓存失效可重算，因此未必值得同步复制每个 KV 块。可是付费长上下文会话、跨节点恢复或昂贵前缀可能需要更高保存等级；由恢复目标与重算成本决定，而不是照搬数据库日志协议。

**追问链**

1. **第一层：最近最少使用为何不总合适？** 最近最少使用（Least Recently Used，LRU）不直接考虑重算代价和预期复用频率；若按变长前缀对象淘汰，还需考虑对象大小。固定大小 KV 块没有块大小差异，但重算与复用价值仍可能不同。
2. **第二层：对象写一半时节点宕机？** 先写不可见内容，校验完整后发布元数据；读取失败回退重算，避免把半块当有效状态。
3. **第三层：缓存目录与数据不一致？** 目录是提示而非正确性依据；读取时验证版本与存在性，清理失效引用，避免反复访问坏条目。
4. **第四层：多租户怎么分账？** 配额覆盖常驻字节、取回带宽与缓存构建工作；只限制 GPU 容量会把竞争转移到网络和 CPU。

**常见差答／陷阱**

“内存不够就 swap”“加 Redis 缓存 KV”“远程内存等价于本地显存”都没有建立带宽、布局与生命周期契约。KV 是派生数据不意味着可以返回损坏状态；正确回退与静默错误之间必须有明确边界。

### 题 7：PD 分离为什么不是默认答案？

**题目**：比较预填充／解码分离（Prefill-Decode Disaggregation，PD 分离）、混合部署和仅分块预填充，给出容量规划与退化方案。

**强答要点**

PD 分离让预填充与解码使用不同工作节点或资源池，分别选择并行配置与扩容策略。它减少两阶段直接竞争，但会引入 KV 交接与多队列协调；交接可发生在同节点的不同 GPU 之间，跨节点部署才额外依赖节点间网络，传输也可能与计算重叠。

【事实】DistServe 的核心是隔离两阶段并围绕有效吞吐规划资源，同时考虑带宽与并行配置；Mooncake 更强调 KV 中心的状态管理和过载调度。两者都不是“增加网络后自动更快”的证明。[DistServe](https://arxiv.org/abs/2401.09670)、[Mooncake](https://arxiv.org/abs/2407.00079)

【推断】先用混合部署建立基线，定位干扰占比，再比较可省下的等待与新增传输时间。短输入、小规模或低带宽环境，拆分可能扩大首词时延；长上下文、高负载且资源干扰明显的环境，更值得验证分离。

容量规划不能只按历史请求数配比。输入长度决定预填充工作，输出长度与活跃上下文共同影响解码负担；必须测每池服务能力和传输链路，再保留负载变化与故障冗余。

**追问链**

1. **第一层：KV 在什么时候可被解码端消费？** 说明层或块级完成条件、传输完成通知与可见性；“发送完成”未必等于目标设备已可读。
2. **第二层：两池并行配置不同怎么办？** 明确布局重分片、转换与通信代价；传输字节数和端到端延迟不能只按总 KV 容量推算。
3. **第三层：预填充成功，解码节点失败？** 由请求标识和阶段状态决定重试范围，防止重复输出；缓存状态可重建，客户端流语义仍需定义。
4. **第四层：某池成为瓶颈？** 准入按剩余端到端预算做判断，限制上游继续堆积；必要时路由到经过验证的混合池，而不是无限等待。

**常见差答／陷阱**

“预填充计算密集、解码访存密集，所以必须分离”把常见特征当成无条件决策。“RDMA 很快”也没回答网络拥塞、拓扑与格式转换。远程直接内存访问（Remote Direct Memory Access，RDMA）降低部分数据传输开销，但不消除排队和同步。

## 三、算子与生成算法的优化必须有各自的正确性边界

【推断】批处理、缓存、低精度和图执行作用在不同层，收益通常不能直接相乘。前一项优化改变批量或工作量，可能使后一项原本的瓶颈消失；组合实验必须重新确认关键路径。

### 题 8：FlashAttention 与 PagedAttention 能互相替代吗？

**题目**：解释 FlashAttention（面向访存优化的注意力算法）为何有效，并说明数据库向量化经验在哪些地方能迁移。

**强答要点**

FlashAttention 通过分块、片上存储复用和在线 softmax（归一化指数函数）组织注意力计算，避免在高带宽显存（High Bandwidth Memory，HBM）中物化完整注意力分数与概率矩阵，减少中间结果的读写。常规稠密自注意力对序列长度的计算规模仍为平方级。[FlashAttention 原始论文](https://arxiv.org/abs/2205.14135)

【事实】FlashAttention-3 针对 Hopper 架构研究异步计算与数据搬运重叠、矩阵乘与 softmax 流水，以及低精度路径。其硬件专门化意味着不能把 H100 上的算子结果外推到任意设备。[FlashAttention-3，2024](https://arxiv.org/abs/2407.08608)

【推断】PagedAttention 管 KV 的物理块与访问映射；FlashAttention 管注意力计算的数据流。实际后端是否把两者有效结合，取决于布局、内核和形状支持，不是概念兼容就代表某个版本实现全覆盖。

数据库的向量化执行（Vectorized Execution）、缓存局部性和算子融合经验有助于分析访存；但 CPU 单指令多数据（Single Instruction Multiple Data，SIMD）经验不能直接替代 GPU 的线程束、同步和占用率分析。

**追问链**

1. **第一层：为什么在线 softmax 可行？** 按块维护当前最大值和归一化累加量，最大值变化时重标定旧累加量，保持数学表达等价。
2. **第二层：数学等价是否逐位一致？** 浮点运算次序改变会影响舍入；要区分数值误差容限、任务质量与精确字节一致。
3. **第三层：为何解码收益不同？** 单查询位置、长 KV 与批量形状改变计算和访存比例，应独立测解码内核而不是套用训练长序列结果。
4. **第四层：如何判断瓶颈？** 先看时间线中的等待和空隙，再看内核访存与计算利用；优化最耗时内核之前要确认它是否处于关键路径。

**常见差答／陷阱**

“FlashAttention 就是稀疏注意力”“它压缩了全部 KV”“把 CPU 向量化算子搬到 CUDA 即可”都混淆语义与执行。回答不能用一个 GPU 利用率数字代替数据流分析。

### 题 9：CUDA Graph 为什么能加速，为什么会引入内存问题？

**题目**：解码中有大量短内核，CPU 提交开销显著。如何使用 CUDA Graph（CUDA 执行图），并处理动态批量与取消？

**强答要点**

【事实】图捕获与重放把多次操作的提交组织成可重复执行的图，从而减少 CPU 侧启动成本。所引 PyTorch 文档讨论的常规捕获与重放要求固定内核参数及其指针地址，并通过长生命周期的输入缓冲区更新内容；这里不涵盖显式图更新等其他 CUDA Graph 用法。[PyTorch 官方 CUDA Graph 说明](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/)

【推断】变长服务可以按一组形状捕获，运行时选择桶并填充，或让不适合捕获的路径退回普通执行。这是服务设计方式，不能推定所有算子、通信和动态控制流都支持捕获。

图数量、静态缓冲区与私有内存池会占显存，可能挤压 KV 容量。单步更快而并发下降时，端到端有效吞吐未必增加；图优化必须和容量重新联合评估。

取消请求通常改变有效掩码与未来调度，而不是立即改写正在重放的内存。GPU 仍可能持有设备指针，宿主对象生命周期结束不代表设备访问结束。

**追问链**

1. **第一层：动态批量怎么映射？** 解释桶边界、填充成本与未覆盖形状的回退；观察命中桶分布，避免为罕见形状捕获大量图。
2. **第二层：捕获前要做什么？** 预热分配及相关状态，确认捕获路径支持情况；冷启动成本与稳定运行收益分别报告。
3. **第三层：KV 块回收会破坏地址吗？** 区分稳定的物理池地址与每轮变化的映射内容；映射更新和重放之间必须建立顺序。
4. **第四层：何时不值得开启？** 当关键路径是长内核、通信或状态取回时，减少启动开销可能很有限；同时量化额外内存。

**常见差答／陷阱**

“CUDA Graph 会自动融合全部算子”“图重放等于零 CPU 开销”“RAII 析构即可安全释放 GPU 缓冲”均不成立。资源获取即初始化（Resource Acquisition Is Initialization，RAII）解决宿主对象的资源归属，异步设备完成仍需事件或其他同步契约。

### 题 10：推测解码到底保留了哪一种正确性？

**题目**：解释推测解码（Speculative Decoding）及 EAGLE，判断它在高并发推理中何时可能退化。

**强答要点**

推测解码让草稿机制先提出多个候选，再由目标模型验证，从而尝试用一次较大验证工作替代多次串行生成。有效收益取决于接受长度、草稿成本、验证成本与目标设备的剩余能力。

【事实】精确推测采样使用接受与拒绝修正，在相应算法假设下保持目标采样分布。保持分布不意味着相同随机种子下逐词完全一致，也不能把任意“让大模型挑答案”的方案称为无损推测采样。[Speculative Sampling，2023](https://arxiv.org/abs/2302.01318)

【事实】EAGLE-3 在 2025 年取消早期方案的特征预测约束，采用多层特征融合并直接预测词元。介绍 EAGLE 时必须指明代际，不能把早期设计一概套到新版本。[EAGLE-3](https://arxiv.org/abs/2503.01840)

【事实】2026 年修订的系统研究在 vLLM 上比较多种推测方法，指出验证成本、接受长度变化与批量规模是解释实际效果的重要因素。这支持“必须按负载测”的结论，不支持任何统一加速倍数。[Speculative Decoding: Performance or Illusion?，v2](https://arxiv.org/abs/2601.11580v2)

【推断】可用 `每轮提交的期望词元数／（草稿时间 + 验证时间 + 额外调度时间）` 与基线比较。大批量下目标模型已经较充分使用设备，额外草稿和树验证可能争抢同一资源，使低延迟优势无法转成总容量优势。

**追问链**

1. **第一层：接受率高就一定快吗？** 不够；还要看接受长度、每轮验证规模和成本。候选更长可能提高提交量，也可能放大无效计算。
2. **第二层：采样参数改变会怎样？** 温度、截断策略与目标分布定义必须进入正确性讨论；不能只验证贪心路径后就承诺所有采样模式正确。
3. **第三层：树状候选如何管理 KV？** 分支共享前缀，未提交分支需回收；已接受路径的状态和输出必须一致，不能泄漏被拒分支。
4. **第四层：上线怎么决策？** 按任务与并发分桶，必要时动态关闭；同时观察合格完成量、显存与质量，而不是只看单请求词元速度。

**常见差答／陷阱**

“小模型代替大模型所以更快”遗漏验证；“接受率 80% 就快 80%”没有成本模型；“EAGLE 永远预测顶层隐藏状态”忽略版本变化。精确分布保证也不代表量化目标模型等于未量化模型。

### 题 11：量化收益为什么不能只按位宽计算？

**题目**：区分权重量化、激活量化和 KV 量化；为什么从 16 位降到 4 位不代表服务快四倍？

**强答要点**

量化（Quantization）降低表示精度，可能节省容量和带宽；但缩放因子、分组元数据、反量化、内核支持与形状都会影响实际收益。权重变小并不自动让 KV 变小，KV 变小也不保证预填充计算更快。

【事实】AWQ 是感知激活分布的权重量化方案；KIVI 则研究 KV 的非对称量化，分别处理键和值的分布特征。两者优化对象不同，不能作为同一个“开启 INT4”的配置描述。[AWQ](https://arxiv.org/abs/2306.00978)、[KIVI，2024](https://arxiv.org/abs/2402.02750)

【推断】如果短输入解码主要搬运权重，权重压缩更值得先测；长上下文高并发可能首先受 KV 容量或读取约束。判断必须用当前负载的瓶颈证据，不能把这两种情况固化成定律。

质量验收应覆盖真实任务与长上下文，包括工具参数、代码补丁和结构化输出。困惑度（Perplexity）可以提供模型层信号，却不直接证明代理执行的授权判断或 SQL 语义保持。

**追问链**

1. **第一层：节省的字节去了哪里？** 分别统计权重、KV、工作区和量化元数据；检查更大批量是否重新消耗节省空间。
2. **第二层：校准集如何选？** 与语言、上下文长度、任务和离群值分布相关；明确校准数据与验收数据的隔离。
3. **第三层：为什么某些形状变慢？** 反量化与打包成本可能无法摊薄，或没有适合当前设备和形状的高效内核。
4. **第四层：如何回退？** 保留模型及格式版本、路由范围和质量阈值；量化回退可能需要更多显存，不能等事故发生后才检查容量。

**常见差答／陷阱**

“低位宽无损”“模型能加载就算成功”“所有任务只看平均分”都不够。回答应说明允许损失的指标、样本与置信度，并把数值精度变化和实现缺陷分开定位。

## 四、Agent 运行时的核心是有副作用的执行

智能体（Agent）把模型输出转成工具操作，系统因此需要处理权限、重试和外部状态。模型每一步是否聪明与运行时每一步是否可恢复，是不同的验收问题。

【推断】数据库工程师对事务边界、提交不确定性和审计的理解可直接用于这里；但外部工具通常没有统一事务，不能假设把调用写进日志就能自动回滚。

### 题 12：工具调用超时后，为什么不能简单重试？

**题目**：Agent 创建工单时工具超时，模型准备再调用一次。设计工具调用（Tool Calling）的运行时状态和重试协议。

**强答要点**

先区分只读查询、天然幂等写入、支持幂等键的创建操作和不可安全重试的副作用。模型只提出操作意图；宿主验证参数模式、调用者身份与授权，再由执行器真正提交。

【推断】每次业务意图生成稳定操作标识，记录规范化参数摘要、目标资源和授权上下文。工具执行器应尽可能把操作标识与结果原子保存；否则“远端已经提交、响应丢失”仍无法通过本地日志判定。

恢复时先查操作结果，再决定继续；结果未知就进入待核对状态。模型可以重新规划，但不能靠换一个调用标识把同一业务写入当成新意图自动提交。

```text
已规划 → 已校验 → 待授权 → 已提交 → 已确认
                              └→ 结果未知 → 查询状态／人工核对
已提交后收到取消：先查副作用是否已发生，再决定是否补偿
```

这里的“待授权”表示宿主按策略判断当前授权是否足够，并非每个工具调用都要求人工点击。补偿操作也可能失败，需有自己的状态与审计，不能伪装成数据库回滚。

**追问链**

1. **第一层：本地记录成功能否保证只执行一次？** 不能；本地日志与远端写入之间存在失败窗口，需要远端幂等或状态查询配合。
2. **第二层：至少一次与恰好一次怎么区分？** 至少一次提交可能重复；恰好一次业务效果需要限定资源、去重窗口和外部系统保证，不能由提示词承诺。
3. **第三层：用户取消时怎么办？** 停止后续计划和可取消调用；已提交写入需核对或补偿，不能把连接关闭当作撤销完成。
4. **第四层：如何限制长任务？** 为模型步骤、工具时延、费用和副作用设置预算；重试次数计入总预算，避免局部重试放大整体消耗。

**常见差答／陷阱**

“异常都重试三次”“让模型判断是否成功”“数据库事务包住所有工具”都忽略外部系统边界。Agent 的事件日志能提供证据，但不是跨服务原子性证明。

**可交付证据**：注入提交后丢响应、执行前超时、重复回调和取消，展示每个状态如何恢复以及何时必须停止自动执行。

### 题 13：MCP 标准化了连接，哪些责任仍在宿主？

**题目**：接入模型上下文协议（Model Context Protocol，MCP）后，能否认为工具已经安全、可信且可自动调用？

**强答要点**

【事实】本文固定讨论 MCP 2025-11-25 修订版：它定义宿主、客户端和服务端之间的协议，使用 JSON-RPC 2.0，并区分工具、资源和提示。版本号属于接口契约，不能把这一版生命周期假设扩展成所有后续版本的规则。[MCP 2025-11-25 规范](https://modelcontextprotocol.io/specification/2025-11-25)

【推断】标准协议降低连接成本，不替代业务授权。服务端声明的工具描述和返回文本属于外部数据；工具说“为了完成任务必须读取其他目录”不等于用户授予了该权限。

宿主需要把用户意图映射到允许的工具和资源，把服务端输出保留为低信任输入。提示注入（Prompt Injection）不能只靠再写一段“不要相信恶意文本”解决；执行前仍要用独立策略检查目标、参数和副作用。

【事实】该修订版的 Streamable HTTP（可流式 HTTP）传输规定了 Origin 校验等安全要求。协议接入测试既要覆盖消息模式，也要覆盖连接和认证边界。[MCP 2025-11-25 传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

**追问链**

1. **第一层：工具列表可信到什么程度？** 它能描述可调用接口，但不能证明实现无害；来源、版本和权限仍需配置管理。
2. **第二层：认证成功是否意味着有权读所有资源？** 否；身份认证与资源授权分开，宿主要传播正确用户上下文并限制凭据用途。
3. **第三层：协议版本不一致？** 显式协商或拒绝不支持组合；对照具体修订版测试生命周期、传输和能力，避免静默降级权限。
4. **第四层：如何观测事故？** 记录用户意图、所选工具、策略判定、参数摘要和结果；敏感数据脱敏，审计数据本身也要设权限和保留期。

**常见差答／陷阱**

“MCP 等于 Agent 框架”“工具描述是系统指令”“OAuth 完成就自动获得所有业务权限”都扩大了协议职责。接入成功和执行可信是两个需要分别验证的结论。

### 题 14：给编码 Agent 一个容器，算不算沙箱？

**题目**：设计一个能读仓库、修改代码和运行测试的研发 Agent，怎样避免错误命令、凭据外泄与测试被篡改？

**强答要点**

沙箱（Sandbox）应从威胁模型倒推：不可信仓库可以包含诱导文本、测试脚本和构建钩子；模型生成的命令也可能错误。隔离边界必须由执行环境实现，不能让模型自行决定哪些文件可写。

【推断】为每个任务创建独立工作副本，限定读写挂载、执行身份、网络出口、CPU、内存与时长。只授予当前任务需要的凭据或代理能力；避免把宿主凭据目录和容器管理套接字暴露给任意构建脚本。

隔离强度按执行代码的信任程度选择。容器适合很多开发隔离场景，但共享宿主内核的边界不能自动等同于独立虚拟机；需要更强隔离时再评估虚拟机及其启动与运维成本。

验证与生成环境也要分权：Agent 可以修改测试来表达新需求，但最终验收必须保留可信测试来源。补丁能让它自己改过的测试通过，并不能证明满足外部任务。

**追问链**

1. **第一层：仓库 README 要求导出密钥？** 将其视为任务数据，不是授权；命令执行前的环境权限应使该操作无法读到密钥。
2. **第二层：测试下载依赖怎么办？** 使用受控出口、依赖镜像或按任务开放的网络能力，记录依赖版本；不能靠全面开放网络解决可重复构建。
3. **第三层：后台进程超时后仍运行？** 对整个进程树或任务资源组回收，确认子进程和临时服务清理；仅杀前台 shell 不充分。
4. **第四层：多 Agent 并行改代码？** 分配文件或独立分支，明确合并责任并重新验证最终组合；多份局部通过不能证明合并后的正确性。

**常见差答／陷阱**

“Docker 默认安全”“禁止几个危险命令即可”“Agent 答应不会读密钥”没有形成隔离机制。安全策略也要可操作：允许的任务完成不了时，应报告明确缺失能力，而不是绕过边界。

**可交付证据**：一份任务权限声明及越权读写、出口访问、超时残留进程的失败测试；不需要凭空声称通过了某项安全认证。

### 题 15：SWE-bench 分数能证明团队研发提效吗？

**题目**：候选方案声称编码 Agent 在 SWE-bench（软件工程任务评测基准）上得分很高。你如何评估它是否适合数据库内核研发？

**强答要点**

【事实】原始 SWE-bench 来自真实 GitHub 问题及对应仓库；Verified 是经人工筛选的 500 个实例。基准有不同子集与运行设置，报告分数必须同时说明使用哪一个。[SWE-bench 官方说明](https://www.swebench.com/)

【推断】离线修复成功率是特定任务集合、模型、执行框架和预算下的结果，不能直接转换成工程师节省的工时。数据库内核还涉及并发、语义、性能和跨版本回归，公开问题集合未必覆盖目标团队分布。

建立内部验收时，冻结任务、仓库版本、隐藏测试和工具权限。把首次补丁通过率、最终解决率、人工审查耗时、引入回归和成本分别统计；失败任务也计入费用与时间。

研发流程可以采用“定位—最小复现—补丁—独立验证—人工审查”。模型生成的说明与补丁都是待审材料；语义反例和性能条件的审查方法可复用 [Code Review 系列](/2026/10/24/code-review-series-index/)。

**追问链**

1. **第一层：换模型后成绩上涨，归因给谁？** 固定运行框架、预算与工具；再分别更换模型或调度策略，避免多变量变化。
2. **第二层：多次尝试选最好结果公平吗？** 可以研究，但必须报告尝试次数、选择规则和总成本，不能与单次结果直接对比。
3. **第三层：测试都过了为何仍拒绝合入？** 隐藏需求、未覆盖并发和性能回归可能仍存在；需要能说明证据覆盖范围的审查。
4. **第四层：如何测净收益？** 任务分层、设置人工对照，统计包含等待、复核和返工的全流程；先小范围试点再推广。

**常见差答／陷阱**

“排行榜第一就全面接管研发”“测试通过等于需求完成”“把生成代码行数当生产力”都无法支持投资决策。Agentic 研发（Agentic Development，智能体参与的研发流程）的价值需要通过任务结果和维护成本验证。

## 五、AI for DB 与 DB for AI 要分别承担正确性

AI for DB（人工智能辅助数据库）让模型参与 SQL 生成或内核决策；DB for AI（数据库服务人工智能）提供检索、数据管理与状态支撑。两条路线共享数据基础，但评估对象不同：前者要约束模型错误如何影响系统，后者要约束检索误差与数据可见性。

### 题 16：Text-to-SQL 为什么不是“生成后执行一下”？

**题目**：为企业分析系统设计 Text-to-SQL（自然语言转 SQL），如何处理指标语义、权限、查询成本和错误反馈？

**强答要点**

先约定问题中的业务含义：收入是否含退款、日期使用什么时区、用户按什么键去重、允许看哪些租户。模式匹配正确不代表指标正确，SQL 能执行也不代表回答了用户的问题。

【事实】BIRD 强调数据库内容、外部知识与执行效率；Spider 2.0 则把企业工作流中的元数据、方言文档和项目上下文纳入评估。两者都说明仅验证 SQL 语法不足以覆盖真实任务。[BIRD](https://arxiv.org/abs/2305.03111)、[Spider 2.0，2024／2025](https://arxiv.org/abs/2411.07763)

【推断】流水线可分为权限过滤后的元数据检索、业务口径确认、候选生成、静态检查、受限执行和结果核对。权限由执行身份和数据库策略落实，不能让生成模型自行添加一个租户条件就视为隔离完成。

执行检查应限制扫描量、运行时间和结果规模；只读语句仍可能耗尽资源或读取越权信息。报错反馈也需要过滤，不能把凭据、完整敏感值或系统内部信息无条件回送模型。

**追问链**

1. **第一层：结果和参考 SQL 一样就算正确？** 在一个数据快照上相同可能是偶然；用空集、重复行、NULL、边界日期等数据检验语义差异。
2. **第二层：元数据过期怎么办？** 固定或记录模式版本，执行时校验；字段重命名和指标口径变化要触发重生成或人工澄清。
3. **第三层：自动修复怎么停止？** 设定轮次与成本预算；语法错误可反馈修复，业务歧义应请求确认，不能靠执行成功掩盖。
4. **第四层：如何评价系统？** 分别报告语义正确、权限违规、执行成功和成本；保留未能回答的请求，不能只统计成功生成部分。

**常见差答／陷阱**

“用检索增强生成就不幻觉”“加只读权限就安全”“执行结果相同就数学等价”都过度承诺。检索增强生成（Retrieval-Augmented Generation，RAG）提供证据上下文，不自动证明生成结论或 SQL 的语义。

### 题 17：哪些 learned 组件可以进入数据库关键路径？

**题目**：在基数估计、代价估计、索引或调参中使用学习型组件（Learned Components），如何确保模型错误不会变成不可控事故？

**强答要点**

先按错误后果分层。基数估计误差通常通过计划选择影响性能；若模型介入等价重写是否合法的判断，错误则可能影响结果。性能预测可以试错与回退，语义正确性不能只由模型置信度决定。

【事实】学习型索引（Learned Index）把键到位置的映射建模，并结合搜索机制完成实际定位；其论证不是“模型预测一个地址就直接当成正确答案”。[The Case for Learned Index Structures](https://arxiv.org/abs/1712.01208)

【推断】对于学习型基数估计，可先影子运行，记录预测与实际行数，再按查询族评估计划退化。新计划的性能回归由异常耗时、资源预算与已知基线约束；回退本身也需要设计触发时机，不能等查询运行完才发现预算已耗尽。

与 Kevin 的优化器及物化视图（Materialized View，MV）背景连接时，应明确：模型可建议候选或排序，重写等价条件、增量维护边界与失效规则仍由可验证机制检查。这是迁移设计，不是声明他已经把模型用于这些模块。

**追问链**

1. **第一层：平均估计误差下降是否足够？** 不够；少量极端低估可能选择灾难性连接计划，要按实际延迟和最坏退化评估。
2. **第二层：分布漂移如何发现？** 按表、谓词和查询族观察误差与资源变化，覆盖新数据和更新；不能只在训练时随机切分同分布样本。
3. **第三层：推理开销如何计入？** 记录优化器路径增加的时延与资源；短查询中毫秒级额外工作也可能抵消计划收益。
4. **第四层：模型不可用怎么办？** 回退经典统计与代价路径，保留模型版本和决策记录；不能让辅助服务故障阻断所有查询。

**常见差答／陷阱**

“用大模型替代优化器”“置信度高就跳过等价检查”“训练误差低说明可上线”没有识别风险等级。优先选可观察、可回退、错误只影响性能的边界开展实验。

### 题 18：HNSW、IVF 与 DiskANN 应按什么维度比较？

**题目**：十亿规模向量检索，带租户过滤并要求新数据尽快可见。你如何选索引，怎样证明召回与延迟满足目标？

**强答要点**

先确定向量维度、距离函数、数据分布、更新率、过滤选择率、内存预算和召回率（Recall）口径。近似最近邻（Approximate Nearest Neighbor，ANN）的验收对象应是带业务过滤和可见性条件的结果，不能只复用无过滤离线成绩。

【事实】分层可导航小世界图（Hierarchical Navigable Small World，HNSW）用分层邻接图完成导航搜索，搜索宽度影响召回与工作量；它不是具有任意数据最坏对数时延保证的 B+ 树替代品。[HNSW 原始论文](https://arxiv.org/abs/1603.09320)

【事实】倒排文件（Inverted File，IVF）将向量按聚类划入列表，查询探测若干列表；pgvector 的 IVFFlat 使用这一路线。DiskANN 则围绕 SSD 上的图搜索组织索引与数据访问，目标是在有限内存下扩展容量。[pgvector v0.8.0](https://github.com/pgvector/pgvector/blob/v0.8.0/README.md)、[DiskANN，NeurIPS 2019](https://proceedings.neurips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html)

| 维度 | HNSW | IVF 路线 | DiskANN 路线 |
|---|---|---|---|
| 缩小搜索空间的方式 | 图导航与候选扩展 | 先选聚类列表，再查候选 | 图导航配合分层存储访问 |
| 主要预算 | 图与向量的内存、构建和搜索宽度 | 聚类质量、探测列表数和候选扫描 | SSD 读放大、缓存与并发 I/O |
| 必须追问 | 图更新、删除、过滤后连通性 | 分布漂移、重建与列表倾斜 | 冷缓存、设备尾延迟与更新路径 |
| 不应承诺 | 任意分布固定低时延 | 少量列表即可稳定高召回 | 磁盘容量扩大而查询成本不变 |

【推断】向量距离计算适合批量与 SIMD，但图访问可能更受随机访存限制；对象数量、候选访问数与距离算子的占比必须分别测。不能仅凭向量维度高就认定算力是主瓶颈。

**追问链**

1. **第一层：过滤放在 ANN 后面会怎样？** 候选可能大部分被滤掉，返回不足 k 条；过采样有帮助但没有任意过滤选择率下的固定保证。
2. **第二层：先过滤是否一定更好？** 若合格集合很小，可精确扫描；若过滤破坏图导航或需要建立大量子索引，也会产生额外成本。
3. **第三层：如何构造真值？** 对同一快照、同一过滤条件和同一距离精确计算 top-k，说明并列距离、空集合与不足 k 条时的计分规则。
4. **第四层：新数据和删除怎么纳入？** 规定可见时间，比较构建、增量更新、墓碑与合并成本；只测静态索引不足以支持在线更新承诺。

**常见差答／陷阱**

“HNSW 都是 O(log N)”“DiskANN 不需要内存”“ANN 后面加 WHERE 就正确”把经验性能或接口形式当成系统保证。十亿向量也不是足够的测试条件，向量维度与过滤分布可能改变整个选择。

### 题 19：选 pgvector，还是把向量放在湖上？

**题目**：业务元数据在 PostgreSQL，训练数据在对象存储。怎样选择 pgvector 与湖上向量方案，并定义索引更新的一致性？

**强答要点**

【事实】pgvector 提供精确检索与近似索引；v0.8.0 文档解释了过滤、迭代索引扫描（Iterative Index Scans）以及 HNSW、IVFFlat 的使用条件。它不是默认每条查询都会使用近似索引。[pgvector v0.8.0 README](https://github.com/pgvector/pgvector/blob/v0.8.0/README.md)

【推断】数据与事务元数据共存时，pgvector 可以减少跨系统可见性协调；但是否适合目标规模仍需测内存、构建、更新和查询隔离。把向量列加入现有数据库不意味着资源竞争消失。

【事实】Lance 项目把列式数据访问、向量索引与数据版本作为多模态数据基础的一部分。它是讨论湖上向量的具体实现参照，不能据此声称任意 Parquet 数据湖天然具有相同的随机访问或索引能力。[Lance 官方项目](https://github.com/lance-format/lance)

【推断】“湖上向量”设计应把数据快照、嵌入模型版本和索引覆盖范围一起发布。嵌入（Embedding）由哪个模型生成，属于数据语义；两个不同模型即使维度相同，也不能默认在同一距离空间比较。

增量路径可让旧索引负责已覆盖快照，让增量区负责新数据，查询合并并去重；后台重建后原子切换覆盖范围。这是待验证方案，正确性依赖覆盖集合、删除可见性和无缝切换，不是产品现成功能声明。

**追问链**

1. **第一层：索引比数据落后怎么办？** 明确新鲜度目标；若要求新数据立即可见，必须扫描未覆盖增量或选择同步维护，不能静默遗漏。
2. **第二层：删除何时生效？** 逻辑删除应在结果可见性层立即生效，物理回收可滞后；重建与缓存不能重新暴露已删除数据。
3. **第三层：嵌入模型升级？** 并行保留两个版本，分开检索与评估，再迁移；不能仅修改模型名字就继续复用旧向量。
4. **第四层：对象存储延迟如何控制？** 测请求次数、读取粒度、预取、缓存与冷启动；“存算分离”本身没有证明交互尾延迟。

**常见差答／陷阱**

“pgvector 只能小规模”“上湖就不需要数据库”“每天重建即可保证实时”都跳过工作负载与可见性。选择条件应落到更新、新鲜度、过滤和成本，而不是把数据规模当唯一分界线。

### 题 20：十多年数据库经验，凭什么胜任 AI infra 的 Staff？

**题目**：用三分钟说明你的迁移方向，再接受一次跨层系统设计追问。

**强答要点**

开场可以基于已提供背景表述：“我长期做数据库内核与 OLAP，参与 StarRocks 核心开发，现在做 MaxCompute SQL 引擎与 IVM。我的迁移切入点是推理调度、派生状态管理和性能验证；我会用可复现工作证明新领域能力。”如果尚未完成 AI 实验，后一句应改为准备计划。

后续用真实案例证明一个具体能力，不能罗列全部技术栈。历史 P8、Committer 身份可以说明职责背景，但不能替代本人决策、影响范围和证据，也不能直接换算成另一家公司的 Staff 职级。

| 原有能力 | 可迁移的问题 | 新岗位仍需补的证据 |
|---|---|---|
| 优化器与代价分析 | 资源预算、请求路由、是否重算 | GPU 执行与 KV 传输的测量模型 |
| MV／IVM | 派生状态、版本、增量覆盖 | 模型状态兼容性和缓存生命周期 |
| 向量化与 SIMD | 数据布局、批处理、算子瓶颈 | GPU 同步、访存与硬件分析 |
| 存算分离 | 状态搬运、分层缓存和故障边界 | 推理尾延迟与阶段容量配比 |
| C++／Java／Rust 工程 | 所有权、并发、接口和维护 | Python 调度栈及异步设备生命周期 |

【模板】“在【真实项目及版本】中，我负责【准确边界】。最初判断是【有记录的假设】，随后【测量或反例】迫使我们调整为【真实方案】。我本人完成【可核验部分】，团队其他成员完成【协作部分】；结果在【负载与资源条件】下成立，尚未覆盖【限制】。”

【模板】“我把这个方法迁移到【AI 实验】；对照是【基线】，改动是【单一机制】，观察到【实际结果／尚未测得】。它目前只能证明【证据范围】，不能证明已经具备生产部署经验。”没有结果时保留占位，不把计划改写为成就。

**追问链**

1. **第一层：你与纯 AI 背景候选人的差异？** 用可核对的系统判断和工程结果回答；承认训练、GPU 内核或模型结构中的具体缺口。
2. **第二层：最先负责哪个模块？** 选与证据最接近的调度、KV 或运行时边界，并说明接口、验收和协作方，避免一开始承诺重写全栈。
3. **第三层：如何体现 Staff 范围？** 解释跨团队协议、容量与故障责任如何统一，以及如何形成别人可执行的验证标准；必须补真实案例。
4. **第四层：什么时候选择不做某项优化？** 给出被状态传输、维护成本或质量风险抵消收益的条件，并说明由什么测量决定停止。

**常见差答／陷阱**

“数据库和推理本质一样”“我有 P8 所以能带 AI 团队”“最近把热门项目都看过”都无法证明岗位匹配。也不必把已有经验全部贬为过时；应展示可复用机制与确实尚未掌握的部分。

### 题 21：入职后第一项验证工作怎么选？

**题目**：只有有限设备与一个月时间，你如何选择能证明能力、又对团队有用的 AI 基础设施实验？

**强答要点**

【推断】先选能形成闭环的问题：有固定基线、有可控变量、有预期失败条件。单卡也可以研究混合长度调度、前缀局部性或图内存开销；没有多机设备就不声称复现了 PD 分离收益。

若岗位偏 Agent，选择带只读和写入工具的最小运行时，验证提交后丢响应、重复执行和沙箱越界；若偏向量系统，选择带真实过滤分布的检索实验，先构造精确真值再比较索引。

实验文档保留环境、版本、输入集合、启动参数、原始结果和否定发现。只写最终最优点会隐藏收益边界；一个证明“不值得上线”的实验，只要条件完整，同样体现技术判断。

**追问链**

1. **第一层：如何避免实验变成教程抄写？** 明确待证伪假设，例如“高前缀复用是否足以抵消热点路由排队”，并设计反例负载。
2. **第二层：设备不足怎么办？** 缩小可验证结论，区分模拟和实测；把多机通信或容量预测留作待验证项。
3. **第三层：何时停止？** 达到预定置信度、发现硬性约束或收益不足以覆盖维护成本时停止；不能无限调参挑最好结果。
4. **第四层：如何转成团队资产？** 输出可复跑脚本、边界说明和决策记录，由同事独立复核，而不是只交一张截图。

**常见差答／陷阱**

“一个月把所有框架跑一遍”“先做一个全功能 Agent”“只要复现论文最好倍数”都没有收敛范围。第一项工作应连接团队当前瓶颈，而不是按技术热度选题。

## 参考与验证：把面试回答落到实验协议

以下是备考实验设计，不是已完成的实验记录，也不要求每个候选人全部执行。选择与目标岗位最接近的一组做深，比没有上下文地罗列结果更可核验。

### 推理实验的最小记录

```text
模型：权重标识、修订版本、词元化与提示模板、最大上下文
引擎：版本／提交、后端、量化格式、调度和图执行配置
设备：GPU 型号与数量、互连、CPU、主存、驱动与运行库
负载：输入／输出长度分布、到达过程、租户、取消与重试
缓存：冷启动／热启动、前缀复用比例、各层容量与带宽
指标：TTFT、ITL、端到端分位数、成功／失败／拒绝／取消
成本：设备时间、状态传输、CPU 开销、每个成功任务费用
对照：一次只改变一个机制，再验证组合是否仍有收益
```

【推断】测试至少包括短输入短输出、长输入短输出、长输入长输出和共享前缀突发四类；具体长度来自岗位工作负载或显式设定。只在共享前缀极高的热缓存条件下证明的收益，不应描述成所有聊天流量的收益。

闭环压测会在服务变慢时自然降低发送速度，可能掩盖排队崩溃；固定到达率的开环测试更容易观察过载，但需要正确记录发送失败和积压。两种方式回答不同问题，应在图例写清楚。

重复实验要保留预热方式和波动范围。没有足够样本支撑尾分位数时，直接报告限制，不用很多小数位制造精确感。

### Agent 与检索实验的最小记录

```text
Agent：模型版本、工具定义、任务集、上下文、步骤与费用上限
执行：权限、网络出口、工作副本、依赖、超时与进程清理
恢复：超时发生点、幂等标识、状态查询、未知结果与补偿
评测：可信测试来源、尝试次数、选择规则、人工复核与返工
检索：快照、维度、距离函数、过滤分布、精确真值与并列规则
更新：插入、删除、索引覆盖范围、嵌入版本与可见时延
输出：原始日志、指标计算方式、失败样本与适用范围
```

【推断】多 Agent 研发的并行收益应扣除冲突合并、上下文重复、独立验证与返工。没有这些成本项时，只能证明增加并发尝试，不能证明提高交付效率。

### 口头回答如何收敛

第一分钟给判断与条件，第二分钟展开一条状态或数据路径，第三分钟给失败场景和验证方法。面试官继续追问时，沿同一路径深入，不要用更多项目名称逃避已提出的问题。

每次模拟面试选一道推理题和一道 Agent 或数据题，追问到资源回收、可见性或未知结果。若需要用个人项目支撑，先补齐上面的【模板】，再删除不符合事实的表述。

## 勘误：原料中哪些表述不能直接迁移

本节只校正本篇会用到的基础，并列明原料位置；不修改 xlab 原文件。原料没有系统讲述 vLLM、SGLang 或 MCP，因此不把新增内容伪称为对原文 AI 技术错误的纠正。

1. **`cpp-interview-questions.md` §1.3 的固定 128 KB 分界。** 原料按小于／大于等于 128 KB 划分 `brk` 与 `mmap`。更正为：glibc 分配策略受分配区（Arena）、已有空闲块和可动态变化的阈值影响，不能由请求大小单独断言路径；也不能把 CPU 分配器规则套用到 GPU 内存池。[Linux `mallopt(3)`](https://man7.org/linux/man-pages/man3/mallopt.3.html)

2. **`os-network-interview-questions.md` §4.2 的 epoll 整体 O(1) 与“无限制”。** 更正为：就绪列表减少反复扫描全部监视项的工作，但事件返回与处理仍随就绪数量增长，文件描述符受系统资源上限约束。不能据此推导 Agent 工具并发或流式连接“没有成本”。[Linux `epoll(7)`](https://man7.org/linux/man-pages/man7/epoll.7.html)

3. **`interview-questions(raw).md` 关于 `tcp_fin_timeout` 缩短 TIME_WAIT。** 更正为：该参数针对孤儿连接的 FIN_WAIT_2 等待，不是通用 TIME_WAIT 时长开关；非阻塞 I/O 或更快网卡也不直接缩短协议等待。推理网关应先分析连接复用与关闭责任。[Linux `tcp(7)`](https://man7.org/linux/man-pages/man7/tcp.7.html)

4. **`os-network-interview-questions.md` §3.5 把 protobuf 本身列作消息边界方案。** 更正为：Protocol Buffers（协议缓冲区）编码本身不自带完整消息流分帧，连续消息仍需长度前缀或外层协议。工具 RPC 与状态传输要分别说明编码、分帧和重试。[Protocol Buffers 官方技术说明](https://protobuf.dev/programming-guides/techniques/)

5. **`algorithm-interview-questions.md` §3.1 把 1 TB 哈希成 1000 个文件就认为每个能装进 1 GB。** 更正为：均匀分布只提供平均文件大小，倾斜、不同单位和哈希表内存放大都可能超限。应测分区峰值，必要时递归分区或外部聚合；同样不能按平均 KV 大小推导绝不会显存溢出。这是由容量约束直接推出的修正。

6. **`algorithm-interview-questions.md` §3.3 声称虚拟节点“解决”倾斜。** 更正为：虚拟节点缓解键空间分布不均，不消除热门键造成的请求倾斜。前缀缓存亲和路由仍需考虑热点复制、队列与迁移成本。这是键分布与访问分布不同所导致的逻辑边界。

7. **`database-interview-questions.md` §4.1 把 EXPLAIN 访问类型顺序写成近似优劣排名。** 本篇改用候选行数、访存、过滤选择率和更新代价建立成本判断；全表或精确扫描并非天然差方案。若过滤后只剩很小的集合，维护并访问近似索引的成本可能反而更高。这是成本推导，不是声称所有数据库版本会选择相同计划。

8. **职业资料中以身份标签代替能力的风险。** 原料也提醒不要夸大简历，但各处示例容易被直接套用。本篇只保留用户提供的背景，个人性能成果、AI 项目和跨团队决策全部用【模板】待填；不引用陈旧签证、薪酬或职级换算信息作为当前求职事实。
