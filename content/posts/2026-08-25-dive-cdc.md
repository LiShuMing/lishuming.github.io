设想同一句再普通不过的业务更新：账户 `id = 42` 原先余额是 `100`，现在执行一条 `UPDATE accounts SET balance = 90 WHERE id = 42`。如果下游实时风控或增量物化视图订阅了这张表的变更流（CDC，Change Data Capture），它期望收到两条严丝合缝的事件：一条撤回旧值的更新前像 `-U(42, 100)`，紧接着一条写入新值的更新后像 `+U(42, 90)`。

一个耐人寻味的系统现象就在这里浮现：**为什么在 MySQL、PostgreSQL 这类 OLTP 行存数据库里，完整的 `-U / +U` 前后镜像几乎是“白送”的副产品；而一旦换到现代湖仓一体或列式 Merge-on-Read（MOR）表格式上，想拼出同一条 `-U(42, 100)` 却动辄要付出高昂的随机读放大、写放大甚至后台合并延迟？**

顺着物理执行路径往下摸，账本立刻一清二楚。OLTP 引擎采用 B+Tree 原地更新（In-place Update），事务要想把 `100` 改成 `90`，首先就得把 `id = 42` 所在的叶子数据页加载进内存 Buffer Pool，同时为了支持事务回滚与崩溃恢复，Undo Log 和 WAL / Binlog 本来就必须把修改前的旧值 `100` 和修改后的新值 `90` 一并顺序刷盘——Debezium 等日志捕获工具只是顺手读走了这份现成的物理账本。

反观基于不可变列存文件（Parquet / ORC）的湖仓表格式，整套架构的立身之本恰恰是**写时不碰旧文件**。在 MOR 模式下，Writer 为了保住高吞吐批量写入，根本不去对象存储上翻找历史 Base 文件里 `id = 42` 原先是多少钱，而是直接盲写一条增量记录 `Delta(+42, 90)`（或追加一个指向旧文件行号的删除向量 Deletion Vector 外加新文件行）。写入端倒是轻快了，可前像 `-U(42, 100)` 在提交那一刻压根没进过内存！更棘手的是，如果紧接着下一个事务又把余额从 `90` 改回了 `100`（即 `100 → 90 → 100`）：

- 要是图省事只拿首尾两个快照做集合相减（Snapshot Diff），算出来的净变化是“零改动”，中间真实发生过的两笔资金变动被彻底抹平；
- 要是底层走的是写时复制（Copy-on-Write, COW），为了改 `id = 42` 这一行把整块 10 万行的 Parquet 文件重写了一遍，朴素的文件级增删对比又会把旁边 99,999 行纹丝未动的陪跑记录（Carryover Rows）全当成“先删后插”吐给下游；
- 要是后台 Compaction 在下游消费者赶来读取之前，悄悄把中间那几次 Delta 合并压实成了单张最新 Base 表，中间状态直接灰飞烟灭，连回查的线索都断了。

古希腊哲学家赫拉克利特在河流残篇（[B12](https://plato.stanford.edu/entries/heraclitus/#Flu)）里说，“踏入同一条河流的人，遇到的是不断流来的不同水流”——快照（Snapshot）拍下的是某一瞬间的河面，而表内 CDC 要回答的是两个时刻之间究竟流过了哪些水。在工程上，这意味着我们不能靠粗糙的“首尾文件做差”凑合，而必须建立一套严密的**状态迁移代数**：

$$
\text{State}(v_1) = \text{Apply}\big(\text{State}(v_0),\ \Delta(v_0, v_1]\big), \qquad \Delta(v_0, v_2] = \Delta(v_0, v_1] \oplus \Delta(v_1, v_2]
$$

下文聚焦**如何从一张湖仓/列存表自身派生可靠的表内 CDC**，先拆解前像获取与消费契约的物理约束，再横向剖析 **Snowflake、BigQuery、Apache Iceberg、Delta Lake、Apache Hudi 与 Apache Paimon** 的源码及架构分野，最后落脚到托管式 MOR 表格式下“合并前保存变更证据（Compaction Anchor + 短尾段推导 + Row Lineage）”的完整设计与重放验证。

## 一、CDC 契约与物理账单：前像从哪来，谁来买单？

很多团队在设计表内增量能力时，一上来就扎进“怎么扫新增文件”，等到上下游联调才发现语义处处漏风：有的消费者做增量聚合（如 `SUM(balance)`），漏掉一条 `-U` 就会把账算翻倍；有的消费者做搜索引擎同步，只需要最终净状态（Upsert），多吐中间过程纯属浪费带宽。因此，动手选物理路线前，必须先把七项消费契约钉死：

| 契约维度 | 内核设计必须拍板的核心问题 |
| --- | --- |
| **水位定位（Offset）** | 按 Snapshot ID、单调递增 Commit Sequence 还是时间戳寻址？跨分片是否严格单调？ |
| **顺序保证（Ordering）** | 仅保证单行/单主键因果序，还是严格按 Commit 序列还原表级事务顺序？ |
| **实体身份（Identity）** | 靠业务主键、物理 `(file, row_pos)` 还是跨重写稳定的逻辑 `_row_id` 识别“同一行”？ |
| **镜像完整度（Image）** | 只吐后像（After-only），还是完整提供 `+I / -U / +U / -D` 四类操作事件？ |
| **模式演化（Schema）** | 历史变更按写入时旧 Schema 输出，还是统一投影到当前查询 Schema？列删除/改名如何对齐？ |
| **投递与幂等（Delivery）** | 消费端崩溃重放时，Source 能否产出确定性的 `(commit_seq, row_id, ordinal)` 供下游幂等去重？ |
| **保留期（Retention）** | Offset 落后于 Vacuum / Snapshot 清理水位时，系统是显式报错阻断，还是静默漏行？ |

一旦消费契约要求交付完整的 `+I / -U / +U / -D`，全系统的物理瓶颈立刻聚焦到同一件事上：**谁、在哪个阶段、花什么代价去把旧值（Before-image）翻出来？** 把 OLTP 日志、湖仓写时物化与 MOR 合并期捕获三条技术路线并排放在一起，成本转移的脉络清晰可见：

![更新一行如何取得前像（Before-Image）：三类引擎的代价转移路径](/images/diagrams/aug-exec-cdc-before-image-paths.svg)

可以看到，世上从来没有“零成本的免费 CDC”，只有把查旧值的账单挂在不同的生命周期节点上：

1. **挂在写入事务上（写时同步物化）**：强迫 Writer 在提交更新或删除时，当场点查历史 Base 文件取出旧值，把配好对的 `-U / +U` 双写进独立的 `_change_data` 目录。好处是下游读取像扫普通日志一样便宜且强一致；代价是直接把高吞吐盲写拖成了随机 I/O 密集型点查，写放大显著。
2. **挂在后台合并上（Compaction 时物化）**：写入端照常盲写轻量 Delta；等到后台 Compaction 把 Base 与 Delta 拉到一起做归并排序时，新旧记录天然在内存里碰面，此时顺手写出完整 Changelog，把回查成本完美摊销进本来就要发生的合并 I/O 中。代价是 CDC 的可见性延迟被绑死在了 Compaction 触发周期上。
3. **挂在消费读取上（读时在线推导）**：平时一份额外 CDC 文件都不写；等消费者发起 `(v0, v1]` 区间扫描时，读取器根据区间内的删除向量（DV）或行血缘（Row Lineage）反查旧 Base 文件并在线配对前后像。写入零负担且支持任意历史区间回放，但一旦查询跨度拉长或中间文件已被压实改写，读放大与规划复杂度就会急剧攀升。

## 二、六大主流系统拆解：云数仓与开放湖仓如何选边站？

带着“前像来源、物化时机与保留期边界”这把标尺去检视工业界主流系统，就会发现各家的架构差异全都对应着各自的控制边界。

### 2.1 云原生托管数仓：Snowflake Streams 与 BigQuery `CHANGES`

当同一套内核完全掌控了底层的微分区存储、事务元数据与查询引擎时，**读时推导 + 消费游标**是最轻巧的产品形态。

[Snowflake Streams](https://docs.snowflake.com/en/user-guide/streams-intro) 创建时几乎不占额外空间，只记录源表当前版本的一个事务 Offset。源表开启 Change Tracking 后，读取 Stream 会在 `(offset, current_version]` 区间上利用隐藏列 `METADATA$ACTION`、`METADATA$ISUPDATE` 与跨重写稳定的 `METADATA$ROW_ID` 在线推导出净变更或追加变更；一旦下游在事务里消费了 Stream，Offset 原子前移。同理，[BigQuery `CHANGES`](https://cloud.google.com/bigquery/docs/reference/standard-sql/time-series-functions#changes) 表值函数在开启 `enable_change_history` 后按时间窗口在线还原 `INSERT / UPDATE / DELETE`。这两套系统没有凭空变出历史，而是把变更证据内嵌进了底层时间旅行（Time Travel）保留窗口——一旦消费者的 Stream Offset 停滞太久越过了表的 Data Retention 期限，Stream 就会直接变为 `Stale` 拒绝服务，绝不拿残缺数据糊弄下游。

### 2.2 Apache Iceberg：从 COW 文件扫描到 v3 Row Lineage 身份革命

翻开 Apache Iceberg（源码基线 `457854f`）的核心扫描实现 [`BaseIncrementalChangelogScan.java`](https://github.com/apache/iceberg/blob/457854fb3d05887c7bd263703cb99bcd97c13429/core/src/main/java/org/apache/iceberg/BaseIncrementalChangelogScan.java)，能看到开放表格式早期的真实边界：它在 `(fromSnapshot, toSnapshot]` 祖先链上跳过纯物理重写的 `REPLACE` 快照，按 Manifest Entry 的 `ADDED` / `DELETED` 吐出文件级增删任务；**但只要扫描区间内撞见任何 Delete Manifest，该核心路径当场抛出 `UnsupportedOperationException`！** 换言之，旧版 Core 扫描器只覆盖了 COW 场景，并且消除 COW 重写带来的 Carryover 未变行、把同主键的删插配对成 `-U / +U`，还要靠上层 Spark 引擎的 [`ChangelogIterator`](https://iceberg.apache.org/javadoc/latest/org/apache/iceberg/spark/ChangelogIterator.html) 接力完成。

为了让开放表格式真正拥有跨文件重写的行级身份，[Iceberg Format v3 正式引入了 Row Lineage 规范](https://iceberg.apache.org/spec/#row-lineage)（并在社区 [`[DISCUSS] Row lineage required for v3`](https://www.mail-archive.com/dev@iceberg.apache.org/msg09643.html) 讨论后确立为 v3 表的通用基座）：每行携带稳定的 `_row_id` 与 `_last_updated_sequence_number`。新插入行在写入 Parquet 时留空这两个物理值，提交快照时直接通过元数据树 `TableMetadata.next_row_id → Snapshot → Manifest → DataFile.first_row_id + row_pos` 零重写继承唯一行号；发生行更新时保留原 `_row_id` 并推进更新序列号；而纯 Compaction 重写文件时（如 Spark [`#13555`](https://github.com/apache/iceberg/pull/13555) 与 Flink [`#14149`](https://github.com/apache/iceberg/pull/14149)），原封不动复制旧行的 `_row_id` 与旧序列号！

Snowflake 已率先在其 [Dynamic Iceberg Tables 与 Streams](https://www.snowflake.com/en/blog/apache-iceberg-v3-support/) 中打通了这套 v3 Row Lineage，使得无主键表与重写文件也能精确剔除 Carryover 行。但源码与规范同样揭示了两条不可逾越的物理红线：

1. **Equality Delete 无法继承旧 `_row_id`**：如果上游引擎为了极速盲写采用等值删除（只写一条 `DELETE WHERE pk = 42` 再盲插新行，全程没读旧行），Writer 自己都不知道旧行的 `_row_id` 是多少，新行只能分配全新 ID——此时底层 Lineage 扫描器只能诚实地输出 `-D + +I`，除非上层显式按业务主键再做一次归并；
2. **身份不等于前像数据本体**：`_row_id` 解决了“谁和谁是同一行”的配对难题，但要拿到被 Position Delete 或删除向量（DV）干掉的那行旧值（参见社区正在推进的 MOR Delete 支持 [`#14264`](https://github.com/apache/iceberg/pull/14264)），Reader 依然必须去打开旧 Data File 读取对应行，并妥善维护历史重叠 Delete 去重。

### 2.3 Delta Lake、Apache Hudi 与 Apache Paimon：显式物化与双轨合流

相比之下，另外三大湖仓项目把写时、合并时与读时的权衡展现得淋漓尽致：

- **Delta Lake（从写时 CDF 走向 Row Tracking 自动推导）**：传统的 `delta.enableChangeDataFeed` 在执行 `UPDATE / DELETE / MERGE` 的同一事务里把带 `_change_type` 的前后像直接写出到 `_change_data` 文件夹（纯追加或整文件增删则直接从事务日志零拷贝推导），下游用 [`table_changes`](https://docs.databricks.com/aws/en/sql/language-manual/functions/table_changes) 极速读取；而新一代 [Automatic CDF](https://docs.databricks.com/gcp/en/tables/features/change-data-feed) 则依托 Delta Row Tracking 与删除向量，允许表无需预先承担写时双写开销，而在读取端按稳定行身份动态还原变更——印证了“一旦拥有行级血缘，CDC 重心就能安全向读侧后移”的演进趋势。
- **Apache Hudi（Merge Handle 分级补充日志）**：Hudi 的 [RFC-51](https://github.com/apache/hudi/blob/master/rfc/rfc-51/rfc-51.md) 提供了像数据库重做日志一样精细的落盘旋钮：`KEY_OP`（只记变更键与操作码，读时再去拼前后数据）、`DATA_BEFORE`（额外存旧值）与 `DATA_BEFORE_AFTER`（全量存新旧镜像）。因为 Hudi 生成新 Base 文件的 Merge 算子本来就同时握着旧记录与增量日志，顺手写下补充日志块非常自然，唯独必须严防 Cleaner 清理策略早于下游消费水位把依赖的旧块删掉。
- **Apache Paimon（把前像成本位置直接做成表属性）**：Paimon（源码基线 `b782f24`）的 [`changelog-producer`](https://paimon.apache.org/docs/master/primary-key-table/changelog-producer/) 把账单明明白白摆在桌面上供用户四选一：`none`（不产完整前像）、`input`（直接透传上游 Flink CDC 自带的完整日志，存储层免回查）、`lookup`（每次小合并时通过本地多级索引点查底层 LSM 旧文件补齐 `-U`，兼顾亚分钟级延迟与完整性，但增加 Compaction I/O）以及 `full-compaction`（攒到全量合并时对比前后快照统一产出，吞吐高但延迟大；顺带注意 `first-row` 属于合并引擎而非第五种 Producer）。

把这六套体系压缩到一张全景对照表里，各自的适用半径便水落石出：

| 系统与机制 | 变更物化时机 | Before-image 物理来源 | 版本对齐粒度 | 历史失效边界 | 核心工程取舍 |
| --- | --- | --- | --- | --- | --- |
| **Snowflake Streams / BQ `CHANGES`** | 读时在线推导 | 隐藏行元数据 + 微分区时间旅行历史 | 表事务 Offset / 时间窗 | 超出 Retention 变 `Stale` | 写入极轻、多游标零副本；强依赖托管底座保留旧块 |
| **Iceberg Core `ChangelogScan`** | 读时文件级扫描 | Manifest 增删文件 + 引擎侧去重配对 | Snapshot 区间 | Snapshot / 数据文件过期 | 仅限 COW 路径，遇 Delete Manifest 直接抛异常 |
| **Iceberg v3 Row Lineage** | 读时按 `_row_id` 配对 | 旧数据文件 + Delete/DV 定位 | Snapshot Sequence | 旧文件与 DV 存活窗口 | 根治无主键与文件重写身份丢失；等值删除退化为删插 |
| **Delta CDF（Legacy / Auto）** | 写时双写 / 读时推导双轨 | Writer 同步写出，或 Row Tracking 反查 | Delta Commit 版本 | `VACUUM` 与日志保留期 | Legacy 写贵读快；Auto 免预开但依赖行追踪运行时 |
| **Apache Hudi CDC** | Merge 期物化 + 读时补全 | Merge Handle 内存新旧行 + Log Block | Hudi Timeline Instant | Cleaner 清理水位 | 三档补充日志灵活折中存储体积与读时回查开销 |
| **Apache Paimon** | 输入透传或 Compaction 物化 | 上游自带，或 LSM `lookup` / 全量对比 | Snapshot / Compaction | Changelog 独立或跟随保留 | 成本位置最透明，但 `lookup` 显著消耗合并期 CPU 与 I/O |

## 三、架构设计：托管 MOR 表格式如何在合并前保全变更证据？

如果我们自己操刀设计一套像 [MaxCompute Delta Table](https://www.alibabacloud.com/help/en/maxcompute/user-guide/delta-tables/) 这类统一管控 Writer、元数据、后台 Compactor 与查询引擎的**托管式 MOR 列存表**（公开文档中其现有增量查询返回的是合并后的最新状态，尚未直接提供完整的 `+I / -U / +U / -D` 操作流），怎样才能既保住 MOR 盲写 Delta 的极致吞吐，又不让后台 Compaction 吃掉中间更新历史，还能避免像 Paimon `full-compaction` 那样动辄等上几十分钟才吐出变更？

如果用异步独立作业定时扫主表写一张“影子 CDC 表”，上线最快，但永远摆脱不了主表与影子表跨事务水位错位、作业挂起导致主表旧文件被提前清理的顽疾。真正内生自洽的解法，是利用 MOR 自身的物理周期，采用 **“Compaction 变更锚点（Changelog Anchor）固化历史 + 读时在线推导补齐新鲜短尾 + 可选 Row Lineage 贯穿身份”** 的双段式架构：

![托管 MOR 表格式的合并前证据保全、原子锚点与分段 CDC 重放](/images/diagrams/aug-exec-cdc-mor-change-evidence.svg)

### 3.1 核心机制：Compaction 原子双输出与 `(v0, v_anchor] + (v_anchor, v1]` 分段拼接

仔细观察 MOR 表的生命周期就会发现：后台 Compaction 并不是 CDC 的敌人，恰恰相反，**Compaction 把旧 Base 与多批增量 Delta/DV 读进内存按主键或位置归并的那一刻，正是全系统唯一一次免费同时看见旧值与新值的黄金窗口！**

只要我们给后台 Compactor 立下一条铁律——**“语义透明不变量：任何抹平中间 Delta 状态的物理合并，必须在同一笔元数据事务中留下语义等价的变更锚点（Changelog Anchor）”**——整条链路立刻豁然开朗：

1. **已压实历史段 `(v0, v_anchor]` 零回查直读 Anchor**：当 Compactor 合并 `[v0, v_anchor]` 区间的 Base 与各层 Delta 时，同一个归并算子一边向新 Base 文件吐出压实后的最新快照行，一边把合并途中逐版本碰撞出的 `+I / -U / +U / -D` 事件流顺序写成列式 `Changelog Anchor` 文件，并在一次原子 Commit 中同时挂载新 Base 与该区间的 Anchor 元数据。哪怕区间里发生过 `100 → 90 → 100` 的反复横跳，只要合并输入里还留着这两次 Delta，Anchor 就能分毫不差地把两次更新全部录下来。
2. **未压实新鲜尾段 `(v_anchor, v1]` 在线轻量推导**：Compaction 之后刚刚写入、还没来得及合并的那几分钟新鲜 Delta 怎么办？根本不用傻等下一轮 Compaction！因为这段尾巴非常短、文件数极少，CDC Reader 直接在线扫描 `(v_anchor, v1]` 的新增 Delta 与删除向量（DV），利用 DV 记录的 `(file_path, row_pos)` 或主键索引精准点查刚刚压实好的新 Base 取出 Before-image，在内存里快速拼出尾段事件流。
3. **跨段无缝拼接**：对任意消费请求 `CDC_Scan(v0, v1]`，元数据规划器自动将其切分为“前段顺序扫 Anchor + 尾段在线合 Delta”，按单调递增的 `(_commit_sequence_number, _row_id, _change_ordinal)` 流式拼接输出。这样既保住了写入端的纯追加极速路径，又把最昂贵的大跨度历史回查摊销进了后台合并，同时让下游依然享有秒级到分钟级的消费新鲜度！

### 3.2 接入 Row Lineage 后的逐快照精确归因规则

当表需要支持无主键 CDC，或者允许在保留期内穿插纯物理文件重排（如 Z-Order 聚簇重写）时，就可以把前文 Iceberg v3 式的 `_row_id` 与 `_last_updated_sequence_number` 接入上述双段管线。

在逐个业务 Commit（跳过纯重写的 `REPLACE` 快照事件输出，但保留其新文件映射供后续 DV 寻址）配对前后状态时，Reader 按照 `_row_id` 的继承关系执行严格确定性的五路分类，彻底告别启发式猜测：

| 旧状态（Before） | 新状态（After） | 行血缘（Lineage）不变量特征 | 产出的标准 CDC 事件 |
| --- | --- | --- | --- |
| 不存在 | 存在 | `_row_id` 在本轮 Commit 首次由元数据树分配 | `+I`（新增） |
| 存在 | 不存在 | 旧 `_row_id` 被当前 Commit 的 DV / Position Delete 标记移除 | `-D`（删除） |
| 存在 | 存在 | `_row_id` 相同，且 `_last_updated_sequence_number` 推进至当前版本 | `-U` 紧接 `+U`（更新前后像，`_change_ordinal` 保序） |
| 存在 | 存在 | `_row_id` 与 `_last_updated_sequence_number` 均未变化 | **Carryover 物理搬迁行，直接静默过滤** |
| 存在 | 存在 | 业务主键相同，但新旧 `_row_id` 不同（如盲写 Equality Delete） | 底层如实输出 `-D` + `+I`；仅在显式开启主键归并时合并为净更新 |

这里同样要向业务方挑明 Commit 级存储 CDC 的天然粒度边界：如果同一个数据库事务内部对同一行连续执行了 `100 → 80 → 90` 两条 SQL 语句，而底层文件只持久化了提交时的 `90`，表格式级 CDC 看到并承诺的只能是 Commit 粒度的 `100 → 90`；若业务强依赖还原事务内部未提交的每一条子语句轨迹，那就必须在 Writer 端直接开启操作日志落盘。

## 四、正确性护栏与故障重放验证矩阵

把架构图画通只是第一步。在真实的分布式生产环境里，Compaction 中途崩溃重试、消费者停滞、Schema 加减列以及 Cleaner 并发删文件每天都在同时发生。一套敢上线扛核心资金或账单链路的表内 CDC，必须把“Retention 是语义承诺而非单纯磁盘定时任务”写进死规矩里，并通过下面六组破坏性故障注入验证：

| 故障注入与边界测试场景 | 必须守住的系统行为与可验证不变量 |
| --- | --- |
| **跨 Commit 往复修改（`A → B → A`）** | 无论走在线尾段推导还是经 Compaction 压成 Anchor 后再读，操作级 CDC 均须完整吐出两次 `-U / +U`，绝不能因首尾状态相同而静默抵消 |
| **Compaction 与增量写入并发交错** | 纯文件重排不吐出任何伪业务事件；后续事务针对重写后新文件发出的 Position Delete 仍能精确回查到正确的 Before-image |
| **Anchor 双输出中途崩溃与重试** | Base 快照与对应区间的 Anchor 元数据必须在同一笔原子提交中生效；重试不得产生区间空洞或重复挂载两份相同 Anchor |
| **消费端写完下游但在提交 Offset 前宕机** | 重放同一 `(v0, v1]` 区间吐出的 `(_commit_sequence_number, _row_id, _change_ordinal)` 字节级确定一致，支撑下游事务或去重表实现端到端幂等 |
| **慢消费者拖尾 vs Cleaner 文件回收** | Cleaner 水位取 `min(活跃注册消费者安全 Offset, 表最大 Retention 上限)`；一旦未注册或超时游标请求已被清理的历史区间，API 必须显式报 `OffsetOutOfRange / Stale` 错误，严禁返回缺了 `-U/-D` 的残缺流 |
| **区间内穿插加列/改类型等 Schema 演化** | 读取器基于字段唯一 Field ID（而非列名或位置下标）将历史 Anchor 与旧 Base 前像准确投影至目标 Schema，缺省列按演化规则补 `NULL` 或默认值 |

归根结底，Snapshot 存的是“此刻的结果”，CDC 存的是“结果何以至此的证据”。只要抓住了**稳定行身份（Row Identity）、合并前前像捕获（Pre-Merge Evidence）与统一生命周期护栏（Unified Watermark）**这三根支柱，无论是评估开源湖仓选型还是自研底层存储引擎，都不会再迷失在纷繁的配置名词里。
