为什么没有任何一款现代分析引擎，敢在查询启动前拍胸脯给出一个永远正确的静态并行度（Degree of Parallelism，DOP）？

设想一条再普通不过的两表关联聚合查询：扫两张表，做一次过滤和 Shuffle 连接，最后把结果写回对象存储。如果你在编译期静态拍板一个 `DOP = N`，立刻就会掉进两座悬崖之间的夹缝里：

- **开得太小（比如 `N = 4` 撞上过滤失效后的 1 TiB 中间数据）**：集群里几百个 CPU 核心和网卡带宽闲在一旁干瞪眼，4 个下游任务各自被塞进几百 GiB 状态，哈希表瞬间撑爆内存触发连环落盘（Spill）甚至 OOM；只要其中一个分区多撞上几个热点键，整条流水线就被这一个慢任务（Straggler）死死拖住。
- **开得太大（比如 `N = 2000` 撞上高选择率过滤后仅剩的 50 MiB 数据）**：全交换 Shuffle 瞬间裂变出 `2000 × 2000 = 4,000,000` 个只有十几字节的微型网络数据块，RPC 握手、任务派发与反序列化缓冲区把控制面和内存开销拉满；广播连接（Broadcast Join）的哈希表在成百上千个执行单元里重复拷贝，最后落盘时还会往湖仓里喷出两千个几 KB 的碎文件，给下游查询埋下元数据灾难。

更棘手的是，数据库语境里随口说出的“调大并行度”，背后改动的根本不是同一个物理实体。把 1,000 个 Shuffle 分桶合并给 100 个任务去读、只给这 100 个任务批 20 个并发槽位，以及在单个节点内部开 16 个流水线驱动器（Pipeline Driver），分别动在了**数据切分、任务编排、本地算子状态和线程池配额**四个截然不同的层次上——多给几个线程槽位只需通知调度器，改写 Shuffle 读取映射需要对齐上下游键范围，而推翻已经写好的哈希分区则意味着整批数据重新过网洗牌。

正因为“知道真实数据有多大”的时间点越来越晚，而“推翻重来”的物理代价越来越高，现代查询引擎不约而同地把并行度决策拆成了贯穿查询生命周期的**三次出手机会**：

1. **编译期（运行前）**：在统计信息残缺、尚未读到一行真实数据时，结合节点拓扑与安全护栏给出一个“选错了也容易挽回”的初始分区数；
2. **阶段与流水线边界（运行中）**：趁上游 Shuffle 物化完成或本地缓冲区攒够样本、下游算子尚未实例化的时间窗口，用实测字节分布合并碎桶、拆解倾斜块或收缩本地并发；
3. **跨查询演进（运行后）**：把上一轮执行中验证过的真实分布与重分区方案沉淀下来，在下一次同类查询编译时直接跳过试错弯路，同时配合集群准入控制防止单条查询榨干公共资源。

下面我们就先厘清并行度的四层物理粒度，再沿着“编译期 → 运行中 → 跨执行”这三次决策窗口，走进 Spark、PrestoDB、Trino、Flink、StarRocks 的源码与工业界顶会论文里看个究竟。

## 一、拆解“并行度”：四层控制粒度与两座性能悬崖

在对比不同引擎之前，先把术语对齐。假设上游 Shuffle 写出了 1,000 个哈希分桶（Bucket），执行引擎把它们打包成 100 个分布式消费任务（Task），集群资源队列此刻只批给这条查询 20 个并发执行槽位（Slot），而每个拿到槽位的 Task 内部又拉起了 4 个本地流水线驱动器（Driver）去共享节点的 Worker 线程池——从底层存储分片到最终的物理核与内存配额，数据流经由跨节点 `Shuffle Exchange` 与节点内 `Local Exchange` 层层解耦映射：

![MPP 查询引擎的四层物理并行度映射关系](/images/diagrams/exec-dop-four-layers.svg)

把这四层主干连同旁路的容错重试维度摊开对照，很多跨系统鸡同鸭讲的误会就迎刃而解了：

| 控制层次 | 操控的物理对象 | 工业界典型实例 | 运行期调整它的真实代价 |
| --- | --- | --- | --- |
| **逻辑工作划分** | 文件切片（Split）、Shuffle 桶、微分区 | Spark 初始 Reducer 分区、HyPer Morsel | 若数据尚未生成只需改切分参数；若已按哈希落盘，改桶数就得重新做一次 Shuffle |
| **分布式任务形成** | Stage / Fragment 的逻辑 Task 实例 | Trino FTE 的 Task Partition | 在下游尚未启动前合并或切分读取范围（Reader Spec），无需重写上游文件 |
| **节点内局部并发** | 单个 Task 内部的 Pipeline Drivers | StarRocks `pipeline_dop`、Presto `task.concurrency` | 必须在算子初始化前敲定本地状态分片与缓冲区归属，运行中很难直接销毁 |
| **集群资源分配** | 硬件工作线程、Executor 槽位、计算配额 | Spark Executor Cores、BigQuery Slots | 纯粹改变排队轮次与并发吞吐，不动任何哈希分区与中间状态所有权 |
| **重试与投机执行** | 同一逻辑任务的多副本尝试（Attempts） | 慢节点投机备份任务（Speculative Task） | 消耗额外算力对冲单机抖动，对数据本身造成的数据倾斜毫无办法 |

在编译期估算逻辑划分数量时，最直观的朴素公式是拿预估总工作量除以单个任务的理想目标容量：

$$
P_{\text{est}} = \left\lceil \frac{W_{\text{est}}}{W_{\text{target}}} \right\rceil
$$

工程实现里最常拿来充当 `W` 的指标是输入字节数（`bytes/task`），因为它最容易从文件元数据或表统计里直接汇总。但单靠字节数给任务定量，马上就会撞上两类反例：第一，100 MiB 全是窄整数列但包含五千万个不同键的 `COUNT(DISTINCT)`，CPU 哈希聚合算到冒烟，字节数看着却很小；第二，同样是 100 MiB 输入，经过多对多连接或复杂正则/UDF 展开后，内存状态可能原地膨胀几十倍。

再把视野拉高到整个 Stage 的端到端完工耗时，它从来不是简单的“总活儿除以并行度”，而是五个分量叠加的结果：

$$
T_{\text{stage}} \approx T_{\text{queue}} + T_{\text{dispatch}} + T_{\text{work}} + T_{\text{exchange}} + T_{\text{tail}}
$$

随着并行度一路调大，单任务理想计算耗时 `T_work` 虽然往下掉，但等待空闲槽位的排队时间 `T_queue`、控制面派发开销 `T_dispatch` 与全连接网络交换开销 `T_exchange` 都在一路抬升；要是瓶颈卡在某个不可切分的热点键尾延迟 `T_tail` 上，盲目把任务数翻十倍除了多造九倍空转碎片外寸功未立。更微妙的是集群视角与单查询视角的冲突：**让单条查询跑得最快的激进并行度，往往会把共享线程池和网络缓冲占满，反过来拖垮整个多租户集群的整体吞吐。**

## 二、第一次决策（编译期）：在模糊统计与拓扑约束下给出初值

在查询刚刚走完语法解析与逻辑优化、还没碰到底层数据的那一刻，引擎手里只有文件列表、未必新鲜的直方图以及当前在线的节点拓扑。这时候各家系统的共同智慧是：**扫描端按物理文件做带开销补偿的装箱，Shuffle 端则结合集群规模与安全护栏给出一个留有余地的初值。**

### 2.1 Spark：文件扫描装箱与 Shuffle 初值的双轨路径

新手调优 Spark 时常犯的一个错误，是以为 `spark.sql.shuffle.partitions`（默认 `200`）统管了整条 SQL 的所有任务数。实际上，在 Spark（基线 `786bb3d`）里，源头扫描与中间洗牌走的是两条完全独立的轨道。

文件扫描并发由 [`FilePartition.scala`](https://github.com/apache/spark/blob/786bb3d9751fc6c4993997c088345ceba1b7a8d5/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/FilePartition.scala) 拍板。试想目录里躺着一万个 100 KB 的碎 Parquet 文件，如果真按默认 `maxPartitionBytes = 128 MiB` 纯算文件净字节，一个 Task 就会被硬塞进一千多个小文件，光是对象存储的打开请求和 Footer 解析就能把任务拖死。为此，Spark 给每个文件额外加收了一笔默认 `4 MiB` 的虚拟开户费（`openCostInBytes`），先算出单切片上限 `maxSplitBytes`，再把切好的文件片段按体积从大到小塞进分区桶：

```scala
partitionedFiles.foreach { file =>
  if (currentSize + file.length > maxSplitBytes) {
    closePartition()
  }
  // 判定能否塞入时只看真实 file.length，塞入后才累加 4 MiB 打开成本，防止碎文件无限堆叠
  currentSize += file.length + openCostInBytes
  currentFiles += file
}
closePartition()
```

注意这段装箱循环里的两处微妙边界：一是判满条件看的是净长度 `file.length`，入桶后才补记 `openCostInBytes`，所以单桶真实字节并不是一刀切的硬上限；二是如果碰上 Gzip 这类不可切分（Non-splittable）的超大单文件，哪怕配了 `files.maxPartitionNum` 调整目标切片尺寸，单个文件也没法被拦腰劈成两半。

反观下游 Shuffle 阶段，开源 Spark 传统上直接给一个静态配置初值 `200`（见 [Spark SQL Performance Tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html)），把精准修剪的活儿留给后面的运行时 AQE；而在 Databricks Serverless 等托管环境里，`spark.sql.shuffle.partitions` 已默认切为 `auto`（见 [Databricks Spark 配置](https://docs.databricks.com/aws/en/spark/conf) 与 [AQE 文档](https://docs.databricks.com/aws/en/optimizations/aqe)），在洗牌发生前先根据计划结构与输入体积预估一个合理的起点，再交给执行期二次微调。

### 2.2 PrestoDB、Trino 与云数仓：拓扑封顶与保守向下的统计裁剪

如果把目光转向纯流式流水线调度的 MPP 引擎，所有中间 Stage 必须同时在线接发数据，任务数自然不能脱离存活节点数天马行空。

在 **PrestoDB**（基线 `1b7b342`）的常规固定哈希分布路径（[`SystemPartitioningHandle.java`](https://github.com/prestodb/presto/blob/1b7b342e4461cc6bc391228e551b3c7a4bf205f3/presto-main-base/src/main/java/com/facebook/presto/sql/planner/SystemPartitioningHandle.java) 与 [Presto 属性文档](https://prestodb.io/docs/current/admin/properties.html)）中，单阶段最大任务数受 `fragment.partitionCount`、`query.hash-partition-count`（典型默认 `100`）与 `stage.max-tasks-per-stage` 共同约束，并且最终映射到随机挑出的可用工作节点上——也就是说，在一个只有 16 台 Worker 的小集群里跑常规固定分布查询，每个节点通常就驻留一个固定 Task，由节点内部的 `task.concurrency` 驱动多线程并行，绝不会凭空生出 100 个独立排队的分布式任务。

当集群扩大到上百台机器，每条扫几兆小表的查询都默认拉起 100 个远端重分区任务就太浪费了。为此，**Trino**（基线 `68dae09`）专门引入了编译期规则 [`DeterminePartitionCount.java`](https://github.com/trinodb/trino/blob/68dae096719f5ac7a14d5a5cbcbfa1b247c0620c/core/trino-main/src/main/java/io/trino/sql/planner/optimizations/DeterminePartitionCount.java)（配置见 [优化器参数](https://trino.io/docs/current/admin/properties-optimizer.html) 与 [查询管理参数](https://trino.io/docs/current/admin/properties-query-management.html)），利用全局统计信息主动为小查询“瘦身”：

```java
// 写操作未开启自动缩容、缺少可靠统计或含 UNNEST 等危险膨胀算子时，原样放行
if (!eligibleExchange || unsupportedWrite || unsafeExpansion || missingStats) {
    return originalPlan;
}

// 综合字节数（默认每任务 5 GiB）、行数（每任务 1,000 万行）与节点内存上限（2 * B / maxMem）取最大值
int candidate = max(countByBytes, countByRows, countByMemory, minCount);

// 只做向下裁剪，绝不越过默认上限；且普通执行下缩减幅度不到一半时免于折腾
if (candidate >= maxCount || (!taskRetry && candidate * 2 >= maxPossibleTaskCount)) {
    return originalPlan;
}

return rewriteEligibleRemoteExchangesWithSameCount(candidate);
```

这段不到二十行的骨架堪称工业级防御式设计的典范：**第一，行数和字节数双管齐下**，防止窄行高 CPU 负载被字节阈值漏放，再用 `2 * B / queryMaxMemoryPerNode` 给单节点内存留出余量；**第二，看的是整条查询最大膨胀点而非仅仅叶节点表扫描量**，避免小表连完炸出大中间结果；**第三，把“不动原计划”当成默认安全退路**，只要统计缺失、包含写入放大风险（写查询最小分区门槛默认为 50 且默认关闭该规则）或缩减收益不足两倍，绝不拿半生不熟的估算去乱改拓扑。

至于 **BigQuery** 与 **Snowflake** 等全托管云数仓，文档暴露出来的观测指标同样印证了前文的四层解耦：BigQuery 执行计划里的 `parallelInputs` 反映逻辑扫描段或 Shuffle 分区数，而真正决定此刻算得有多快的 [Slots](https://cloud.google.com/bigquery/docs/slots) 则由底层公平调度器按队列负载实时伸缩（见 [BigQuery 执行计划说明](https://cloud.google.com/bigquery/docs/query-plan-explanation)）；Snowflake 的 [微分区（Micro-partitions）](https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions) 固定在未压缩 50–500 MB 量级充当存储裁剪单元，而查询实际动用的计算并发则横跨虚拟数仓规格（[Warehouse](https://docs.snowflake.com/en/user-guide/warehouses-overview)）、`MAX_CONCURRENCY_LEVEL` 与按需接管长尾扫描的 [查询加速服务（QAS）](https://docs.snowflake.com/en/user-guide/query-acceleration-service)（见 [Snowflake EXPLAIN](https://docs.snowflake.com/en/sql-reference/sql/explain)）。分区裁剪掉了九成文件，只代表待办工作总量变少了，跟底层调度器最终派几个线程槽位完全是两码事。

## 三、第二次决策（运行中）：趁物化边界改写映射、切分倾斜与延迟派工

无论编译期算得多精，只要碰上一串带复杂过滤条件的多表连接或黑盒 UDF，静态基数估计偏离十倍百倍都是家常便饭。好在分布式计算天然存在物化断点——**当上游 Stage 把数据写完落入 Shuffle 缓冲，或者本地管道攒够一批样本，而下游算子还没真正拉起时，模糊的预测就变成了板上钉钉的字节账单。**

不过，运行期改主意必须算清一笔状态所有权账：**不重洗数据的“改映射”很便宜，拆散同键状态的“切倾斜”受连接语义严密制约，而插入新一轮 Shuffle 的“重分区”则要实打实重付一遍网络搬运费。**

### 3.1 Spark AQE：只改 Reader 映射的合并与 Map-Block 级倾斜拆解

Spark 的自适应查询执行（Adaptive Query Execution，AQE）抓住了 Shuffle 写端刚收工、读端尚未实例化的黄金窗口：此时 `MapOutputStatistics` 已经精确汇报了每一个 Reducer 分桶落盘后的真实字节数。

如果初始设了 200 个分桶，结果跑完发现每个桶只有可怜的几兆字节，[`CoalesceShufflePartitions.scala`](https://github.com/apache/spark/blob/786bb3d9751fc6c4993997c088345ceba1b7a8d5/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/CoalesceShufflePartitions.scala) 与 [`ShufflePartitionsUtil.scala`](https://github.com/apache/spark/blob/786bb3d9751fc6c4993997c088345ceba1b7a8d5/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/ShufflePartitionsUtil.scala) 根本不需要让上游重新算一遍哈希，而是直接改写下游消费者的**读取范围说明书（Reader Specs）**，让同一个下游 Task 顺手把相邻几个碎桶一并拉过来读：

```text
原始 Reducer 桶号：   0       1       2       3       4       5
实测落盘字节数：     12 MiB  10 MiB  35 MiB   8 MiB  40 MiB   5 MiB
                     └───────┬───────┘       └───┬───┘       │
合并后下游 Task 0：  连读桶 [0, 3) 共 57 MiB      │           │
合并后下游 Task 1：                          连读桶 [3, 5)    │
合并后下游 Task 2：                                      单读桶 [5, 6)
```

这里有一条绝对不能踩红线的正确性铁律：**如果是两表 Sort-Merge Join 或 Shuffle Hash Join 的左右两路输入，绝不允许左表把桶 `[0, 1, 2]` 合成一个任务，右表却把桶 `[0, 1]` 和 `[2, 3]` 合成两个任务！** 否则桶 2 里的相同键值在左右两侧就会错位失散。因此源码专门把需要按键对齐的多路 Shuffle 编进同一个 `coalesceGroup`，按各路对应桶字节之和统一划定切分边界（默认参考目标 `64 MiB`、下限 `1 MiB`，且在 `parallelismFirst=true` 时优先保住 `defaultParallelism` 核心利用率）。

那要是反过来，某个热点桶 `r` 独自膨胀到了几个 GiB（默认同时超过中位数的 5 倍且大于 `256 MiB`），既然数据已经按哈希写死了，还能不能拆？[`OptimizeSkewedJoin.scala`](https://github.com/apache/spark/blob/786bb3d9751fc6c4993997c088345ceba1b7a8d5/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/OptimizeSkewedJoin.scala) 给出了一个极巧的拆法——它不按字节偏移去硬劈压缩流，而是查出**上游各个 Map 任务分别往这个热点桶 `r` 贡献了多大的数据块（Map-to-Reduce Block）**，按 Map 任务序号区间 `[startMapIndex, endMapIndex)` 把它拆成多份 `PartialReducerPartitionSpec`：

```text
热点 Reducer 桶 r 的物理构成：
  Map 0 → r : Block A (300 MiB)
  Map 1 → r : Block B (280 MiB)
  Map 2 → r : Block C (310 MiB)
  Map 3 → r : Block D (290 MiB)

按 Map 序号区间拆给两个下游任务并行消费：
  Consumer 0 读取桶 r 的 [Map 0, Map 2) 即 A + B，同时完整复制读取右表桶 r
  Consumer 1 读取桶 r 的 [Map 2, Map 4) 即 C + D，同时完整复制读取右表桶 r
```

看懂这张物理切分图，也就看懂了 Spark 倾斜拆解的两道硬边界：**第一，它的最小拆解原子是单个 `Map → Reduce` 数据块**——如果所有热点数据恰巧全来自上游同一个 Map 任务吐出的巨型单块 `Block A`，按 Map 范围切分也爱莫能助；**第二，拆开左表意味着右表对应的桶必须完整广播复制给每一个分身**（双侧同时倾斜则需做笛卡尔配对组合），且必须严守连接类型约束（例如左表拆成两半后，右表某行在 Consumer 0 没配上，绝不能在 `RIGHT OUTER JOIN` 下贸然吐出 `NULL`）。而在 PVLDB 2024 的 **[Lakehouse AQE](https://www.vldb.org/pvldb/vol17/p3947-bu.pdf)** 中，这套基于 `QueryStage` 与 `LogicalLink` 的事件循环还进一步延伸到了广播连接回退、无用 Shuffle 消除与运行期异常自愈上。

### 3.2 Trino FTE：用持久化 Spool 解耦 Bucket 与 Task，按需重分区

前面提到常规流式 Trino 受限于在线节点数。但一旦开启任务级容错执行（Fault-Tolerant Execution，FTE，`retry-policy=TASK`，见 [FTE 官方文档](https://trino.io/docs/current/admin/fault-tolerant-execution.html) 与 [`QueryManagerConfig.java`](https://github.com/trinodb/trino/blob/68dae096719f5ac7a14d5a5cbcbfa1b247c0620c/core/trino-main/src/main/java/io/trino/execution/QueryManagerConfig.java)），中间交换数据被持久化暂存到外部 Spool 存储中，**逻辑哈希分桶与实际调度的 Task 生命周期瞬间彻底解耦**——哪怕集群只有 20 个节点，也可以切出 500 个 Task 分批排队跑完。

在非哈希的任意分布（Arbitrary / Source）路径上，Trino FTE 采取了“起步切细保并发、后续放大防碎任务”的渐进装箱策略：计算任务初始目标只有 `512 MiB`（写入任务 `4 GiB`），之后每攒满 64 个任务就把目标体积乘以 `1.26` 倍，一路平滑涨到 `50 GiB` 封顶（同时受单任务最多 `2,048` 个标准 `64 MiB` 切片约束）。

而在哈希分布路径上，[`HashDistributionSplitAssigner.java`](https://github.com/trinodb/trino/blob/68dae096719f5ac7a14d5a5cbcbfa1b247c0620c/core/trino-main/src/main/java/io/trino/execution/scheduler/faulttolerant/HashDistributionSplitAssigner.java) 维护了一个最小堆优先队列，每次挑出当前累计字节最轻的 `TaskPartition`，只要加上新桶不超过目标容量就合并装入。那如果反过来碰上一个超大哈希桶，它能像切香肠一样随便拆给多个 Task 吗？翻开源码里的 `canSplit` 判断就会恍然大悟：**常规的哈希连接和哈希聚合根本不允许直接把单个哈希桶劈给多个独立 Task！** 只有具备 `scale-writers` 属性的写出阶段，且除最大输入源之外的其余输入总和不超过目标容量的四分之一时，才允许把最大源切片打散、其余源复制分发——原因和前面讲的一模一样：一旦把同一个分组键拆进两个互不通气的聚合或外连接 Task，状态所有权当场破裂。

既然常规哈希桶写死后不能硬劈，万一初始只开了 100 个桶、跑完上游发现下游内存根本兜不住怎么办？Trino FTE 在 [`AdaptivePartitioning.java`](https://github.com/trinodb/trino/blob/68dae096719f5ac7a14d5a5cbcbfa1b247c0620c/core/trino-main/src/main/java/io/trino/sql/planner/optimizations/AdaptivePartitioning.java) 里准备了一招重武器：当预估内存压力（单分区输入看总字节，多分区输入看总和减去可流式穿过的最小输入）超过 `maxTaskSize × 当前分区数` 时，直接触发运行期重规划——如果远端 Exchange 还没跑就直接把桶数拔高（默认目标 `1,000` 个桶，随后仍可由前面的 Assigner 把小桶合装进较少 Task）；如果上游已经物化完毕，甚至敢在后面**硬插一道全新的重分区 Exchange** 把数据重洗一遍！至于写出端瓶颈，则由 [`ScaledWriterScheduler.java`](https://github.com/trinodb/trino/blob/68dae096719f5ac7a14d5a5cbcbfa1b247c0620c/core/trino-main/src/main/java/io/trino/execution/scheduler/ScaledWriterScheduler.java)（配置见 [Writer Scaling 文档](https://trino.io/docs/current/admin/properties-writer-scaling.html)）按上游输出缓冲区拥塞水位与已写出字节数，从 1 个 Writer 起步在线动态扩容，既避免小导出制造碎文件，又不让大导出卡在落盘最后一公里。

### 3.3 延迟顶点绑定：Flink Adaptive Batch、Tez 与 SCOPE

批处理有向无环图（DAG）里另一条极其干净的思路是**“上游没探明虚实之前，下游连并行度都不急着定”**。

**Flink Adaptive Batch**（基线 `3d6f144`，见 [Flink 2.3 自适应批调度文档](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/deployment/adaptive_batch/)）在作业启动时故意让未显式指定并行度的下游 `JobVertex` 处于未初始化悬空态。等上游消费统计就绪后，[`AdaptiveBatchScheduler.java`](https://github.com/apache/flink/blob/3d6f1444de490eccdeb6cadcf8dc6ee262d3c4d3/flink-runtime/src/main/java/org/apache/flink/runtime/scheduler/adaptivebatch/AdaptiveBatchScheduler.java) 才唤醒 [`DefaultVertexParallelismAndInputInfosDecider.java`](https://github.com/apache/flink/blob/3d6f1444de490eccdeb6cadcf8dc6ee262d3c4d3/flink-runtime/src/main/java/org/apache/flink/runtime/scheduler/adaptivebatch/DefaultVertexParallelismAndInputInfosDecider.java)，把非广播输入的真实字节数按目标容量（默认 `16 MiB`，默认上下界 `1` 到 `128`）折算为子任务规模，并同步敲定每个子任务负责消费的子分区范围：

$$
P_{\text{next}} = \operatorname{bound}\!\left(\left\lceil \frac{B_{\text{nonbroadcast}}}{B_{\text{target}}} \right\rceil, P_{\min}, P_{\max}\right)
$$

遇到数据倾斜时，[`AdaptiveSkewedJoinOptimizationStrategy.java`](https://github.com/apache/flink/blob/3d6f1444de490eccdeb6cadcf8dc6ee262d3c4d3/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/strategy/AdaptiveSkewedJoinOptimizationStrategy.java) 同样会汇总各子分区字节，按中位数倍数与绝对阈值锁定热点并结合连接语义拆解输入边。对比早期 **Hive on Tez** 的 [`ShuffleVertexManager`](https://cwiki.apache.org/confluence/spaces/TEZ/pages/62686375/How%2Bdoes%2BShuffleVertexManager%2BAuto%2BReduce%2BParallelism%2Bwork)（参见 [Hive 配置说明](https://hive.apache.org/docs/latest/user/configuration-properties/)，典型按 `256 MB/reducer`、上限 `1009` 预留初始桶，再根据源端事件只做向下合并连续分区范围），Flink 从源头动态推导（`DynamicParallelismInference`）到倾斜边改写的闭环已经完整得多。

而把“运行期交回优化器”推向极致的先驱，当属微软在 PVLDB 2013 发表的 **[SCOPE 持续查询优化](https://www.vldb.org/pvldb/vol6/p961-bruno.pdf)**：每当上游顶点收工，Job Manager 不仅上报真实行数、平均行宽、分区直方图乃至 UDF 实测 CPU 开销组成的“统计包（Statistics Package）”，还会附上一份详述哪些中间文件已落盘、具备何种分区与排序属性的“物化包（Materialization Package）”，异步唤醒优化器重编剩余整张子图——小活儿直接退回单机串行免去调度税，大倾斜则连连接算法和分区键一起重选。

### 3.4 节点内的细粒度弹性：StarRocks 自适应 Pipeline 与 Morsel 派工

跨机器的 Task 定下来之后，单台机器内部开多少个并发算子实例同样大有讲究。在 **StarRocks**（基线 `0fd27fd`）中，前端 [`SessionVariable.java`](https://github.com/StarRocks/starrocks/blob/0fd27fd409f3a1ad8a4634d30baf8f22f48254f1/fe/fe-core/src/main/java/com/starrocks/qe/SessionVariable.java) 与 [`PlanFragment.java`](https://github.com/StarRocks/starrocks/blob/0fd27fd409f3a1ad8a4634d30baf8f22f48254f1/fe/fe-core/src/main/java/com/starrocks/planner/PlanFragment.java) 把“Fragment 发往哪几台 BE 节点”与“单节点内开多少个流水线驱动器（默认 `pipeline_dop=0` 自适应，上限 `max_pipeline_dop=64`）”拆成两步决策。

假设一台 64 核机器默认准备开 32 个本地 Pipeline Driver。如果一条点查经过底层存储索引过滤后只吐上来寥寥几百行，下游照常实例化 32 套聚合哈希表和算子状态纯属杀鸡用牛刀；可如果为了数清上游到底有多少行，先把几千万行大结果全堵在内存里等上游跑完再启动下游，又会彻底废掉流式管道的低延迟优势！

翻开后端 C++ 源码 [`collect_stats_context.cpp`](https://github.com/StarRocks/starrocks/blob/0fd27fd409f3a1ad8a4634d30baf8f22f48254f1/be/src/exec/pipeline/adaptive/collect_stats_context.cpp)、[`collect_stats_source_operator.cpp`](https://github.com/StarRocks/starrocks/blob/0fd27fd409f3a1ad8a4634d30baf8f22f48254f1/be/src/exec/pipeline/adaptive/collect_stats_source_operator.cpp) 与初始化事件 [`adaptive/event.cpp`](https://github.com/StarRocks/starrocks/blob/0fd27fd409f3a1ad8a4634d30baf8f22f48254f1/be/src/exec/pipeline/adaptive/event.cpp)，StarRocks 用一个极轻巧的三态状态机完美化解了这个两难：

```text
[BLOCK 试探态]：暂存上游吐出的首批 Chunks，下游 Drivers 暂缓实例化
  ├─ 若暂存行数率先撞上缓冲阈值 ──→ [PASSTHROUGH 透传态]：确认为大查询！保持原高并发立即放行流水线
  └─ 若所有上游已跑完且总行数很小 ──→ [ROUND_ROBIN 收缩态]：确认为小结果！缩减下游 DOP 并重绑缓冲区
```

看一眼收缩分支的核心实现：

```cpp
size_t num_partial_rows = _ctx->_max_block_rows_per_driver_seq;
// 向下取不超过商值的最大 2 的幂，并夹在 [1, upstream_dop] 区间内
size_t adjusted_dop = compute_max_le_power2(_num_rows / num_partial_rows);
adjusted_dop = std::min<size_t>(std::max<size_t>(1, adjusted_dop), _ctx->_upstream_dop);
_ctx->_transform_state(CollectStatsStateEnum::ROUND_ROBIN, adjusted_dop);
```

随后在拓扑初始化阶段先调用 `adjust_dop()`（综合考量依赖管线与输出放大系数），再执行 `instantiate_drivers(state)`，让缩减后的新 Driver 按 `driver_sequence + k * downstream_dop` 轮询接管原先多个上游通道攒下的缓冲块——既分毫不丢数据，又把小查询的算子实例化开销压到了最低。

再往底层追一步，这与 SIGMOD 2014 经典的 **[Morsel-Driven Parallelism](https://15721.courses.cs.cmu.edu/spring2016/papers/p743-leis.pdf)**（[CWI 索引](https://ir.cwi.nl/pub/22547)）一脉相承：把输入数据切成成千上万个几万行大小的微型碎块（Morsels），硬件层只养一个与物理 CPU 核数等宽、严格绑定 NUMA 本地内存的固定工作线程池。不同于早期 MPP 为每个 Fragment 实例绑死独立内核线程、一遇网络空等或反压就触发大量操作系统上下文切换的阻塞模型，现代 Pipeline 执行引擎把算子局部状态封装进用户态 `Driver` 状态机里——无论撞上缺输入（`BlockedOnInput`）、下游反压（`BlockedOnOutput`）还是异步刷盘（`Spilling`），`Driver` 都会在毫秒级 Chunk 边界主动让出物理核，把宝贵的硬件线程留给处于 `Ready` 态的就绪管线：

![Pipeline 执行引擎 Driver 协作式用户态调度状态机](/images/diagrams/exec-dop-pipeline-driver-states.svg)

新查询插队或某核跑慢时，调度器在 Morsel / Chunk 边界动态改派活儿，根本不用触动上层算子拓扑——**把工作切细解决负载均衡与资源弹性，把算子并发收紧控制状态拷贝开销**，两边各司其职。

## 四、第三次决策（跨执行）：历史反馈如何绕开反事实陷阱

既然运行期自适应这么能干，为什么还需要跨执行的历史反馈（History-Based Optimization，HBO）？因为运行期纠偏并非免费午餐：不管是 Trino 临时补插一道重分区 Exchange，还是 Spark AQE 先开 2000 个碎桶再合并，第一次跑歪的调度税、缓冲税或重洗牌费已经实打实花出去了。对于每天定时重跑的数仓任务或高频报表模板，把上一次踩坑得来的真相记下来，下一次从起跑线就选对规模，收益立竿见影。

但历史反馈也是最容易写出“玄学 Bug”的地方。试想一条查询昨天用 `DOP = 64` 跑了 10 秒，今天你能直接把 `64` 当成永恒最优解锁死吗？万一昨天快只是因为缓存全热、集群恰巧没人抢网卡呢？更致命的是**反事实盲区（Counterfactual Blindness）**——线上日志只记录了 `DOP = 64` 跑完耗时 10 秒，你根本不知道如果当时选了 `32` 会不会只要 8 秒且省一半内存！

因此，成熟的工业级历史反馈绝不会无脑背诵上次的整数，而是严格区分三类证据：**事实标签**（某个规范化子计划真实吐出了多少字节与行数）、**策略标签**（上一轮运行时最终收敛到了怎样的分区方案或 Writer 规模）与**验证收益标签**（切换后相比基线是否真的变快且未劣化），并在复用前连过五道安检门：

| 安检维度 | 必须回答的工程问题 | 失守时的典型翻车后果 |
| --- | --- | --- |
| **身份匹配（Match）** | 怎样判定两次查询或子计划“等价”？ | 只按 SQL 文本哈希会漏掉相同子图；忽略分区过滤参数又会把查一天和查一年的任务混为一谈 |
| **采集信号（Signal）** | 存真实字节直方图、最终任务数，还是等待事件？ | 把受当时配额上限截断的任务数误当成理想需求保存下来 |
| **执行抓手（Actuator）** | 反馈回去改基数估计、改初始桶数，还是改最大并发？ | 抓手粒度太粗，修好了某一步连接却把下游写出并发搞崩 |
| **漂移失效（Applicability）** | 表膨胀十倍、热点转移或引擎升级后何时作废？ | 死抱三个月前的小表低并发配置，在促销峰值日直接打爆内存 |
| **回退兜底（Safety）** | 新初值跑慢了或遇上突发异常，谁来救场？ | 关掉了运行期 AQE 兜底，一次脏历史污染导致整条链路永久退化 |

### 4.1 分布式引擎的克制复用：BigQuery HBO、Presto Writer Seed 与 Ultron

观察主流分布式数仓的落地路径，大家在动用历史改并行度时都表现得相当克制：

- **BigQuery HBO** 公开提供了 [`parallelism_adjustment`](https://cloud.google.com/bigquery/docs/history-based-optimizations)（另见 [官方技术博客](https://cloud.google.com/blog/products/data-analytics/new-bigquery-history-based-optimizations-speed-query-performance) 及早期 [内存执行架构](https://cloud.google.com/blog/products/bigquery/in-memory-query-execution-in-google-bigquery)、[查询优化指南](https://cloud.google.com/blog/topics/developers-practitioners/bigquery-admin-reference-guide-query-optimization)）：在同一云项目作用域内，仅当相似负载分布具备高置信度时才拿历史记录优化后续 Stage 的初始并行度，同时全程保留运行期动态重分区与投机执行兜底，一旦实测收益不达标便自动撤销回退。
- **Presto HBO**（见 PVLDB 2024 论文 [《Presto's History-based Query Optimizer》](https://www.vldb.org/pvldb/vol17/p4077-shankhdhar.pdf) 与 [Presto HBO 文档](https://prestodb.io/docs/current/optimizer/history-based-optimization.html)）对剔除常量干扰后的规范化统计等价子计划（Canonicalized Stats-Equivalent Subplan）计算 SHA-256 指纹，主要用于精准喂回真实行数与字节统计以改善连接次序和广播选型。而在少数直接触碰任务数的规则 [`ScaledWriterRule.java`](https://github.com/prestodb/presto/blob/1b7b342e4461cc6bc391228e551b3c7a4bf205f3/presto-main-base/src/main/java/com/facebook/presto/sql/planner/iterative/rule/ScaledWriterRule.java) 中，它写下了一行极其精妙的折中公式：
  ```text
  initialWriterTasks = ceil(historyFinalWriterTasks / 2)
  ```
  为什么明明知道上次结束时扩到了 16 个 Writer，这次起步却只肯先开 **8 个（一半）**？因为今日输入量万一缩水一半，直接开满 16 个就会白白多产出一倍小文件；而先拿一半垫底，既省掉了从 1 个 Writer 苦苦爬坡的热身延迟，万一今天流量照旧甚至更大，运行期的在线扩容控制器随时还能继续往上加！
- **Databricks Ultron（PVLDB 2026）** 在论文 [《Ultron: History-Based Query Optimization at Databricks》](https://upenn.ferric.systems/dbscholar/vldb_papers/2026/p4358-marcus.pdf) 中展示了跨集群软状态存储 `Softstore` 与低延迟本地检索 `QuickPredict` 如何协同赋能分区数决策：如果某条大查询第一回跑的时候，因为初始桶太少触发了昂贵的运行期自适应重分区（Adaptive Repartition），Ultron 就会把纠偏后的最终分区方案记录在案；第二次再跑同类子计划时，直接一步到位采用该方案起步，免去中途二次洗牌，同时用输入规模缩放因子（Size Factors）盯防数据暴涨，随时允许运行期自适应重新接管（在论文 30 TB TPC-H 的分区敏感子集测试中显著跑赢全局单一固定配置；至于目前商业版公开文档则以 [Snowflake Optima](https://docs.snowflake.com/en/user-guide/snowflake-optima) 的计划形状匹配、[2026 性能演进说明](https://docs.snowflake.com/en/release-notes/performance-improvements-2026) 以及 Databricks 的 [`HISTORY_BASED_JOIN_STRATEGY`](https://docs.databricks.com/aws/en/sql/user/queries/performance-insights) 连接策略复用为主，均先从最稳妥的算子选型逐步放开）。

### 4.2 单机与共享集群反馈：SQL Server、Oracle 与学习型曲线预测

切回高并发共享数据库服务器，历史反馈的目标函数就从“让这一条 SQL 跑最快”变成了**“用恰到好处的线程换取全库最高吞吐”**。

**SQL Server** 的 [DOP Feedback](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing-degree-parallelism-feedback?view=sql-server-ver17)（架构背景见 [查询处理架构指南](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)）专门盯着那些“开了高并行度却大半时间卡在锁、闩锁或交换队列等待上”的重复查询，循序渐进地试探下调其并行上限，把验证过未明显拉长扣除外部干扰后耗时（Adjusted Elapsed Time）的更低 DOP 持久化进 Query Store；一旦后续发现性能回退，立刻自动回滚到上一个安全值。**Oracle** 的自动并行度体系（见 [Oracle Parallel Execution 文档](https://docs.oracle.com/en/database/oracle/oracle-database/26/vldbg/using-parallel.html)）则把编译期基于代价的 Auto DOP、资源吃紧时的并行语句排队（Parallel Statement Queuing）以及 `PARALLEL_DEGREE_POLICY=ADAPTIVE` 下的执行性能反馈串成闭环（取代了早期已废弃的 `PARALLEL_ADAPTIVE_MULTI_USER`）。

而在学术探索侧，Fan 等人在 [《A Comparative Exploration of ML Techniques for Tuning Query Degree of Parallelism》](https://arxiv.org/pdf/2005.08439)（[摘要页](https://arxiv.org/abs/2005.08439)）中给出了一个很有启发的建模视角：与其训练分类器去死猜“最佳 DOP 等于几”，不如把计划特征（区分行存/批模式、串行/并行算子占比）与候选 `DOP` 一起喂给模型去预测完整的响应曲线 `T(plan, DOP)`。一旦手里有了整条边际收益曲线，调度器就能一眼看出“从 8 核加到 16 核能快一倍，但从 16 核加到 32 核只快 3%”，把宝贵的核数留给旁边嗷嗷待哺的并发查询。

## 五、全局代价账本：十五种机制同台对表与工程取舍

一路拆解下来可以看到，嘴上同样说着“把并行度从 32 调到 64”，底层引擎付出的真金白银可能差出三个数量级：

```text
档位 1（最轻）：细粒度工作早已切好，仅多批 32 个空闲 Worker 槽位参与动态领活（Morsel / BigQuery Slots）
  └─ 代价：几乎零数据搬运，仅增加共享数据结构同步与缓存争用

档位 2（中等）：上游分桶已落盘，在下游启动前拆解或重排读取映射（Spark Skew Split / Trino FTE Assigner）
  └─ 代价：增加元数据与调度批数；若拆解连接一侧，另一侧对应分区需承担重复读取开销

档位 3（最重）：原有哈希状态无法直接拆解，被迫插入新 Exchange 重洗数据或取消在途任务（Trino AdaptivePartitioning）
  └─ 代价：全量数据二次序列化过网落盘，甚至废弃已消耗的半程计算
```

把前文涉及的所有开源内核机制与商业系统控制器拉到同一张刻度表下，就能看清每一把手术刀精确切在哪个时机、哪一层对象上：

| 系统与机制 | 出手时机 | 观测的核心信号 | 直接改写的物理对象 | 硬性语义与物理护栏 |
| --- | --- | --- | --- | --- |
| **Spark 文件扫描装箱** | 扫描启动前 | 文件字节数 + `4 MiB` 打开费 | `FilePartition` 切片组合 | 不可切分压缩文件无法硬劈 |
| **Trino `DeterminePartitionCount`** | 编译期静态规划 | 全局估算行数、字节与节点内存比 | 远端重分区 Exchange 桶数 | 只缩不扩；写操作与残缺统计默认跳过 |
| **Spark AQE Coalesce** | Shuffle 写完后 | 各 Reducer 桶实测落盘字节 | 下游消费者 Reader 范围映射 | 多路连接输入必须同组对齐切分边界 |
| **Spark AQE Skew Join** | Shuffle 写完后 | 桶字节 > 5 倍中位数且超 `256 MiB` | `PartialReducer` 的 Map 块区间 | 最小粒度卡在单个 `Map→Reduce` 块；对侧需复制 |
| **Trino FTE Split Assigner** | 上游分桶就绪时 | 源端各哈希桶估算字节 | `TaskPartition` 与分桶装箱关系 | 常规连接与聚合严禁拆散单桶同键状态 |
| **Trino `AdaptivePartitioning`** | FTE 运行期重规划 | 预估内存压力超 `maxTaskSize × P` | 未来 Exchange 桶数或补插重洗牌 | 目标 `1,000` 指桶数而非并发槽位；重洗牌有网络税 |
| **Flink Adaptive Batch** | 下游顶点初始化前 | 上游非广播实测消费字节 | `JobVertex` 子任务数与输入区间 | 受点对点/全连接拓扑与最大并行度上界制约 |
| **Hive/Tez Auto-Reduce** | 源端采样、消费启动前 | 上游完成任务上报的输出规模 | 原始预留 Reducer 的连续合并范围 | 单向往下合并，初值给小了无法向上突破 |
| **StarRocks 自适应 DOP** | 本地 Driver 实例化前 | 管道暂存行数、依赖拓扑与放大比 | 单节点内 Pipeline Driver 数与块归属 | 大结果撞阈值立即透传保流式；不突破上游并发 |
| **Trino Writer Scaling** | 写出阶段运行中 | 上游输出缓冲拥塞度与已写字节 | 分布式 Writer 任务或本地算子数 | 单向扩容为主，区分跨节点任务与单任务内局部扩容 |
| **BigQuery 运行期重调** | 查询执行途中 | 内部 Shuffle 分布与慢节点状态 | 动态 Stage 图重分区、合并与槽位 | 投机重试、槽位伸缩与逻辑重分区三层独立运作 |
| **BigQuery HBO 并行度** | 后续同类查询编译期 | 同项目高置信度历史负载分布 | 后续 Stage 初始并行度 | 全程保留运行期动态纠偏并在劣化时自动回退 |
| **Presto HBO Writer Seed** | 后续同类查询编译期 | 规范化子计划上次最终 Writer 数 | 初始 Writer 任务种子（取上次一半） | 留出一半余量防输入缩水造碎文件，靠在线扩容补足 |
| **Databricks Ultron 分区** | 后续同类查询编译期 | 上次触发自适应重分区后的终态方案 | 初始分区方案（配合规模缩放因子） | 输入体量剧变时自动交还运行期自适应接管 |
| **SQL Server DOP Feedback** | 跨执行周期持续调优 | 扣除干扰耗时与并行等待指标 | Query Store 中的语句级并行度上限 | 兼顾全库并发吞吐，性能回退时自动回滚安全值 |

将这十五种控制抓手放回时间轴上串联起来，就能清晰看到编译期静态估算、阶段边界 AQE 合并拆斜与跨执行 HBO 指纹反哺如何咬合成一条完整的决策闭环：

![查询并行度的三阶段决策闭环：静态初值、运行期 AQE 与跨查询 HBO](/images/diagrams/exec-dop-three-stage-loop.svg)

回望这三次决策构成的闭环，编译估计、运行期修正与历史学习从来不是“新架构淘汰旧架构”的替代关系，而是环环相扣的三道防线：**没有编译期初值，第一轮扫描连手都伸不出去；没有运行期边界纠偏，一次基数漏估就足以酿成整场雪崩；没有跨执行历史记忆，每天重跑的报表就得日复一日重交试错学费；而没有底层的细粒度分片与缓冲解耦，每一次资源波动都会被迫演变成伤筋动骨的全量重分区。**

这也给我们在自研或调优执行引擎时留下了一条最核心的设计准绳：**评判一个初始并行度好不好，不仅要看它估准时跑得多快，更要看它估错十倍以后，系统能不能在不重洗数据、不撕裂状态所有权的前提下，花最小的代价把局面救回来。**
